# 奢侈品识别方案

## 1. 目标与边界

系统目标不是“找最像的商品”，而是把雷小安、奢当家、腕表之家、小迈步、爱回收等来源的记录归一到**同一个官方商品变体（Official Variant）**。

第一阶段覆盖腕表与箱包，历史数据约 100 万–1000 万条。腕表已有部分品牌/系列/型号标准库；箱包主档不完整，因此系统必须同时支持 **Entity Linking** 与 **Entity Discovery**。

核心原则：

> **Precision >> Recall。宁可输出 UNKNOWN，也不能把不同官方变体错合并。**

只有会定义官方变体的关键属性兼容时，才允许自动认定 `SAME_VARIANT`。系统不做真假鉴定；成色、价格、库存、卖家、单件序列号、保卡状态等属于 Offer / 单件属性，不定义官方商品变体。

## 2. 核心实体、关系与标识符语义

统一实体层级：

```text
Brand
  └── Product Family / Series
       └── Product Model
            └── Canonical Variant
                 └── Source Product / Offer
```

关系至少包括：

```text
SAME_VARIANT
VARIANT_OF
SAME_MODEL
SAME_SERIES
VISUALLY_SIMILAR
UNKNOWN
```

只有 `SAME_VARIANT` 可以生成自动 Recognition。

Canonical Variant 状态：

```text
ACTIVE         已验证，可参与自动挂接
PROPOSED       新发现，等待证据/治理
SPLIT_PENDING  一个 Canonical 疑似混入多个官方 Variant，冻结新自动挂接并进入拆分修复
MERGE_PENDING  两个或多个 Canonical 疑似其实是同一官方 Variant，冻结相关实体新自动挂接并进入去重修复
RETIRED        历史实体，不再接受新自动挂接
MERGED         已治理合并到唯一 surviving Canonical
SPLIT          已确认 one-to-many 拆分；仅保留历史身份与 lineage
TAINTED        发现关键事实污染，暂停自动挂接
```

新发现实体默认 `PROPOSED`，不得因为若干来源名称或图片相似直接进入 `ACTIVE`。`MERGED` 是 many-to-one，可有唯一 surviving Canonical；`SPLIT` 是 one-to-many，旧 Canonical **不能**自动 redirect 到任一子 Variant。

### 2.1 Identifier namespace

统一采集：

```text
reference_full / style_code / mpn
gtin / ean / upc
merchant_sku
product_group_id / item_group_id
variant_dimension_keys / variant_dimension_values
barcode_symbology / payload / checksum
market
identifier_namespace / identifier_owner / identifier_scope
identifier_source / source_field_path / confidence
```

标识符必须解释“谁分配、在哪个字段出现、作用于 Product Group 还是 Variant、在哪个市场有效”，不能只看字符串像不像型号。

规则：

- 高可信完整 Reference / Style Code 精确一致：最强 Identity Anchor 之一。
- 官方品牌来源中的 `mpn`，经品牌规则和格式验证后，可作为 Manufacturer-grade Identifier。
- 第三方商家 `sku` 默认属于 merchant namespace，不得直接升级为官方 Reference / Style Code。
- `productGroupID / item_group_id / inProductGroupWithID` 是父商品组/变体组关系标识，不是 Variant Identity Anchor。
- `ProductGroup.hasVariant / Product.isVariantOf / variesBy / variant_option` 是高价值变体边界证据，用于解释哪些属性产生独立 Variant。
- 高可信、校验通过的 GTIN/EAN/UPC：Strong Positive + Exact Retrieval Key。
- 不同 GTIN 默认 `POSSIBLE_CONFLICT`；只有品牌/市场规则证明该语境下 GTIN 与本系统 Variant 1:1 时才升级 Hard。
- Vintage 必须考虑旧编码、市场差异、包装变化与历史规则。

维护 `identifier_semantics_policy`，最小粒度：

```text
brand × market × source_group × field_path × identifier_type
```

策略声明：

```text
MANUFACTURER_ID / MERCHANT_ID / GROUP_ID / INSTANCE_ID / UNKNOWN
```

以及是否允许 Exact Retrieval、Strong Positive、Hard Conflict、Auto Activation。

## 3. 标准 Schema 与 Hard Constraint

每个属性事实保存：

```text
raw_value
normalized_value
canonical_value_id
extractor / extractor_version
source_type / source_id / source_url
evidence_span / image_bbox
confidence / validation_status
effective_from / effective_to
observed_at / content_hash
```

`observed_at` 与有效期分离；新证据不覆盖旧事实，而用 version / supersedes 表达变化。只有双方属性都达到对应可信度门槛时才形成 Hard Conflict；低置信 OCR/VLM 冲突只能触发 `POSSIBLE_CONFLICT → UNKNOWN`。

### 3.1 腕表

| 字段 | 默认策略 |
|---|---|
| brand | Hard |
| series / family | Blocking + Strong；品牌规则可 Hard |
| subseries / model | Strong |
| official_reference_full | Hard；最强身份字段之一 |
| reference_base | Retrieval / Strong，默认不能代替 full |
| gtin/ean/upc | Strong；条件 Hard |
| case_diameter_mm | Hard |
| case_material | Hard |
| dial_color | Hard |
| dial_type | 定义独立变体时 Hard |
| bezel | 定义独立变体时 Hard |
| bracelet_or_strap | 条件 Hard；需识别后换件 |
| caliber / movement | 代际/变体区分时 Hard，否则 Strong |
| functions | 变体区分时 Hard |
| edition / generation | Hard |
| serial_number | 单件属性 |
| condition / price | Offer 属性 |

Reference 保存 `raw / normalized / base / full / parts / brand_rule_version`。默认以 `reference_full` 为准；只有品牌规则明确证明后缀不定义 Variant 时才允许 base reference 参与自动合并。

### 3.2 箱包

| 字段 | 默认策略 |
|---|---|
| brand | Hard |
| family / series | Blocking + Strong |
| model / style | Strong |
| official_style_code | Hard；最强身份字段之一 |
| gtin/ean/upc | Strong；条件 Hard |
| official_size | Hard |
| material | Hard |
| official_color | Hard |
| hardware | Hard |
| pattern / print | Hard |
| edition / collaboration | Hard |
| season / year / generation | 官方由其区分时 Hard |
| serial / date_code | 单件/生产证据 |
| condition / price | Offer 属性 |

图片颜色不直接成为 Hard Constraint；灯光、白平衡、老化、修图会造成偏差，视觉颜色只做 Soft Evidence。

### 3.3 两级标准化

```text
material_group = ROSE_GOLD
material_brand_value = ROLEX_EVEROSE_GOLD

color_group = BLACK
color_brand_value = CHANEL_NOIR
```

通用层用于跨平台召回，品牌精确层用于 Variant 判定，避免把品牌专有语义压平。

## 4. Evidence、来源独立性与事实状态

来源等级：

```text
T0  品牌官网、官方目录、官方标识体系
T1  已验证内部标准库、授权/专业数据库
T2  高质量专业平台、可信二手平台
T3  普通电商、聚合站、搜索网页
```

可信度按“来源 × 属性”定义，而不是整站一刀切。

### 4.1 来源独立性

维护：

```text
source_group_id
syndication_group_id
content_fingerprint
image_hash_group_id
upstream_hint
```

多个 URL 不等于多个独立来源。复制同一 feed、相同/近重复图片、相同异常文案、相同字段错误不能增加 `independent_source_count`。

### 4.2 Evidence Family：避免重复计票

至少定义：

```text
IDENTIFIER        Reference / Style Code / MPN / GTIN
STRUCTURED_ATTR   size / material / color / hardware / movement
VARIANT_GRAPH     ProductGroup / isVariantOf / variesBy
LEXICAL_TEXT      BM25 / token overlap
SEMANTIC_TEXT     text embedding / reranker
IMAGE_VISUAL      image embedding / patch feature / perceptual hash
OCR_TEXT          image → OCR → identifier/attribute
EXTERNAL_WEB      外部网页证据
TEMPORAL          year / generation / effective period
```

同一原始观测派生出的多个分数不是多个独立证据：

- 同一标题的 BM25 + Text Embedding 不算两票。
- 同一张图的 pHash + SigLIP/DINO + VLM 观察不算多票。
- 同一网页中的 JSON-LD、DOM 与搜索摘要默认属于同一 evidence origin。
- OCR 从图片读出的 Reference 可升级为 Identifier，但必须保留 image/OCR provenance。

Student Matcher 可使用全部特征学习联合分布，但 `CERTAIN_MATCH` 风险策略不得把相关特征机械相加解释为独立支持。

### 4.3 Fact Promotion Barrier

事实状态至少包括：

```text
OBSERVED      原始可追溯观测
DERIVED       规则/模型/聚类推导
REVIEWED_GOLD 人工确认标签
GOVERNED_FACT 主档治理确认事实
APPROVED_ALIAS 已批准别名/标识符映射
TAINTED       已知被污染
```

`DERIVED` 结果不得直接写入 Exact Identity 索引、Hard Constraint 主档或 Gold Training Set。只有经过 Review/Governance/Factual Promotion Gate 后才能晋升。

任何 Exact Alias、Canonical Fact、Reviewed Gold Label 必须能沿 lineage 回溯到真实 observed/reviewed/governed artifact；只有 DERIVED→DERIVED 的闭环不能完成晋升。

### 4.4 时间版本

Canonical 属性保存 `valid_from / valid_to / version / evidence_ids`，用于同名跨年份改款、Reference 规则变化、新旧机芯/五金/尺寸变化和 Vintage 回溯。没有明确代际证据时，不跨年代自动合并。

## 5. 属性抽取与标准化

```text
Raw Source Product
→ Schema Mapping
→ Deterministic Parsing / Dictionary
→ Barcode Decode
→ Text Attribute Extraction
→ Scene OCR
→ Document-like OCR/VLM（按需）
→ General VLM Fallback（少量困难样本）
→ Normalization / Ontology Mapping
→ Attribute Validation / Quality Check
→ Normalized Product Profile
```

优先级：规则/主档 → 条码 → 文本 → Scene OCR → 文档 OCR/VLM → General VLM → Quality Check。能用确定性方法解决的问题不交给大模型。

### 5.1 Barcode / OCR

条码先用 zxing-cpp 等确定性 decoder 解析 EAN/UPC/Code128/Data Matrix/QR，经过 check digit、格式、品牌/市场校验后进入 Exact Retrieval。

PoC Scene OCR 基线：PP-OCRv6。OCR 输出必须分类：

```text
reference / style_code
gtin/ean/upc
serial_number
date_code
size
material_text
other_text
```

密集文档、保卡整页、历史目录页、复杂表格可用 PaddleOCR-VL-1.6 / PP-Structure 类能力作为 document-like fallback。

### 5.2 General VLM

PoC 困难样本结构化抽取基线：Qwen3.5-4B。职责是产生**可验证候选证据**，不是最终身份判断。

VLM 结果必须经过 ontology、品牌规则、主档、OCR/文本交叉验证；无权直接写 ACTIVE Canonical 或直接输出 `CERTAIN_MATCH`。

## 6. 缺模态与 EvidenceProfile Route Policy

每条 Source Product 先计算：

```text
identifier_quality = NONE / WEAK / STRONG
text_quality       = NONE / WEAK / STRONG
image_quality      = NONE / WEAK / STRONG
hard_attr_coverage = 0..1
conflict_state     = NONE / POSSIBLE / HARD
catalog_mode       = LINK / DISCOVERY
synthetic_evidence = true / false
```

固定路由：

| 场景 | 主要召回 | 最终判定上限 |
|---|---|---|
| 强 Reference/Style/GTIN + Hard Attr 无冲突 | Exact + 属性过滤 | 可进入 CERTAIN_MATCH |
| 文本强、无图片 | Exact/BM25/Text ANN/属性 | 可进入 CERTAIN_MATCH；无图不是负证据 |
| 图片强、文本弱、无可靠型号 | Image ANN + OCR + 视觉属性 + 少量 VLM | 默认不能仅视觉 CERTAIN_MATCH |
| 文本强 + 图片强 | 多路召回 + Rerank | 可进入 CERTAIN_MATCH |
| 型号疑似错误 | raw/normalized identifier 双路 + 非 identifier 召回 | 冲突时 UNKNOWN/NON_MATCH |
| 文本与图片冲突 | 两种模态独立保留 | POSSIBLE_CONFLICT → UNKNOWN |
| 无图无可靠型号、结构化属性完整 | BM25/Text ANN/Attribute | 只有经认证的高区分组合才自动，否则 UNKNOWN |
| 只有泛化标题、缺 Hard Attr | BM25/Text ANN | UNKNOWN |
| Vintage / 新款无 Canonical | Neighbor + Official/Web Evidence | PROPOSED |

### 6.1 Synthetic Evidence

- 模型生成的缺失图片/描述不得当真实商品事实。
- `synthetic_evidence=true` 不得形成 Hard Constraint、Identity Anchor、官方颜色/尺寸/材质事实。
- 图→文本补全只可用于 query expansion、候选召回、属性候选提示。
- 文本→图像生成默认不进入身份识别链路。
- Catalog Pattern/RAG 可预测缺失属性候选，但预测值需真实来源或审核确认后才能升级 Canonical Fact。

### 6.2 低质量图片

Image ANN 前独立评估 blur、resolution、subject_area_ratio、occlusion、background_complexity、watermark、crop_type、color_cast。低质量图降低 `IMAGE_VISUAL` 权重与候选配额；局部细节图不能与完整正面图等权。

## 7. Candidate Retrieval、Fusion 与 Open-world Guard

100 万–1000 万记录禁止 N²。

召回通道：

```text
Exact Full Reference / Style Code / Manufacturer MPN
Exact GTIN/EAN/UPC
Brand + normalized model/reference
Brand + series/model + Hard Attributes
BM25
Text ANN
Image ANN
Image exact/perceptual hash
Historical Canonical Alias
Unmatched Entity-Discovery Neighbors
```

默认按 `category`，通常再按 `brand_id` 过滤。

PoC 初始 K：Exact≤20、BM25 30、Text ANN 50、Image ANN 每图 30/总≤60、Attribute 30；union≤150，Cheap Rerank≈30，Expensive Matcher 10–20。

Retrieval Gate：

```text
Recall@100 after fusion/truncation >= 99.5%
Exact-candidate survival rate = 100%
```

### 7.1 多路 Fusion

- 不同通道 raw score 不直接相加。
- Exact/Identity 候选单独保留，不能被 soft fusion 截断。
- 零/少标签阶段使用 RRF 作为 Soft Retrieval 基线。
- 截断前保留每通道 minimum quota。
- Exact ∪ RRF 后再 Cheap Rerank。
- 有足够 judgment 后再比较 RRF、归一化 weighted fusion、learned fusion。
- 记录 fusion version、各通道 rank/raw/normalized score，并监控 fusion 前后 Recall。

### 7.2 Search Engine

生产基线：OpenSearch 3.8，统一承载 Exact/filter、BM25、filtered k-NN、hybrid retrieval、RRF/score normalization、on-disk vector、quantization/rescore、versioned index/alias。

Milvus 只在 10M 真实压测证明 OpenSearch 的 Recall/QPS/资源成本不满足时再拆分；pgvector 适合小规模 PoC/内部工具。

### 7.3 NIL / None-of-the-Candidates

检索总能返回 Top-1，不代表正确 Canonical 一定存在。

`CandidateSetAssessment` 保存：

```text
best_candidate_id / best_score_calibrated
second_candidate_id / second_score_calibrated
score_margin / near_tie_count
candidate_set_state
none_of_candidates_score
nil_reason
retrieval_health_snapshot
policy_version
```

状态：

```text
KNOWN_CANDIDATE
AMBIGUOUS_KNOWN
POSSIBLE_NIL
RETRIEVAL_FAILURE
```

规则：

- 禁止强制 Top-1。
- 无 Strong Identity Anchor 时，Top-1 必须达到 segment 校准阈值，并通过 Top-1/Top-2 ambiguity guard。
- near-tie 且关键 Variant 属性缺失 → `UNKNOWN_AMBIGUOUS`。
- 候选整体低且 Retrieval Health 正常、输入证据充分 → `UNKNOWN_POSSIBLE_NIL`，进入 Web Evidence + Discovery。
- 搜索/索引/route 不健康 → `UNKNOWN_SEARCH_FAILURE`，不得误判新品。

## 8. Embedding、Visual Search 与局部复核

### 8.1 Text

PoC 基线：Qwen3-Embedding-0.6B。先测试 512d，再比较 256/384d。文本同时保存结构化模板与原始标题/描述表示。

Text Reranker：Qwen3-Reranker-0.6B，仅对 Top-N 使用。

### 8.2 Image

语义/跨模态基线：SigLIP2-B/16 384；细粒度视觉 challenger：DINOv3 ViT-B/16。DINOv3 使用自定义许可证，生产前必须 Legal/Compliance Gate；无法接受则保留 SigLIP2 + DINOv2/其他可商用方案。

每图独立保存向量，聚合使用 `max_similarity / topk_mean / front/detail similarity / image_quality_weight`。完全相同或近重复图片也不能单独证明 `SAME_VARIANT`。

Qwen3-VL-Embedding-2B / Reranker-2B 作为多模态 challenger；只有显著提升 `Coverage @ 99.9% Precision` 且成本可接受时才进入困难路径。

### 8.3 Local/Patch Visual Verify

全局视觉向量负责高召回候选发现；近邻 SKU 的盘面刻度、表圈、刻字、五金、走线、印花局部差异用 shortlist 局部复核：

```text
Global Image ANN Top-K
→ Region Selection
→ Patch / Local Descriptor
→ Shortlist Local Rerank / Correspondence
→ local_visual_score / patch_match_coverage
→ Pair Decider + Ambiguity Guard
```

局部视觉仅属于 `IMAGE_VISUAL` Evidence Family，不得单独升级 Identity Anchor，也不得覆盖 Hard Conflict。

## 9. Pair Matcher、Conflict Engine 与 Decision Policy

```text
Candidate Pair
→ Pre-Conflict Check
→ Cheap Deterministic Features
→ Structured / Text Matcher
→ Multimodal Difficult-Pair Matcher（少量）
→ Local Visual Verify（仅 near-tie）
→ Post-Conflict Check
→ Calibration
→ Evidence-Family Risk Policy
→ Candidate-set / NIL / Ambiguity Guard
→ Decision
```

### 9.1 CERTAIN_MATCH

至少满足：

```text
NO HARD_CONFLICT
AND CandidateSetState == KNOWN_CANDIDATE
AND
(
  Strong Identity Anchor
  OR
  Calibrated Matcher >= tau_segment
  + >= 2 个非重复 Evidence Family 一致支持
  + Ambiguity Guard 通过
)
```

Strong Identity Anchor：高可信 full Reference / official Style Code / Manufacturer-grade MPN exact，或高可信 GTIN exact + Hard Attributes 无冲突。

`tau_segment` 与 `margin_segment` 按品牌/品类/来源/EvidenceProfile 独立认证，不使用 ANN raw score 或全局固定阈值。

### 9.2 Conflict Engine

独立安全墙，Matcher 前后执行：

```text
HARD_CONFLICT
POSSIBLE_CONFLICT
NO_CONFLICT
```

典型：

- 品牌不同 → Hard。
- 36mm vs 41mm 且双方官方高可信 → Hard。
- Mini vs Medium 且双方官方尺寸 → Hard。
- 图片黑 vs 深蓝、无官方颜色 → Possible。
- 官方钢链 vs 疑似后换皮带 → Possible。
- validated GTIN 不同 → 默认 Possible；规则确认 1:1 才 Hard。
- Product Group 相同但 Variant 属性不同 → 不是 SAME_VARIANT。
- Merchant SKU 与官方 Reference 不同 → namespace 不同，不能直接形成 Hard。

任何模型高分都不能覆盖 Hard Conflict。

### 9.3 UNKNOWN reason code

至少包括：

```text
UNKNOWN_AMBIGUOUS
UNKNOWN_POSSIBLE_NIL
UNKNOWN_INSUFFICIENT_EVIDENCE
UNKNOWN_SEARCH_FAILURE
UNKNOWN_DEPENDENCY_FAILURE
UNKNOWN_PUBLICATION_INCONSISTENT
UNKNOWN_CONFLICT
UNKNOWN_CATALOG_REPAIR
```

`SPLIT_PENDING / MERGE_PENDING / TAINTED` Canonical 或处于未完成 repair publication 的候选不得继续 Auto-Match；需要挂接到这类实体的请求统一 `UNKNOWN_CATALOG_REPAIR`。

## 10. Entity Linking、Discovery 与 Canonical Health

### 10.1 Linking

```text
Source
→ Hybrid Retrieval
→ Pair / Conflict / Calibration
→ CandidateSetAssessment
→ CERTAIN_MATCH or reason-coded UNKNOWN
→ Recognition（仅 CERTAIN_MATCH）
```

### 10.2 Discovery

只有 `UNKNOWN_POSSIBLE_NIL` 且输入证据达到最低质量要求时进入发现池：

```text
POSSIBLE_NIL
→ Official/Web Evidence（按需）
→ Strict Blocking
→ High-confidence Pair Edges
→ Constraint-aware Clustering
→ PROPOSED Canonical
→ Canonical Novelty / Uniqueness Gate
→ ACTIVE or remain PROPOSED
```

**`POSSIBLE_NIL` 只说明线上 Linking 没有安全地找到正确 Canonical，不等于“已经证明这是新商品”。** Product Synthesis 的“识别新品”和普通 Offer→Catalog Matching 必须分成两个风险层。

### 10.2.1 Canonical Novelty / Uniqueness Gate

任何 `PROPOSED → ACTIVE` 必须生成 `canonical_novelty_assessment`，并在**当前 pinned publication** 上对已有 Canonical 做比普通在线 Linking 更高召回、更低时延敏感度的去重检查。

检查范围至少覆盖：

```text
ACTIVE Canonical
PROPOSED Canonical
MERGED historical identity / aliases
Official external variant ids
Governed Manufacturer-grade identifiers
```

召回使用：

```text
all Exact Identifier collisions
Brand/Family/Model/Hard-Attribute blocking
BM25 / Text ANN
Image ANN / perceptual hash
Official Web Variant Graph
reviewed alias / historical identifier mapping
```

Novelty 状态：

```text
UNIQUE
DUPLICATE_SUSPECT
AMBIGUOUS_EXISTING
CONFLICTING_EXISTING
RETRIEVAL_UNHEALTHY
```

默认激活条件：

1. 不存在任何 governed Manufacturer-grade Identifier / official external Variant ID 与其他非 MERGED Canonical 的碰撞。
2. 对 Top duplicate candidates，要么存在可靠 Hard Attribute / 官方 Variant 边界证明“确实不同”，要么域内 benchmark 已证明 duplicate risk 足够低。
3. 无可靠唯一 Identifier 且与现有 Canonical 高度近似、同时缺少能区分 Variant 的 Hard Attribute 时，**保持 PROPOSED**；不能因为 Pair score 不够高就自动当新品。
4. Search/Publication/Route 不健康时不能得出 `UNIQUE`；该状态不是 Retrieval Failure 的替代解释。
5. Exact/official collision 永不被 soft retrieval 截断。
6. `catalog_activation_policy` 只允许 `novelty_state=UNIQUE` 的对象进入自动激活。

为防两个 Discovery Worker 同时创建重复主档，增加 `canonical_identity_claim`：对已证明 variant-unique 的 Manufacturer Identifier / official external Variant ID 建唯一 claim。无强 ID 的 proposal 在激活提交前必须在同一事务/锁语境重新执行 novelty check，避免 TOCTOU 竞争导致双 ACTIVE。

### 10.3 传递冲突

禁止 `Connected Component = Canonical Variant`。

使用：

```text
Union-Find / Cluster Graph
+ Cannot-Link
+ Cluster Signature
+ Anchor Validation
```

合并前检查 cannot-link、Hard Attributes、时间版本、来源互斥与 anchor；高风险小 cluster 可做 complete-link/关键 pair 检查。有冲突立即写 cannot-link，阻断 A=B、B=C 推导 A=C。

### 10.4 ACTIVE Cluster Health 与 Canonical Split Repair

Entity Resolution 不能只检查“新边能否并入”，还必须持续检查**已经存在的 ACTIVE Canonical 是否内部一致**。成熟商品关系库会因为原始数据错误、旧聚类错误、数据变化等原因产生 inconsistent clusters；一旦 Canonical 内实际混有多个官方 Variant，继续把它作为一个可挂接实体会持续制造 False Merge。

每个 ACTIVE Canonical 周期性/事件驱动计算 `canonical_health_snapshot`，至少观察：

```text
high_trust_hard_conflict_count
cannot_link_inside_cluster_count
manufacturer_identifier_partition_count
variant_attribute_mode_count
review_disagreement_rate
new_evidence_conflict_rate
temporal_generation_conflict
cluster_partition_score (optional)
health_state
```

触发规则：

- 同一 ACTIVE Canonical 内出现两个经过治理的互斥 Hard Attribute、两个不可兼容 Manufacturer-grade Identifier 分区，或新增 `cannot-link` 穿过当前成员集合 → 立即进入 `SPLIT_PENDING`，停止新自动挂接。
- 仅有模型/图片/低可信来源形成的多峰不直接 split，只创建 `canonical_repair_case` 做 Governance Review；宁可保持冻结/UNKNOWN，也不能用软相似度自动拆主档。
- supervised graph partitioning / inconsistent-cluster classifier 只作为 repair candidate detector，不直接执行 Canonical mutation。

确认 split 后：

```text
ACTIVE old Canonical
→ SPLIT_PENDING
→ Governance confirms N distinct Official Variants
→ Create N new Canonical Variants
→ Re-resolve every member from ORIGINAL OBSERVED Evidence
→ Proven members reassign / ambiguous members UNKNOWN_CATALOG_REPAIR
→ Revalidate Alias / Identifier / Labels / Cannot-Link
→ Atomic repair publication
→ old Canonical = SPLIT
```

固定规则：

1. 旧 Canonical ID 不复用；`SPLIT_INTO` 指向多个 child，读取旧 ID 返回 `requires_re_resolution=true`。
2. 旧成员资格不继承；所有 source_product 从原始 Evidence 重新跑 Linking/Conflict。
3. Recognition 不原地改写历史；旧记录保留，新增 superseding Recognition/invalidating event。
4. Alias / Identifier 重新定级；同时覆盖多个 child 的 base reference/俗称降级为 Family/Model retrieval key。
5. 因旧共簇生成的 Pseudo Positive 全部 taint；跨 child Positive 失效。
6. Split 本身不增加独立 Evidence 数；不能用 cluster partition 自证新 child。
7. repair 通过 Outbox + Publication Barrier 原子发布。
8. Merge 与 Split 语义分离：`MERGED` 可 many-to-one redirect；`SPLIT` 不能。

### 10.5 Canonical Fragmentation 与 Duplicate Canonical Repair

Split Repair 防“**一个 Canonical 包含多个 Variant**”；系统还必须防相反问题：**同一个官方 Variant 被建成多个 ACTIVE/PROPOSED Canonical**。这种 identity fragmentation 会让同一 Source Offer 在不同时间/来源挂到不同主档，造成 Alias 冲突、审核口径分裂、训练标签不一致和重复主档持续扩张。

周期性与事件驱动执行 Canonical-to-Canonical duplicate scan。高优先级信号：

```text
same governed Manufacturer-grade identifier across Canonicals
same official external variant id / variant URL across Canonicals
same GTIN in a brand/market rule certified as Variant-unique
same governed Hard-Attribute signature + strong family/model evidence
repeated reviewed SAME_VARIANT bridge between two Canonicals
persistent Top-1/Top-2 ambiguity concentrated on the same Canonical pair
cross-store / cross-language duplicate or near-duplicate retrieval evidence
```

规则：

1. governed variant-unique Identifier 或 official Variant ID 跨两个 ACTIVE Canonical 碰撞 → 创建 `canonical_merge_case`，相关 Canonical 进入 `MERGE_PENDING`，停止新 Auto-Match。
2. 只有 Image/Text Embedding 高相似不能自动 Merge；软信号只生成治理候选。
3. Merge 前必须确认**不存在** governed Hard Conflict、confirmed cannot-link、时间代际冲突或 reviewed DIFFERENT_VARIANT 证据。
4. 默认由 Governance Review 确认 SAME_VARIANT 后选择唯一 survivor；后续新 Recognition 只写 survivor。
5. 原 Canonical ID 保留历史并 `MERGED_INTO` survivor；历史 Recognition 不原地覆盖，read-time/current-identity 层解析到 survivor。
6. Alias / Identifier 合并前重跑 collision/semantics check；错误或多义 alias 不因为 Merge 自动获得更高权重。
7. 两 Canonical 之间若存在旧 Negative/Hard-Negative/Reviewed DIFFERENT label，必须 taint 并 re-review；不能让旧冲突静默污染后续训练。
8. Merge 不能用 Canonical membership 自证；必须回到 OBSERVED/GOVERNED/REVIEWED Evidence。
9. survivor、MERGED 状态、Alias/Identifier 迁移、Search tombstone 与 redirect 在同一个 repair publication 中生效；publication 未完成时保持 `UNKNOWN_CATALOG_REPAIR`。

`canonical_merge_case` 状态：

```text
DETECTED
FROZEN
UNDER_REVIEW
READY_TO_PUBLISH
PUBLISHED
REJECTED
```

对弱信号 candidate 可先保持 ACTIVE 并进入低优先治理队列；只有达到 identity-critical trigger 时才强制 `MERGE_PENDING`，避免低质量相似度造成大面积无谓冻结。

## 13. Review、风险认证与 Reviewer Quality

输出状态：

```text
CERTAIN_MATCH
LIKELY_MATCH
UNKNOWN
CERTAIN_NON_MATCH
```

只有 CERTAIN_MATCH 创建 Recognition。

### 13.1 三轨 Review

```text
TRAINING_REVIEW
  Active Learning / Hard Negative / LIKELY / UNKNOWN / rare slices

CERTIFICATION_AUDIT
  从真实最终 Decision 流按预定义 probability sampling 抽样

GOVERNANCE_REVIEW
  PROPOSED/Novelty/Merge/Split Canonical / Web 冲突 / Identifier semantics / 主档治理
```

生产风险认证单位是最终 `Recognition Decision`，不是 candidate pair。Certification 样本记录 `inclusion_probability / stratum_key`；全局风险按真实流量权重汇总。Active Learning / Hard Negative 默认只能用于训练与诊断，不能未经设计权重校正就宣称代表线上 Precision。

### 13.2 Calibration 与 Certification 分开

- 调参集与最终认证集分离。
- 对 Auto-Match 使用单侧二项置信上界。
- 若目标错合并率 <0.1%，0 错误时 95% 单侧置信水平约需 2995 个独立审核样本把上界压到约 0.1%。
- 主要品类/来源/品牌/EvidenceProfile/CandidateState 做 slice-level 认证。
- KNOWN / AMBIGUOUS / NIL 分开评估。
- 分布漂移后重新校准/认证。

### 13.3 Certification Label Quality

正式 `CERTIFICATION_AUDIT` 默认双人独立盲审：首轮不展示模型 score、置信解释、Teacher/VLM 建议或另一 reviewer 标签。

标签：

```text
SAME_VARIANT
DIFFERENT_VARIANT
INSUFFICIENT_EVIDENCE
SOURCE_DATA_ERROR
```

分歧或不确定进入高级 reviewer/专家 adjudication；仍无法裁决的 `AUDIT_UNRESOLVED` 不计作正确匹配。Reviewer 维护 brand/category qualification，定期插入隐藏 control items。审核指南、UI、资格版本全部保存。

Certification set 不参与同一版本 threshold/model/policy 选择；释放进后续训练后，下一版本必须使用新的 holdout/时间窗重新认证。

## 15. Incremental、CDC 与 Catalog Publication Barrier

历史初始化：

```text
Raw Import
→ Normalize / Extract / QC
→ Barcode/OCR
→ EvidenceProfile / Route
→ Batch Text/Image Embedding
→ Build Versioned OpenSearch Generation
→ Publication Parity Validation
→ Atomic Alias Publish
→ Link to Existing Canonical
→ CandidateSetAssessment
→ Recognition / UNKNOWN
→ POSSIBLE_NIL Discovery
```

每日增量：

```text
New/Changed Source or Governed Canonical Mutation
→ DB Transaction: mutation + catalog_outbox_event
→ CDC / Outbox Relay
→ Idempotent Projection Consumer
→ External-versioned OpenSearch Upsert / Tombstone
→ Refresh Visibility + Advance Search Checkpoint
→ Advance Catalog Publication Watermark
→ Recognition under pinned publication_id
```

规则：

- Canonical/Alias/Identifier promotion、撤销、`RETIRED/MERGED/SPLIT_PENDING/SPLIT/MERGE_PENDING/TAINTED` 与 outbox event 在同一 DB transaction 提交。
- Indexer 以 `event_id` 幂等去重，用 `mutation_version` 做 OpenSearch external version。
- 删除/撤销必须生成 tombstone/状态事件。
- 增量更新只有在 `search_apply_checkpoint` 追平且 refresh 可见后才允许 publication watermark 前移。
- breaking mapping/embedding/大规模回填使用新 generation，完成 parity + Recall benchmark 后原子 alias 切换。
- Split/Merge Repair 的 Canonical 状态、Alias/Identifier 迁移与 Search tombstone 必须在同一可验证 publication 中完成。

### 15.1 Publication Pin

关系库是 Canonical Fact 唯一事实源；OpenSearch 是异步 near-real-time 投影。Auto-Match 请求入口 pin 一个已 `ACTIVE` 的 `publication_id`。

`catalog_publication` 绑定 canonical snapshot/mutation watermark、search generation/alias/refreshed watermark、ontology、identifier semantics、fact promotion policy 与状态。

Search hit 进入 Pair/Conflict 前校验 pinned publication。`RETIRED / MERGED / SPLIT_PENDING / SPLIT / MERGE_PENDING / TAINTED`、撤销 Identifier/Alias、Hard Attribute 修订即使仍被旧索引召回，也必须在最终 gate 丢弃。

`search_apply_checkpoint < publication.mutation_watermark`、refresh 未确认、projection parity 失败、alias 指向未认证 generation、混合 publication → `UNKNOWN_PUBLICATION_INCONSISTENT`。

目标是：

> **事务性发出 + 幂等投影 + 单调版本 + 可验证 publication。**

## 16. Production Runtime Reliability

### 16.1 Fail-closed

Route Policy 为每个 EvidenceProfile 定义 mandatory/optional stage。任一 mandatory stage 被跳过、timeout、熔断都会改变 `route_execution_signature`；未经该 degraded route 独立 benchmark + risk certification，不允许 CERTAIN_MATCH，只能 UNKNOWN 或异步重试。

禁止因为 Reranker/Local Visual/VLM 不可用而静默退化成 ANN/BM25 Top-1 自动挂接。

### 16.2 End-to-end Deadline

每条在线请求入口生成绝对 deadline，沿 OpenSearch、Reranker、OCR、GPU/VLM 调用链传播。

- 每个 route 配置 `total_deadline_ms`、stage budget、mandatory/optional、最小剩余预算。
- Expensive stage 开始前检查剩余 deadline；不足则不启动。
- mandatory stage 未执行 → `UNKNOWN_DEPENDENCY_FAILURE`。
- 客户端取消/上游 deadline 到期向下传播 cancellation。
- Web/VLM 慢路径使用独立异步 SLA。

### 16.3 Retry / Queue / Circuit Breaker

- 每个依赖只有一个 retry owner，禁止多层重试。
- 只重试明确 transient 错误。
- 指数退避 + jitter + max attempts + retry budget，并受原始 deadline 约束。
- OpenSearch、Reranker、OCR、GPU/VLM、Web Agent 分别设置 `max_inflight / max_pending / queue_deadline / circuit threshold / half-open budget`。
- 队列有界；没有足够 deadline 的排队请求直接 shed/UNKNOWN。
- 依赖健康状态写入 Recognition runtime snapshot。

### 16.4 Load Shedding

```text
P0 Strong Identifier 在线 Linking
P1 普通 Hybrid Linking
P2 Near-tie Local Visual / Difficult Pair
P3 Entity Discovery / Web Evidence / Novelty Scan
P4 历史 backfill / optional re-embedding / periodic Canonical dedupe scan
```

过载优先停止 P4→P3→P2。任何简化 route 未独立认证时只能降低 Coverage，不能降低 Identity Safety。

定期故障注入：timeout、OpenSearch partial failure、GPU unavailable、queue overload、retry storm、CDC lag、重复/乱序事件、refresh lag、撤销 alias 旧索引命中、publication rollback、Split/Merge Repair 部分发布。

## 17. 容量、成本与性能

### 17.1 10M 向量容量

假设 10M 商品、平均 3 图、10M text + 30M image vectors、512d。

模型导出 FP16 数组约 40.96GB；OpenSearch on-disk 完整 float 向量按 FP32：

```text
Text   20.48GB
Images 61.44GB
合计完整向量磁盘基线 ≈ 81.92GB / active vector set
```

不含 Lucene segment、HNSW/量化索引、倒排、doc values、metadata、translog、merge 临时空间、副本、shadow index。

HNSW 量化内存参考：

```text
HNSWBytes ≈ 1.1 × (dimension × bits / 8 + 8 × m) × vector_count
```

512d、m=16、40M vectors：32x/1-bit 约 8.45GB，16x/2-bit 约 11.26GB（仅 HNSW 图量级）。

### 17.2 资源档位

PoC（1–2M）：1×L4 24GB、1×8 vCPU/64GB OpenSearch、0.5TB SSD/block storage。

```text
3 × 8 vCPU / 64GB OpenSearch data/search nodes
3 × 1TB usable storage, replica=1，可容纳 active+shadow
2 × L4 24GB online GPU（HA 时）
历史 backfill 临时扩 4–8 × L4/同级 GPU
```

公有云核心 compute+block storage 量级约 PoC $1k/月、10M 起点约 $3k/月；仅作立项量级，采购时按实际区域重算，另计 DB、原图、快照、日志、网络、备份。

成本与 `Coverage @ 99.9% Precision` 联合优化。

## 20. 正式开启自动识别 Gate

全部满足才扩大 Auto-Match：

1. 主要品类/来源 `Precision@Auto-Match >= 99.9%`。
2. `Recall@100 after fusion/truncation >= 99.5%`。
3. Exact/官方标识符候选 survival = 100%。
4. 有足够独立 Certification Audit 样本支撑目标错误率上界。
5. 所有 Hard Conflict 回归 0 自动错合并。
6. Seen/Strict Unseen/Time-shift、Vintage、缺图、缺型号、脏型号、低质图、文本图像冲突分别达标。
7. Image-only 路径不得无额外身份/结构证据产生 CERTAIN_MATCH。
8. Synthetic/Pseudo evidence 不得成为 Hard Fact / Identity Anchor / Certification Gold，违规=0。
9. AMBIGUOUS/NIL/RETRIEVAL_FAILURE 不得绕过 Candidate Guard。
10. 新 SKU challenge set forced Known-Link / near-tie 错误挂接=0。
11. Final certification split leakage=0。
12. 每个品牌/来源/品类/EvidenceProfile/CandidateState 有阈值或 kill switch。
13. 模型、规则、ontology、index、fusion、route、candidate/runtime/publication policy 均可回滚。
14. Recognition 可重放完整 Evidence、CandidateSetAssessment、publication、dependency health、deadline/retry、immutable model hash 与 training lineage。
15. Source/model/route/retrieval drift 超阈值自动 UNKNOWN 或关闭 Auto-Match。
16. Product Group ID 作为 Variant Identity Anchor 违规=0。
17. 未认证 merchant SKU 作为官方 Reference 违规=0。
18. Official Web JSON-LD/DOM 未解决冲突时自动 ACTIVE=0。
19. 正式 Precision 证明来自冻结版本真实 CERTAIN_MATCH 流的概率审计。
20. Certification sampling provenance 完整率=100%，认证 label 同版本调参复用违规=0。
21. mandatory stage timeout/熔断且 degraded route 未认证时 CERTAIN_MATCH=0。
22. Catalog/Search publication 不一致时 CERTAIN_MATCH=0。
23. 所有 ACTIVE 模型 model lineage 完整率=100%。
24. 上游 Gold Label/Canonical Fact taint 后，受影响模型/索引能在 SLA 内发现并 kill-switch/re-certification。
25. Teacher/Pseudo-label 训练结果必须在独立 sealed human/time-shift set 上认证。
26. `SPLIT_PENDING / SPLIT / MERGE_PENDING / TAINTED` Canonical 新增自动挂接违规=0。
27. Confirmed Split 所有成员必须完成 re-resolution；不唯一成员自动迁移违规=0。
28. Split 后跨多个 child 的 Alias/Identifier 进入 Exact Variant Retrieval 违规=0。
29. Split/Merge Repair partial publication 下 CERTAIN_MATCH=0。
30. ACTIVE Canonical 内治理级 Hard Conflict/confirmed cannot-link 必须在 SLA 内 freeze/repair。
31. **任何 `PROPOSED → ACTIVE` 都必须有同 publication 的 `canonical_novelty_assessment`，缺失违规=0。**
32. **被策略认定 variant-unique 的 governed Manufacturer Identifier / official external Variant ID 同时属于多个非 MERGED ACTIVE Canonical 的违规=0。**
33. **`novelty_state != UNIQUE` 的 Canonical 自动激活违规=0。**
34. **Confirmed duplicate Canonical 必须通过 `MERGE_PENDING → MERGED_INTO survivor` 的原子 repair publication 完成；旧 Canonical 在发布前 redirect/继续 Auto-Match 的违规=0。**
35. **并发 Discovery 导致同一 identity claim 产生多个 ACTIVE Canonical 的违规=0。**

任何指标退化时，优先降低 Coverage，而不是放宽 Hard Constraint、NIL/Ambiguity Guard、Novelty Gate、Fact Promotion、Publication Barrier、ML lineage 或 Canonical Repair。

## 22. 最终生产原则

```text
官方知识 / 标准化 / 确定性标识
          ↓
EvidenceProfile / Route Policy
          ↓
只运行真实证据所需检索与模型
          ↓
Exact Preserve + Versioned Fusion
          ↓
结构化 + 文本 + 图片多证据
          ↓
Hard Conflict + Calibration
          ↓
Candidate-set / NIL / Ambiguity Guard
          ↓
Constraint-aware Graph Resolution
          ↓
仅 CERTAIN_MATCH Recognition
          ↓
Canonical Novelty / Uniqueness Gate
          ↓
ACTIVE Catalog Health: Split + Merge Repair
          ↓
Review Feedback + Independent Risk Audit
          ↓
Controlled Training + Immutable ML Lineage
```

固定原则：

1. **Identity first，Similarity second。**
2. **Hard Conflict 优先于任何模型高分。**
3. **UNKNOWN 是合法且必要的生产输出，并必须有 reason code。**
4. **缺模态不能靠生成模态伪装成完整证据。**
5. **Synthetic/Pseudo evidence 不能形成 Hard Fact / Identity Anchor / Certification Gold。**
6. **仅视觉相似不能自动 SAME_VARIANT。**
7. **全局视觉负责召回，局部视觉只验证 near-tie shortlist。**
8. **必须显式允许 NIL / None-of-the-Candidates。**
9. **Top-1/Top-2 near-tie 时必须 Abstain。**
10. **所有 Evidence、事实、Review、数据集、模型、路由、Publication 与运行时状态可版本化、可重放。**
11. **多个 URL 不等于多个独立来源；同一原始证据的多个分数不等于多个独立证据。**
12. **Exact 候选永不被 soft fusion 截断。**
13. **新 SKU / Vintage / time-shift / missing-modality / NIL 单独评测。**
14. **训练 Review 与风险 Certification 分流。**
15. **Product Group ID 是关系标识，不是 Variant 身份；Merchant SKU 与 Manufacturer Identifier 分命名空间。**
16. **官网结构化数据是高价值 Evidence，不是无条件 Canonical Truth。**
17. **DB→Search 使用事务性 outbox + 幂等投影 + 单调版本 + publication barrier。**
18. **timeout/过载/依赖故障形成的新 route 未认证时 fail closed 为 UNKNOWN。**
19. **每一个 ACTIVE 模型是不可变、可哈希、可追溯 Artifact。**
20. **伪标签用于训练效率，不用于证明自己的正确性。**
21. **ACTIVE Canonical 不是永久真值：持续检查 over-merge 与 under-merge 两种 Catalog Health。**
22. **Split 处理一个 Canonical 混入多个 Variant；Merge 处理同一 Variant 被拆成多个 Canonical。两种 repair 都必须回到原始 Evidence，并通过一致 publication 发布。**
23. **Entity Discovery 是“新品证明”问题，不是“没有匹配上”问题；`POSSIBLE_NIL` 不能直接推出新 Canonical。**
24. **任何 `PROPOSED → ACTIVE` 都必须通过 Canonical Novelty/Uniqueness Gate；有近邻而缺少可靠区分属性时宁可继续 PROPOSED。**
25. **variant-unique Manufacturer Identifier / official Variant ID 必须具备唯一 identity claim，防止并发 Discovery 生成重复 ACTIVE。**
26. **任何复杂度只有在提高 Coverage@99.9% Precision、提升可靠性、降低 Catalog fragmentation 或降低总成本时才有价值。**
