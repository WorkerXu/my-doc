# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站和公开 Newsletter** 的长期知识库采集平台，并能平滑扩展到数千站点、百万至千万级文章。

系统必须同时满足：

1. **全历史回填**：尽可能完整发现每个已批准 Source 的历史文章，并能解释覆盖率、缺口与停止原因；
2. **持续增量同步**：稳定发现新文章、正文更新、URL 迁移、重定向、删除和重发布；
3. **稳定 Markdown**：从不可变 Raw Artifact 经确定性抽取、质量门禁、Canonical IR 生成可重放 Markdown；
4. **低成本扩站**：新增站点优先通过 Source Profile、Provider、Traversal Policy、Extraction Recipe 配置完成，不维护 1000 份站点脚本；
5. **Web 可运营**：支持站点接入、审批、Backfill、Incremental、Coverage、Frontier、质量、成本、暂停、恢复、诊断和审计；
6. **可恢复、可重放**：URL、Run、Task、Attempt、Runtime Result、Artifact、Document、Version 全链路可追溯；
7. **可搜索/RAG**：支持 BM25、向量和混合检索，并能回到原文、版本、Source 与抓取证据；
8. **渐进扩展**：开发期 Docker Compose，生产期各执行面独立水平扩容；
9. **主链不依赖 LLM**：LLM 只做可选增强，不参与历史完整性、URL 身份、robots、正文存在性等最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 都有 Provider Inventory、Known Gap、Backfill Stop Reason；
- **Freshness**：新文章从发布/发现到 PASS Markdown 的延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文、代码块、表格、列表保留率和噪声率；
- **Reliability**：Task 成功率、Retry、DLQ、Queue Age、Lease Recovery；
- **Browser Efficiency**：HTTP 命中率、Browser Avoided、Pool Reuse、每文档 Browser 成本；
- **Runtime Stability**：queue saturation、真实内存压力、browser acquire latency、pool churn、drain latency；
- **Result Integrity**：批量/流式 Runtime Result 的物化完整率、cardinality mismatch、schema mismatch；
- **Replayability**：同 Raw Artifact + 同 Release 可复现 IR 和 Markdown；
- **Artifact Durability**：required runtime artifact 在 TTL 到期前晋升到平台对象存储的比例接近 100%。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不默认使用个人持久 Browser Profile、模拟用户等反爬绕过手段；
- 不把 HTTP 200、Runtime `success=true`、DOM 很长直接视为文章正确；
- 不把搜索结果数、Common Crawl、Wayback 或 Deep Crawl 页数当作历史完整性证明；
- 不把 Crawl4AI 即时 Markdown、LLM 摘要直接作为 Canonical Markdown；
- 不把 Redis、Runtime Cache、Browser Session、Visited Set、Runtime Queue、Search Index 当业务真相；
- 不允许外部用户提交任意 JS/Python、代理、CDP、服务器路径或任意 webhook URL。

## 2. 核心设计原则

1. **Coverage First**：先建立 URL Inventory，再批量抓正文；
2. **Authoritative First**：CMS/API、Sitemap、RSS/Atom、官方 Archive 优先；
3. **Historical Gap Is Evidence, Not Truth**：Common Crawl、Wayback 只作为补洞证据；
4. **Discovery / Fetch / Extract / Quality / Projection 分离**；
5. **HTTP First, Browser Slow Lane**；
6. **Snapshot First**：先保存不可变 Raw Artifact；
7. **Canonical IR First, Markdown as Projection**；
8. **Recipe, Not 1000 Site Scripts**；
9. **Persistent Frontier, Not In-Memory Traversal**；
10. **Idempotent + Recoverable**：幂等键、Lease、Fencing Token、Checkpoint、Inbox/Outbox；
11. **Fair by Default**：大站 Backfill 不得饿死 Incremental、小站和 Repair；
12. **Bounded Concurrency Everywhere**；
13. **No Silent Degradation**：过滤、截断、预算耗尽、降级、结果缺失必须有原因；
14. **Observation Before Selection**：链接事实先保存，再 Filter/Score/Budget；
15. **Runtime Is Execution Plane**：第三方 Runtime 不拥有 Coverage、Identity、Document 或 Markdown 真相；
16. **Correlate by Identity, Never by Position**；
17. **Config Is Capability**：能改变代码、网络、浏览器或 secret 的字段必须经过 Capability Firewall；
18. **Untrusted by Default at Network Boundary**；
19. **Caller Never Owns Paths**；
20. **Webhook Is Hint, Reconciliation Is Truth**；
21. **Runtime Queue != Durable Queue**；
22. **Behavior Beats Naming**：pinned release + Contract Test 才是生产行为契约；
23. **Runtime Artifact Is Ephemeral Until Promoted**；
24. **Zero Must Not Mean Unbounded by Accident**；
25. **Runtime State Is Observation, Not Truth**；
26. **Control Browser Config Cardinality**：大量站点映射到少量 Browser Profile Class；
27. **Result Transport Is Not State Store**：Runtime Result 只做短期交接，结果立即逐条物化；
28. **Drain/Replace Before In-Place Kill**；
29. **Local Safety Is Not Global Admission**：Runtime Dispatcher/RateLimiter 只负责实例内保护，平台负责跨 Worker 的持久公平和礼貌性限流。

## 5. Source 接入与配置模型

### 5.1 Source Profile

新增网站创建声明式 Source Profile：

```yaml
source:
  name: example-tech-blog
  entry_url: https://example.com/blog/
  approved_hosts: [example.com]
  allowed_paths: [/blog/]
  denied_paths: [/login/, /account/]

providers:
  - type: sitemap
    url: https://example.com/sitemap.xml
  - type: rss
    url: https://example.com/feed.xml
  - type: archive
    start_url: https://example.com/blog/archive/

fetch:
  mode: auto
  http_timeout_s: 20
  browser_profile_class: public-default
  browser_intent:
    render_js: true
    scroll: bounded
    wait_selector: article

extract:
  recipe: generic_article_v3
  content_selectors: ["article", ".post-content"]
  exclude_selectors: ["nav", "footer", ".related"]

incremental:
  feed_poll: 10m
  sitemap_poll: 1h
  archive_reconcile: 1d
  full_reconcile: 7d
```

### 5.2 Capability Firewall

Web/API 用户只提交 intent，不允许直接透传 Runtime 高能力字段。

普通配置禁止：

- 任意 `js_code` / Python code；
- 任意 `proxy` / `proxy_config`；
- `user_data_dir` / `cdp_url`；
- 任意 cookies/headers/secret；
- 任意服务器 path；
- 任意 LLM base URL；
- 任意 webhook destination；
- `0=unbounded` 的 queue/time/budget；
- 不受控 deep crawl strategy。

Config Compiler 根据已审批 Profile Release 生成 Runtime Config，并输出编译报告、最终能力集合、预算和拒绝原因。

### 5.3 Browser Profile Class

平台只维护少量受审 Browser Profile，例如：

```text
public-default
public-js-heavy
public-media-light
isolated-authenticated
```

站点 selector、wait、scroll、正文规则优先放入低成本 CrawlerRunConfig/Extraction Recipe。只有真正改变浏览器进程能力、网络边界或 credential scope 的需求才生成新的 Browser Profile Release。

## 6. 历史 URL 发现与 Coverage

### 6.1 Provider 优先级

推荐顺序：

1. CMS/官方内容 API；
2. Sitemap / Sitemap Index；
3. RSS/Atom；
4. 官方 Archive / Category / Pagination；
5. 站内静态链接图；
6. Crawl4AI Domain Mapping / Deep Crawl 作为发现增强；
7. Common Crawl / Wayback；
8. 合规 Search Adapter 作为 Gap Evidence。

每个 Provider 只产生 Observation，不直接决定最终文章集合。

### 6.2 Observation

```text
url_observation
- source_id
- provider_type
- provider_ref
- observed_url
- discovered_at
- published_at_hint
- updated_at_hint
- parent_url
- anchor_text
- depth
- evidence_artifact_id
- provider_release_id
```

链接事实先落库，再做 scope/filter/dedup，避免过滤错误后无证据可查。

### 6.3 Coverage Snapshot

```text
coverage_snapshot
- provider inventories
- accepted URL count
- fetched count
- PASS count
- known gaps
- excluded reasons
- pagination stop reason
- earliest known date
- latest known date
- provider disagreement
- last_full_reconcile_at
```

Backfill 停止原因必须显式，例如：

```text
AUTHORITATIVE_PROVIDER_EXHAUSTED
ARCHIVE_PAGINATION_EXHAUSTED
DATE_BOUND_REACHED
ROBOTS_BLOCKED
ACCESS_DENIED
BUDGET_EXHAUSTED
PROVIDER_ERROR
```

Deep Crawl、Adaptive Crawling、搜索结果或归档库只能补充证据，不能单独宣称“历史完整”。

### 6.4 Adaptive / Focused Discovery

Adaptive Crawling 只用于：

- 无权威列表时的 focused discovery；
- Provider disagreement 的定向补洞；
- 大型文档站只需特定主题时的预算优化。

它的停止条件必须记录 target、confidence、budget、termination reason，不替代 Coverage Inventory。

## 7. URL Identity、Scope 与 Persistent Frontier

### 7.1 Conservative Normalization

URL 身份分层：

```text
observed_url
normalized_url
redirect_target
canonical_url_hint
url_identity_id
```

默认只做保守规范化：scheme/host 小写、默认端口、fragment 删除、已知 tracking 参数剥离。路径大小写、尾斜杠、业务 query 不做激进合并。

`rel=canonical`、重定向、站点规则只是证据；真正 Document Identity 由平台版本化规则决定。

### 7.2 Persistent Frontier

```text
frontier_item
- source_id
- url_identity_id
- stage
- priority
- reason
- discovered_at
- next_attempt_at
- attempt_count
- lease_owner
- lease_until
- fencing_token
- last_error_class
- provider_evidence
```

Frontier 永久保存在 PostgreSQL。Runtime queue、Crawl4AI PriorityQueue、asyncio Task 都不能替代它。

## 8. Scheduler、Task、Lease 与公平性

### 8.1 Durable Task

```text
task
- task_id
- source_id
- run_id
- url_identity_id
- task_type
- priority_class
- state
- attempt_no
- next_attempt_at
- lease_owner
- lease_until
- fencing_token
- idempotency_key
```

Task 状态示例：

```text
PENDING -> LEASED -> RUNNING -> MATERIALIZING -> SUCCEEDED
                    |              |
                    |              +-> REPAIR
                    +-> RETRY_WAIT -> PENDING
                    +-> DLQ
```

所有写入必须校验 fencing token，避免旧 Worker 在 lease 失效后覆盖新结果。

### 8.2 Fair Scheduler

平台使用分层 DRR/WFQ：

```text
job class
  |- INCREMENTAL
  |- NEW_SOURCE_BACKFILL
  |- HISTORICAL_BACKFILL
  |- REPAIR
  |- RECONCILE
       |
       v
Source/Tenant fair queue
       |
       v
Domain admission
```

必须给 Incremental 和 Repair 保留容量，避免大站 Backfill 长时间霸占执行面。

### 8.3 Global Admission

跨 Worker 共享：

```text
per_host_qps
per_host_concurrency
per_registrable_domain_concurrency
per_source_concurrency
global_http_slots
global_browser_slots
origin_backoff_until
Retry-After
```

实现采用 Redis Lua Token Bucket/Semaphore；PostgreSQL 保存可审计的长期 backoff/Observation。

## 9. Fetch Plane

### 9.1 HTTP Fast Lane

优先使用 HTTP：

- robots.txt；
- Sitemap/Feed/API；
- 普通文章；
- Conditional GET：`If-None-Match` / `If-Modified-Since`；
- HEAD 仅作提示，最终以 GET + MIME sniffing 为准；
- 记录 redirect chain、status、headers、TLS/网络错误分类；
- 304 只表示 representation 未变，不表示 Source Inventory 完整。

### 9.2 Browser Slow Lane

仅在以下条件升级 Browser：

- HTTP DOM 缺正文；
- 页面正文依赖 JS；
- 需要有限滚动/点击才能加载正文；
- Source Profile 明确声明；
- HTTP Candidate 质量门禁失败且 Browser Repair 有价值。

Browser 请求必须经过 Global Admission 和 Runtime Admission，禁止直接从 Discovery 大批量灌入 Browser。

## 10. Crawl4AI Runtime Service Plane

### 10.1 Runtime Registry 与版本固定

每个实例注册：

```text
runtime_instance
- runtime_instance_id
- runtime_release_id
- image_digest
- crawl4ai_version
- browser_version
- browser_profile_classes
- dispatcher_capabilities
- max_input_body_bytes
- max_runtime_wall_clock
- max_artifact_bytes
- health
- drain_state
```

生产只允许 pinned release。升级前运行 Contract Probe，不根据文档字段名推断实际行为。

### 10.2 双层 Backpressure

```text
Persistent Frontier
  -> Platform Fair Scheduler
  -> Global Admission
  -> bounded micro-batch
  -> Runtime Dispatcher
  -> Browser pool / HTTP execution
  -> streaming materialization
```

平台队列负责 durable/global/business fairness；Runtime Dispatcher 负责 ephemeral/local/resource safety。

### 10.3 Dispatcher Policy

```text
runtime_dispatch_policy_release
- dispatcher_type: MEMORY_ADAPTIVE | SEMAPHORE
- max_session_permit
- semaphore_count
- memory_pressure_threshold_percent
- memory_critical_threshold_percent
- memory_recovery_threshold_percent
- memory_check_interval_s
- memory_wait_timeout_s
- fairness_timeout_s
- local_rate_limit_profile
- runtime_batch_max_urls
- stream_mode
- stream_close_policy
- result_contract_version
```

这些字段是期望配置，真正有效行为以 pinned Runtime Contract Test 为准。

### 10.4 MemoryAdaptiveDispatcher 执行契约

其当前行为应按“局部内存滞回 Admission”理解：

- 达到 pressure threshold：停止继续从本地队列填充新 active task；
- 达到 critical threshold：已经进入执行入口的 URL 可能被重新放回本地 PriorityQueue；
- 降到 recovery threshold：才恢复放任务，避免阈值附近抖动；
- 高内存持续超过 `memory_wait_timeout`：按 `RUNTIME_MEMORY_PRESSURE_TIMEOUT` 分类，不按文章失败分类；
- PriorityQueue 的 aging/fairness 只对当前 Runtime batch 生效，不是跨 Source 公平；
- 单任务 `memory_usage/peak_memory` 是并发进程 RSS 差值，只做诊断，不能相加做容量账本。

本地 requeue 必须归一化为：

```text
LOCAL_REQUEUED
```

它不是平台 retry，不消耗 origin retry budget，也不能触发文章 DLQ。

### 10.5 SemaphoreDispatcher 的生产边界

固定 semaphore 模式适合资源成本稳定的小批量任务，但当前实现有两个必须固化到 Contract 的行为：

1. `run_urls()` 会先为输入列表中的每个 URL 创建 asyncio Task，再由 `asyncio.Semaphore(semaphore_count)` 控制真正进入 `crawler.arun()` 的并发。也就是说，**抓取并发有界不等于调度对象数量有界**；如果一次传入十万 URL，仍会产生 O(N) Python Task、Future 和结果引用。
2. 当前源码构造函数虽然保存 `max_session_permit`，但 Semaphore 执行路径的实际并发门由 `semaphore_count` 控制；`max_session_permit` 不能在没有 Contract Test 的情况下被管理端宣传为 Semaphore 模式的有效并发上限。

因此平台要求：

- Semaphore 只接收 bounded micro-batch；
- `runtime_batch_max_urls` 是硬上限，不允许 `0` 表示无界；
- Capacity Planner 在当前 pinned release 下以实测 `semaphore_count` 作为并发旋钮；
- 每次升级都测试 `max_session_permit` 是否开始参与执行语义；
- Runtime 监控增加 `scheduled_async_tasks` 与 `semaphore_waiters`，识别“抓取并发正常但事件循环积压”的情况。

### 10.6 Runtime RateLimiter 不是全局礼貌性限流

当前 `RateLimiter` 的 domain state 是进程内状态，主要包含：

```text
last_request_time
current_delay
fail_count
```

429/503 会扩大 delay，正常响应会逐步降低 delay。`max_retries` 在当前实现中不能直接解释为“自动重新请求当前 URL N 次”。

另外，`wait_if_needed()` 没有建立一个跨等待期的严格 per-domain reservation/lock。多个同域任务可能基于同一个 `last_request_time` 同时 sleep，并在相近时刻一起醒来，因此它更像 **实例内 pacing hint/backoff state**，而不是严格 QPS token bucket。

平台要求：

- 跨 Pod/跨 Worker 的 host/domain QPS、并发、Retry-After、backoff 由 Redis Lua + 共享 `origin_backoff_state` 统一控制；
- Runtime RateLimiter 只做第二道局部保护；
- Runtime 重启不能清除平台 backoff；
- 429/503 反馈写入 Observation，供所有 Worker 共享；
- Contract Test 同时验证延迟变化、真实请求次数和是否真的发生重发。

### 10.7 Config first-match 契约

当一个 Job 携带多个 `CrawlerRunConfig` 时，当前 Dispatcher 按顺序选择第一个 `is_match(url)` 的配置。未命中时返回 `NO_CONFIG_MATCH`。

Config Compiler 必须：

- 做 matcher overlap/shadow 检测；
- 显式 rule order；
- 显式 default；
- 用代表性 URL fixture 做 match coverage test；
- 每个 Attempt 保存最终命中的 `crawler_run_config_release_id`、`matcher_rule_id`、matcher evidence。

`NO_CONFIG_MATCH` 是配置/路由问题，不消耗源站 retry budget。

### 10.8 Batch 与 Streaming 结果契约

Browser micro-batch 优先使用 Streaming：结果完成一个就立刻物化一个，降低大 `CrawlResult` 的驻留时间。

平台禁止：

```python
for input_url, result in zip(urls, results):
    persist(input_url, result)
```

必须按 identity 关联：

```text
runtime_task_item
- runtime_task_id
- attempt_id
- input_url_identity_id
- correlation_key
- normalized_outcome
- materialized_at
```

原因：MemoryAdaptive 的 local requeue 在 batch 与 stream 下可见行为不同。Batch 路径可能先出现 requeue placeholder，再出现最终结果；stream 路径会屏蔽该 placeholder 后再推进完成计数。结果条数和顺序都不能作为身份契约。

Adapter 输出统一 outcome：

```text
FINAL_SUCCESS
FINAL_FAILURE
LOCAL_REQUEUED
NO_CONFIG_MATCH
CANCELLED_ON_STREAM_CLOSE
RUNTIME_MEMORY_PRESSURE_TIMEOUT
```

### 10.9 Stream close 是取消协议

消费者取消、Worker shutdown 或 Materializer 失败都可能提前关闭 stream。

平台状态机：

```text
RUNNING_STREAM
  -> RUNTIME_STREAM_ABORTED
  -> verify runtime cleanup
  -> inspect already materialized terminal items
  -> reconcile unmaterialized items
  -> durable requeue with fencing
```

已经 yield 且 Raw Artifact 已持久化的 item 保持 terminal；未 materialize 的 in-flight/queued item 才重新调度。

Runtime Contract Test 必须覆盖：

- early `aclose()` / cancel；
- in-flight task 被取消并 await；
- local queue 被 drain；
- page/context/session 不残留；
- 同一 crawler 随后可再次工作；
- 不出现旧任务继续输出；
- 平台只重发未 terminal 的 item。

### 10.10 Micro-batch 计算

```text
batch_size = min(
  runtime_batch_max_urls,
  available_runtime_slots * batch_factor,
  per_domain_budget,
  lease_deadline_budget,
  expected_result_bytes_budget,
  memory_headroom_budget
)
```

高成本 Browser Repair 默认 `1 URL / Job`；普通 Browser Backfill 使用小批量。具体数值由压测和 P95/P99 页面成本决定，不使用文档默认值直接上线。


Runtime state 只作为 Observation；平台 Task 状态由物化证据和 Reconciler 推导。

### 11.2 Result Materializer

每收到一个 terminal result：

1. 校验 runtime task/correlation identity；
2. 校验 result schema；
3. 保存原始 response metadata；
4. 将 required artifact 从 Runtime 临时存储晋升到 S3/MinIO；
5. 写 artifact checksum/size/MIME；
6. 创建 Raw Artifact；
7. 用事务更新 Attempt/Task；
8. Outbox 触发 Extraction。

“Runtime 返回成功”但 required artifact 未晋升时，不允许 Task 进入业务 `SUCCEEDED`。

### 11.3 Webhook Inbox + Reconciler

Webhook 只做提示：先入 Inbox、验签/去重，再异步处理。Reconciler 周期检查：

- lease 超时；
- Runtime 消失；
- stream 中断；
- expected item 没 terminal materialization；
- artifact promotion 未完成；
- cardinality/schema mismatch。

最终以 PostgreSQL + Object Storage 的证据闭合状态。

## 21. 取消、暂停、Drain 与恢复

### 21.1 Stop 语义

- **Pause Source**：停止发新 Task，不杀已 materialize 成功项；
- **Cancel Run**：停止新 lease，通知 Runtime stream close，并 reconcile 未 terminal item；
- **Drain Runtime**：停止新 Admission，等待 active job 收敛，超时后取消并 reconcile；
- **Replace Runtime**：新实例健康并通过 Contract Probe 后切流，再终止旧实例。

### 21.2 Crash Recovery

Worker/Runtime 崩溃：

1. lease 到期；
2. Reconciler 检查哪些 item 已 terminal materialize；
3. 已持久化成功项不重抓；
4. 其余 item 重新进入 PENDING；
5. fencing token 防止旧 Worker 回写；
6. origin shared backoff、Coverage、Frontier 不受 Runtime 重启影响。

## 27. 验收标准

上线前至少满足：

1. 新站可通过配置接入，不需要复制站点爬虫代码；
2. 每个 Source 可展示 Provider Inventory、Coverage 和 Stop Reason；

12. Source 配置、Runtime、Extractor、IR、Renderer 全部可版本追溯；

15. 全链路有 correlation、指标、审计和 Chaos Recovery 验证。

## 28. 最终架构结论

最终方案不是“让一个爬虫进程抓 1000 个博客”，而是把长期知识库拆成四类清晰事实：

```text
Coverage / Frontier / Task Truth
    = PostgreSQL

Raw / IR / Markdown Truth
    = Object Storage + PostgreSQL Metadata

Cross-worker Scheduling / Politeness
    = Platform Scheduler + Redis Lua + Durable Backoff

Browser Execution
    = Pinned Crawl4AI Runtime + Bounded Dispatcher + Browser Pool
```

Crawl4AI 的 Advanced Multi-URL Crawling 适合作为 **单 Runtime 的局部执行控制**：MemoryAdaptiveDispatcher 提供内存压力滞回和局部队列，SemaphoreDispatcher 提供简单固定并发，Streaming 支持边完成边物化。但这些能力都不能替代平台级持久任务、公平调度、跨 Worker 限流、Coverage 和版本真相。

生产关键约束是：**平台只给 Runtime 有界 micro-batch；所有结果按 identity 关联；Runtime 本地 requeue 不等于平台 retry；stream close 必须 reconcile；RateLimiter 只是本地安全网；Semaphore 的有效并发与任务创建语义必须由 pinned release Contract Test 验证。**

以这组边界实现后，平台既能利用 Crawl4AI 的高吞吐 Browser 执行，又不会把 1000+ 站点长期同步的完整性、可靠性和可扩展性绑定在某个进程内队列、某个文档默认值或某个 Runtime 版本细节上。
