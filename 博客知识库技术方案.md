# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站和公开 Newsletter** 的长期采集与知识库平台，可平滑扩展到数千站点、百万到千万级文章。

平台必须满足：

1. **全历史回填**：尽可能完整发现每个已批准 Source 的历史文章，并能解释发现通道、覆盖率、缺口、截断和停止原因；
2. **持续增量同步**：发现新文章、正文修改、元数据变化、URL 迁移、重定向、删除和重发布；
3. **Markdown 稳定可重放**：保存不可变 Raw Artifact，经版本化 Cleaner、Extractor、Canonical IR、Renderer 生成最终 Markdown；
4. **技术内容保真**：代码块、表格、公式、Mermaid、列表、引用、脚注、图片说明不能被通用降噪算法静默删除；
5. **低成本扩站**：新增站点优先通过 Source Profile、Provider、Recipe、Traversal Policy 配置完成，不维护 1000 份独立爬虫脚本；
6. **Web 可运营**：支持站点接入、审批、Backfill、Incremental、Coverage、Frontier、质量、成本、诊断、暂停、恢复、重跑、灰度和审计；
7. **任务可恢复**：Provider Run、Task、Attempt、URL、Artifact、Candidate、Document、Version 全链路有持久状态，Worker/Runtime 崩溃可恢复；
8. **可搜索/RAG**：支持 BM25、向量和混合检索，并能回溯原文、版本、Source、抓取证据和处理 Release；
9. **主链不依赖 LLM**：LLM 只做可选 Repair/Enrichment，不参与历史完整性、URL 身份、正文存在性、版本真相和权限边界的最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 可查看 Provider Inventory、Completion Attestation、Known Gap、Backfill Stop Reason；
- **Freshness**：新文章/更新从发布或发现到 PASS Markdown 的 P50/P95/P99 延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文、代码、表格、列表、链接、图片说明、公式的召回率与噪声率；
- **Protected Structure Recall**：受保护技术节点在 Candidate/IR 中的保留率；
- **Multilingual Retention**：中文、日文及中英混排正文保留率；
- **Reliability**：Task 成功率、Retry、DLQ、Queue Age、Lease Recovery；
- **Replayability**：相同 Raw Artifact + 相同 Release 必须得到相同派生结果；
- **Provider Integrity**：部分返回、cache hit、预算耗尽不能被误报为“已完整枚举”；
- **Artifact Durability**：需要保留的 Runtime/Provider Artifact 必须晋升平台对象存储；
- **Browser Efficiency**：HTTP Fast Lane 命中率、Browser Avoided、Browser 单文档成本；
- **Revalidation Integrity**：强验证成功率、弱验证漏检率、`hit_fallback` 数量、强制刷新抽样命中变化率；
- **Validator Integrity**：业务 validator 必须能追溯到具体 Raw Artifact/body hash，不允许弱信号把新 validator 绑定到旧正文；
- **Fairness**：大型 Backfill 不得长期饿死 Incremental、小站、Repair 和 Reconcile。

## 2. 核心设计原则

1. **Coverage First**：先构建可解释 URL Inventory，再抓正文；
2. **Authoritative First**：官方 CMS/API、Sitemap、Feed、Archive 优先；
3. **Observation Before Selection**：先保存发现事实，再 Normalize、Scope、Classify、Dedup；
4. **Successful Return != Provider Complete**：HTTP 200、非空结果、`success=true`、cache hit 均不能自动代表 Provider 完成；
5. **Completion Must Be Attested**：只有具备可验证结束语义的 Provider Adapter 才能声明完成；
6. **Discovery / Revalidation / Fetch / Clean / Extract / Quality / Canonicalize / Projection 分离**；
7. **HTTP First, Browser Slow Lane**；
8. **Snapshot First**：先保存 Provider Evidence / Raw Artifact，再生成派生物；
9. **Candidate Portfolio, Not Single Extractor**：多个确定性候选互相校验；
10. **Protected Structures Are First-Class**：代码、表格、公式等先识别，再验证召回；
11. **Language Assumptions Must Be Explicit**：word/token threshold 必须声明适用语言；
12. **Canonical IR First, Markdown as Projection**；
13. **Recipe, Not 1000 Site Scripts**；
14. **Persistent Frontier, Not In-Memory Traversal**；
15. **Idempotent + Recoverable**：幂等键、Lease、Fencing Token、Checkpoint、Inbox/Outbox；
16. **Fair by Default**：Incremental、Revalidation、Repair 必须预留容量；
17. **Bounded Concurrency Everywhere**：任务数、在途请求、结果集合、Browser、进程生命周期都有硬边界；
18. **No Silent Degradation**：过滤、截断、partial result、预算耗尽、cache fallback、降级必须有 typed reason；
19. **Correlate by Identity, Never by Position**；
20. **Config Is Capability**：高能力配置必须经过 Capability Firewall；
21. **Runtime Is Execution Plane**：第三方 Runtime 不拥有 Coverage、Identity、Document、Version、Freshness 或 Markdown 真相；
22. **Behavior Beats Naming**：生产语义以 pinned release + Contract Test 为准，而不是 enum 名称或某一页文档；
23. **Runtime Cache Is Disposable**：本地 cache 可丢弃，不得推进业务版本真相；
24. **Derived Artifact Never Overwrites Evidence**：Cleaned HTML、Candidate、IR、Markdown 均是可重放派生物；
25. **Weak Freshness Signal Cannot Close Truth**：head fingerprint、长度相近等弱信号不能单独证明正文未变化；
26. **Validator Must Bind To Artifact**：ETag/Last-Modified 等业务 validator 必须绑定到具体 Raw Artifact/body hash；
27. **Same URL Does Not Imply Same Representation**：locale、Cookie、UA、Proxy、session、JS、Browser Profile 等不同上下文必须有 `fetch_variant_key`；
28. **Offline Means No Network**：离线 Replay 必须由平台 Artifact + egress deny 保证，不能依赖 `READ_ONLY` 之类的 Runtime 名称；
29. **Explicit Runtime Config**：生产 Attempt 必须显式记录 cache_mode、freshness 开关和 effective config，不能依赖 Runtime 默认值。

### 3.1 业务真相边界

**PostgreSQL + S3/MinIO 是业务真相。**

- PostgreSQL：Source、Scope、Provider、Provider Run/Checkpoint、Observation、URL Identity、Frontier、Task、Attempt、Revalidation Ledger、Validator Binding、Coverage、Candidate Manifest、Quality、Document、Version、Release、Audit；

- OpenSearch/pgvector：Serving Projection，可重建；
- Crawl4AI queue/cache/browser/session/seen/results：Runtime 临时状态，不是业务真相。

- **httpx/aiohttp**：CMS API、robots、Sitemap、Feed、Conditional GET、普通网页；

- **平台原生 SitemapProvider**：显式 Sitemap、robots Sitemap、Sitemap Index durable shard；

- **Crawl4AI AsyncUrlSeeder pinned release**：Sitemap/CC URL 发现加速器；

### 4.3 Extraction / Search

- **Trafilatura**：Generic Candidate；
- **lxml/BeautifulSoup**：DOM/XPath、Metadata、Repair、Protected Structure Fingerprint；
- **JSON-LD/OpenGraph/Microdata**；
- **CSS/XPath/Regex Recipe**；
- **Crawl4AI DefaultMarkdownGenerator / ContentFilter**：Markdown Candidate，不直接作为 canonical；
- **SimHash/MinHash**：近重复；
- **OpenSearch BM25 + pgvector + RRF**；
- embedding、reranker、LLM 只做增强。


Source Profile 只表达业务意图；具体 Crawl4AI/Playwright 参数由 Config Compiler 生成，普通用户不能直接透传任意脚本、代理、CDP、路径或 secret。

### 5.3 Fetch Variant

同一个 URL 在不同上下文中可能得到不同表示。平台必须生成稳定的 `fetch_variant_key`，输入至少考虑：

```text
source_id
browser_profile_class
locale / timezone
user_agent_class
auth/cookie class
proxy/region class
session class
render_js / interaction class
accepted representation / device class
runtime_security_profile_release
```

`fetch_variant_key` 用于：

- 判断某次 Raw Artifact 是否可复用；
- 隔离 Runtime cache namespace；
- 避免同 URL 在不同 locale、Cookie、UA、Proxy、session 下交叉污染；
- 诊断“同 URL 不同正文”的来源。

Extractor/Markdown 配置变化不应通过复用 Runtime 已派生的 `cleaned_html/markdown/extracted_content` 解决，而应从平台 Raw Artifact 重放新的处理 Release。

### 5.4 Capability Firewall

高风险能力必须单独授权：

- 自定义 JS；
- 任意 Header/Cookie；
- Proxy；
- Browser CDP；
- 文件下载；
- iframe/Shadow DOM；
- 任意外部回调；
- 高并发/长超时；
- 跨 host 跳转。

未经审批的 Source 配置只能使用安全 allowlist。

## 6. 全历史 URL 发现与 Coverage

### 6.1 Provider 优先级

每个 Source 的历史发现按以下优先级执行：

1. 官方 CMS/API；
2. Sitemap / Sitemap Index；
3. RSS / Atom；
4. Archive / Pagination / Tag / Category；
5. 静态链接图；
6. Common Crawl Index；
7. Wayback；
8. Crawl4AI URL Seeder、Domain Mapping、Deep/Adaptive Crawl 作为补洞和加速。

任何单一 Provider 都不能自动证明“全历史完整”。

### 6.2 Observation 模型

Provider 返回的每一条 URL 先写 `url_observation`：

```text
observation_id
source_id
provider_id
provider_run_id
observed_url
observed_at
provider_timestamp
provider_metadata
provider_evidence_uri
```

随后统一执行：

```text
Normalize -> Scope Check -> MIME Hint -> URL Identity -> Dedup -> Frontier Upsert
```

不允许 Provider 内部去重结果直接成为平台最终 Inventory。

### 6.3 Provider Completion Attestation

每次 Provider Run 保存：

```text
started_at / finished_at
checkpoint / cursor / shard
items_seen / unique_urls
status
completion_type
stop_reason
truncated
budget_exhausted
known_gap
provider_release
```

只有满足 Adapter 的明确完成条件时，`completion_type=ATTESTED_COMPLETE`。

以下情况一律不能标完整：

- 返回非空列表；
- HTTP 200；
- `success=true`；
- 达到 limit；
- cache hit；
- 搜索结果不再增加但没有协议级结束条件；
- Deep Crawl 达到配置深度/页面预算。

### 6.4 SitemapProvider

Sitemap Index 必须拆成 durable shard：

```text
sitemap_index_run
  -> sitemap_shard_1
  -> sitemap_shard_2
  -> ...
```

每个 shard 单独保存 URL、ETag/Last-Modified、fetch time、parse result、child count、checkpoint、completion attestation。

增量阶段对 Sitemap 使用 Conditional GET；`lastmod` 只做变化线索，不直接代表正文已变化。

### 6.5 Common Crawl / Wayback

只作为历史缺口补洞：

- 固定 index/release；
- 保存查询条件和返回证据；
- 流式读取，避免一次性加载大结果；
- URL 仍进入 Observation/Scope/Identity；
- Archive 出现不等于当前 URL 仍有效；
- Archive 缺失也不能证明文章从未存在。

### 6.6 Crawl4AI URL Seeder 的定位

AsyncUrlSeeder 可批量从 Sitemap/CC 等发现 URL，但平台必须：

- pin release；
- 限定 modes/domain；
- 将返回值转成 Observation；
- 保存 provider evidence 和 cutoff；
- 不把 Seeder 内部 cache/seen/queue 当 durable checkpoint；
- 不用 Seeder 返回条数证明 Coverage。

### 6.7 Coverage 计算

每个 Source 维护：

```text
provider_inventory
provider_attestation
historical_time_range
observed_url_count
fetchable_url_count
article_count
known_gap_count
unresolved_gap_count
backfill_stop_reason
```

Web 后台必须能回答：“为什么系统认为这个站回填完成/未完成？”

## 7. URL Identity、Canonical 与去重

### 7.1 三种 URL 分开

```text
observed_url      Provider 实际看到的 URL
normalized_url    平台规则归一化后的 URL
canonical_url     经证据判定的文章主 URL
```

不能直接把 `<link rel=canonical>` 当绝对真相，因为网站模板、镜像、错误配置可能把大量文章指向同一个 canonical。

### 7.2 Normalize

可安全做：host 小写、默认端口移除、fragment 移除、已知 tracking query 移除、Unicode/percent encoding 规范化、Source 级 trailing slash 规则。

不可全局盲做：query 参数排序/删除、path 大小写合并、日期段重写、`www` 与 apex 合并、HTTP/HTTPS 强制合并。这些必须受 Source Policy 控制。

### 7.3 Dedup

```text
URL exact identity
        -> redirect/canonical alias
        -> raw body hash exact duplicate
        -> semantic body hash
        -> SimHash/MinHash near duplicate
```

近重复只用于候选关联，不能自动删除原始 Document Version。

### 8.2 公平调度

分层队列：

```text
P0 incremental-hot
P1 revalidation
P2 new-source-backfill
P3 historical-gap
P4 repair/replay
```

按 `source_id / host / domain / workload_class` 做 Weighted Fair Queueing，并预留 Incremental/Revalidation 容量。

### 8.3 全局限流

Redis Lua 维护：

- host Token Bucket；
- source concurrency semaphore；
- domain concurrency semaphore；
- browser slot semaphore；
- provider-specific quota。

robots、站点政策和明确 Rate Limit 优先级高于吞吐量目标。

### 8.4 Backpressure

触发条件：Redis Stream Pending/Queue Age、PostgreSQL latency、S3 上传积压、Browser pool 饱和、Worker memory/CPU 高水位、单 host 429/503 增加。

策略：

```text
暂停低优先级 discovery
-> 降低 batch size
-> 减少 browser slots
-> 延迟 historical-gap
-> 保留 incremental/revalidation 预算
```

## 9. Revalidation Engine 与增量同步

这是增量同步的业务核心，不直接依赖 Crawl4AI Runtime Cache。

### 9.1 增量入口

- CMS API 新 revision；
- Sitemap `lastmod`；
- RSS/Atom `updated`；
- Webhook；
- Archive 新链接；
- 定时 Revalidation；
- 强制完整刷新；
- 用户手工重抓；
- Provider Reconcile。

### 9.3 证据强度

**STRONG**：

- CMS/API revision/version id；
- 使用“绑定到当前 authoritative Raw Artifact”的 validator 得到的标准 Conditional GET 304；
- 完整 GET 后 body hash 与历史一致。

**MEDIUM**：

- ETag/Last-Modified 发生变化；
- Sitemap/RSS 更新时间发生变化；
- 已知可靠但非正文级的 Provider change signal。

**WEAK**：

- `<head>` fingerprint 相同；
- 页面长度相近；
- link graph 相似；
- 局部 metadata 未变化。

只有符合 Source Policy 的强证据才允许推进 `last_verified_at`。

### 9.4 Validator Binding Invariant

这是避免 Smart Cache 把旧正文错误升级为 fresh 的关键约束。

平台维护：

```text
validator_binding_state = BOUND | UNBOUND_HINT | INVALIDATED
validator_artifact_id
validator_body_sha256
validator_origin = FULL_GET | CMS_REVISION | HEAD_HINT | RUNTIME_HINT
```

规则：

1. **只有与完整网络响应一起获得的 validator，才能绑定到该 Raw Artifact。**
2. HEAD、局部 metadata、head fingerprint 流程看到的新 ETag/Last-Modified 只能记录为 `UNBOUND_HINT`，不能覆盖当前 authoritative validator；
3. 304 只有在请求使用的 validator 已绑定到“当前 authoritative Raw Artifact/body hash”时，才能计为 STRONG unchanged；
4. Runtime Smart Cache 在 weak head match 后更新的 Runtime ETag/Last-Modified，不得直接导入业务 Ledger 作为 authoritative validator；
5. 若绑定 Artifact 已被新 DocumentVersion 取代，旧 validator 必须失效或进入历史绑定；
6. 每次 Runtime 升级必须测试“body 改变、head 不变、ETag 改变”的场景，防止 validator promotion/stale validator poisoning。

### 9.5 状态机

```text
DUE_FOR_REVALIDATION
      |
      +-- Provider 明确 changed ------> FETCH_REQUIRED
      |
      +-- bound validator 304 --------> VERIFIED_UNCHANGED
      |
      +-- validator changed ----------> FETCH_REQUIRED / UNBOUND_HINT
      |
      +-- weak unchanged -------------> WEAK_UNCHANGED
      |                                  |
      |                                  +-- sample due -> FETCH_REQUIRED
      |
      +-- validation error -----------> VALIDATION_DEGRADED
                                         |
                                         +-- 可服务旧版本
                                         +-- 不推进 last_verified_at
                                         +-- 安排重试

FETCH_REQUIRED
      |
      v
RAW_ARTIFACT
      |
      +-- body hash unchanged --------> VERIFIED_UNCHANGED + bind validators
      |
      +-- body hash changed ----------> NEW_DOCUMENT_VERSION + bind new validators
```

### 9.6 强制定期完整抽样

任何 weak/validator 路径都必须配置：

```text
forced_full_refresh_interval
forced_sample_rate
min_validator_trust_score
```

抽样完整抓取发现“validator 未报变化但 body hash 已变”时：记录 false negative、降低 Source validator trust score、缩短强制刷新周期、提高 fresh-fetch 比例，必要时禁用该 Source 的弱验证跳过策略。

## 10. HTTP Fast Lane、Browser Slow Lane 与 Runtime Cache

### 10.1 HTTP First

普通文章优先 `httpx/aiohttp`：

- GET/Conditional GET；
- Redirect chain；
- ETag/Last-Modified；
- Content-Type/MIME；
- Content-Length 上限；
- robots；
- Response headers；
- 原始字节与编码检测。

满足正文质量条件则不启 Browser。

### 10.2 Browser Escalation

仅以下情况进入 Browser Slow Lane：

- HTTP 页面正文为空/占位；
- JS 客户端渲染；
- 需要有限滚动/点击才能出现正文；
- Shadow DOM/iframe 且 Source Policy 允许；
- HTTP Candidate 明显低质量；
- Source Recipe 指定。

Browser 通过长期 Runtime Pool 复用，不为每 URL 启新进程。

### 10.3 平台 Cache Policy Compiler

业务层不直接暴露 Crawl4AI `CacheMode`，只暴露：

```text
AUTHORITATIVE_FETCH
VALIDATE_THEN_FETCH
REPLAY_FROM_ARTIFACT
RUNTIME_CACHE_WARMUP
DIAGNOSTIC_CACHE_READ
```

Compiler 根据 pinned runtime release 生成实际配置，并把 effective config 写入 Attempt。

生产 Attempt 必须显式生成：

```text
runtime_cache_policy
cache_mode_effective
check_cache_freshness_effective
cache_validation_timeout_effective
runtime_cache_namespace
fetch_variant_key
runtime_release
runtime_cache_contract_release
```

不能依赖 Runtime 默认值；尤其不能让“遗漏配置”退化为 `ENABLED + freshness off`。

#### AUTHORITATIVE_FETCH

- 禁止从 Runtime cache 返回旧正文；
- 必须产生真实网络响应证据；
- 使用 Contract Test 验证过的配置，不按 enum 名称猜测；
- 结果晋升平台 Raw Artifact；
- 响应 validator 绑定到该 Artifact/body hash。

#### VALIDATE_THEN_FETCH

- 平台 Revalidation Engine 先使用 bound validator 判断；
- 确认需要抓取后使用 fresh fetch；
- Runtime Smart Cache 只做可选额外优化；
- Runtime `hit_validated` 不能覆盖平台 Freshness 结论；
- Runtime 新发现的 validator 若来自 weak flow，只作为 hint。

#### REPLAY_FROM_ARTIFACT

- 直接处理 S3/MinIO Raw Artifact；
- 不访问网络；
- Replay Worker 使用 egress deny；
- **不能映射成 Crawl4AI `READ_ONLY` 来保证离线**，因为 cache miss 仍可能真实联网。

#### RUNTIME_CACHE_WARMUP / DIAGNOSTIC_CACHE_READ

允许 Runtime cache，但不推进业务 Version、Freshness、Coverage 或 authoritative validator。

### 10.4 Crawl4AI CacheMode 的生产契约

当前已验证源码的读写矩阵为：

| 模式 | 读 Runtime Cache | 写 Runtime Cache |
|---|---:|---:|
| ENABLED | 是 | 是 |
| DISABLED | 否 | 否 |
| READ_ONLY | 是 | 否 |
| WRITE_ONLY | 否 | 是 |
| BYPASS | 否 | 否 |

同时当前源码旧参数迁移为：

```text
disable_cache -> DISABLED
bypass_cache -> BYPASS
no_cache_read -> WRITE_ONLY
no_cache_write -> READ_ONLY
```

但官方不同文档页面与当前源码存在语义漂移，特别是旧参数映射以及 BYPASS 的描述。因此：

- 禁止新配置使用 legacy boolean flags；
- 生产只允许 pinned release；
- 每次升级都重新验证 `should_read/should_write/network_called/cache_written`；
- Runtime Registry 保存 `known_behavior_diff`；
- **行为以 Contract Test 为准，不以文档名称为准。**

### 10.5 Smart Cache 的使用边界

当前 Smart Cache 是 `check_cache_freshness` 的附加校验，默认关闭。典型流程：

```text
Runtime cache hit
    -> 条件 HEAD(If-None-Match / If-Modified-Since)
        -> 304: Runtime 判 FRESH
        -> 200: 取新 validator，再流式读取 <head>
                 -> head fingerprint 相同: Runtime 判 FRESH
                 -> head fingerprint 变化: STALE -> full crawl
        -> error/timeout: ERROR -> hit_fallback
```

`<head>` 流式读取会在发现 `</head>` 或达到大小上限后停止，fingerprint 聚焦 title、description、OpenGraph、modified-time 等元信息。

平台必须遵守：

1. `check_cache_freshness` 必须显式配置，不能假定默认启用；
2. `<head>` fingerprint 是 WEAK 证据，正文可以在 head 不变时变化；
3. Runtime validation error 可能返回旧 cache (`hit_fallback`)；
4. `hit_fallback` 只能作为 serving fallback，不得更新 `last_verified_at`；
5. Runtime cache 不进入 Coverage/Version 真相；
6. `READ_ONLY` 只表示不写 Runtime cache，不表示禁止联网；
7. Runtime 在 weak head match 后获得的新 validator 不得升级为平台 authoritative validator；
8. CacheMode 真实语义必须以 pinned release Contract Test 为准。

### 10.6 URL-only Runtime Cache 风险与隔离

当前 Runtime Cache 本质上以 URL 为核心键，并保存完整 CrawlResult，包括 HTML、Cleaned HTML、Markdown、Extracted Content、Metadata 等。

因此以下情况默认禁止共享 Runtime Cache：

- Cookie/Auth；
- session；
- proxy/region；
- locale/timezone；
- User-Agent/device profile；
- 自定义 JS/交互状态；
- 不同 Browser profile；
- 同 URL 可能按用户/地区/语言返回不同内容。

若确有性能收益，必须按：

```text
source_id + fetch_variant_key + runtime_release
```

隔离 Runtime cache namespace/实例。

无论是否隔离，Runtime cached `cleaned_html/markdown/extracted_content` 都不能直接成为平台 canonical；Extractor/Renderer 版本变化必须从平台 Raw Artifact 重放。

### 10.7 Runtime Cache 状态归一化

平台统一记录：

```text

HIT_UNVERIFIED
HIT_VALIDATED
HIT_FALLBACK
DISABLED
BYPASSED
UNKNOWN
```

并附加：

```text

freshness_evidence_strength = STRONG | MEDIUM | WEAK | NONE
business_verification_advanced = true | false
validator_binding_state = BOUND | UNBOUND_HINT | INVALIDATED | NONE
fetch_variant_match = true | false | unknown
```

### 10.8 Runtime Cache Contract Test Matrix

每次 Runtime package/image 升级至少验证：

| 场景 | 必验结果 |
|---|---|
| ENABLED + hit + freshness=false | 可直接 hit，不发生 freshness 网络校验 |
| ENABLED + hit + 304 | Runtime `hit_validated`；平台仍校验 validator binding |
| ENABLED + hit + 200 + head 相同 | Runtime 可判 fresh；平台只认 WEAK |
| ENABLED + hit + head 变化 | 重新抓取 |
| ENABLED + hit + timeout/error | `hit_fallback`，不推进业务验证时间 |
| READ_ONLY + hit | 读 cache，不写 |
| READ_ONLY + miss | 会真实联网，但不写 Runtime cache |
| WRITE_ONLY + hit | 不读旧 cache，真实抓取并写 |
| DISABLED | 不读、不写、真实抓取 |
| BYPASS | 实测读写/联网语义，禁止按名字推断 |
| legacy `no_cache_read/no_cache_write` | 验证 pinned release 的实际映射 |
| 同 URL、不同 locale/cookie/UA | 不得错误跨 variant 复用 |
| 同 URL、不同 extractor/markdown release | canonical 必须从 Raw Artifact 重放 |
| body 改变、head 不变、ETag 改变 | 新 ETag 不得绑定到旧 Artifact；后续 304 不得误报强验证 |
| validation error | stale serving 与 business verification 分离 |

每个 case 记录：

```text
should_read
should_write
network_called
request_method
conditional_headers
cache_status
cache_written
returned_content_hash
returned_artifact_origin
validator_used
validator_binding_state
fetch_variant_key
```

## 14. Document、Version 与变化判定

```text
Document = 逻辑文章身份
DocumentVersion = 某次业务意义上的正文版本
RawArtifact = 某次真实抓取证据
```

完整抓取后：

```text
raw body hash unchanged
    -> 不创建新 DocumentVersion
    -> 更新 fetch evidence，并可重新绑定当前响应 validator

raw changed
    -> Cleaner/Extractor/IR
        -> semantic content hash unchanged
            -> 只更新 fetch evidence / metadata
        -> semantic content hash changed
            -> 创建新 DocumentVersion
```

标题、作者、发布时间、canonical 变化单独记录 metadata diff；是否创建新 DocumentVersion 由 Version Policy 决定。

## 21. 安全、合规与抓取边界

### 21.1 SSRF

所有 URL Fetch 前解析 DNS，禁止 loopback/private/link-local/metadata IP；redirect 每跳重新校验；防 DNS rebinding；执行 Approved Host/Scope allowlist。

### 21.2 Browser 隔离

独立容器/Pod、非 root、最小文件系统权限、egress policy、secret 不进入页面 JS、禁止任意 host CDP、下载目录隔离和大小限制。

### 21.3 Robots / Rate Limit / Terms

默认遵守 robots；保存 robots snapshot/release；429/Retry-After 优先；Source 可配置 legal/compliance note；登录、付费墙、明确禁止自动化的 Source 单独审批。

### 21.4 Secret

Source Profile 只保存 secret reference，真实值由 Vault/KMS 在受控 Worker 注入。

## 23. 容量、成本与扩展

初始建议：PostgreSQL 高可用、Redis HA、S3/MinIO、HTTP Worker 与 Browser Worker 分池、Browser Pool 独立 autoscaling、Extraction/Render Worker 水平扩展、OpenSearch/pgvector 独立 Serving Plane。

扩容按 workload 独立进行：Discovery CPU/IO、HTTP network、Browser memory/CPU、Extraction CPU、Embedding GPU/API quota、Index IO。不要使用一个万能 Worker 承载所有工作。

成本优化顺序：

1. Provider 权威发现减少无效 crawl；
2. HTTP First；
3. 平台 Revalidation 避免重复 Browser；
4. 在可证明安全的 fetch variant 上使用 Runtime cache；
5. Browser Pool 复用；
6. Candidate/IR Replay 避免重新联网；
7. embedding 只对 PASS Version；
8. 历史旧 Artifact 使用对象存储生命周期策略。

## 27. 最终推荐架构

最终采用：

> **PostgreSQL Truth Store + S3/MinIO Immutable Artifact + Redis Streams Durable Transport + Declarative Source/Profile + Multi-Provider Discovery + Persistent Frontier + Revalidation Engine + Validator-to-Artifact Binding + Fetch Variant Isolation + HTTP First / Browser Slow Lane + Crawl4AI Runtime Service Plane + Cache Policy Compiler + Runtime Contract Release Gate + Extraction Portfolio + Canonical IR + Deterministic Markdown + OpenSearch/pgvector + Web Admin。**

最关键的边界是：

- **Provider 返回不是 Coverage 真相；**
- **Runtime cache 不是 Freshness、Version 或 Replay 真相；**
- **同一个 URL 不代表同一个表示，Runtime cache 不能跨 fetch variant 盲目复用；**
- **Runtime 已缓存的 Markdown/Extracted Content 不是 canonical，处理 Release 变化必须从平台 Raw Artifact 重放；**
- **Smart Cache 的 head fingerprint 是弱证据，不能证明正文未变化；**
- **Runtime weak match 得到的新 validator 不能绑定到旧正文；业务 validator 必须绑定 Raw Artifact/body hash；**
- **只有使用 bound validator 得到的 304 才能作为强 unchanged 证据；**
- **`hit_fallback` 是可用性降级，不是 freshness proof；**
- **`READ_ONLY` 不是离线安全边界；**
- **CacheMode、legacy flags、BYPASS 等生产语义以 pinned release + Contract Test 为准，不以名称或单页文档为准；**
- **生产 Runtime 配置必须显式编译和审计，不能依赖默认值；**
- **Raw Artifact 不可变，所有清洗/抽取/Markdown 都可重放；**
- **Browser 是昂贵慢路径，不是默认路径；**
- **Coverage、Version、Freshness、Validator Binding、Markdown 的最终真相始终在平台层。**
