# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个长期运行、可横向扩展、可审计、可重放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章并稳定清洗为 Markdown；后续持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计、单 URL 手工摄取和离线重处理。

设计按以下量级考虑：

- 1000+ Source，后续扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 千万级 Chunk / Embedding 长期增长；
- 中英日韩等多语言技术内容；
- HTML、PDF、TXT、Markdown、JSON/API、Feed 等多种资源类型；
- HTTP 为主，Browser 为受控 fallback；
- 历史发现支持 CMS API、Sitemap、Feed、Archive、Common Crawl URL Index 等多来源；
- PostgreSQL + Object Storage 保存事实；Markdown、Filtered Markdown、Chunk、Embedding、全文/向量索引均为可重建 Projection。

平台必须能回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已基本覆盖；
2. 一个 URL 从哪里发现、如何规范化、经过哪些跳转后被抓取；
3. 一个 URL 最终返回的是 HTML、PDF、Markdown、JSON 还是其他资源，路由判断依据是什么；
4. 一个动态页面执行了哪些点击、滚动、等待，使用哪一版 Recipe；
5. 一个 Markdown 来自哪个 Snapshot、Extractor、Filter、Schema 和 Document Version；
6. 源站变化后哪些内容真的变化，哪些派生物需要重建；
7. Chunk、Embedding、Analyzer、Browser Runtime、内容过滤器和索引策略升级后能否不重新访问源站完成重放；
8. 抓取失败、结构漂移、Browser 成本、内容过滤误删、反爬、索引或检索回归时能否在 Web 中定位和运营；
9. 一个批量抓取任务发生取消、限流、Worker 崩溃或流式消费中断后，哪些 URL 已可靠提交、哪些仍应重试；
10. 用户手工提交一个 URL 后，当前处理到 Probe、Fetch、Extraction、Markdown、Embedding 还是 Index 哪一步；
11. “对这一篇文章提问”“只搜索某个站点”“只查询某个版本”时，检索作用域是否可严格约束。

## 2. 核心设计原则

1. **Config First**：普通站点主要通过 Source / Site Profile / Release 配置接入，不修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence 与 exhaustion reason 证明，不能用“队列为空”或达到 `max_pages` 冒充完整。
3. **Discovery Before Fetch**：先低成本发现、分类、去重 URL，再决定是否真实抓取正文。
4. **Authoritative First**：CMS/API/Sitemap/Feed 优先，Archive/Common Crawl 用于补洞和外部证据。
5. **URL Is Locator, Not Content Type**：URL 后缀只作为弱证据，资源类型以最终响应、MIME、文件签名和站点规则综合判断。
6. **HTTP First, Browser Last**：Browser 只处理动态发现面、动态渲染、结构探索或低质量 fallback。
7. **Recipe, Not Site-Specific Code**：动态交互和结构化抽取必须声明式、版本化，禁止长期堆积 `if site == ...` 分支。
8. **Bounded Interaction**：点击、滚动、等待、session 复用都必须有预算和明确停止条件。
9. **Snapshot First**：先保存不可变网络事实，再做抽取、清洗、建版。
10. **IR First, Markdown as Projection**：Canonical IR / Document Version 是内容事实层，Markdown 是可重建输出。
11. **Filtered Content Is Projection**：Pruning、BM25、LLM Filter 都是有损派生，不得覆盖 Canonical IR 或 canonical Markdown。
12. **LLM Extraction Is Optional**：LLM 抽取、摘要、实体识别属于可版本化 Projection/fallback，不作为 canonical 正文默认主路径。
13. **Stable Identity**：Document、Version、Chunk、Embedding、Index 身份必须稳定且 release-aware。
14. **Release Everything**：影响结果的策略、Browser Recipe、Schema、Content Filter、资源探测、模型、索引和 Runtime 均版本化。
15. **Idempotent + Recoverable**：任务具备幂等键、lease、fencing、checkpoint、retry、partial success。
16. **Stream and Commit Per URL**：多 URL 批任务按单 URL 流式持久化、提交与 ack，一个失败项不能回滚成功项。
17. **Local Dispatcher Is Not Global Scheduler**：Crawl4AI Dispatcher/RateLimiter 只保护单 Worker，平台 Scheduler 才是 durable 调度与限流真相。
18. **Async Command API**：抓取、PDF 解析、Embedding 等长任务由 API 接收命令并返回 durable ID，后台 Worker 执行；API 不长时间同步阻塞。
19. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary、Search Index 故障不能阻塞抓取事实同步。
20. **Projection Readiness Is Explicit**：Canonical、Markdown、全文、Chunk、Embedding、Vector 等就绪状态独立表达，允许 `PARTIAL_READY`。
21. **Evidence Everywhere**：发现、分类、资源探测、跳转、交互、抓取、抽取、过滤、身份、版本和检索均保存证据。
22. **Language-aware Retrieval**：分词、stemming、stopwords、技术 token 处理由 Analyzer Release 管理。
23. **Hybrid Retrieval by Default**：技术语料默认 BM25 + Vector + RRF，Reranker 是可降级增强层。
24. **Retrieval Scope Is First-Class**：检索作用域必须显式建模，不用 prompt 暗示替代数据库/索引过滤。
25. **Benchmark Before Switch**：Analyzer、Content Filter、Embedding、Vector Index、RRF、Reranker 升级经固定评测后切生产。
26. **Generation Instead of Destructive Rebuild**：索引升级后台构建新 Generation、验证、原子切换，禁止生产 drop-and-recreate。
27. **Web 管理是平台能力**：Coverage、失败、版本、成本、Recipe、Schema、Filter、Manual Ingestion、Generation、实验和 Release 都必须可运营。
28. **安全边界每跳执行**：起始 URL、Redirect 和 Browser navigation 每跳重新执行 SSRF/Egress/Scope 校验。
29. **Ephemeral State Is Not Truth**：Crawl4AI cache、Browser session、Worker 内 dispatcher state 不承载决定性业务状态。
30. **One Durable Task System**：不并存多套互相竞争的业务任务真相；PostgreSQL durable state + Transactional Outbox + Redis Streams 作为统一任务体系。

### 3.1 真相边界

```text
PostgreSQL + Object Storage = Truth
Redis Streams              = Transport
OpenSearch / Vector Engine = Rebuildable Projection
Canonical Markdown         = Rebuildable Projection
Filtered/Fit Markdown      = Rebuildable Projection
Chroma                      = Optional Dev Projection Adapter
Crawl4AI cache/session      = Ephemeral Execution State
Dispatcher/RateLimiter      = Worker-local Execution State
Common Crawl / Archive     = External Evidence / Optional Snapshot Origin
```

任何决定性业务状态不得只存在 Redis、搜索引擎、向量库、本地 cache、Browser session、Filtered Markdown、Dispatcher 或 Worker 内存中。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST / Command API、Schema 校验、内部服务接口；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、URL Observation、Resolution、Resource Probe、Fetch、Interaction、Document、Version、Projection、Manual Ingestion、Release、Audit、Outbox；
- **Transactional Outbox**：数据库状态变更与消息发布事务一致；
- **Redis Streams**：consumer group、retry、backpressure，只做任务运输；
- **React/Vue + TypeScript**：Web 管理台。

### 4.2 抓取与抽取

- **HTTPX / aiohttp**：HTML、Feed、Sitemap、API、Conditional GET、Range GET、低成本跳转解析；
- **python-magic / libmagic 等等价能力**：必要时根据文件签名辅助 MIME 判定；
- **BeautifulSoup / lxml / CSS / XPath / Regex**：wrapper、meta refresh、selector、结构化抽取；
- **Trafilatura / Readability**：确定性正文候选；
- **PDF 解析器**：文本型 PDF 确定性解析，扫描型 PDF 进入受控 OCR fallback；
- **Crawl4AI / Playwright**：URL Seeding、Prefetch、动态页面、Browser Interaction、结构化抽取、Markdown Candidate、Browser fallback 与 Worker 内批量调度；
- **S3 / MinIO**：raw response、HTML、Rendered DOM、Feed payload、PDF、WARC、Canonical IR、Markdown、Asset、debug artifact、fixture。

Crawl4AI 生成的 `raw_markdown`、`fit_markdown` 都只能作为 Extraction Candidate / Projection，不能替代 Snapshot 与 Canonical IR。

### 4.3 历史发现

- CMS API / Sitemap / RSS / Atom / JSON Feed；
- Archive / Category / Tag / Author / Docs TOC；
- Common Crawl URL Index；
- DuckDB / Athena / Spark / Polars 用于批量历史索引扫描。

### 4.4 检索

- **OpenSearch**：生产 BM25、过滤、聚合、Alias/Generation、Hybrid Search；
- **pgvector / OpenSearch kNN**：首期向量实现；
- **Qdrant / Milvus**：向量规模或独立扩缩容需求提高后可替换；
- **Chroma**：开发、PoC、本地单机 Adapter，不作为事实存储；
- **RRF**：默认融合；
- **Cross Encoder Reranker**：可选精排服务；
- **Haystack/LlamaIndex 等**：可作为 Query/RAG 编排层 Adapter，但不得持有唯一业务状态。

### 4.5 可观测与部署

- Prometheus + Grafana + OpenTelemetry；
- Docker / Kubernetes；
- Artifact Registry 保存应用镜像、浏览器内核、Embedding/Reranker 模型和运行时依赖。

## 10. 新站接入 PROBE

新增站点先 PROBE，不直接深爬：

1. 规范化 entry URL，确定 domain、allowed origins、scope；
2. 获取 robots 和 Sitemap 声明；
3. 探测 Sitemap Index / Sitemap；
4. 探测 RSS / Atom / JSON Feed；
5. 探测 WordPress REST、Ghost、Substack 等平台能力；
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination；
7. 低成本查询 Common Crawl；
8. 对 URL path 做模板聚类；
9. 对未知 hub 做轻量 HTML + links Prefetch；
10. 小预算 BFS / BestFirst 探索未知结构；
11. 抽样比较 HTTP 与 Browser 的正文质量与成本；
12. 检测 wrapper、short-link、meta refresh、JS redirect；
13. 对 HTML/PDF/JSON/Feed 等代表 URL 运行 Resource Probe，校验 MIME 与 Route Hint；
14. 如果只有动态页面才能发现历史 URL，生成候选 Interaction Recipe；
15. 对重复 DOM 生成候选 Structured Schema，并用 fixture 校验；
16. 推断语言、Analyzer、Content Filter 和 article template；
17. 对已知 URL 类型生成 Route Match fixture；
18. 自动生成首版 Profile，在 Web 审核后启用。

Prefetch 只用于轻量发现、分类和路由决策，不是正文 Snapshot，也不能替代 Fetch Attempt。

## 13. URL Normalization、Classification 与 Resolution

### 13.1 Normalization

典型规则：lowercase host、default port removal、fragment removal、path slash normalization、安全 percent-encoding、query key ordering、tracking param removal、站点级 semantic param allowlist。

禁止全局删除所有 query，因为 `?id=123`、`?p=456`、`?page=7` 可能具备正文或分页语义。

### 13.2 URL Intent Classification

URL 发现阶段的分类只表达“这个 URL 看起来像什么用途”，不是最终 MIME：

```text

DISCOVERY_SURFACE
ASSET
NAVIGATION
EXTERNAL_REFERENCE
IGNORE_BY_POLICY
UNKNOWN
```

过滤只影响后续调度，原始 Observation 与 Evidence 永久保留。

### 13.3 Resolution Plane

```text
Observed URL
 -> Normalized Candidate
 -> HTTP Redirect
 -> Wrapper Param / HTML Target
 -> Meta Refresh
 -> Browser Navigation Fallback
 -> Resolved Fetch Target
```

`rel=canonical`、`og:url` 属于 Identity Evidence，不等同于 Redirect。

每次 redirect / Browser navigation 都重新进行 Scope、SSRF 和 Egress 校验。

## 16. 调度、`arun_many()` 与 Worker 并发模型

Crawl4AI 的 `arun_many()` / Dispatcher 只负责单 Worker 内多 URL 并发、内存保护和本地速率控制，不能替代平台 durable scheduler。

### 16.1 两层调度

```text
平台 Scheduler
  global token bucket
  + registrable-domain token bucket
  + source token bucket
  + route/provider budget
  + priority
  + durable Task / lease / fencing / retry / next_run_at
        ↓
HTTP / Browser / Probe Worker
  MemoryAdaptiveDispatcher / SemaphoreDispatcher
  + RateLimiter
        ↓
AsyncWebCrawler.arun_many(stream=True) / HTTP batch
```

平台限流是跨节点持久事实；Worker-local RateLimiter 只是第二道安全阀。429/503、`Retry-After` 等信号需要写回 Task 的 `next_run_at`，不能只在某个 Worker 内 sleep 后丢失。

### 16.2 小批 lease + 单 URL 流式提交

```text
lease N tasks
 -> build per-URL CrawlerRunConfig
 -> arun_many(stream=True)
 -> one result arrives
 -> persist FetchAttempt / Snapshot / failure
 -> commit transaction
 -> ack per URL
```

一个失败 URL、超时 URL 或取消 URL 不能回滚整个 batch。严禁用一个长事务包住整个 `arun_many()`。

### 16.3 自适应批大小

批次大小根据：

- Worker 可用内存；
- 页面 DOM/HTML/PDF 大小；
- Browser context 数；
- CPU；
- 流式结果消费速度；
- 目标域名限流；
- 大文件比例。

动态调整，不固定 `batch_size=1000`。

### 16.4 per-URL CrawlerRunConfig

```text
PDF URL / observed PDF -> PDF config
Article HTML            -> article config
Dynamic Hub             -> interaction config
JSON/API                -> structured config
Fallback                -> default config
```

所有 matcher 的顺序、优先级和 config 引用保存到 Route Match Release，发布前通过 fixture。

### 16.5 Batch Dispatch Attempt


## 20. 增量同步与 Reconcile


## 24. Chunk 设计与稳定身份

### 24.1 主策略：Structure-aware

默认：

1. Heading / Section 是第一层语义边界；
2. 段落、列表、引用尽量完整；
3. fenced code 默认不拆；
4. 表格默认不拆；
5. PDF 尽量按章节/页内块语义切分而不是纯页切分；
6. 保存 heading path、page range 与 block range；
7. 超长代码/表格走专门策略；
8. 超长普通 section 再进入 recursive fallback。

### 24.2 Recursive fallback

优先段落、换行、语言标点，再退化到空格/字符；长度优先使用目标 Embedding tokenizer 的 token 计数。

`chunk_size` 与 `overlap` 属于 Chunk Release，并通过检索评测选择。

### 24.3 稳定 Chunk ID

禁止：

```text
hash(file_path + chunk_index)
hash(source + chunk_index)
```

推荐：

```text
chunk_id = hash(
  document_version_id
  + chunk_release_id
  + logical_block_range
  + normalized_text_hash
)
```

文档头部新增内容不能导致所有后续未变化 Chunk 被误判为新 Chunk。

## 25. Embedding 与流式批处理


```text

```

### 25.2 流式 Worker

禁止一次性把全库 Chunk 加载到内存并一次 encode：

```text
query pending chunks
 -> lease batch
 -> tokenize/embed
 -> validate
 -> persist embedding
 -> idempotent upsert target generation
 -> commit per-item result
 -> checkpoint
 -> next batch
```

支持动态 batch、最大 batch token、OOM 自动缩 batch、retry、partial success 和 backpressure。Embedding backlog 不阻塞 Source Sync。

### 25.3 Vector Payload Contract

写入向量引擎前统一校验：

```text
embedding_release_id == target_generation.embedding_release_id
dimension == embedding_release.dimension
values are numeric
no NaN / Inf
canonical dtype / serialization matches adapter
normalization invariant matches release when required
chunk_id and embedding_id are present
payload schema version matches vector_index_release
```

单条坏向量进入 quarantine / retry，不拖垮整个 batch。

Vector Store 使用 deterministic ID + upsert，不允许依赖向量库自动生成的随机业务主键。

## 28. Hybrid Search、Retrieval Scope 与 Retrieval Trace

默认：

```text
OpenSearch BM25
 + Vector Search
 -> metadata scope filter
 -> RRF Fusion
 -> optional Reranker
 -> Context Assembly
```

### 28.1 Retrieval Scope

```text
ALL
```

## 30. Reranker 与 Context Assembly

```text
大规模粗召回
 -> Top-N 融合候选
 -> Cross Encoder Reranker
 -> Top-K
 -> Context Assembly
```

Reranker 不扫描全库。

独立 `rerank-service`：模型常驻优先、dynamic batch、最大 batch token、GPU 并发限制、OOM 自动降 batch、超时降级到 RRF，不进入 Source Sync 关键路径。

Context Assembly 根据 document diversity、heading path、chunk adjacency、same-document overlap、token budget、source trust、duplicate suppression、scope consistency 组装，避免 Top-K 全来自同一文章相邻 Chunk。

## 31. Index Generation 生命周期

禁止生产 Index `drop-and-recreate`。

```text
BUILDING
 -> VALIDATING
 -> READY
 -> ACTIVE
 -> RETIRED
```

触发新 Generation：

- Chunk Release 变化；
- Analyzer Release 变化；
- Embedding 模型/维度/metric 变化；
- Vector Index Release 变化；
- OpenSearch schema 变化；
- 检索数据模型变化。

流程：

```text
创建新 Generation
 -> 后台批量构建
 -> 离线回归验证
 -> READY
 -> Alias/逻辑指针原子切换
 -> 观察窗口
 -> 旧 Generation RETIRED
```

RECHUNK / REEMBED / REINDEX 优先使用已有 Snapshot / Canonical IR，不重新抓源站。

旧 Document Version 的向量不能在 Active 查询中误召回；索引 payload 必须包含 `document_version_id`、generation 和 active/tombstone 语义。

## 40. 验收标准

### 40.1 Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有 exhaustion evidence；
- known gap 可枚举、可重跑；
- 达到预算不会错误标 COMPLETE；
- Common Crawl 不作为完整性证明。

### 40.2 Resource Probe / 多类型资源

- 无扩展名 PDF 能正确识别为 PDF；
- `.pdf` URL 302 到 HTML 时不会进入 PDF parser；
- HEAD 不支持时能受控 fallback；
- Content-Type 错误时可结合文件签名纠正或进入冲突审核；
- HTML/PDF/TXT/MD/JSON/Feed 使用正确 extractor；
- 超大文件、压缩炸弹、异常 MIME 能被预算/安全策略拦截；
- Route Hint 与 Probe 冲突可追踪。

### 40.3 增量

- Feed/API/Sitemap 新文章在目标 SLA 内进入系统；
- 304 不重复抽取、建版、投影；
- PDF/文件未变化不重复解析；
- 未变化 Projection 不重复计算；
- Reconcile 能发现 Feed 窗口外遗漏和结构漂移。

### 40.4 Browser / Recipe / Batch

- Browser 不是默认抓取路线；
- 动态 Discovery Surface 可独立使用 Browser，文章正文仍优先 HTTP；
- 每个 Interaction Recipe 可版本化、可 diff、可回滚；
- click/scroll/wait 有明确预算和停止条件；
- `arun_many()` 批处理结果按 URL 独立提交；
- stream 提前关闭、Worker SIGTERM 后资源可靠释放；
- 未 ack task 可重放；
- Crawl4AI cache/session 不承载持久业务状态；
- Runtime Artifact 能复现 Browser + Crawl4AI 运行环境。

### 40.5 Schema / Markdown / Filter

- Structured Schema 有 fixture、必填字段和 zero-match 告警；
- 抽样验证 title/author/time、正文完整、导航噪声低、heading 正确、code/list/table/image/link 保留；
- PDF/Markdown 原生结构能尽量保留；
- Markdown 可从 IR 确定性重建；
- query-dependent `fit_markdown` 不作为 canonical 文档；
- LLM Extraction 失败不影响 canonical 主路径。

### 40.6 Manual Ingestion

- `POST /ingestions` 长任务返回 202 + durable ingestion ID；
- 相同 Idempotency-Key 不重复创建业务 Run；
- Web 能展示单 URL 全链路阶段状态；
- Manual URL 同样执行 SSRF/Scope/robots/大小预算；
- canonical READY 而 Embedding 未完成时可显示 `PARTIAL_READY`；
- Query API 不会隐式同步访问远程 URL。

### 40.7 Chunk / Embedding

- Chunk 保留 heading path、page/block range；
- fenced code 与表格默认不破坏；
- Chunk ID 不依赖 chunk_index；
- RECHUNK 不创建新 Document Version；
- REEMBED 不重新抓源站；
- Embedding backlog 不影响 Source Sync；
- 向量维度、NaN/Inf、归一化、Release/Generation 不一致在入库前拦截；
- 单条无效向量不会导致整批回滚；
- Vector Store 使用 deterministic ID 幂等 upsert。

### 40.8 检索

- 中文/英文/技术 token 有固定回归集；
- CJK 不依赖 whitespace tokenizer；
- BM25 + Vector + RRF 可解释；
- Vector Index 参数有 benchmark；
- Reranker 故障可降级；
- Retrieval Trace 能区分不同 score type；
- DOCUMENT/SOURCE/VERSION Scope 不召回范围外 Chunk；
- 旧 Document Version 向量不会出现在 Active 查询；
- 新 Generation 验证通过后才能 ACTIVE；
- 生产升级无 drop-and-recreate。

### 40.9 可靠性

- Worker 崩溃后 lease 可恢复；
- fencing 能阻止过期 Worker 覆盖结果；
- fan-out 保留 partial success；
- Browser session 丢失不丢 durable checkpoint；
- Embedding/Index/Reranker/LLM 故障不阻塞 Source Sync；
- Runtime/Model Artifact 可复现、可回滚；
- 所有高风险管理操作可审计。

## 41. 最终架构原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：发现、分类、去重后再抓正文。
3. Authoritative First：权威来源优先，Archive/Common Crawl 只补洞。
4. URL Is Locator：资源类型由实际响应证据决定，不由扩展名拍脑袋决定。
5. Route Hint + Probe Evidence：静态匹配提供 hint，运行时 MIME/签名证据决定最终路由。
6. HTTP First, Browser Last：Browser 是昂贵兼容层，不是默认抓取器。
7. Browser Discovery Is Separate：动态发现面可用 Browser，但不要因此把全部文章正文 Browser 化。
8. Recipe, Not Site-Specific Code：动态交互用版本化 Recipe，不在业务代码堆站点分支。
9. Deterministic Schema First：规则化结构优先 CSS/XPath/Regex，LLM 只做辅助和 fallback。
10. Bounded Interaction：点击、滚动、等待、session 均有明确预算和停止条件。
11. Worker Dispatcher Is Local：Crawl4AI `arun_many()` 负责 Worker 内资源保护，平台 durable scheduler 负责全局任务事实。
12. Stream and Commit Per URL：批任务单 URL 持久化和 ack，partial success 不丢失。
13. Snapshot First, Replay Later：原始网络事实不可变，规则升级优先离线重放。
14. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
15. LLM Is Projection, Not Truth：LLM 抽取/摘要可版本化、可重建、可失败，不阻塞 canonical。
16. Stable Chunk Identity：Chunk 身份不能依赖 file path + chunk_index。
17. Structure-aware First：技术文档优先按标题、块、代码、表格、PDF 页面语义切分。
18. Streaming Embedding：批次、lease、checkpoint、幂等，禁止全库一次性加载。
19. Validate Before Vector Write：向量维度、有限数值、归一化、序列化和 Release 一致性写前校验。
20. Language-aware BM25：生产全文检索有可版本化 Analyzer。
21. Benchmark Vector Index：IVF/HNSW/FLAT 等通过 recall/latency 基准选择。
22. Hybrid Retrieval by Default：BM25 与 Vector 互补，RRF 为稳定融合基线。
23. Retrieval Scope Is First-Class：单文档、站点、版本范围在召回层强约束。
24. Typed Retrieval Scores：不同阶段 raw score 带 score type，不做跨阶段数值比较。
25. Reranker as Optional Service：精排可降级，不进入事实同步关键路径。
26. Generation Instead of Destructive Rebuild：后台构建、验证、原子切换。
27. Async Command API：长任务 202 + durable ID，后台执行，前台查状态。
28. Projection Readiness Is Explicit：允许 canonical READY、Embedding PENDING 的部分就绪状态。
29. One Durable Task System：PostgreSQL + Outbox + Redis Streams 维护统一业务任务真相。
30. Release Everything：策略、Probe、Recipe、Schema、Filter、模型、索引、浏览器、运行时均可追踪和回滚。
31. Ephemeral State Is Not Truth：Crawl4AI cache、proxy runtime、browser session、dispatcher state 不能成为业务真相。
32. Model Artifact Is Immutable：模型在构建阶段固定 revision 与 digest，生产不临时下载。
33. Benchmark Before Switch：任何检索升级经过固定 judgment set。
34. Idempotent + Recoverable：任务可重复、可恢复、可观察，partial success 不丢失。
35. Source Sync 与 AI 解耦：抓取事实不依赖 Embedding、Reranker、LLM 或 Search 服务。
36. Evidence Everywhere：所有重要判断均保存可解释证据。
37. Security on Every Hop：起始 URL、redirect、Browser navigation、manual ingestion 均执行同一安全边界。
38. Web 管理是平台能力：Coverage、质量、Probe、Recipe、版本、成本、Ingestion、Generation、实验和 Release 都必须可运营。
