# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个长期运行、可横向扩展、可审计、可重放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章，稳定清洗为 Markdown；后续持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计和离线重处理。

设计按以下量级考虑：

- 1000+ Source，后续扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 千万级以上 Chunk / Embedding 的长期增长；
- 多年运行，站点结构、抓取框架、浏览器、模型都会持续变化；
- 中英日韩等多语言技术内容；
- HTTP 为主，Browser 为受控 fallback；
- 历史 URL 发现支持 CMS API、Sitemap、Feed、Archive、Common Crawl URL Index 等多来源；
- PostgreSQL + Object Storage 保存事实，Markdown、Chunk、Embedding、全文/向量索引均作为可删除重建的 Projection。

平台必须能够回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已基本覆盖；
2. 一个 URL 从哪里发现、如何规范化、经过哪些跳转后被抓取；
3. 一个 Markdown 来自哪个 Snapshot、哪个抽取规则、哪个文档版本；
4. 源站变化后哪些内容真的变化，哪些派生物需要重建；
5. Chunk、Embedding、Analyzer、索引或模型升级后能否不重新访问源站完成重放；
6. 抓取失败、结构漂移、反爬、成本、检索回归时能否在 Web 中定位和运营。

## 2. 核心设计原则

1. **Config First**：新增普通站点主要通过 Source / Site Profile 配置完成，不修改核心代码。
2. **Coverage First**：历史完整性必须由 Provider Evidence 与 exhaustion reason 证明，不能用“队列为空”或“达到 max_pages”冒充完整。
3. **Discovery Before Fetch**：先低成本发现和分类 URL，再决定是否真实抓取正文。
4. **Authoritative First**：CMS/API/Sitemap/Feed 优先，Archive/Common Crawl 只做历史补洞和外部证据。
5. **HTTP First, Browser Last**：Browser 仅处理动态渲染、结构探索或低质量 fallback，不作为默认抓取方式，更不是绕过访问控制的手段。
6. **Snapshot First**：网络事实先保存不可变 Snapshot，再做抽取、清洗、建版。
7. **IR First, Markdown as Projection**：Canonical IR / Document Version 是事实层，Markdown 是确定性可重建输出。
8. **Stable Identity**：Document、Version、Chunk、Embedding、Index 身份都必须 release-aware，禁止依赖可漂移的顺序编号。
9. **Language-aware Retrieval**：分词、stemming、stopwords、技术 token 处理与 BM25 参数按 Analyzer Release 管理。
10. **Hybrid Retrieval by Default**：技术语料默认 BM25 + Vector + RRF，Reranker 是可降级增强层。
11. **Benchmark Before Switch**：向量索引、Embedding、Analyzer、RRF、Reranker 等升级必须经过固定评测集后才能切生产。
12. **Generation Instead of Destructive Rebuild**：索引升级后台构建新 Generation，验证后原子切换，禁止生产 drop-and-recreate。
13. **Release Everything**：所有影响结果的策略、模型、浏览器和运行时版本都可追踪、比较、回滚。
14. **Idempotent + Recoverable**：任务具备幂等键、lease、checkpoint、retry 和 partial success。
15. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary、Search Index 故障不能阻塞抓取事实同步。
16. **Evidence Everywhere**：发现、分类、跳转、抓取、抽取、身份、版本、检索均有可审计证据。
17. **Web 管理是平台能力**：Coverage、失败、版本、成本、索引 Generation、检索实验和 Release 必须可运营。
18. **安全边界每跳执行**：Redirect 和 Browser navigation 都重新执行 SSRF/Egress/Scope 检查。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST / Command API、Schema 校验、内部服务接口；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、URL Observation、Resolution、Fetch、Document、Version、Projection、Release、Audit、Outbox；
- **Transactional Outbox**：数据库状态变更与消息发布事务一致；
- **Redis Streams**：consumer group、retry、backpressure，只做任务运输；
- **React/Vue + TypeScript**：Web 管理台。

### 4.2 抓取与抽取

- **HTTPX / aiohttp**：HTTP、Feed、Sitemap、API、条件请求、低成本跳转解析；
- **BeautifulSoup / lxml / CSS / XPath**：wrapper、meta refresh、selector、结构化 HTML；
- **Trafilatura / Readability**：确定性正文候选；
- **Crawl4AI / Playwright**：URL Seeding、Prefetch Mapping、动态页面、Browser fallback；
- **S3 / MinIO**：raw body、HTML、Rendered DOM、Feed payload、PDF、WARC 恢复快照、Canonical IR、Markdown、Asset、debug artifact。

Crawl4AI 生成的 Markdown 只能作为 Extraction Candidate，不能替代 Snapshot 与 Canonical IR。

### 4.3 历史发现

- CMS API / Sitemap / RSS / Atom / JSON Feed；
- Archive / Category / Tag / Author / Docs TOC；
- Common Crawl URL Index；
- DuckDB / Athena / Spark / Polars 用于批量历史索引扫描。

### 4.4 检索

- **OpenSearch**：生产 BM25、过滤、聚合、Alias/Generation、Hybrid Search；
- **pgvector / OpenSearch kNN**：首期向量实现；
- **Qdrant / Milvus**：向量规模或独立扩缩容需求提高后可替换；
- **RRF**：默认融合；
- **Cross Encoder Reranker**：可选精排服务。

进程内 `rank_bm25 + pickle` 只允许用于单元测试或小样本实验，不作为生产全文索引。

### 4.5 可观测与部署

- Prometheus + Grafana + OpenTelemetry；
- Docker / Kubernetes；
- Artifact Registry 保存应用镜像、浏览器内核、Embedding/Reranker 模型和运行时依赖。

## 8. 新站接入 PROBE

新增站点先执行 PROBE，不直接深爬：

1. 规范化 entry URL，确定 domain、allowed origins、scope；
2. 获取 robots 和 Sitemap 声明；
3. 探测 Sitemap Index / Sitemap；
4. 探测 RSS / Atom / JSON Feed；
5. 探测 WordPress REST、Ghost、Substack 等平台能力；
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination；
7. 低成本查询 Common Crawl；
8. 对 URL path 做模板聚类；
9. 对未知 hub 做轻量 HTML + links Prefetch；
10. 小预算 BFS / BestFirst 探索未知结构；
11. 抽样比较 HTTP 与 Browser 的正文质量与成本；
12. 检测 wrapper、short-link、meta refresh、JS redirect；
13. 推断语言、Analyzer 和 article template；
14. 自动生成首版 Profile，在 Web 审核后启用。

## 10. Common Crawl 的边界

Common Crawl 只能证明某 URL 在某次 crawl 中被观察或抓取，不能证明站点历史完整。

```text
common_crawl_observation
  source_id
  crawl_id
  url_id
  capture_time
  status
  mime
  warc_filename
  warc_offset
  warc_length
  content_digest
```

1000 站点级历史枚举优先批量扫描 URL Index，并缓存 `(registered_domain, crawl_id)`；CDX 仅用于低频补充。

恢复已下线文章时必须标记 archive origin 和 capture time，且不能伪装为当前 live fetch。

## 11. URL Normalization、Classification 与 Resolution

### 11.1 Normalization

典型规则：lowercase host、default port removal、fragment removal、path slash normalization、安全 percent-encoding、query key ordering、tracking param removal、站点级 semantic param allowlist。

禁止全局删除所有 query，因为 `?id=123`、`?p=456`、`?page=7` 可能具备正文或分页语义。

### 11.2 Classification

```text
ARTICLE_CANDIDATE
DISCOVERY_SURFACE
ASSET
NAVIGATION
EXTERNAL_REFERENCE
IGNORE_BY_POLICY
UNKNOWN
```

过滤只影响后续调度，原始 Observation 与 Evidence 永久保留。

### 11.3 Resolution Plane

```text
Observed URL
 -> Normalized Candidate
 -> HTTP Redirect
 -> Wrapper Param / HTML Target
 -> Meta Refresh
 -> Browser Navigation Fallback
 -> Resolved Fetch Target
```

`rel=canonical`、`og:url` 属于 Identity Evidence，不等同于 Redirect。

## 12. Fetch Route Policy

默认：

```text
HTTP_STATIC
 -> HTTP_ALT_HEADERS
 -> HTTP_PLATFORM_API
 -> BROWSER_CRAWL4AI
 -> BROWSER_PLAYWRIGHT_RECIPE
 -> SITE_CUSTOM_EXTRACTOR
```

Browser Worker 与 HTTP Worker 独立部署。Browser 不与 API 服务共享 Playwright event loop。

验证码、登录、付费墙、WAF、明确 robots/policy 阻止应记录 blocker，不无限升级重试。

`fetch_attempt` 至少记录 route、status、etag、last_modified、response_bytes、latency、browser_seconds、snapshot_id 和 outcome_code。

## 14. Quality、Document Identity 与版本

Quality 至少包含：

```text

content_length
paragraph_ratio
link_density
boilerplate_ratio
code_preservation
table_preservation
language_consistency
published_at_confidence

```

低质量候选进入 quarantine，可在 Web 比较抽取器结果。

Document Identity 综合使用：平台稳定 ID、canonical/og:url、Redirect Evidence、normalized URL、exact hash、near-duplicate、title + published time。

`Document Version` 只有 Canonical IR 或关键元数据变化时才创建。304、重复抓取、Chunk/Embedding/Analyzer/Markdown 策略升级都不创建正文版本。

单次 404 不立即删除文章；多次观察或 authoritative API 明确下线后创建 Tombstone，历史版本保留。

## 15. 增量同步与 Reconcile

信号优先级：

```text
Feed/API cursor
 -> Sitemap lastmod
 -> High-yield Surface
 -> Conditional GET
 -> Metadata Probe
 -> Full HTTP
 -> Browser
```

保存 ETag、Last-Modified、previous_body_hash。

304 时：不创建 body Snapshot 副本、不抽取、不建新 Version、不重复 Projection。

调度分层可从：

```text
Tier 0 Feed/API            分钟级
Tier 1 Sitemap/Blog Index  10~60 分钟
Tier 2 Category/Archive    1~6 小时
Tier 3 Deep Reconcile      每周/每月
Tier 4 Common Crawl        新 collection 或按月
```

开始，并根据新 URL 率、失败率、重复率和成本动态调频。

即使有 Feed，也周期 Reconcile Sitemap、Archive、Surface、Common Crawl，用于发现 Feed 窗口外遗漏、URL 迁移、删除、结构漂移和新历史候选。

## 18. Chunk 设计与稳定身份

### 18.1 主策略：Structure-aware

默认：

1. Heading / Section 是第一层语义边界；
2. 段落、列表、引用尽量完整；
3. fenced code 默认不拆；
4. 表格默认不拆；
5. 保存 heading path 与 block range；
6. 超长代码/表格走专门策略；
7. 超长普通 section 再进入 recursive fallback。

### 18.2 Recursive fallback

对于超长普通文本，可采用 `RecursiveCharacterTextSplitter` 类思想：优先段落、换行、语言标点，再退化到空格/字符；长度优先使用目标 Embedding tokenizer 的 token 计数，而不是把固定字符数当成通用语义长度。

`chunk_size` 与 `overlap` 必须属于 Chunk Release，并通过检索评测选择。

### 18.3 稳定 Chunk ID

禁止：

```text
hash(file_path + chunk_index)
hash(source + chunk_index)
```

推荐：

```text
chunk_id = hash(
  document_version_id
  + chunk_release_id
  + logical_block_range
  + normalized_text_hash
)
```

文档头部新增内容不能导致所有后续未变化 Chunk 被误判为新 Chunk。

## 19. Embedding 与流式批处理

### 19.1 Embedding Release

```text
id
model_name
model_digest
dimension
normalization
metric
max_tokens
batch_policy
runtime_artifact_release_id
created_at
```

Embedding ID：

```text
embedding_id = hash(chunk_id + embedding_release_id)
```

### 19.2 流式 Worker

禁止一次性把全库 Chunk 加载到内存并一次 encode。采用：

```text
query pending chunks
 -> lease batch
 -> tokenize/embed
 -> persist embedding
 -> idempotent upsert target generation
 -> commit per-item result
 -> checkpoint
 -> next batch
```

支持动态 batch、最大 batch token、OOM 自动缩 batch、retry、partial success 和 backpressure。Embedding backlog 不阻塞 Source Sync。

## 22. Hybrid Search、RRF 与 Retrieval Release


## 23. Reranker 与 Context Assembly

正确链路：

```text
大规模粗召回
 -> Top-N 融合候选
 -> Cross Encoder Reranker
 -> Top-K
 -> Context Assembly
```

Reranker 不扫描全库。

独立 `rerank-service`：

- 模型常驻优先；
- dynamic batch；
- 最大 batch token；
- GPU 并发限制；
- idle 可卸载；
- OOM 自动降 batch；
- 可选 CPU fallback；
- 超时或故障降级到 RRF；
- 完全不进入 Source Sync 关键路径。

Context Assembly 根据 document diversity、heading path、chunk adjacency、same-document overlap、token budget、source trust 和 duplicate suppression 组装，避免 Top-K 全来自同一文章相邻 Chunk。

## 33. 验收标准

### 33.1 Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有 exhaustion evidence；
- known gap 可枚举、可重跑；
- 达到预算不会错误标 COMPLETE；
- Common Crawl 不作为完整性证明。

### 33.2 增量

- Feed/API/Sitemap 新文章在目标 SLA 内进入系统；
- 304 不重复抽取、建版、投影；
- 未变化 Projection 不重复计算；
- Reconcile 能发现 Feed 窗口外遗漏和结构漂移。

### 33.3 Markdown

抽样验证 title/author/time、正文完整、导航噪声低、heading 正确、code/list/table/image/link 保留，且 Markdown 可从 IR 确定性重建。

### 33.4 Chunk / Embedding

- Chunk 保留 heading path 与 block range；
- fenced code 与表格默认不破坏；
- Chunk ID 不依赖 chunk_index；
- RECHUNK 不创建新 Document Version；
- REEMBED 不重新抓源站；
- Embedding backlog 不影响 Source Sync。

### 33.5 检索

- 中文/英文/技术 token 有固定回归集；
- CJK 不依赖 whitespace tokenizer；
- BM25 + Vector + RRF 可解释；
- Vector Index 参数有 benchmark；
- Reranker 故障可降级；
- 新 Generation 验证通过后才能 ACTIVE；
- 生产升级无 drop-and-recreate。

### 33.6 可靠性

- Worker 崩溃后 lease 可恢复；
- fan-out 保留 partial success；
- Embedding/Index/Reranker 故障不阻塞 Source Sync；
- Runtime Artifact 可复现、可回滚；
- 所有高风险管理操作可审计。

## 34. 最终架构原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：发现、分类、去重后再抓正文。
3. Authoritative First：权威来源优先，Archive/Common Crawl 只补洞。
4. HTTP First, Browser Last：Browser 是昂贵兼容层，不是默认抓取器。
5. Snapshot First, Replay Later：原始网络事实不可变，规则升级优先离线重放。
6. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
7. Stable Chunk Identity：Chunk 身份不能依赖 file path + chunk_index。
8. Structure-aware First：技术文档优先按标题、块、代码、表格切分，recursive splitter 只做超长 fallback。
9. Streaming Embedding：Embedding 必须批次、lease、checkpoint、幂等，禁止全库一次性加载。
10. Language-aware BM25：生产全文检索必须有可版本化 Analyzer。
11. Benchmark Vector Index：IVF/HNSW/FLAT 等索引和参数通过 recall/latency 基准选择。
12. Hybrid Retrieval by Default：BM25 与 Vector 互补，RRF 为默认稳定融合基线。
13. Reranker as Optional Service：精排是可降级增强层，不进入事实同步关键路径。
14. Generation Instead of Destructive Rebuild：后台构建、验证、原子切换。
15. Release Everything：策略、模型、索引、浏览器、运行时均可追踪和回滚。
16. Benchmark Before Switch：任何检索升级必须经过固定 judgment set。
17. Idempotent + Recoverable：任务可重复、可恢复、可观察，partial success 不丢失。
18. Source Sync 与 AI 解耦：抓取事实不依赖 Embedding、Reranker、LLM 或 Search 服务。
19. Evidence Everywhere：所有重要判断均保存可解释证据。
20. Web 管理是平台能力：Coverage、质量、版本、成本、Generation、实验和 Release 都必须可运营。
