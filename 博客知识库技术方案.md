# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个长期运行、可横向扩展、可审计、可重放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章并清洗为稳定 Markdown；后续可持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计和离线重处理。

设计按以下量级考虑：

- 1000+ Source，后续扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 千万级 Chunk / Embedding 长期增长；
- 多年运行，站点结构、抓取框架、浏览器、模型和索引策略持续变化；
- 中英日韩等多语言技术内容；
- HTTP 为主，Browser 为受控 fallback；
- 历史发现支持 CMS API、Sitemap、Feed、Archive、Common Crawl URL Index 等多来源；
- PostgreSQL + Object Storage 保存事实，Markdown、Chunk、Embedding、全文/向量索引均为可重建 Projection。

平台必须能回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已基本覆盖；
2. 一个 URL 从哪里发现、如何规范化、经过哪些跳转后被抓取；
3. 一个动态页面执行了哪些点击/滚动/等待，使用哪一版 Recipe；
4. 一个 Markdown 来自哪个 Snapshot、Extractor、Schema、Document Version；
5. 源站变化后哪些内容真的变化，哪些派生物需要重建；
6. Chunk、Embedding、Analyzer、Browser Runtime、索引策略升级后能否不重新访问源站完成重放；
7. 抓取失败、结构漂移、Browser 成本、反爬、索引或检索回归时能否在 Web 中定位和运营。

## 2. 核心设计原则

1. **Config First**：普通站点主要通过 Source / Site Profile / Release 配置接入，不修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence 与 exhaustion reason 证明，不能用“队列为空”或达到 `max_pages` 冒充完整。
3. **Discovery Before Fetch**：先低成本发现、分类、去重 URL，再决定是否真实抓取正文。
4. **Authoritative First**：CMS/API/Sitemap/Feed 优先，Archive/Common Crawl 用于补洞和外部证据。
5. **HTTP First, Browser Last**：Browser 只处理动态发现面、动态渲染、结构探索或低质量 fallback。
6. **Recipe, Not Site-Specific Code**：动态交互和结构化抽取必须声明式、版本化，禁止长期堆积 `if site == ...` 分支。
7. **Bounded Interaction**：点击、滚动、等待、session 复用都必须有预算和明确停止条件。
8. **Snapshot First**：先保存不可变网络事实，再做抽取、清洗、建版。
9. **IR First, Markdown as Projection**：Canonical IR / Document Version 是内容事实层，Markdown 是可重建输出。
10. **Stable Identity**：Document、Version、Chunk、Embedding、Index 身份必须稳定且 release-aware。
11. **Release Everything**：影响结果的策略、Browser Recipe、Schema、模型、索引和 Runtime 均版本化。
12. **Idempotent + Recoverable**：任务具备幂等键、lease、checkpoint、retry、partial success。
13. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary、Search Index 故障不能阻塞抓取事实同步。
14. **Evidence Everywhere**：发现、分类、跳转、交互、抓取、抽取、身份、版本和检索均保存证据。
15. **Language-aware Retrieval**：分词、stemming、stopwords、技术 token 处理由 Analyzer Release 管理。
16. **Hybrid Retrieval by Default**：技术语料默认 BM25 + Vector + RRF，Reranker 是可降级增强层。
17. **Benchmark Before Switch**：Analyzer、Embedding、Vector Index、RRF、Reranker 升级经固定评测后切生产。
18. **Generation Instead of Destructive Rebuild**：索引升级后台构建新 Generation、验证、原子切换，禁止生产 drop-and-recreate。
19. **Web 管理是平台能力**：Coverage、失败、版本、成本、Recipe、Schema、Generation、实验和 Release 都必须可运营。
20. **安全边界每跳执行**：Redirect 和 Browser navigation 每跳重新执行 SSRF/Egress/Scope 校验。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST / Command API、Schema 校验、内部服务接口；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、URL Observation、Resolution、Fetch、Interaction、Document、Version、Projection、Release、Audit、Outbox；
- **Transactional Outbox**：数据库状态变更与消息发布事务一致；
- **Redis Streams**：consumer group、retry、backpressure，只做任务运输；
- **React/Vue + TypeScript**：Web 管理台。

### 4.2 抓取与抽取

- **HTTPX / aiohttp**：HTML、Feed、Sitemap、API、Conditional GET、低成本跳转解析；
- **BeautifulSoup / lxml / CSS / XPath / Regex**：wrapper、meta refresh、selector、结构化抽取；
- **Trafilatura / Readability**：确定性正文候选；
- **Crawl4AI / Playwright**：URL Seeding、Prefetch、动态页面、Browser Interaction、结构化抽取和 Browser fallback；
- **S3 / MinIO**：raw response、HTML、Rendered DOM、Feed payload、PDF、WARC、Canonical IR、Markdown、Asset、debug artifact、fixture。

Crawl4AI 生成的 Markdown 只能作为 Extraction Candidate / Projection，不能替代 Snapshot 与 Canonical IR。

### 4.3 历史发现

- CMS API / Sitemap / RSS / Atom / JSON Feed；
- Archive / Category / Tag / Author / Docs TOC；
- Common Crawl URL Index；
- DuckDB / Athena / Spark / Polars 用于批量历史索引扫描。

### 4.4 检索

- **OpenSearch**：生产 BM25、过滤、聚合、Alias/Generation、Hybrid Search；
- **pgvector / OpenSearch kNN**：首期向量实现；
- **Qdrant / Milvus**：向量规模或独立扩缩容需求提高后可替换；
- **RRF**：默认融合；
- **Cross Encoder Reranker**：可选精排服务。

进程内 `rank_bm25 + pickle` 只用于测试或算法对照，不作为生产全文索引。

### 4.5 可观测与部署

- Prometheus + Grafana + OpenTelemetry；
- Docker / Kubernetes；
- Artifact Registry 保存应用镜像、浏览器内核、Embedding/Reranker 模型和运行时依赖。

## 9. 新站接入 PROBE

新增站点先执行 PROBE，不直接深爬：

1. 规范化 entry URL，确定 registrable domain、allowed origins、scope；
2. 获取 robots 和 Sitemap 声明；
3. 探测 Sitemap Index / Sitemap；
4. 探测 RSS / Atom / JSON Feed；
5. 探测 WordPress REST、Ghost、Substack 等平台能力；
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination；
7. 低成本查询 Common Crawl；
8. 对 URL path 做模板聚类；
9. 对未知 hub 做轻量 HTML + links Prefetch；
10. 小预算 BFS / BestFirst 探索未知结构；
11. 抽样比较 HTTP 与 Browser 的正文质量与成本；
12. 检测 wrapper、short-link、meta refresh、JS redirect；
13. 若只有动态页面才能发现历史 URL，生成候选 Interaction Recipe；
14. 对重复 DOM 生成候选 Structured Schema，并用 fixture 校验；
15. 推断语言、Analyzer 和 article template；
16. 自动生成首版 Profile，在 Web 审核后启用。

### 10.2 历史发现顺序


## 11. Discovery Surface 与 Link Graph

Archive、Category、Tag、Author、Blog Index、Docs TOC、pagination/API collection 等长期产出文章链接的页面建模为一等 `Discovery Surface`。

每次扫描保存：

```text
outgoing_link_count
article_like_count
new_candidate_count
novel_document_count
pagination_detected
temporal_span
structure_hash
yield_score
```

`yield_score` 只用于探索顺序和扫描频率，不能删除 FULL_BACKFILL 合法 Candidate。

允许对低收益 branch 做可逆剪枝，但必须保存 evidence、sample、URL template、marginal yield、reopen 时间；周期 RECONCILE 必须重新抽样，发现新模板或结构漂移时 reopen。

## 12. Common Crawl 的边界

Common Crawl 只能证明某 URL 在某次 crawl 中被观察或抓取，不能证明站点历史完整。

```text
common_crawl_observation
  source_id
  crawl_id
  url_id
  capture_time
  status
  mime
  warc_filename
  warc_offset
  warc_length
  content_digest
```

1000 站点级历史枚举优先批量扫描 URL Index，并缓存 `(registered_domain, crawl_id)`；CDX 仅用于低频补充。

恢复下线文章时必须标记 archive origin 和 capture time，不能伪装为当前 live fetch。

## 13. URL Normalization、Classification 与 Resolution

### 13.1 Normalization

典型规则：lowercase host、default port removal、fragment removal、path slash normalization、安全 percent-encoding、query key ordering、tracking param removal、站点级 semantic param allowlist。

禁止全局删除所有 query，因为 `?id=123`、`?p=456`、`?page=7` 可能具备正文或分页语义。

### 13.2 Classification

```text
ARTICLE_CANDIDATE
DISCOVERY_SURFACE
ASSET
NAVIGATION
EXTERNAL_REFERENCE
IGNORE_BY_POLICY
UNKNOWN
```

过滤只影响后续调度，原始 Observation 与 Evidence 永久保留。

### 13.3 Resolution Plane

```text
Observed URL
 -> Normalized Candidate
 -> HTTP Redirect
 -> Wrapper Param / HTML Target
 -> Meta Refresh
 -> Browser Navigation Fallback
 -> Resolved Fetch Target
```

`rel=canonical`、`og:url` 属于 Identity Evidence，不等同于 Redirect。

每一跳保存证据并重新执行 DNS/IP/Egress/Scope 校验。

## 14. Fetch Route Policy

默认：

```text
HTTP_STATIC
 -> HTTP_ALT_HEADERS
 -> HTTP_PLATFORM_API
 -> BROWSER_CRAWL4AI_RECIPE
 -> BROWSER_PLAYWRIGHT_CUSTOM
 -> SITE_CUSTOM_EXTRACTOR
```

Browser Worker 与 HTTP Worker 独立部署。Browser 不与 API 服务共享 Playwright event loop。

验证码、登录、付费墙、WAF、robots/policy 阻止记录 blocker，不无限升级重试。

Proxy 是受控 Fetch Route 参数：

```text
DIRECT
REGIONAL_PROXY
APPROVED_PROXY_POOL
```

不得用于绕过明确访问控制。

`fetch_attempt` 至少记录：route、status、etag、last_modified、response_bytes、latency、browser_seconds、proxy_route、snapshot_id、outcome_code。

## 15. Browser Worker 并发模型

Crawl4AI `arun_many()` / Dispatcher 只负责单 Worker 内并发和资源保护，不能替代全平台 durable scheduler。

两层模型：

```text
Platform Scheduler
  durable Task + lease + retry
  global / domain / source / route token bucket
        ↓
Browser Worker
  MemoryAdaptiveDispatcher / SemaphoreDispatcher
  RateLimiter
        ↓
AsyncWebCrawler.arun_many(stream=True)
```

Worker 批量 lease 后按单 URL 流式提交：

```text
lease N tasks
 -> arun_many(stream=True)
 -> result arrives
 -> persist FetchAttempt / Snapshot per URL
 -> ack per URL
```

一个失败 URL 不能回滚整个 batch。

### 16.4 Clean Markdown

Markdown 从 IR 确定性生成：

- 去导航、广告、推荐、评论；
- 保留标题层级；
- 保留 fenced code 与语言 hint；
- 保留列表、引用、表格；
- 保留重要图片 alt、caption 和链接；
- 解析相对链接；
- 不做 query-dependent 删减。

Crawl4AI 的完整 Markdown 可作为候选；经 BM25/LLM 等与查询相关 Filter 生成的 `fit_markdown` 只能作为检索/LLM 上下文优化，不得成为 canonical Markdown。

## 17. Quality、结构漂移与 Document Identity

Quality 至少包含：


Structured Schema / Interaction Recipe 维护 fixture 与历史基线。HTTP 200 但 `matched_item_count=0`、必填字段缺失率突升、DOM signature 大幅变化时触发结构漂移告警，不能静默生成空文档。

`Document Version` 只有 Canonical IR 或关键元数据变化时才创建。304、重复抓取、Chunk/Embedding/Analyzer/Markdown/Recipe 策略升级都不创建正文版本。

单次 404 不立即删除文章；多次观察或 authoritative API 明确下线后创建 Tombstone，历史版本保留。

## 18. 增量同步与 Reconcile

信号优先级：

```text
Feed/API cursor
 -> Sitemap lastmod
 -> High-yield Surface
 -> Conditional GET
 -> Metadata Probe
 -> Full HTTP
 -> Browser fallback
```

保存 ETag、Last-Modified、previous_body_hash。

304 时：不创建 body Snapshot 副本、不抽取、不建新 Version、不重复 Projection。

调度分层：

```text
Tier 0 Feed/API            分钟级
Tier 1 Sitemap/Blog Index  10~60 分钟
Tier 2 Category/Archive    1~6 小时
Tier 3 Deep Reconcile      每周/每月
Tier 4 Common Crawl        新 collection 或按月
```

根据新 URL 率、失败率、重复率、Browser 比例和成本动态调频。

即使有 Feed，也周期 Reconcile Sitemap、Archive、Surface、Common Crawl，用于发现 Feed 窗口外遗漏、URL 迁移、删除、结构漂移和新历史候选。

## 21. Chunk 设计与稳定身份

### 21.1 主策略：Structure-aware

默认：

1. Heading / Section 是第一层语义边界；
2. 段落、列表、引用尽量完整；
3. fenced code 默认不拆；
4. 表格默认不拆；
5. 保存 heading path 与 block range；
6. 超长代码/表格走专门策略；
7. 超长普通 section 再进入 recursive fallback。

### 21.2 Recursive fallback

优先段落、换行、语言标点，再退化到空格/字符；长度优先使用目标 Embedding tokenizer 的 token 计数。

`chunk_size` 与 `overlap` 属于 Chunk Release，并通过检索评测选择。

### 21.3 稳定 Chunk ID

禁止：

```text
hash(file_path + chunk_index)
hash(source + chunk_index)
```

推荐：

```text
chunk_id = hash(
  document_version_id
  + chunk_release_id
  + logical_block_range
  + normalized_text_hash
)
```

文档头部新增内容不能导致所有后续未变化 Chunk 被误判为新 Chunk。

## 22. Embedding 与流式批处理

### 22.1 Embedding Release

```text
id
model_name
model_digest
dimension
normalization
metric
max_tokens
batch_policy
runtime_artifact_release_id
created_at
```

Embedding ID：

```text
embedding_id = hash(chunk_id + embedding_release_id)
```

### 22.2 流式 Worker

禁止一次性把全库 Chunk 加载到内存并一次 encode：

```text
query pending chunks
 -> lease batch
 -> tokenize/embed
 -> validate
 -> persist embedding
 -> idempotent upsert target generation
 -> commit per-item result
 -> checkpoint
 -> next batch
```

支持动态 batch、最大 batch token、OOM 自动缩 batch、retry、partial success 和 backpressure。Embedding backlog 不阻塞 Source Sync。

### 22.3 Vector Payload Contract

写入向量引擎前统一校验：

```text
embedding_release_id == target_generation.embedding_release_id
dimension == embedding_release.dimension
values are numeric
no NaN / Inf
canonical dtype / serialization matches adapter
normalization invariant matches release when required
chunk_id and embedding_id are present
payload schema version matches vector_index_release
```

单条坏向量进入 quarantine / retry，不允许拖垮整个 batch。

## 26. Reranker 与 Context Assembly

正确链路：

```text
大规模粗召回
 -> Top-N 融合候选
 -> Cross Encoder Reranker
 -> Top-K
 -> Context Assembly
```

Reranker 不扫描全库。

独立 `rerank-service`：模型常驻优先、dynamic batch、最大 batch token、GPU 并发限制、idle 可卸载、OOM 自动降 batch、超时降级到 RRF，不进入 Source Sync 关键路径。

Context Assembly 根据 document diversity、heading path、chunk adjacency、same-document overlap、token budget、source trust、duplicate suppression 组装，避免 Top-K 全来自同一文章相邻 Chunk。

## 36. 验收标准

### 36.1 Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有 exhaustion evidence；
- known gap 可枚举、可重跑；
- 达到预算不会错误标 COMPLETE；
- Common Crawl 不作为完整性证明。

### 36.2 增量

- Feed/API/Sitemap 新文章在目标 SLA 内进入系统；
- 304 不重复抽取、建版、投影；
- 未变化 Projection 不重复计算；
- Reconcile 能发现 Feed 窗口外遗漏和结构漂移。

### 36.3 Browser / Recipe

- Browser 不是默认抓取路线；
- 动态 Discovery Surface 可独立使用 Browser，文章正文仍优先 HTTP；
- 每个 Interaction Recipe 可版本化、可 diff、可回滚；
- click/scroll/wait 有明确预算和停止条件；
- `arun_many()` 批处理结果按 URL 独立提交；
- Crawl4AI cache/session 不承载持久业务状态；
- Runtime Artifact 能复现 Browser + Crawl4AI 运行环境。

### 36.4 Schema / Markdown

- Structured Schema 有 fixture、必填字段和 zero-match 告警；
- 抽样验证 title/author/time、正文完整、导航噪声低、heading 正确、code/list/table/image/link 保留；
- Markdown 可从 IR 确定性重建；
- query-dependent `fit_markdown` 不作为 canonical 文档。

### 36.5 Chunk / Embedding

- Chunk 保留 heading path 与 block range；
- fenced code 与表格默认不破坏；
- Chunk ID 不依赖 chunk_index；
- RECHUNK 不创建新 Document Version；
- REEMBED 不重新抓源站；
- Embedding backlog 不影响 Source Sync；
- 向量维度、NaN/Inf、归一化、Release/Generation 不一致在入库前拦截；
- 单条无效向量不会导致整批回滚。

### 36.6 检索

- 中文/英文/技术 token 有固定回归集；
- CJK 不依赖 whitespace tokenizer；
- BM25 + Vector + RRF 可解释；
- Vector Index 参数有 benchmark；
- Reranker 故障可降级；
- Retrieval Trace 能区分不同 score type；
- 新 Generation 验证通过后才能 ACTIVE；
- 生产升级无 drop-and-recreate。

### 36.7 可靠性

- Worker 崩溃后 lease 可恢复；
- fan-out 保留 partial success；
- Browser session 丢失不丢 durable checkpoint；
- Embedding/Index/Reranker 故障不阻塞 Source Sync；
- Runtime/Model Artifact 可复现、可回滚；
- 所有高风险管理操作可审计。

## 37. 最终架构原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：发现、分类、去重后再抓正文。
3. Authoritative First：权威来源优先，Archive/Common Crawl 只补洞。
4. HTTP First, Browser Last：Browser 是昂贵兼容层，不是默认抓取器。
5. Browser Discovery Is Separate：动态发现面可用 Browser，但不要因此把全部文章正文 Browser 化。
6. Recipe, Not Site-Specific Code：动态交互用版本化 Recipe，不在业务代码堆站点分支。
7. Deterministic Schema First：规则化结构优先 CSS/XPath/Regex，LLM 只做辅助和 fallback。
8. Bounded Interaction：点击、滚动、等待、session 均有明确预算和停止条件。
9. Worker Dispatcher Is Local：Crawl4AI `arun_many()` 负责 Worker 内资源保护，平台 durable scheduler 负责全局任务事实。
10. Snapshot First, Replay Later：原始网络事实不可变，规则升级优先离线重放。
11. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
12. Stable Chunk Identity：Chunk 身份不能依赖 file path + chunk_index。
13. Structure-aware First：技术文档优先按标题、块、代码、表格切分。
14. Streaming Embedding：Embedding 必须批次、lease、checkpoint、幂等，禁止全库一次性加载。
15. Validate Before Vector Write：向量维度、有限数值、归一化、序列化和 Release/Generation 一致性写前校验。
16. Language-aware BM25：生产全文检索必须有可版本化 Analyzer。
17. Benchmark Vector Index：IVF/HNSW/FLAT 等索引通过 recall/latency 基准选择。
18. Hybrid Retrieval by Default：BM25 与 Vector 互补，RRF 为默认稳定融合基线。
19. Typed Retrieval Scores：不同阶段 raw score 必须带 score type，不做跨阶段数值比较。
20. Reranker as Optional Service：精排是可降级增强层，不进入事实同步关键路径。
21. Generation Instead of Destructive Rebuild：后台构建、验证、原子切换。
22. Release Everything：策略、Recipe、Schema、模型、索引、浏览器、运行时均可追踪和回滚。
23. Ephemeral State Is Not Truth：Crawl4AI cache、proxy runtime、Browser session 不能成为业务真相。
24. Model Artifact Is Immutable：模型在构建阶段固定 revision 与 digest，生产运行时不临时下载。
25. Benchmark Before Switch：任何检索升级必须经过固定 judgment set。
26. Idempotent + Recoverable：任务可重复、可恢复、可观察，partial success 不丢失。
27. Source Sync 与 AI 解耦：抓取事实不依赖 Embedding、Reranker、LLM 或 Search 服务。
28. Evidence Everywhere：所有重要判断均保存可解释证据。
29. Web 管理是平台能力：Coverage、质量、Recipe、版本、成本、Generation、实验和 Release 都必须可运营。
