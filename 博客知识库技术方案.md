# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站和公开 Newsletter** 的长期知识库采集平台，并可继续扩展到数千站点。

平台需要同时解决：

1. **历史尽量抓全**：知道文章有哪些、从哪里发现、为什么认为 Provider 已到边界、还有哪些 Known Gap；
2. **持续增量同步**：及时发现新文章、修改、迁移和删除；
3. **内容稳定可用**：把 HTML、动态页面、PDF 等转换为可追溯的 Canonical IR 和 Markdown；
4. **低成本可扩展**：新增站点主要依赖 Source Profile/Recipe，不为每个站点长期维护一套专用爬虫；
5. **Web 可管理**：支持接入、Probe、审核、调度、回放、失败处理、质量、Coverage、成本和 Release 管理；
6. **结果可审计**：任意 Markdown 都能定位到 Source、URL、Snapshot/Render Artifact、Recipe、Runtime、Extractor、IR、Quality、Version 和 Release。

最终提供：

- 全历史文章 URL Discovery + Backfill；
- Sitemap/RSS/CMS/API/Archive/动态列表/受限 Deep Crawl 等多 Provider；
- 定时 Incremental、Known URL Verify、删除/迁移判定；
- HTTP-first、Browser-last 的正文获取；
- 动态栏目 Infinite Scroll / Load More / Virtual Scroll；
- 原始事实、Canonical IR、Markdown、全文和向量索引分层保存；
- Web 管理、RBAC、审计、成本治理、告警、Canary/回滚；
- Markdown/JSONL/IR 等批量与增量导出。

### 1.1 核心 SLO

平台不以 HTTP 200 比例作为核心 SLO，而以业务结果衡量：

- **Coverage**：历史 URL 覆盖、Provider exhaustion evidence、Known Gap；
- **Freshness**：新文章从发布到进入 PASS Markdown 的延迟；
- **Quality**：正文完整率、噪声率、结构质量、Quarantine 比例；
- **Data Supply**：URL 从首次发现到 `Quality=PASS` 且投影可用的 `time_to_usable_data`；
- **Reliability**：任务成功率、Retry/DLQ、队列年龄、Worker 故障恢复；
- **Cost**：每 Source、每 1000 个 PASS 文档、每个 accepted version 的网络/CPU/Browser/存储/LLM 成本；
- **Traceability**：任意结果可回溯到不可变事实和版本化执行环境。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不用 LLM 主观判断代替 Coverage 证明；
- 不把 Redis、Browser session、Crawler cache/frontier 当业务真相；
- 不允许 Web/API 直接向 Browser 透传任意 JavaScript、Playwright evaluate、代理或系统参数；
- 不把 LLM 摘要/重写作为 Canonical Markdown；
- 不把标题、slug、图片 alt、图片 URL 或展示文本当跨阶段唯一主键；
- 不因为 URL 曾经抓过就永久停止复检；
- 不把 crawler `success=true`、HTTP 200 或“最终 HTML 看起来较长”直接等价为正文成功或 Coverage 完成。

## 2. 核心设计原则

1. **Coverage First**：先证明“文章有哪些”，再批量抓正文。
2. **Authoritative First**：CMS/API、Sitemap、Feed、Archive 优先，动态列表/Deep Crawl 用于补洞。
3. **Discovery Before Fetch**：URL 发现、规范化、Scope、分类和去重独立于正文抓取。
4. **Discover Cheap, Fetch Expensive**：低成本 Provider 先跑，Browser 后置。
5. **HTTP First, Browser Last**：静态 HTTP 优先；确定性 Browser fallback；Agent Browser 极少使用。
6. **Deterministic Before Agentic**：主链在没有 LLM 时也能完成 Backfill 与 Incremental。
7. **Snapshot First**：先保存不可变抓取事实，再做 Extract/IR/Markdown。
8. **IR First, Markdown as Projection**：Canonical IR 是内容事实，Markdown 是可重建投影。
9. **Quality Is First-Class**：传输成功与内容合格是两套状态。
10. **Cost Is First-Class**：高成本 Browser/LLM 必须可归因、可预算。
11. **Tool Contract, Not Framework Coupling**：Crawl4AI/Playwright/httpx 通过 Adapter 接入。
12. **Recipe, Not Site Code**：selector、pagination、scroll、click、virtual scroll、wait 通过版本化 Recipe 表达。
13. **Semantic Recipe, Not Runtime Parameters**：Recipe 表达业务动作语义，不绑定某版本 crawler 参数名。
14. **Capability != Outcome**：Runtime Capability 说明“支持什么”，Runtime Outcome 说明“本次实际执行了什么”。
15. **Business Identity Over Runtime Dedup**：文章 Coverage 以规范化 URL/URL Identity 为准，不依赖 crawler 内部 DOM/文本去重。
16. **Stable Identity**：Source、URL、Artifact、Document、Version 使用稳定不可变 ID 关联。
17. **Idempotent + Recoverable**：Task 有幂等键、lease、fencing token、checkpoint、retry、DLQ。
18. **Fair by Default**：大站 Backfill 不得长期饿死 Incremental 和小站。
19. **Detect Drift Online**：Golden Corpus 防平台升级回归，Drift Detector 防站点改版静默退化。
20. **Security on Every Hop**：start URL、redirect、href、iframe、Asset、Browser navigation 每跳重新校验。
21. **Release Everything That Changes Results**：Profile、Recipe、Compiler、Runtime、Extractor、Schema、Renderer 全版本化。
22. **Projection Is Rebuildable**：Markdown、全文索引、向量和其他派生结果可从事实层重建。
23. **Fail Closed on Semantic Incompatibility**：运行时无法保持 Recipe 语义时阻止 Release，不能静默少抓。
24. **No Silent Fallback for Coverage**：请求的动态能力没有真正生效时必须显式降级为 Known Gap/DEGRADED，而不是借 crawler success 宣称抓全。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST、Command API、Schema 校验；
- **PostgreSQL**：Source/Profile、Run/Task、Coverage、Observation、Artifact、Document/Version、Quality、Drift、Cost、Release、Audit、Outbox；
- **Redis Streams**：任务运输、consumer group、backpressure；
- **Redis Lua token bucket / semaphore**：跨 Worker Domain Admission；
- **React/Next.js + TypeScript**：Web 管理台；
- **Prometheus + Grafana + OpenTelemetry**：Metric/Log/Trace；
- **S3/MinIO**：Raw HTML、DOM/MHTML、IR、附件、失败诊断、导出；
- **OpenSearch**：全文/BM25；
- **pgvector**：首期向量检索，通过 Adapter 可替换；
- **Docker Compose**：本地开发与小规模验证；
- **Kubernetes**：生产 Worker Pool 横向扩展与 HPA。

### 4.2 抓取与解析

- **httpx/aiohttp**：HTTP、Sitemap、Feed、CMS API、Conditional GET、附件；
- **Crawl4AI**：动态页面、批量 Browser、URL mapping、Virtual Scroll 等，通过 Adapter 使用；
- **Playwright**：复杂但确定性的交互 Recipe；
- **lxml + trafilatura/readability 类算法**：默认正文抽取；
- **JSON-LD/OpenGraph/Microdata**：结构化元数据优先；
- **PyMuPDF/pdftotext**：PDF；扫描件才进入 OCR。

### 4.3 Crawler 的边界

```text
平台负责：
Task / Retry / DLQ / Coverage / Fairness / Global Rate Limit /
Budget / Checkpoint / Release / Quality / Audit / Runtime Outcome

Crawler 负责：
单次导航 / 页面动作 / DOM / 链接 / 媒体 / 浏览器资源管理
```

生产锁定经过 Golden Corpus 验证的 Crawl4AI、Playwright、Chromium 与镜像版本。升级必须经过 Capability、Compile、Benchmark、Replay、Canary 与 Approval。

## 6. 新站点接入：Probe -> Review -> Release

### 6.1 自动 Probe

新增 Source 后先进入 `PROBING`：

1. 读取 robots.txt；
2. 探测 `/sitemap.xml`、Sitemap Index、RSS/Atom；
3. 识别 WordPress/Ghost/Medium/Substack 等常见 CMS/API；
4. 发现 Archive、分页、year/month/category index；
5. 抽取 URL/path 样本，生成 include/exclude 候选；
6. 随机选择 5~10 篇文章样本；
7. 比较 HTTP Extractor 与 Browser/Recipe 的正文质量；
8. 检测 JSON-LD、作者、发布时间、代码块、图片；
9. 估算历史 URL 数与时间分布；
10. 权威发现不足时做受限 Prefetch Mapping；
11. 若栏目依赖 JavaScript，识别 Pagination/Load More/Append Scroll/Virtual Scroll，生成 Dynamic Listing Recipe 候选；
12. Probe 动态能力时同时记录 Runtime Outcome，确认能力真正生效，而不是只看 crawler success；
13. 估算 Browser 比例、Backfill 和日常增量成本；
14. 生成 DRAFT Source Profile。

### 6.2 Web 审核

管理员审核：

- Provider 与优先级；
- URL 样本、include/exclude/path 分类；
- HTTP/Browser URL 产出与正文质量对比；
- Dynamic Listing 每轮 URL 增长、Runtime Outcome、编译执行计划和收敛原因；
- Markdown 预览；
- Quality 分数；
- robots/Scope；
- 预计文章数、已发现数、Known Gap；
- 预计 Backfill 成本和 Browser 占比。

审核通过后发布 Source Profile/Recipe Release，再进入 Backfill。

## 7. 历史全量 URL 发现与 Coverage

### 7.1 Provider 优先级

推荐：

```text
1. CMS / 官方 API
2. Sitemap / Sitemap Index
3. RSS / Atom
4. Archive / Pagination / Year-Month Index
5. Category/Tag Index（补充）
6. URL Seeder / 公开索引
7. Prefetch Mapping
8. Dynamic Listing Discovery
9. bounded Deep Crawl
10. 人工补充 / CSV 导入
```

Browser Provider 默认不压过可用的权威低成本数据源。

### 7.2 Coverage 不是“队列空了”

Backfill 完成必须有可审计证据：

- CMS/Sitemap cursor 已穷尽或明确不可用；
- Archive 到达最老分页/年份边界；
- Provider 集合交叉后新增 URL 收敛；
- Dynamic Listing 达到可解释的 exhaustion boundary，且 Runtime Outcome 证明请求的交互语义真正生效；
- Prefetch/Deep Crawl 达到 max_pages/max_depth/time budget 时形成 Known Gap；
- expected_count 存在时进行数量对照；
- 历史时间分布异常空洞进入补洞队列。

以下都 **不能** 单独作为 Coverage 完成证据：

```text
queue empty
crawler success=true
HTTP 200
DOM 高度不再变化
最终 HTML 体积较大
某个 selector 一次命中
crawler 内部合并/去重后的 item 数
```

### 7.3 URL 规范化

统一：

- scheme/host 小写；
- 默认端口清理；
- fragment 移除；
- tracking 参数移除；
- query 仅保留 Source allowlist；
- trailing slash 由 Profile 决定；
- relative URL resolve；
- Canonical Link 只作为证据，不无条件信任；
- redirect final URL 重新过 Scope/SSRF；
- 保留原始 observed URL 与 normalized URL。

### 7.4 Prefetch Mapping

```text
Phase A: Map
seed URLs
 -> cheap HTML + links
 -> normalize/scope/filter
 -> URL Observation + parent edge
 -> page/path classifier
 -> 估算站点空间

Phase B: Process
article candidates
 -> 正式 HTTP/Browser Fetch
 -> Snapshot/Render
 -> Extract/IR/Quality
```

必须设置 `max_depth / max_pages / time_budget`，并对日历、搜索、tag、query 无限空间设置 guard。

## 8. Dynamic Listing Discovery

JavaScript 栏目、Infinite Scroll、Load More、Virtual Scroll 是独立 Discovery Provider，不是正文 Browser 中的临时脚本。

### 8.1 语义 Recipe IR

```yaml
name: dynamic_blog_list_v5
kind: dynamic_listing
start_urls:
  - https://example.com/blog

ready:
  type: CSS
  selector: ".information-flow-list"

harvest:
  item_selector: ".information-flow-list article"
  link_selector: "a[href]"
  extract:
    url: "a::attr(href)"
    title: "a::text"
    published_hint: "time::attr(datetime)"

interaction:
  mode: APPEND_SCROLL
  action: SCROLL_PAGE
  expected_runtime_mode: APPEND
  wait_after_action:
    type: ITEM_GROWTH
    selector: ".information-flow-list article"
    timeout_ms: 5000

convergence:
  no_growth_rounds: 3
  max_rounds: 40
  max_runtime_seconds: 120
  max_items: 5000
```

支持：

```text
STATIC
PAGINATION
CLICK_MORE
APPEND_SCROLL
```

能力示例：

```json

  "supports_scan_full_page": true,

    "navigate",
    "js_before_wait",

```

### 8.3 Recipe Compiler

当前 Crawl4AI 0.9.x Adapter 的典型语义映射：

```text
TRIGGER -> WAIT -> HARVEST
 -> js_code_before_wait + wait_for + capture

CLICK_MORE 多轮交互
 -> session_id + js_only=True + 多次受控 action

APPEND_SCROLL
 -> scan_full_page 或逐轮 scroll + harvest

 -> VirtualScrollConfig 或逐轮 harvest + 业务 URL union

```

禁止把旧版本 `js_code/wait_for` 参数文本原样搬到新 Runtime；编译目标是保持语义，而非参数名。

### 8.5 文章身份提取

Discovery 主身份必须来自真实链接：

```json
{
  "observed_url": "https://example.com/post/123",
  "title_hint": "文章标题",
  "published_hint": "2026-08-01T10:00:00Z",
  "parent_url": "https://example.com/blog",
  "round": 7,
  "provider": "DYNAMIC_LISTING"
}
```

禁止用图片 alt、图片 URL、卡片文本或 runtime 文本 fingerprint 作为文章唯一身份。

### 8.6 收敛算法

```python
seen = set()
no_growth = 0

for round_no in range(max_rounds):
    candidates = harvest_current_state()
    urls = normalize_scope_filter_classify(candidates)
    new_urls = urls - seen
    seen |= new_urls
    persist_observations(new_urls, round_no)

    if incremental_overlap_reached(new_urls):
        stop("OVERLAP_BOUNDARY")
        break

    no_growth = no_growth + 1 if not new_urls else 0
    if no_growth >= no_growth_rounds:
        stop("NO_GROWTH")
        break

    outcome = perform_next_semantic_action()
    verify_runtime_outcome(outcome)
    wait_for_item_growth_or_timeout()
else:
    stop("MAX_ROUNDS")
```

收敛核心是“规范化且通过 Scope/文章分类后的唯一文章 URL 是否继续增长”。DOM 高度、文本内容和 runtime 合并 item 数只作辅助证据。

### 8.7 Virtual Scroll 的业务正确性

虚拟列表会回收旧 DOM，必须：

- 每轮滚动立即 harvest URL 并持久化；或
- 使用 Runtime 的 virtual-scroll chunk 合并能力，但把合并结果重新进入 URL pipeline。

Crawler 的 Virtual Scroll 合并属于执行优化，不是业务 Coverage 真相。某些 Runtime 可能按文本指纹合并元素，这与文章 URL Identity 不是同一概念。

因此：

```text
runtime text/html dedup
 != URL Identity dedup
 != Coverage proof
```

### 8.8 Runtime Outcome Gate

请求动态能力时必须验证“实际执行结果”：

```text
feature_requested
feature_engaged
container_found
detected_mode
actions_attempted
actions_completed
waits_satisfied
harvest_rounds
unique_url_union_count
stop_reason
warnings
```

Gate：

```text
feature_requested && !feature_engaged
 -> Provider DEGRADED
 -> exhausted=false
 -> Known Gap

VIRTUAL_SCROLL && !container_found
 -> VIRTUAL_SCROLL_CONTAINER_NOT_FOUND
 -> exhausted=false

expected_runtime_mode != detected_mode
 -> INTERACTION_MODE_MISMATCH
 -> 保存 Artifact/Trace
 -> Recipe Review

crawler success=true 但 URL 无增长
 -> 进入 convergence 判断
 -> 不可直接判定 Provider exhausted
```

这可避免“页面本身抓成功，但动态能力没有真正执行”的 silent fallback。

## 9. 正文抓取与最小成本路由

### 9.1 Acquisition Planner

```text
L0 CMS/API payload
L1 HTTP
L2 Crawl4AI deterministic Browser
L3 Playwright deterministic Recipe
L4 LLM-assisted extraction / Controlled Agent Browser
```

优化目标：

```text
minimize expected_cost / expected_accepted_document_version
subject to Quality SLO and Freshness SLO
```

策略建议与生产 Release 分离，变化必须可审核、可回滚。

### 9.2 HTTP Worker

支持：

- `If-None-Match`；
- `If-Modified-Since`；
- gzip/br；
- connect/read/write 分阶段 timeout；
- redirect 上限；
- per-domain connection pool；
- `Retry-After`；
- 429/503 指数退避 + jitter；
- body size 上限；
- MIME allowlist；
- 原始 header + body hash 保存。

### 9.3 Browser Worker

Browser 进程复用，Context 按安全域隔离，Page 按 Task 短生命周期：

- 默认拦截广告、追踪、字体、视频等非必要资源；
- 默认不截图、不生成 PDF；
- 仅诊断/Golden Corpus/审核时截图；
- wait/scroll/click 来自版本化 Recipe；
- 单 Worker crawler 限流只作第二层保护，全局公平与限流由平台控制。

资源池：

```text
Browser Discovery Worker
- 长页面、多轮交互、低并发、强预算

Browser Content Worker
- 单文章、短生命周期、正文完整度优先
```

### 9.4 Browser Fallback 条件

HTTP 成功但以下条件不满足时才升级 Browser：

- 正文过短；
- text density 低；
- JSON-LD/正文 DOM 明显缺失；
- 仅 hydration shell；
- Challenge/login/cookie 模板命中；
- Source Profile 明确要求 Browser。

Browser 仍失败则 Quarantine，不无限重试。

## 11. Quality Gate、Golden Corpus 与 Drift

### 11.1 Quality Gate

至少检查：

- 标题存在；
- 正文长度；
- text density；
- boilerplate/link density；
- heading/code/table 结构；
- metadata confidence；
- 与历史版本的大幅缩水；
- 与其他页面的高度重复；
- Challenge/login/cookie/error-page 特征；
- Source 特定规则。

```text
PASS       -> 可成为 current version
QUARANTINE -> 保存，等待人工/备用 Extractor
FAIL       -> 不进入默认知识库
```

### 11.2 Golden Corpus

每个 Source 保存 3~10 个代表样本：

- 普通文章；
- 长文；
- 代码密集；
- 图片密集；
- 旧模板；
- 新模板；
- 关键动态列表页。

Runtime/Extractor/Recipe/Renderer 升级自动比较：

```text
URL yield
Runtime Outcome
正文长度
结构 block 数
semantic hash diff
quality score
browser seconds
network requests
```

### 11.3 在线 Drift Detector

典型信号：

- selector hit rate 下降；
- container_found rate 下降；
- runtime feature engaged rate 下降；
- detected_mode 分布改变；
- action completion rate 下降；
- Dynamic Listing 每轮唯一 URL yield 骤降；
- HTTP Quality 降低同时 Browser fallback 暴涨；
- 大量页面变成相同 Cookie/Login/Challenge；
- Sitemap/Archive 路径模式变化；
- title/author/time 元数据缺失率上升；
- Source 平均正文长度突然缩水。

处置：

```text
Drift Alert
 -> Source DEGRADED / 保护性降速
 -> 保存失败 Artifact + Runtime Outcome
 -> Golden Corpus + 最近样本回放
 -> 生成 Profile/Recipe 候选
 -> Compare Coverage / Quality / Cost / Outcome
 -> Approval
 -> New Release
```

如果同一 Runtime Release 后多个不同 Source 同时出现 feature 未生效或 mode 突变，优先判定平台回归。

## 12. 增量同步与版本管理

### 12.1 增量发现

按 Source 能力组合：

```text

Sitemap lastmod

```

使用 overlap window，例如从上次 watermark 往前回退 24 小时，通过 URL 去重吸收重复。

### 12.2 Dynamic Listing 增量

```text
打开列表顶部
 -> harvest
 -> normalize/dedupe
 -> 继续动作并验证 Runtime Outcome
 -> 遇到 overlap 时间边界
    或连续 K 个已知 URL + N 轮无 unseen URL
 -> 停止
```

Browser session 不作为 checkpoint。PostgreSQL 保存 watermark、Observation、Provider cursor、Recipe/Runtime Release、Runtime Outcome 与 Coverage Evidence。

### 12.3 已知 URL 复检

```text
Conditional GET
 -> 304: 更新时间戳，不创建 Version
 -> 200 + body hash 相同: 不 Extract
 -> body hash 变化: Extract -> IR
 -> semantic hash 相同: 不创建 Version
 -> semantic hash 变化: 新 Document Version -> Quality -> Projection rebuild
```

### 12.4 删除与 URL 迁移

不能把一次 404 当永久删除：

- 404/410 连续 N 次；
- 多个增量 run 不再观察到；
- Sitemap/CMS 明确消失；
- redirect 指向新 canonical；
- grace period 后再标记 DELETED/MOVED。

保留旧 Version 和历史 URL Identity。

### 12.5 周期性深度校验

- 周/月级 Provider cross-check；
- 随机历史 URL Verify；
- Sitemap 全量 diff；
- 低频 Archive/Prefetch gap scan；
- Coverage 时间分布空洞检测；
- Dynamic Runtime Outcome 异常样本复跑。

## 13. 调度、可靠性与公平性

### 13.1 Transactional Outbox

```text
DB transaction:
  update business state
  insert outbox event
commit

Outbox Relay -> Redis Streams
```

Worker 完成后先写 PostgreSQL 再 ACK，Redis 丢失可从事实重建运输层。

### 13.2 Lease + Fencing Token

Worker claim task：

```text
lease_owner
lease_until
fencing_token++
```

所有最终写检查 fencing token，旧 Worker 恢复后不能覆盖新结果。

### 13.3 Retry 分类

```text
RETRYABLE:
timeout / connection reset / 429 / 503 / browser crash

RECIPE_OR_SOURCE:
selector timeout / container not found / interaction mode mismatch /
feature not engaged / template drift / no article links

PERMANENT:
out-of-scope / unsupported MIME / explicit denied
```

指数退避 + jitter，超过 max_attempts 进入 DLQ。

### 13.4 Weighted Fair Scheduler

- Incremental > Verify > Backfill；
- Source 轮转；
- 大站分片；
- per-domain concurrency；
- Browser/HTTP 独立资源池；
- aging 防永久饥饿。

### 13.5 Global Domain Admission

```text
Redis token bucket  -> requests/sec
Redis semaphore     -> concurrent requests
DB policy           -> Source truth
```

429/503/Retry-After 自动降速并逐步恢复。Crawler 内部限速只作第二层保护。

### 13.6 Backpressure

监控：

- stream lag；
- oldest task age；
- Browser pool saturation；
- object storage upload latency；
- Extract/index throughput。

压力高时优先保证 Incremental Freshness，暂停低优先级 Deep Crawl/Backfill。

- screenshot 默认不保存，仅用于失败诊断、Golden Corpus 和人工审核。

### 18.4 容量估算

Backfill 前由 Probe 估算：

```text
estimated_urls
avg_raw_bytes
avg_ir_bytes
asset_download_ratio
browser_ratio
avg_browser_seconds
```

按 P50/P95 给出网络、存储与 Browser 成本，避免 1000 站点无预算直接开跑。

## 23. 最终验收标准

### 23.1 Coverage

随机抽取代表 Source，要求：

- Sitemap/CMS/Archive Provider 有 exhaustion evidence；
- 动态列表有逐轮 URL 增长曲线与 exhaustion reason；
- 动态列表请求的交互能力有 `feature_engaged/container_found/detected_mode/actions_completed` 等 Outcome 证据；
- crawler success 但 feature 未生效时不得被判定为 exhausted；
- bounded Provider 达预算时明确 Known Gap；
- Provider 交叉后历史时间分布无无法解释的大空洞；
- crawler 内部文本/HTML 去重不作为文章身份或 Coverage 主键。

### 23.2 Freshness

- HOT Source 新文章在目标时间进入 PASS Markdown；
- Backfill 期间 Freshness SLO 不显著退化；
- watermark 丢失后可通过 overlap/URL Observation 恢复。

### 23.3 Quality

- Cookie/Login/Challenge 页面不进入 current version；
- 代码块/标题/发布时间等结构在 Golden Corpus 中稳定；
- Runtime/Extractor 升级无明显 Quality 回归。

### 23.4 Reliability

- Worker 强杀后 lease/fencing 自动恢复；
- Redis 清空后可从 PostgreSQL 重建任务；
- 重复投递不产生重复 Document Version；
- DLQ 可定位并重放。

### 23.5 Runtime Compatibility & Outcome

- 所有 ACTIVE Recipe 能针对目标 Runtime 编译；
- `trigger -> wait -> harvest` 等语义升级后保持一致；
- 不支持能力时 Release 必须失败，而非静默降级；
- Runtime 声称支持的关键能力在 Golden Corpus 上必须产生符合预期的 Outcome；
- Container 未找到、Mode 不匹配、Feature 未 engaged 时 Provider 不能宣称 Coverage 完成；
- 任意 Render Artifact 能定位 `recipe_release + compiler_version + runtime_release + capability_hash + compiled_plan_hash + runtime_outcome`。

### 23.6 Cost

- 每 Source/accepted version 成本可归因；
- Browser 使用率和秒数可观察；
- 预算达到阈值时能降级非关键 Provider，不产生无界成本。

## 24. 最终方案结论

平台以 **PostgreSQL + Object Storage 为事实层，Redis Streams 为运输层，配置化 Discovery/Extraction Recipe 为扩展面，HTTP-first/Browser-last 为成本策略，Canonical IR 为内容事实，Quality/Coverage/Release 为正确性护栏**。

对于 1000+ 站点，可扩展性的核心来自三层解耦：

```text
站点差异
 -> Source Profile + Semantic Recipe

工具/版本差异
 -> Runtime Capability Contract + Recipe Compiler + Adapter

单次实际执行差异
 -> Runtime Outcome Contract + URL Observation + Coverage Evidence
```

因此新增第 1001 个站点主要是 Probe、配置、Golden Corpus 和审核；升级 Crawl4AI/Playwright/Chromium 时无需把数百站点 Recipe 按参数名人工重写。动态栏目、Infinite Scroll、Load More 和 Virtual Scroll 统一通过：

```text
Dynamic Listing Provider
 -> Semantic Recipe
 -> Compiled Plan
 -> Runtime Outcome
 -> URL Observation
 -> Coverage Evidence
```

进入历史全量与增量同步。

必须坚持一个关键边界：**Crawler 的 success、最终 DOM、内部文本去重和 Runtime Capability 都不能单独证明业务 Coverage。** 真正的 Coverage 来自逐轮实际观察并规范化后的文章 URL、可解释的 Provider 边界，以及证明动态交互确实按语义发生的 Runtime Outcome。

最终形成可恢复、可审计、可扩展的知识供应链：

```text
Discover
 -> Prove Runtime Outcome when needed
 -> Prove Coverage
 -> Fetch
 -> Preserve Fact
 -> Extract IR
 -> Quality Gate
 -> Version
 -> Render Markdown
 -> Index/RAG
 -> Incremental Verify
 -> Drift/Release Governance
```

这套边界使知识库长期正确性不绑定某个 crawler 的临时参数、DOM 合并逻辑或文本指纹算法，并能在站点数量、页面模板和抓取运行时持续变化时稳定演进。
