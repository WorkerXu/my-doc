# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站、公开 Newsletter** 的长期知识库采集平台，可平滑扩展到数千站点、百万级文章。

系统需要满足：

1. **全历史回填**：尽可能完整发现并抓取每个已批准 Source 的全部历史文章；
2. **持续增量同步**：发现新文章、正文更新、URL 迁移、删除与重发布；
3. **稳定 Markdown**：Markdown 由可追溯 Raw Artifact 经过确定性抽取、质量门禁、Canonical IR 后生成；
4. **低成本扩站**：新增网站优先通过 Source Profile、Provider、Traversal Policy、Recipe 配置完成，而不是复制站点脚本；
5. **Web 可运营**：支持 Source 接入、Backfill、Incremental、Coverage、Frontier、失败诊断、暂停恢复、质量、版本、成本与审计；
6. **可搜索与 RAG**：支持关键词、向量、混合检索，并能回溯原文与版本；
7. **可观测、可恢复、可重放**：任意 URL、任务、Artifact、Markdown 均可解释来源、版本和执行路径；
8. **渐进扩展部署**：开发期 Docker Compose，生产期按队列和 Worker 类型水平扩容；
9. **采集主链不依赖 LLM**：LLM 仅用于可选增强，不参与 Coverage Truth、URL Identity、Canonical URL 的最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 能解释已发现 URL、Provider、Frontier、Known Gap 与停止原因；
- **Freshness**：新文章从发布/发现到 PASS Markdown 的延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文完整率、噪声率、代码块/表格/列表保留率、截断率；
- **Reliability**：任务成功率、Retry、DLQ、Queue Age、Checkpoint Resume 成功率；
- **Browser Efficiency**：HTTP 命中率、Browser avoided、Browser recovery、每文档 Browser 成本；
- **Identity Quality**：重复文章误合并/漏合并率；
- **Traceability**：任意 Markdown 可回溯 Source、URL、Artifact、Extractor、Quality、Renderer Release；
- **Cost**：按 Source、Run、Queue Class、每 1000 篇 PASS 文档统计抓取、Browser、存储、索引和模型成本。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不把 HTTP 200、DOM 很长或 crawler success 直接视为正文正确；
- 不把搜索引擎结果数、Deep Crawl 页数、`max_pages` 当历史完整性证明；
- 不把 Crawl4AI 即时 Markdown、LLM 摘要或改写直接作为 Canonical Markdown；
- 不因 URL 曾抓过就永久停止复检；
- 不把 Redis、Browser Session、Crawler Cache、Visited Set、Search Index 当业务真相；
- 不允许优先级、Scorer 或相关性阈值永久删除潜在历史文章；
- 不默认对所有文档构建 GraphRAG。

## 2. 核心设计原则

1. **Coverage First**：先建立 URL Inventory，再批量抓正文；
2. **Authoritative First**：CMS/API、Sitemap、RSS/Atom、Archive 优先；
3. **Deep Crawl Is Gap Provider**：站内深度抓取用于补洞，不作为 Coverage Truth；
4. **Search Is Gap Only**：外部搜索只用于补洞与发现新 Source；
5. **Discovery / Fetch / Extract / Quality / Projection 分离**；
6. **HTTP First, Browser Last**：Browser 是受治理慢路径；
7. **Snapshot First**：先保存不可变 Artifact，再抽取与清洗；
8. **Canonical IR First, Markdown as Projection**；
9. **Recipe, Not 1000 Site Scripts**；
10. **Stable Identity**：Source、URL、Artifact、Document、Version 使用稳定 ID；
11. **Idempotent + Recoverable**：任务使用幂等键、lease、fencing token、checkpoint；
12. **Fair by Default**：大站 Backfill 不能饿死 Incremental 和小站；
13. **Bounded Concurrency Everywhere**：禁止无界 asyncio gather、Browser Context、LLM fan-out；
14. **No Silent Degradation**：截断、预算耗尽、降级、过滤、跳过必须显式记录原因；
15. **Release Everything That Changes Results**：Profile、Traversal、Recipe、Runtime、Extractor、Quality、Renderer、Embedding、Rank 全部版本化；
16. **Priority Means When, Not Whether**：优先级决定何时处理，不决定是否永久保存；
17. **Observation Before Selection**：从页面观察到链接后先保存事实，再做 Filter/Score/Budget 选择；
18. **Persistent Frontier, Not In-Memory Traversal**：BFS/DFS/Best-First 的业务语义进入数据库；
19. **Runtime Checkpoint != Business Checkpoint**：第三方 crawler resume state 只是执行优化，PostgreSQL 才是恢复真相；
20. **Same Semantics, Different Topology**：单机 Pilot 与生产集群共享状态机、模型和任务协议。

       +------- Observation -> Persistent URL Inventory / Frontier -+
                                      |

                                      |

                              /              \

                              \              /

### 3.1 真相边界

**PostgreSQL + Object Storage 是业务真相。**

- PostgreSQL：Source、Provider、URL Identity、URL Observation、Crawl Frontier、Task、Cursor、Coverage、Quality、Document、Version、Release、Audit；
- S3/MinIO：Raw HTML、MHTML、截图、Trace、Candidate、IR、Markdown、PDF、Enrichment；
- Redis Streams：任务运输、Consumer Group、背压，不保存不可替代业务状态；
- OpenSearch / pgvector：可重建 Serving Projection；
- Crawl4AI state、Playwright Session、Worker 内存：易失执行状态。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST API、Command、Schema 校验；
- **PostgreSQL**：Truth Store、任务状态、Coverage、Frontier、版本、审计；
- **Redis Streams**：任务队列、Consumer Group、Backpressure；
- **Redis Lua Token Bucket / Semaphore**：跨 Worker 域名限流和资源令牌；
- **React / Next.js + TypeScript**：Web 管理后台；
- **OpenTelemetry + Prometheus + Grafana + Structured Logging**：Trace / Metric / Log；
- **S3/MinIO**：不可变对象存储；
- **Vault/KMS/Secret Manager**：凭据引用。

### 4.2 Discovery / Fetch

- **httpx/aiohttp**：robots、Sitemap、Feed、CMS API、Conditional GET、普通网页；
- **Crawl4AI**：Browser Render、Deep Crawl Prefetch、动态链接发现、简单交互；
- **Playwright Python**：复杂多步、有状态、需要 Step 级恢复的交互；
- **SearXNG / 合规 Search API Adapter**：External Search Gap、新 Source Candidate；
- **PyMuPDF/pdftotext**：PDF；扫描件进入 OCR 慢路径；
- **Python email/MIME parser**：Newsletter Inbox Provider。

### 4.3 Extraction / Search

- **Trafilatura**：Generic Main Content Candidate；
- **lxml/BeautifulSoup**：DOM/XPath、Metadata、DOM Repair；
- **JSON-LD/OpenGraph/Microdata**：结构化元数据；
- **CSS/XPath/Regex Recipe**：确定性正文与字段抽取；
- **SimHash/MinHash**：近重复候选；
- **OpenSearch BM25 + pgvector + RRF**：混合检索；
- **可选 reranker / LLM**：只在 Canonical 数据之后运行。

### 4.4 Release 冻结

必须记录：

```text

provider_adapter_release
traversal_policy_release
interaction_recipe_release
extractor_release
quality_release
identity_release

embedding_release

```

任何改变结果的升级必须经过 Golden Replay / Offline Eval，必要时 Canary。

## 6. Source 接入流程

新增网站先自动探测，再人工确认。

### 6.1 自动探测

```text
1. robots.txt
2. sitemap index / sitemap.xml
3. RSS / Atom
4. CMS 特征：WordPress/Ghost/Medium/Substack/自建 API
5. 首页与归档页结构
6. URL pattern
7. 是否需要 JS Render
8. 是否存在分页、年份归档、标签、分类
9. Deep Crawl 浅层 Prefetch
```

### 6.2 Source Profile 草稿

```yaml
source:
  canonical_domain: example.com
  approved_domains:
    - example.com
  providers:
    - sitemap
    - rss
    - archive
    - deep_crawl
  fetch_route:
    default: http
    browser_patterns:
      - /interactive/*
  traversal:
    mode: bfs
    max_depth: 3
    max_pages_per_run: 5000
    include_external: false
    prefetch: true
    threshold_policy: priority_only
  extraction:
    generic: trafilatura
    article_selector: null
  incremental:
    rss_interval: 10m
    sitemap_interval: 6h
    home_probe_interval: 30m
```

人工在 Web Admin 审核后发布 immutable release。

### 6.3 Seed 安全校验

Deep Crawl 的起始 URL 不得仅依赖 crawler FilterChain 校验。控制面在创建 Run 前必须验证：

```text
seed 属于 approved_domains
scheme 为 http/https
Source enabled
robots/access policy 已计算
Traversal Policy 已发布
凭据/代理策略合法
```

## 7. Discovery 与 Coverage

### 7.1 Provider 优先级

```text
CMS/API
 -> Sitemap
 -> RSS/Atom
 -> Archive/Pagination
 -> HTML Listing
 -> Deep Crawl Prefetch
 -> External Search Gap
```

高优 Provider 的结果不能阻止其它 Provider 做交叉验证。

### 7.2 Coverage Evidence

每个 Provider Run 记录：

```text
provider
cursor / page / time_partition
observed_count
new_url_count
existing_url_count
admitted_count
deferred_count
rejected_count
stop_reason
known_gap
started_at
finished_at
```

停止原因：

```text
FRONTIER_EMPTY
CURSOR_END
TIME_PARTITION_COMPLETE
MAX_DEPTH
MAX_PAGES
BUDGET_EXHAUSTED
RATE_LIMITED
CANCELLED
ERROR
```

`MAX_PAGES`、`MAX_DEPTH`、`BUDGET_EXHAUSTED` 不能标记为 Coverage Complete。

### 7.3 URL Inventory

Discovery 的目标是先建立 Inventory：

```text
OBSERVED
 -> CLASSIFIED
 -> QUEUED
 -> FETCHED
 -> EXTRACTED
 -> PASS
```

这样才能先知道某站大约是 500、5 万还是 50 万 URL，再决定 Backfill 资源配额。

### 7.4 Coverage 完成判定

Coverage Complete 不能是一个布尔猜测，而应由证据组合：

- CMS/API cursor 到尾；
- Sitemap 全部分片完成；
- RSS 用于新鲜度交叉检查；
- Archive / Pagination 到尾；
- Deep Crawl Frontier 为空或只剩明确 policy reject；
- 没有未解释 `DEFERRED_BUDGET`；
- Known Gap 为空或被人工接受；
- 多 Provider URL 集合差异处于阈值内。

## 8. Deep Crawl 与 Traversal Policy

### 8.1 角色定位

Deep Crawl 只用于：

- 发现 Sitemap/RSS/API 漏掉的站内 URL；
- 发现归档、分页、标签、年份入口；
- 发现 JavaScript 渲染后才出现的链接；
- 验证导航结构与 URL pattern；
- 定期执行 Coverage Gap 扫描。

不用于证明“历史已经完整”。

### 8.2 两阶段 Prefetch

```text
Phase A: Prefetch Discovery
- 获取 HTML / links / minimal metadata
- 记录 from_url -> to_url Observation
- 不做 Markdown
- 不做媒体下载
- 不做全文增强
- 快速建立 URL Inventory

Phase B: Full Fetch
- 仅处理 admitted article URL
- 受限并发
- 保存 Raw Artifact
- Extraction / Quality / IR / Markdown
```

对 1000 站历史回填，这是默认模式。

### 8.3 Observation Before Selection

这是 Deep Crawl 的关键平台化规则。

执行顺序必须是：

```text
raw href
-> normalize
-> persist Link Observation
-> policy classify
-> score
-> admission decision
-> persistent frontier
-> scheduler
```

而不是：

```text
filter/score/max_pages
-> 只保存被选中的 URL
```

原因是第三方 crawler 的 visited/seen、`score_threshold`、`max_pages` 都可能在一次运行内裁掉链接；如果 Observation 没有先落库，就无法区分“从未发现”和“发现但本轮未处理”。

### 8.4 BFS / DFS / Best-First

- **BFS**：Backfill 默认探测策略，优先覆盖浅层导航、分页与归档；
- **DFS**：只在路径深度结构明确的 Source Recipe 中启用；
- **Best-First**：固定预算下优先处理更像文章、归档、分页的 URL。

Best-First 分数默认只映射为 priority：

```text
score -> priority
```

除明确 deny rule 或 focused job 外，不因低分永久删除 URL。

### 8.5 Traversal Policy Release

```yaml
traversal:
  mode: bfs
  max_depth: 3
  max_pages_per_run: 10000
  include_external: false
  prefetch: true
  filter_chain:
    allow_domains:
      - example.com
    include_patterns:
      - /blog/*
      - /archive/*
    exclude_patterns:
      - /login/*
      - /search/*
  scorer:
    type: deterministic_path
    weights:
      article_pattern: 5
      archive_pattern: 3
      pagination_pattern: 2
      query_explosion: -8
  threshold_policy: priority_only
```

每个 Observation 记录对应 `traversal_policy_release_id`。

### 8.6 `max_pages` 的业务解释

Crawler 的 `max_pages` 是执行保护，不是平台 URL 预算或 Coverage 证明。平台单独统计：

```text
observed_count
attempted_count
success_count
failed_count
admitted_count
deferred_budget_count
```

如果本轮容量不足，剩余候选进入 `DEFERRED_BUDGET`，而不是消失。

### 8.7 Runtime Checkpoint 与 Business Checkpoint

Crawl4AI 的 `resume_state` / `on_state_change` 可用于恢复单次 traversal，但不与平台 Artifact、Observation、Task 状态形成同一事务。

因此：

```text
Crawl4AI resume_state = 执行优化
PostgreSQL crawl_frontier = 业务恢复真相
S3 Artifact = 抓取事实
Transactional Outbox = 状态与消息一致性
```

Worker 恢复时做 reconciliation：

```text
crawler pending
vs DB READY/LEASED
vs artifact existence
```

以数据库为准。

### 8.8 Crawl4AI Adapter 与兼容性闸门

业务代码不得直接依赖 Crawl4AI 内部状态，统一经 `DeepCrawlAdapter`：

```text
validate_seed()
build_filter_chain()
build_scorer()
build_strategy()
map_result_to_observations()
reconcile_checkpoint()
translate_stop_reason()
emit_metrics()
```

Adapter 必须：

- 每个 Strategy 显式创建独立 FilterChain；
- 不把 crawler visited/seen 映射为 DONE；
- 不把 crawler pages_crawled 当 attempted count；
- 不依赖起始 URL 绕过 Filter 的行为；
- 屏蔽单标签 hostname、过滤默认值等第三方版本差异；
- 版本升级先执行 Golden Replay。

### 8.9 Crawl Graph Evidence

保存 `from_url -> to_url` 可用于：

- 解释 URL 来源；
- 识别分页链；
- 发现孤立文章；
- 比较 Sitemap 与站内链接覆盖差异；
- 发现导航结构变化；
- 审计“为什么 URL 被延迟/过滤”。

## 9. Fetch Router

### 9.1 路由原则

```text
HEAD/HTTP probe
  |
  +-- 静态可用 ----------> httpx
  |
  +-- JS 内容型 ---------> Crawl4AI
  |
  +-- 复杂有状态交互 ----> Playwright
  |
  +-- PDF --------------> PDF Pipeline
```

默认 HTTP First。

### 9.2 Route Decision

```text
route_decision
- url_id
- route
- reason
- route_release_id
- confidence
```

路由决策必须可解释、可重放。

### 9.3 Browser 治理

- Browser Worker 独立队列；
- 每域名 Browser 并发上限；
- 全局 Browser Context 令牌上限；
- 监控 Worker RSS / Chromium process；
- 超时、导航失败、JS 错误进入明确 reason code；
- Backfill 不得无限占用 Browser；
- 可自动从 Browser 成功结果学习 HTTP 可替代路径，但发布为新 route release 后才生效。

## 10. 调度、并发与背压

### 10.1 队列类别

```text
incremental_high
incremental_normal
backfill_normal
backfill_bulk
discovery_prefetch
browser_slow
repair
reindex
```

### 10.2 公平调度

采用 Weighted Fair Queue / Deficit Round Robin 思路：

- Incremental 有最低保证；
- 单 Source 每轮最多固定 slice；
- 大站不能独占队列；
- Browser 与 HTTP 使用不同资源预算；
- Frontier priority 影响先后，不影响永久保留资格。

### 10.3 Domain Admission

每域名维护：

```text
max_concurrency
requests_per_second
burst
retry_after_until
error_rate
latency_ewma
```

调度器根据 429/503/超时动态降速。

### 10.4 幂等、Lease 与 Fencing Token

```text
crawl_task
- id
- idempotency_key
- state
- lease_owner
- lease_until
- fencing_token
- attempt
- next_retry_at
```

Worker 提交状态时必须携带 fencing token，避免旧 Worker 覆盖新执行结果。

执行语义接受 at-least-once，通过：

```text
unique task key
+ content hash
+ immutable artifact
+ transactional state transition
+ fencing token
```

实现幂等副作用。

## 11. Raw Snapshot 与不可变 Artifact

每次有效 Fetch 先保存原始事实：

- Response headers；
- final URL / redirect chain；
- Raw HTML；
- 必要时 MHTML / screenshot / network trace；
- Content-Type；
- ETag / Last-Modified；
- payload SHA-256；
- runtime release。

对象路径：

```text
artifacts/{source_id}/{yyyy}/{mm}/{artifact_id}/raw.html
artifacts/{source_id}/{yyyy}/{mm}/{artifact_id}/meta.json
```

Artifact 不覆盖，只新增版本。

## 12. Extraction Portfolio

同一页面允许多个候选抽取器：

```text
Candidate A: JSON-LD / structured data
Candidate B: Site Recipe CSS/XPath
Candidate C: Trafilatura
Candidate D: DOM heuristic repair
```

统一输出 Candidate Schema：

```text
title
author
published_at
updated_at
language
main_blocks[]
code_blocks[]
tables[]
links[]
images[]
metadata
```

候选抽取器只能生成 Candidate，最终需经过 Quality Gate。

### 12.1 Recipe 设计

Recipe 只描述差异，不复制 Worker：

```yaml
article:
  title: h1.post-title
  body: article.post-content
  remove:
    - .newsletter-box
    - .share-buttons
  published_at:
    selector: time
    attr: datetime
```

Recipe 发布为 immutable release，并支持 Golden URL 回放。

## 13. Quality Gate 与 Repair

### 13.1 基础质量信号

- 标题存在；
- 正文字符/词数合理；
- 主体文本密度；
- 导航/页脚噪声比例；
- 与 Raw HTML 长度/结构的相对完整性；
- 代码块数量与 DOM 对齐；
- 表格/列表是否异常丢失；
- 是否出现登录页、错误页、Cookie 页、CAPTCHA；
- 是否疑似截断；
- published_at 是否可信。

### 13.2 决策

```text
PASS
REPAIR
REJECT_NON_ARTICLE
RETRY_FETCH
MANUAL_REVIEW
```

`REPAIR` 可尝试：

1. 换 Extractor；
2. 使用 Source Recipe；
3. HTTP -> Browser；
4. Browser -> Playwright Recipe；
5. DOM repair；
6. 必要时人工修 Recipe。

LLM 不作为正文事实修复器。

## 15. Document Identity、去重与版本

### 15.1 URL Normalization

至少处理：

- fragment；
- tracking params；
- query 参数排序/白名单；
- host case / default port；
- trailing slash 规则；
- redirect final URL；
- canonical tag。

### 15.2 Identity 层级

```text
Raw URL
-> Normalized URL Identity
-> Canonical URL Candidate
-> Document Identity
-> Document Version
```

不能仅用 URL 字符串作为 Document ID。

### 15.3 重复判定

使用：

- canonical/redirect；
- exact content hash；
- SimHash/MinHash；
- title + published_at + source；
- 人工 override。

近重复只产生候选，不自动跨站强合并。

### 15.4 内容更新

```text
same document identity + different canonical content hash
-> new document_version
```

旧版本不覆盖，保留 provenance。

## 20. 恢复与故障处理

### 20.1 故障分类

```text
NETWORK_TRANSIENT
RATE_LIMIT
ROBOTS_DENY
WAF_OR_CAPTCHA
BROWSER_CRASH
OUT_OF_MEMORY
PARSER_ERROR
QUALITY_FAIL
POLICY_REJECT
CHECKPOINT_MISMATCH
BUG
```

### 20.2 Retry

- 网络、429、503：指数退避 + jitter；
- 429 尊重 Retry-After；
- Browser crash：有限次数恢复；
- 解析失败：尝试其它 extractor，不无限重抓；
- policy reject：不 Retry；
- 代码 bug：DLQ + release 定位。

### 20.3 Crash Recovery

平台恢复顺序：

```text
1. lease 到期
2. 新 Worker 持更大 fencing token 接管
3. 查 DB task/frontier
4. 查 Artifact 是否已存在
5. 对比 crawler runtime checkpoint
6. reconciliation
7. 从安全边界继续
```

不追求网络层 exactly-once，追求业务副作用幂等。

## 21. Crawl4AI 升级 Golden Gate

每次升级 Crawl4AI/runtime 必须至少回放：

1. 自链接首页不重复/无限抓取；
2. fragment、trailing slash、query 变体；
3. 每个 Strategy 的 FilterChain 实例隔离；
4. 单标签 hostname 测试环境行为；
5. `max_pages` 小于一次发现链接数时，未选 URL 仍保留 Observation/Deferred；
6. BFS batch/stream 最终平台 Frontier 语义一致；
7. DFS crash/resume 不丢平台 READY URL；
8. Best-First 同分 URL 稳定排序；
9. exploration 模式低分 URL 不被永久 prune；
10. cancel 后 lease 可释放/超时接管；
11. failed URL 能由平台 Retry，不受 crawler visited 阻止；
12. old checkpoint 与 new runtime 不兼容时拒绝盲目 resume；
13. `include_external=false` 时外链不扩张 Source Scope；
14. HTTP/Browser Route 与 Extraction 的 Golden URL 结果不发生未解释漂移。

升级结果写入 release record；不通过则禁止发布。

## 22. 安全、合规与治理

- robots/access policy 缓存但定期刷新；
- per-domain 限速；
- User-Agent 和联系方式可配置；
- 凭据只存 Secret Manager 引用；
- 禁止把 Cookie/Token 写日志、Artifact metadata 或 Markdown；
- SSRF 防护：DNS/IP 校验，默认禁止内网、metadata endpoint、file scheme；
- redirect 每跳重新验证目的地址；
- 下载大小、压缩比、Content-Type 有上限；
- 只采集已批准 Source；
- 外链 observation 不自动扩大 Scope；
- 所有人工 override 有 Audit Log。

## 26. 最终方案判断

本系统不应把“一个强大的爬虫”当成完整知识库平台，而应把爬虫能力拆入可治理的数据链路：

```text
权威发现
+ Deep Crawl 补洞
+ Observation 先落库
+ 持久 Frontier
+ 公平调度
+ HTTP First / Browser Last
+ 不可变 Artifact
+ 多候选抽取
+ 质量门禁
+ Canonical IR
+ Markdown 投影
+ 版本化增量
+ Web 运营与可观测
```

Crawl4AI 的 BFS/DFS/Best-First、FilterChain、Scorer、Prefetch、Resume、Cancel 都非常有价值，但必须限制在 **Deep Crawl Gap Provider / Browser Discovery Engine** 的角色内。

最重要的可靠性边界是：

> **链接一旦被观察到，先作为事实保存；优先级决定何时抓，不决定是否存在；第三方 crawler checkpoint 负责执行效率，平台 PostgreSQL Frontier 负责业务正确性。**
