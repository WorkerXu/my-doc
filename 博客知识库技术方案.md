# 博客知识库技术方案

## 1. 建设目标与规模

建设一个长期运行、可横向扩展、可审计、可回放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客、技术文档站和公开 Newsletter，尽可能抓取完整历史文章并清洗为稳定 Markdown；后续能够持续新增网站，并支持低成本增量同步、版本追踪、全文/向量/图谱检索、Web 管理、质量审计、单 URL 手工摄取、离线重处理和 AI 派生分析。

设计规模：

- 1000+ Source，后续扩展到数千；
- 百万级 Document / Document Version；
- 数百万到千万级 URL Observation；
- 千万级 Chunk / Embedding；
- HTML、PDF、Markdown、TXT、JSON/API、RSS/Atom/JSON Feed；
- 中英日韩等多语言；
- HTTP 为默认抓取路线，Browser 为受控 fallback；
- CMS API、Sitemap、Feed、Archive、Docs TOC、Common Crawl、Deep Crawl 等多入口历史发现；
- PostgreSQL + Object Storage 保存事实，Markdown、Structured Record、Chunk、Embedding、全文索引、向量索引、Graph、AI Insight、Dashboard Read Model 均作为可重建 Projection。

平台必须能够回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已经基本覆盖；
2. URL 从哪里被发现、如何规范化、为何被过滤或放行、经过哪些跳转、最终抓到了什么；
3. 为什么使用 HTTP、API、文件流、Crawl4AI Browser 或 Playwright；
4. 一个 Markdown 来自哪个 Snapshot、Extractor、Schema、Release 和 Document Version；
5. 源站变化后哪些内容真的发生变化，哪些派生物需要重建；
6. Worker 崩溃或批任务部分失败后如何恢复且不丢成功项；
7. 新增站点、规则、模型、索引、图谱策略时如何灰度、回放和回滚；
8. Web 管理中的暂停、重跑、重新分析、切 Release 等动作由谁发起、是否幂等、是否经过 RBAC；
9. BM25、Vector、Graph 三条召回链路是否严格遵守 SOURCE/DOCUMENT/VERSION/ACL Scope；
10. Graph 是否真的对一次查询产生了增量贡献，而不是仅仅“已经建图”；
11. Dashboard 指标处理到什么 watermark、覆盖多少 Source、使用哪一版指标定义。

## 2. 核心设计原则

1. **Config First**：普通站点靠 Source / Site Profile / Release 接入，不修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence、cursor 和 exhaustion reason 证明，队列为空不代表完整。
3. **Authoritative First**：CMS/API、Sitemap、Feed、Archive 优先，Deep Crawl/Common Crawl 主要用于补洞。
4. **Discovery Before Fetch**：先发现、规范化、过滤、分类、去重 URL，再抓正文。
5. **Filter With Evidence**：URL Filter 区分 HARD/SOFT，但任何过滤都保存 Observation、规则和 reason。
6. **URL Is Locator**：资源类型由响应 MIME、签名、跳转和站点规则共同判断，不能只看后缀。
7. **HTTP First, Browser Last**：Browser 只处理动态发现、动态正文或质量 fallback。
8. **Recipe, Not Site Code**：动态交互、Filter、结构化抽取均声明式、版本化、可回放。
9. **Bounded Crawl**：Deep Crawl、Browser、LLM Extraction、Graph Expansion 都有预算和终止条件。
10. **Snapshot First**：先保存不可变网络事实，再做抽取、清洗、Schema、Graph、AI。
11. **IR First, Markdown as Projection**：Canonical IR / Document Version 是内容事实层，Markdown 可确定性重建。
12. **Structured Record Is Projection**：结构化抽取不覆盖 canonical 内容。
13. **Graph Is Projection**：实体、关系、事实、社区和 GraphRAG 来自 Document Version，不成为唯一事实源。
14. **Literal Is Not Entity by Default**：日期、分数、数量、配置值、版本字符串等标量默认建 Statement/Literal，不制造全局“伪实体”。
15. **Hard Record Boundary**：Chunk、Embedding、Graph Extraction 不跨 Document Version 或 Structured Record 硬边界。
16. **Provenance Before Activation**：没有 Document/Chunk Evidence 的 Graph Relation/Statement 不进入 ACTIVE Graph。
17. **Graph Built != Graph Valuable**：是否启用 Graph Retrieval 由增量检索收益、延迟和成本共同决定。
18. **LLM Is Projection, Not Truth**：LLM Extraction/Analysis 失败不阻塞 Source Sync。
19. **Stable Identity**：Document、Version、Chunk、Embedding、Graph Entity/Relation/Statement、Analysis 身份稳定且 release-aware。
20. **Release Everything**：影响结果的 Filter、Recipe、Schema、Extractor、Ontology、Model、Prompt、Graph、Metric、Index、Runtime 全部版本化。
21. **Idempotent + Recoverable**：任务有幂等键、lease、fencing、checkpoint、retry、partial success。
22. **Stream and Commit Per URL**：批任务按 URL 独立提交，一个失败项不回滚其他成功项。
23. **One Durable Task System**：PostgreSQL durable state + Transactional Outbox + Redis Streams 是唯一业务任务体系。
24. **Async Command API**：抓取、解析、Embedding、Graph、AI、重建等长任务统一使用 202 + durable command ID。
25. **Projection Readiness Explicit**：Canonical、Markdown、Structured、Chunk、Embedding、Graph、AI、Index、Dashboard 状态分别表达。
26. **Hybrid Retrieval by Default**：BM25 + Vector 是基线，Graph 是按需启用的第三召回通道，Reranker 可降级。
27. **Hard Scope Filter**：SOURCE/DOCUMENT/VERSION/ACL Scope 必须下推到所有召回通道和 Graph expansion。
28. **Generation Instead of Destructive Rebuild**：全文、向量、Graph 新版本后台构建、验证、原子切换。
29. **Dashboard Is Read Model**：Dashboard 读取可重建聚合，不把缓存、WebSocket 或 Worker 内存当真相。
30. **Security on Every Hop**：起始 URL、Redirect、Browser navigation 每跳重新做 SSRF/Egress/Scope 校验。
31. **Benchmark Before Switch**：Filter、Extractor、Analyzer、Embedding、Graph、Retrieval、Metric 等升级先固定回归再激活。

## 4. 技术选型

### 4.1 控制面

- FastAPI + Pydantic：REST/Command API、Schema 校验、内部服务接口；
- PostgreSQL：Source、Profile、Run、Task、Coverage、Observation、Snapshot、Document、Version、Release、Audit、Outbox、Graph metadata；
- Transactional Outbox：保证数据库事务与异步消息发布的一致性；
- Redis Streams：consumer group、retry、backpressure，只做任务运输；
- React/Vue + TypeScript：生产 Web 管理台；
- Docker/Kubernetes：隔离不同 Worker 类型并弹性扩缩容。

### 4.2 抓取与解析

- HTTPX/aiohttp：静态 HTML、Feed、Sitemap、API、Conditional GET、Range GET；
- Crawl4AI：URL Seeding、Deep Crawl、Browser Interaction、Markdown/Structured Extraction Adapter；
- Playwright：复杂 JS 页面和特殊交互 fallback；
- lxml/BeautifulSoup/CSS/XPath/Regex：确定性抽取；
- Trafilatura/Readability：通用正文候选；
- PDF Parser + OCR fallback；
- S3/MinIO：raw response、HTML、Rendered DOM、PDF、WARC、Canonical IR、Markdown、Structured JSON、Graph artifact、AI artifact、fixture。

### 4.3 检索与图谱

- OpenSearch：生产 BM25、过滤、聚合、Alias/Generation；
- pgvector/OpenSearch kNN：首期向量；规模增长后可替换 Qdrant/Milvus；
- RRF/Controlled Fusion：BM25 + Vector 基线融合；
- Graph：首期 PostgreSQL entity/relation/statement/evidence 表验证价值；需要高阶图查询后再增加 Neo4j/Memgraph/其他图引擎 Adapter；
- R2R/其他 GraphRAG 平台：只作为可替换 Graph/RAG Projection Adapter，不接管平台 Truth；
- Cross Encoder Reranker：可选精排。

### 4.4 运营分析

- Prometheus + Grafana + OpenTelemetry：低基数指标和 Trace；
- PostgreSQL Materialized/Incremental Read Model：首期运营聚合；
- 数据量进一步增长后可引入 ClickHouse 等分析引擎；
- SSE/WebSocket：仅发送失效通知或事件引用。

```text

discover(cursor, budget) -> candidates + evidence + next_cursor

exhaustion() -> explicit_reason
```

```text

DOCS_TOC

DEEP_CRAWL_BFS
DEEP_CRAWL_DFS
DEEP_CRAWL_BEST_FIRST
```

### 7.2 历史发现顺序

```text
CMS/API
 -> Sitemap
 -> Historical Feed
 -> Archive year/month
 -> Category/Tag/Author
 -> Blog Index / Docs TOC
 -> Common Crawl
 -> HTTP/Browser Discovery Surface
 -> Best-First/BFS gap filling
 -> Site Search supplement
```

Deep Crawl 是 gap discovery，不是 Coverage 真相。

### 7.3 Coverage 事实

```text
coverage_provider_run
- run_id
- source_id
- provider_type
- provider_release_id
- cursor_before
- cursor_after
- status
- exhaustion_reason
- candidate_count
- completed_count
- failed_count
- known_gap
- blocker
- evidence_ref
```

预算耗尽只能标记：

```text

```

## 8. URL Observation、Normalization 与 Filter

### 8.1 Observation First

每个被发现 URL 先保存 Observation：

```text
url_observation
- source_id
- observed_url
- provider_type
- provider_run_id
- parent_url nullable
- anchor_text nullable
- depth nullable
- observed_at
- evidence_ref
```

Filter 不能删除“曾经发现过这个 URL”的事实。

### 8.2 Normalization

全局安全规则：lowercase host、default port removal、fragment removal、path slash、安全 percent-encoding、query key ordering、tracking param removal。

站点规则：semantic query allowlist/denylist。

禁止全局删除 query；`?id=123`、`?p=456`、`?page=7` 可能包含业务语义。

### 8.3 URL Filter Chain

```text
url_filter_release
- rules[]
- action: HARD_REJECT / SOFT_REJECT / DEPRIORITIZE / ACCEPT
- reason_code
- fixture_refs
```

HARD_REJECT 仅用于明确禁止域、robots/policy、后台/登录、静态资产等；路径模式、相关性、category/tag 推断默认属于 SOFT_REJECT/DEPRIORITIZE。

每次 decision 保存：

```text
url_filter_decision
- url_id
- filter_release_id
- rule_id
- action
- reason_code
- score nullable
- evidence_ref
- decided_at
```

新 Filter Release 上线前对已知文章 URL fixture 做 recall 回归。

## 11. Snapshot、Extraction、Canonical IR 与 Markdown

### 11.1 Snapshot First

```text
snapshot
- snapshot_id
- fetch_attempt_id
- snapshot_origin
- content_type
- body_hash
- object_ref
- headers_hash
- rendered_dom_ref nullable
- captured_at
```

Extractor/Filter/Graph/AI 升级优先对旧 Snapshot/Document Version 离线 replay，不重新访问源站。

### 11.2 Extraction Candidate

同一 Snapshot 可产生：

- CMS/API body；
- Site Selector；
- CSS/XPath/Regex；
- JSON-LD；
- Trafilatura/Readability；
- Crawl4AI cleaned HTML/raw Markdown；
- Rendered DOM；
- Feed Content；
- PDF Text/OCR；
- Markdown/TXT native parse。

### 11.3 Canonical IR

```text
DocumentIR
  metadata:
    title/authors/published_at/updated_at/language/canonical_url/tags
  blocks:
    heading/paragraph/list/quote/code/table/image/figure/formula
  assets[]
  outbound_links[]
  source_evidence[]
```

HTML/PDF/MD/TXT 最终统一进入 IR。

### 11.4 Quality

至少检查：

- 正文长度；
- 标题一致；
- link density；
- boilerplate；
- code/table 保留；
- 语言；
- published_at confidence；
- truncation；
- selector match；
- required field 缺失；
- DOM drift。

低质量候选进入 quarantine，Web 可比较不同 Extractor。

### 11.5 Canonical Markdown

Markdown 从 IR 确定性生成：去导航/广告/推荐/评论；保留标题层级、代码、列表、引用、表格、图片 alt/caption、重要链接；解析相对链接；不做 query-dependent 删减。

BM25 pruning、LLM filter 等只能产生 `FILTERED_MARKDOWN`，不能覆盖 canonical Markdown。

## 12. Structured Extraction Plane

结构化抽取与正文 canonical 分离。

### 12.1 Schema 与执行策略分离

```text
structured_schema_release
- schema_json
- required_fields
- field_descriptions
- validation_policy
- fixture_refs

structured_extraction_release
- engine: API / JSON_LD / CSS / XPATH / REGEX / LLM
- input_format
- schema_release_id
- selector_or_instruction
- chunk_policy
- model_release_id nullable
- prompt_release_id nullable
- quality_policy
- runtime_release_id
```

同一 Schema 可以分别用确定性规则和 LLM 实现，在 fixture 上比较准确率、稳定性、延迟和成本。

### 12.2 执行优先级

```text
platform API / JSON-LD / CSS / XPath / Regex
 -> deterministic extractors
 -> LLM Extraction only for complex/unstructured fields
```

LLM 使用 Pydantic/JSON Schema 约束输出，并记录 token usage、validation error、latency、estimated cost。

### 12.3 Structured Record

```text
structured_record
- structured_record_id
- document_version_id
- parent_record_id nullable
- schema_release_id
- extraction_release_id
- record_identity_key
- input_hash
- output_hash
- object_ref
- validation_state
- source_block_range nullable
- token_usage nullable
- cost nullable
```

当抽取返回多个 item 时，必须拆成具有独立 `structured_record_id` 的记录，不能把多个独立记录拼成一个无边界 JSON 文档参与 Chunk/Graph。

### 12.4 Hard Boundary

```text
DOCUMENT_VERSION
STRUCTURED_RECORD
```

Chunk、Embedding、Graph Extraction 默认不得跨越以上硬边界。结构化多 item 的 overlap 只允许发生在同一 record 内。

失败只影响 structured readiness，不影响 canonical Markdown READY。

## 13. Document Identity、版本与增量同步

### 13.1 Identity

综合：

- platform stable ID；
- canonical/og:url；
- redirect evidence；
- Feed GUID；
- 平台 article ID；
- normalized URL；
- exact/near duplicate；
- title + published time。

URL Alias、Document Identity、Document Version 分离。

Document Version 仅在 Canonical IR 或关键元数据变化时创建。304、重复抓取、Markdown/Chunk/Embedding/Graph/AI 策略升级不创建正文版本。

### 13.2 增量信号

```text
Feed/API cursor
 -> Sitemap lastmod
 -> High-yield Surface
 -> Conditional GET
 -> Metadata/Resource Probe
 -> Full HTTP
 -> Browser fallback
```

保存 ETag、Last-Modified、previous_body_hash、content_length、content_kind。

304：不重复保存 body、不抽取、不建 Version、不重做 Projection。

### 13.3 调度分层

```text
Tier 0 Feed/API            分钟级
Tier 1 Sitemap/Blog Index  10~60 分钟
Tier 2 Category/Archive    1~6 小时
Tier 3 Deep Reconcile      每周/每月
Tier 4 Common Crawl        新 collection/按月
```

Feed/API 使用 overlap window；周期 Reconcile 负责发现迟到、排序变化、Feed 窗口外遗漏、URL 迁移、删除和结构漂移。

## 16. Graph Projection：Ontology、Entity、Relation、Statement 与 Provenance

### 16.1 定位

Graph 是 Document Version/Structured Record 的可重建派生能力，适合多跳关系、项目/人物/公司/技术关联、依赖和结构化问题；它不替代原文、BM25 或向量检索。

### 16.2 Graph Ontology Release

```text
graph_ontology_release
- version
- allowed_entity_types
- allowed_predicates
- literal_types
- predicate_domain_range
- cardinality_rules
- inverse_symmetric_rules
- entity_vs_attribute_policy
- temporal_policy
- identifier_policy
- fixture_refs
```

`entity_vs_attribute_policy` 决定哪些对象值得跨文档归并为 Entity，哪些应保留为 Literal Statement。

推荐 Entity：

```text
PERSON
ORGANIZATION
PROJECT
PACKAGE
TECHNOLOGY
DATABASE
PROTOCOL
PRODUCT
MODEL
PAPER
CVE
STANDARD
```

日期、数量、延迟、吞吐量、分数、端口、配置值、普通版本字符串默认作为 Literal，而不是创建全局实体。

### 16.3 Entity / Relation

```text
graph_entity
- graph_generation_id
- entity_id
- canonical_name
- entity_type
- aliases
- stable_identifiers
- confidence

graph_relation
- graph_generation_id
- relation_id
- source_entity_id
- predicate
- target_entity_id
- confidence
```

Relation 只表示 Entity -> Entity 的可遍历语义边。

### 16.4 Statement / Fact

```text
graph_statement
- graph_generation_id
- statement_id
- subject_entity_id
- predicate
- object_entity_id nullable
- object_value_json nullable
- value_type nullable
- unit nullable
- valid_from nullable
- valid_to nullable
- confidence
```

约束：`object_entity_id` 和 `object_value_json` 必须且只能存在一个。

示例：

```text
CVE-xxxx --CVSS_SCORE--> 9.8
ProjectX --RELEASED_AT--> 2026-08-01
BenchmarkRun --THROUGHPUT--> 125000 requests/s
PackageY --LATEST_VERSION--> "3.2.1"
```

这避免把 “Price”“Inventory Count”“9.8”“2026-08-01” 等标量错误变成全局高连接实体。

### 16.5 Evidence

```text
graph_evidence
- graph_object_type: ENTITY / RELATION / STATEMENT
- graph_object_id
- document_version_id
- structured_record_id nullable
- chunk_id nullable
- block_range
- quote_hash
- extraction_release_id
- model_release_id nullable
- prompt_release_id nullable
```

任何 ACTIVE Relation/Statement 必须至少存在一条有效 evidence。无证据候选进入 QUARANTINE。

要求：

```text
graph_provenance_coverage = 1.0
```

### 16.6 Hard Graph Boundary

Graph Extraction 输入默认单位：

```text
one Document Version
or
one Structured Record
```

禁止把多个独立文章/record 聚合成一个无边界 Graph 输入。若同一 Document Version 内有多个结构化 item，各 item 的 Entity/Statement Evidence 必须携带 `structured_record_id`。

### 16.7 Entity Resolution

```text
Mention
 -> type validation
 -> deterministic normalization
 -> stable identifier match
 -> alias lookup
 -> candidate generation
 -> name/embedding similarity
 -> optional LLM adjudication
 -> canonical entity
```

优先使用 GitHub URL、package identifier、DOI、CVE ID、RFC ID、官方域名等稳定标识，避免仅靠名称相似度。

Entity merge/split 形成版本化 correction/audit，不直接修改 ACTIVE 图后丢失历史。

### 16.8 Graph Release

```text
graph_projection_release
- graph_ontology_release_id
- entity_extraction_release_id
- relation_extraction_release_id
- statement_extraction_release_id
- entity_resolution_release_id
- graph_storage_release_id
- runtime_artifact_release_id
```

新模型、Prompt、Ontology、实体归并规则不能在生产图上原地覆盖。

### 16.9 R2R / GraphRAG Adapter Contract

如果接入 R2R：

```text
platform_document_version_id <-> r2r_document_id
structured_record_id nullable
source_id
scope_tags / acl_tags
graph_generation_id
projection_release_id
content_hash
```

规则：

- 默认一个平台 Document Version 对应一个 R2R Document；
- 不把多篇文章或无关 Structured Record 合并为一个 R2R Document；
- R2R document ID 不成为平台 Document Identity；
- R2R projection 删除/重建不影响 canonical；
- 从 R2R 导入的实体/关系只有在能映射回平台 Evidence 后才可进入 ACTIVE Graph；
- R2R 可替换，不承担 Source/Coverage/Version/Task 真相。

## 17. Chunk、Embedding、全文索引与向量索引

### 17.1 Chunk

Structure-aware：Heading/Section 优先；段落、列表、引用尽量完整；code/table 默认不拆；保存 heading path/page/block range；超长 section 才 recursive fallback；长度按目标 Embedding tokenizer 计数。

硬规则：

```text
Chunk NEVER crosses Document Version boundary
Chunk NEVER crosses Structured Record boundary
```

```text
chunk_id = hash(boundary_id + chunk_release_id + logical_block_range + normalized_text_hash)
```

禁止只依赖 file path + chunk_index。

### 17.2 Embedding

```text
embedding_id = hash(chunk_id + embedding_release_id)
```

Worker 支持 batch token 上限、OOM 自动缩 batch、lease、retry、partial success、backpressure。写向量前校验 dimension、finite value、normalization、release 和 payload schema。

### 17.3 Index Generation

全文、向量、Graph 都使用 Generation：后台构建、固定 judgment set 验证、canary、Alias/逻辑指针原子切换。

`RECHUNK / REEMBED / REINDEX / REGRAPH` 都不重新抓源站。

max_edges

- Chunk 不跨 Structured Record；
- Graph Extraction 不跨硬边界；

- ACTIVE Entity/Relation/Statement 必须有 provenance；
- `graph_provenance_coverage = 1.0`；
- entity merge/split 固定回归；

## 27. 实施阶段

### Phase 1：20 个代表性站点

覆盖 WordPress、Ghost、Substack、静态博客、Docs、JS、中英文、HTML/PDF/Markdown。

交付：Source/Profile、Coverage、Normalization、Filter、Resolution、Resource Probe、HTTP/Browser、Snapshot/IR/Markdown、Manual Ingestion、Conditional Fetch、Structure-aware Chunk、基础 BM25/Vector、Web 单 URL 调试台。

### Phase 2：100 个站点

验证 Provider Coverage、Filter recall、配置复用、限流、Browser 成本、Recipe/Schema 漂移、Identity、PDF、Chunk 稳定、多语言 Analyzer、RRF、流式 Embedding、Scope conformance；上线 Structured Record Projection、Hard Record Boundary 和 Ops Read Model。

### Phase 3：1000 个站点

完成 Worker 横向扩容、Common Crawl 批处理、PostgreSQL 分区、对象存储生命周期、全链路监控、Budget/backpressure、Generation 管理、Embedding 批处理、批量运营、Dashboard watermark。

### Phase 4：Graph 与 AI

先用 PostgreSQL entity/relation/statement/evidence 表验证图谱价值；建立 Ontology、Provenance Gate、Entity Resolution、Graph Explorer 和 Graph Retrieval Contribution Gate。

只有固定 judgment set 能证明 +Graph 相对 BM25+Vector 有稳定增量收益时，才逐步扩大 Graph 在线流量。图查询规模达到瓶颈后再引入专用 Graph Store。

同时完善 Summary/Topic/Entity/Sentiment Analysis。

### Phase 5：高级治理

多租户/RBAC、Agent 只读 Analytics Tool、自然语言运营查询、异常解释、容量预测、成本归因、灾备和长期数据生命周期。

## 28. 验收标准

### Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有 exhaustion evidence；
- known gap 可枚举、可重跑；
- Deep Crawl 队列为空不能冒充完整；
- Common Crawl 不作为完整性证明。

### Incremental

- Feed/API/Sitemap 新文章在目标 SLA 内入库；
- 304 不重复抽取/建版/投影；
- Reconcile 能发现 Feed 窗口外遗漏和结构漂移。

### Filter / Crawl

- URL Filter 有 release/evidence；
- HARD/SOFT 明确；
- 新 Filter Release 有文章 recall fixture；
- Browser 不是默认路线；
- Deep Crawl/Interaction 有预算；
- 批处理按 URL 独立提交。

### Markdown / Structured

- Markdown 可从 IR 确定性重建；
- heading/code/list/table/image/link 有质量验证；
- Structured Schema 有 fixture 和 validation；
- 多 item 具有独立 Structured Record 身份；
- Chunk/Graph 不跨 Document/Record 边界；
- LLM Extraction 失败不影响 canonical；
- token/cost 可按 Source/Schema 查询。

### Chunk / Search

- HTML/PDF/MD/TXT 使用统一 Chunk Release；
- Chunk ID 不依赖 chunk_index；
- `chunk_boundary_violation_rate = 0`；
- RECHUNK/REEMBED 不访问源站；
- BM25 + Vector + optional Graph 可解释；
- Scope 不召回范围外 Chunk；
- 新 Generation 验证后才能 ACTIVE。

### Graph

- Graph 是 Projection，不是 Truth；
- Entity/Relation/Statement 有 Document/Chunk provenance；
- ACTIVE Graph 的 provenance coverage = 1.0；
- 标量默认使用 Statement/Literal，不形成无意义通用实体；
- Ontology 可版本化、可验证；
- Entity Resolution 可回放、可 diff；
- REGRAPH 不重新抓源站；
- Graph 失败不阻塞 Source Sync；
- Graph Retrieval 有 hop/node/edge budget；
- Graph ScopeLeakRate 接近 0；
- Graph 是否启用以增量检索收益为依据；
- R2R/图数据库可替换，不承担 Source/Version/Task 真相。

### Web / Ops

- Fleet Overview 不实时扫描所有事实表；
- 每个趋势图显示 watermark/coverage；
- Filter/Schema/Ontology/Graph/Release 可调试、diff、回滚；
- Search Trace 能区分 Graph attempted/nonempty/contributed；
- UI 刷新不触发 Crawl/LLM；
- Prometheus 无 URL/Document/Task 高基数 label；
- Dashboard Command 全部经过幂等、RBAC、Audit。

### Reliability / Security

- Worker crash 后 lease 可恢复；
- fencing 防止旧 Worker 覆盖；
- fan-out 保留 partial success；
- Embedding/Graph/AI/Search/Dashboard 故障不阻塞 Source Sync；
- Query Plane 无任意公网 URL 访问权限；
- Runtime/Model/Ontology/Graph/Metric Artifact 可复现、可回滚。

## 29. 最终技术路线

```text
Coverage-driven Discovery
 -> Evidence-preserving URL Filter
 -> Normalize / Resolve / Probe
 -> HTTP-first Fetch
 -> Immutable Snapshot
 -> Deterministic Canonical IR
 -> Stable Markdown + Document Version
 -> Async Projections
      ├─ Structured Record with Hard Boundary
      ├─ Chunk / BM25 / Vector
      ├─ Graph Entity / Relation / Statement / Evidence
      └─ AI Insight / Ops Analytics
 -> BM25 + Vector + on-demand Graph Retrieval
 -> Contribution / Scope / Cost Gate
 -> Web-operable Release / Generation / Audit
```

这条路线保证：

- 新增站点主要靠配置扩展；
- 全量历史有 Coverage 证据；
- 增量同步使用条件请求和多层信号降低成本；
- Browser 和 LLM 只处理必要长尾；
- Markdown 是稳定、可重建的知识资产；
- Structured Record 与 Chunk 保持严格记录边界；
- 图谱使用 Entity/Relation/Statement 正确表达实体关系和标量事实；
- 每条 ACTIVE 图谱事实都有 provenance；
- GraphRAG 必须用实际增量检索收益证明价值，而不是用“已建图”替代效果验证；
- R2R、图数据库、向量库均处于可替换 Projection 边界；
- 所有关键策略均可版本化、回放、灰度和回滚；
- Source Sync、检索、Graph、AI、Dashboard 可以独立扩缩容和故障隔离。

该方案能够支撑 1000+ 技术博客的长期全量历史抓取、Markdown 知识资产沉淀、增量同步和 Web 化运营，并为后续结构化数据、GraphRAG 和 AI 助手提供可控、可验证的扩展路径。
