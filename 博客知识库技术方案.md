# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个长期运行、可横向扩展、可审计、可重放的技术博客知识库平台。首期约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章并清洗为稳定 Markdown；后续持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计和离线重处理。

设计按以下量级考虑：

- 1000+ Source，后续扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 多年运行，站点结构会持续变化；
- 中英日韩等多语言技术内容；
- HTTP 为主，Browser 为受控 fallback；
- 历史 URL 发现可接入 Sitemap、Feed、CMS API、Archive、Common Crawl URL Index 等多来源；
- 原始事实长期保留，Markdown、Chunk、Embedding、全文索引等派生结果可删除重建。

平台核心目标不是“把网页抓下来”，而是建立一套能够回答以下问题的系统：

1. 一个站点理论上应该有哪些文章，我们凭什么认为历史已基本覆盖；
2. 某个 URL 是从哪里发现、经过什么规范化和跳转后抓取的；
3. 某个 Markdown 是由哪个网络快照、哪个抽取规则和哪个版本生成；
4. 源站更新后哪些内容真正变化，哪些投影需要重建；
5. 抓取、清洗、分块、Embedding、检索模型升级后能否离线重放；
6. 站点结构、反爬、成本或抓取质量变化时能否在 Web 中定位并运营。

## 2. 核心设计原则

1. **Config First**：新增普通站点主要通过 Source / Site Profile 配置完成，不修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence 与 exhaustion reason 证明，不能用“队列为空”“达到 max_pages”冒充完整。
3. **Discovery Before Fetch**：先低成本发现 URL，再决定哪些 URL 需要真实抓取正文。
4. **Prefetch Before Extraction**：未知结构优先轻量获取 HTML + links，发现阶段不默认生成 Markdown。
5. **Discovery Surface First-class**：Sitemap、Feed、Archive、Category、Tag、Blog Index、Docs TOC 等持续产出文章 URL 的页面/接口作为长期资产维护。
6. **Graph, Not Tree**：现代站点按有环图处理，不假设严格目录树。
7. **Soft Pruning Only**：低收益或已饱和分支只降权、设置 TTL、保留抽样复查，不做不可恢复删除。
8. **Authoritative First, Archive as Supplement**：CMS/API/Sitemap/Feed 优先；Common Crawl、Wayback 等只作为补洞和历史证据。
9. **HTTP First, Browser Last**：Browser 只处理动态页面、结构探索或低质量 fallback，不作为默认抓取方式。
10. **Resolution Is a First-class Plane**：Observed URL、Normalized Candidate、Resolved Target、Network Final URL、Canonical Identity 必须分开建模。
11. **Snapshot First**：网络事实先保存不可变 Snapshot，再抽取、清洗、建版。
12. **IR First, Markdown as Projection**：Canonical IR / Document Version 是事实层；Markdown、Chunk、Embedding、全文索引均为可重建投影。
13. **Stable Identity**：Document、Version、Chunk、Embedding、Index 都要有稳定且 release-aware 的身份，不能依赖可漂移的顺序编号。
14. **Language-aware Retrieval**：分词、stemming、stopwords、技术 token 处理和 BM25 参数按 Analyzer Release 版本化。
15. **Hybrid Retrieval by Default**：全文与向量互补，默认采用 BM25 + Vector + RRF，可选 Reranker。
16. **Release Everything**：Profile、Discovery、Normalization、Classifier、Branch Policy、Resolver、Fetch Route、Extractor、Quality、Markdown、Chunk、Analyzer、Embedding、Retrieval、Runtime Artifact 均版本化。
17. **Generation Instead of Destructive Rebuild**：Chunk、Analyzer、Embedding 或索引升级构建新 generation，验证后原子切换，禁止破坏式重建生产索引。
18. **Idempotent + Recoverable**：所有任务具备幂等键、lease、checkpoint、retry 和 partial success 语义。
19. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary、Search Index 故障不能阻塞源站事实同步。
20. **Evidence Everywhere**：发现、分类、分支降权、跳转、抓取、抽取、身份、版本、检索都可解释、可审计。
21. **Web 管理是平台能力**：Coverage、Surface、Branch、异常、证据、版本、成本、索引和策略 Release 必须可运营。
22. **安全边界每跳执行**：重定向和 Browser 导航不能绕过 SSRF/Egress/访问策略。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST / Command API、Schema 校验、内部服务接口。
- **PostgreSQL**：Source、Profile Release、Run、Task、Coverage、Discovery Surface、Branch State、URL Observation、Resolution、Fetch、Document、Version、Projection、Audit、Outbox。
- **Transactional Outbox**：数据库状态变更和消息发布保持事务一致。
- **Redis Streams**：任务运输、consumer group、retry、backpressure，不保存唯一业务事实。
- **React/Vue + TypeScript**：Web 管理。

### 4.2 抓取与抽取

- **HTTPX / aiohttp**：HTTP、Feed、Sitemap、API、条件请求和低成本跳转解析。
- **BeautifulSoup / lxml / CSS / XPath**：wrapper、meta refresh、selector 和结构化 HTML 处理。
- **Trafilatura / Readability**：确定性正文候选。
- **Crawl4AI / Playwright**：URL Seeding、Prefetch Mapping、Deep Crawl、动态页面和 Browser fallback。
- **S3 / MinIO**：HTML、HTTP body、Rendered DOM、Feed payload、PDF、WARC 恢复快照、Canonical IR、Markdown、Asset 和调试产物。

### 4.3 历史发现

- **Sitemap / RSS / Atom / JSON Feed / CMS API**：首选权威来源。
- **Common Crawl URL Index**：1000 站点级批量历史候选发现，优先使用列式 URL Index，不高并发轰炸 CDX。
- **DuckDB / Athena / Spark / Polars**：批量扫描 Common Crawl Parquet 或离线历史索引。
- **Archive / Category / Tag / Author / Docs TOC**：站点级历史补充。

### 4.4 检索

- **OpenSearch**：全文检索、过滤、聚合、BM25、Alias/Generation 管理。
- **pgvector / OpenSearch kNN**：首期向量检索。
- **Qdrant / Milvus**：当向量规模、独立扩缩容或性能需求提高后可替换。
- **RRF**：默认全文 + 向量融合基线。
- **Cross Encoder Reranker**：可选精排层，独立服务化。

### 4.5 可观测与部署

- **Prometheus + Grafana + OpenTelemetry**：指标、日志、Trace。
- **Docker / Kubernetes**：Worker 隔离与横向扩容。
- **Artifact Registry / 内部镜像**：浏览器内核、Embedding/Reranker 模型和运行时镜像版本化分发。

## 8. 新站接入 PROBE

新增站点先执行 `PROBE`，不直接深爬：

1. 规范化 entry URL，确定 registrable domain、allowed origins 和 scope；
2. 获取 robots 及 Sitemap 声明；
3. 探测 Sitemap Index / Sitemap；
4. 探测 RSS / Atom / JSON Feed；
5. 探测 WordPress REST、Ghost、Substack 等公开平台能力；
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination；
7. 低成本查询 Common Crawl；
8. 对 URL path 做模板聚类，推断 article template、surface template 和分页规则；
9. 使用 Prefetch Mapping 获取未知 hub 的 HTML + links，不生成 Markdown；
10. 使用 BFS 1~2 层或 BestFirst 小预算探索未知结构；
11. 建立模板级 Discovery Graph，估算 branch article probability、surface probability 和新模板率；
12. 抽样比较 HTTP 与 Browser 正文质量、JS 依赖和成本；
13. 检测 Feed/Search 链接是否存在 wrapper、短链、meta refresh、JS redirect；
14. 推断主要语言和 analyzer hint；
15. 对 Surface 灰区允许 LLM 辅助分类，但必须由人工审核后才进入生产 Profile；
16. 自动生成首版 Site Profile Release，在 Web 中审核和修正。

### 9.6 FULL_BACKFILL 完成条件

Web 必须能回答：

- 使用了哪些 Provider；
- 每个 Provider 找到多少候选；
- Provider 交集和独有 URL；
- 哪些时间区间/分页已穷尽；
- 哪些候选抓取失败；
- 哪些区间仍有 gap；
- 哪些分支因预算/soft-pruning 尚未完全探索。

## 10. Common Crawl 的使用边界

Common Crawl 只证明某 URL 在某个 collection 中曾被观察或抓取，不证明某个站点所有历史 URL 都已被收录。

`common_crawl_observation`：

```text
source_id
crawl_id
url_id
capture_time
status
mime
warc_filename
warc_offset
warc_length
content_digest
observed_at
```

1000 站点级历史枚举优先 URL Index 批处理并缓存 `(registered_domain, crawl_id)` 结果；CDX 只用于低频交互和补充查询。

若确有业务需要恢复已下线文章，可启用 `ARCHIVE_RECOVERY_COMMON_CRAWL`，但必须：

- live fetch 已明确失败/404/410；
- 已有 Common Crawl Observation；
- Source Policy 允许；
- 权利、许可证和使用目的符合项目政策；
- Snapshot 明确标记 archive origin 和 capture time。

归档内容不能伪装为当前源站抓取事实。

## 17. 增量同步与 Reconcile

### 17.1 信号优先级


### 17.2 Feed/API

```text

```

### 17.3 Surface 调度

初始层级：

```text

Tier 1: Sitemap / Blog Index     10~60 分钟
Tier 2: Category / Archive       1~6 小时
Tier 3: Deep Crawl Reconcile     每周/每月
Tier 4: Common Crawl Reconcile   新 collection 发布后或按月
```

根据 `new_urls_per_scan`、失败率、重复率、分支收益和抓取成本动态调频。

### 17.4 Pagination Early Stop

历史回填完整遍历；增量扫描允许早停：

```text
page 1
 -> 有新 URL：继续
 -> 连续 K 页全是已知 URL 且结构未变：早停
 -> Provider gap / structure drift：取消早停并升级 Reconcile
```

Early Stop 不是 Coverage COMPLETE 证据。

### 17.5 Conditional Fetch

保存：

```text

Last-Modified
previous_body_hash
```

304：

- 不创建 Snapshot body 副本；
- 不创建 Document Version；
- 不重复 Extraction；
- 不重复 Projection。

### 17.6 Reconcile

即使有 Feed，也周期核对 Sitemap / Archive / Surface / Branch Sampling / Common Crawl，用于发现：

- Feed 窗口外遗漏；
- URL 迁移；
- Feed 未更新但正文变化；
- 删除/下线；
- 新历史候选；
- Surface 结构漂移；
- soft-pruned 分支出现新模板；
- Provider 差异扩大。

## 20. Chunk 设计与稳定身份

### 20.1 Structure-aware Chunk

默认使用 heading-aware / block-aware 切分：

1. Heading/Section 是第一层语义边界；
2. 段落、列表、引用尽量保持完整；
3. 代码 fenced block 默认不拆；
4. 表格默认不拆；
5. 超长 section 再按 token/字符切分；
6. overlap 主要用于普通文本边界；
7. 保存 heading path 和 block range；
8. 超长代码/表格走特殊 chunk policy。

### 20.2 Chunk 数据

```text

block_end

```

### 20.3 稳定 Chunk ID

禁止使用：

```text
hash(file_path + chunk_index)
```

因为文档头部插入内容会导致 chunk index 级联漂移。

推荐：

```text
chunk_id = hash(
  document_version_id
  + chunk_release_id
  + logical_block_range
  + normalized_text_hash
)
```

Chunk Release 变化执行 `RECHUNK`，不重新抓源站。

## 23. Hybrid Search、RRF 与 Retrieval Release

默认检索链路：

```text

 + Vector Search
 -> RRF Fusion
 -> metadata filter
 -> optional Reranker
```

### 23.1 为什么使用混合检索

向量擅长语义相似，BM25 擅长精确术语、API 名、版本号、类名和代码 token。技术知识库必须同时支持两者。

### 23.2 RRF

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

RRF 不要求 BM25 score 和 vector score 同量纲，稳定、简单、可解释，适合作为默认融合方式。

## 24. Reranker 与 Context Assembly

### 24.1 Reranker 原则

正确链路：

```text
大规模粗召回
 -> Top-N 融合候选
 -> Cross Encoder Reranker
 -> Top-K
 -> Context Assembly
```

Reranker 不扫描全库。

### 24.2 服务化

独立 `rerank-service`：

- 模型常驻优先；
- 动态 batch；
- 最大 batch token；
- GPU 并发限制；
- idle 较长时间可卸载；
- OOM 自动降 batch；
- 可选 CPU fallback；
- Reranker 故障时降级到 RRF 结果；
- 任何 Reranker 故障不得影响 Source Sync。

### 24.3 Context Assembly

根据：

- document diversity；
- heading path；
- chunk adjacency；
- same-document overlap；
- token budget；
- source trust；
- duplicate suppression；

组装最终上下文，避免 Top-K 全部来自同一文章相邻 Chunk。

- Embedding 模型变化；
- 向量维度/metric 变化；
- OpenSearch schema 变化；

```text

```

这些任务均优先使用现有 Snapshot / Canonical IR，不重新抓源站。

## 34. 验收标准

### 34.1 Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有明确 exhaustion evidence；
- known gap 可枚举、可重跑；
- 达到预算不会错误标记为完整；
- Common Crawl 不被当成完整性证明；
- Provider overlap/unique URL 可查询；
- soft-pruned 分支不被计入 COMPLETE。

### 34.2 增量

- Feed/API/Sitemap/高收益 Surface 新文章在目标 SLA 内进入系统；
- Pagination Early Stop 不造成已知 Coverage 缺口；
- 304 不重复抽取、建版和投影；
- 未变化 Projection 不重复计算；
- Reconcile 能发现 Feed 窗口外遗漏、结构漂移和 Branch 新模板。

### 34.3 Markdown

抽样验证：

- title / author / time；
- 正文完整；
- 导航噪声低；
- heading 正确；
- code block 完整；
- list/table/image/link 保留；
- Markdown 可从 Canonical IR 确定性重建。

### 34.4 Chunk / Embedding

- Chunk 保留 heading path 和 block range；
- 代码块和表格默认不被破坏；
- 同一 Document Version + Chunk Release 可稳定重建相同 Chunk ID；
- Chunk Release 变化不创建新的 Document Version；
- Embedding Release 变化只触发 REEMBED；
- Embedding backlog 不影响 Source Sync。

### 34.5 检索

- 中文/英文/技术 token 有独立回归集；
- CJK 不依赖 whitespace tokenizer；
- BM25 + Vector + RRF 可解释；
- Reranker 故障可降级；
- Retrieval Release 可回放；
- 新 Index Generation 验证通过后才能切 ACTIVE；
- 生产索引升级无破坏式 drop/recreate。

### 34.6 可靠性

- Worker 崩溃后 lease 可恢复；
- fan-out 保留 partial success；
- Embedding/Index/Reranker 故障不阻塞 Source Sync；
- Common Crawl rate limit 不阻塞主抓取链路；
- Crawl4AI/Playwright/模型升级可通过 Release 回滚；
- 所有高风险管理操作可审计。

## 35. 最终架构原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：发现、分类、去重后再抓正文。
3. Prefetch Before Extraction：发现 links 不需要先生成 Markdown。
4. Discovery Surface First-class：把持续产生文章 URL 的入口当长期资产。
5. Graph, Not Tree：站点按有环图处理。
6. Soft Pruning Only：低收益分支只降权和延后，不永久删除。
7. Authoritative First, Archive as Supplement：权威来源优先，历史 Archive 只补洞。
8. HTTP First, Browser Last：Browser 是昂贵 fallback，不是默认抓取器。
9. Resolution Is Not Identity：跳转终点和 canonical 文档身份分离。
10. Snapshot First, Replay Later：原始网络事实不可变，规则升级优先离线重放。
11. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
12. Stable Chunk Identity：Chunk 身份不能依赖可漂移的 chunk_index。
13. Language-aware Analyzer：多语言分词和技术 token 策略必须 Release 化。
14. Hybrid Retrieval by Default：BM25 和 Vector 互补，RRF 作为默认稳定融合基线。
15. Reranker as Optional Service：精排是可降级的检索增强层，不进入事实同步关键路径。
16. Generation Instead of Destructive Rebuild：所有索引升级后台构建、验证、原子切换。
17. Release Everything：所有影响结果的策略、模型、浏览器和运行时可追踪、可比较、可回滚。
18. Idempotent + Recoverable：任务可重复、可恢复、可观察，partial success 不丢失。
19. Source Sync 与 AI 解耦：抓取事实不依赖 Embedding、LLM、Reranker 或 Index 服务。
20. Web 管理是平台能力：Coverage、Surface、Branch、证据、版本、成本和检索解释都必须可运营。
