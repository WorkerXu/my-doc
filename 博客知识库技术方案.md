# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站和公开 Newsletter** 的长期采集与知识库平台，并可平滑扩展到数千站点、百万到千万级文章。

平台必须同时满足：

1. **全历史回填**：尽可能完整发现每个已批准 Source 的历史文章，能解释发现通道、覆盖率、缺口、截断与停止原因；
2. **持续增量同步**：发现新文章、正文修改、元数据变化、URL 迁移、重定向、删除与重发布；
3. **Markdown 稳定可重放**：保存不可变 Raw Artifact，经版本化 Cleaner、Extractor、Canonical IR 和 Renderer 生成最终 Markdown；
4. **技术内容保真**：代码块、表格、公式、Mermaid、列表、引用、脚注、图片说明不能被通用降噪算法静默删除；
5. **低成本扩站**：新增网站优先通过 Source Profile、Provider、Recipe 和 Traversal Policy 配置完成，不维护 1000 份独立爬虫脚本；
6. **Web 可运营**：支持站点接入、审批、Backfill、Incremental、Coverage、Frontier、质量、成本、诊断、暂停、恢复、重跑、灰度、审计；
7. **任务可恢复**：Provider Run、Task、Attempt、URL、Artifact、Candidate、Document、Version 全链路有持久状态，Worker/Runtime 崩溃可恢复；
8. **可搜索/RAG**：支持 BM25、向量与混合检索，并能回溯原文、版本、Source、抓取证据和处理 Release；
9. **主链不依赖 LLM**：LLM 只做可选 Repair/Enrichment，不参与历史完整性、URL 身份、正文存在性、版本真相和权限边界的最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 可查看 Provider Inventory、Completion Attestation、Known Gap、Backfill Stop Reason；
- **Freshness**：新文章/更新从发布或发现到 PASS Markdown 的 P50/P95/P99 延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文、代码、表格、列表、链接、图片说明、公式的召回率与噪声率；
- **Protected Structure Recall**：受保护技术节点在 Candidate/IR 中的保留率；
- **Multilingual Retention**：中文、日文及中英混排正文保留率；
- **Reliability**：Task 成功率、Retry、DLQ、Queue Age、Lease Recovery；
- **Replayability**：相同 Raw Artifact + 相同 Release 可得到相同派生结果；
- **Provider Integrity**：部分返回、缓存命中、预算耗尽不能被误报为“已完整枚举”；
- **Artifact Durability**：需要保留的 Runtime/Provider Artifact 必须晋升平台对象存储；
- **Browser Efficiency**：HTTP Fast Lane 命中率、Browser Avoided、Browser 单文档成本；
- **Revalidation Integrity**：强验证成功率、弱验证漏检率、`hit_fallback` 数量、强制刷新抽样命中变化率；
- **Fairness**：大型 Backfill 不得长期饿死 Incremental、小站、Repair 与 Reconcile。

## 2. 核心设计原则

1. **Coverage First**：先构建可解释 URL Inventory，再抓正文；
2. **Authoritative First**：官方 CMS/API、Sitemap、Feed、Archive 优先；
3. **Observation Before Selection**：先保存发现事实，再 Normalize、Scope、Classify、Dedup；
4. **Successful Return != Provider Complete**：正常返回、非空结果、cache hit 均不能自动代表 Provider 完成；
5. **Completion Must Be Attested**：只有具备可验证结束语义的 Provider Adapter 才能声明完成；
6. **Discovery / Revalidation / Fetch / Clean / Extract / Quality / Canonicalize / Projection 分离**；
7. **HTTP First, Browser Slow Lane**；
8. **Snapshot First**：先保存 Provider Evidence / Raw Artifact，再生成派生物；
9. **Candidate Portfolio, Not Single Extractor**：多个确定性候选互相校验；
10. **Protected Structures Are First-Class**：代码、表格、公式等先识别、再验证召回；
11. **Language Assumptions Must Be Explicit**：word/token threshold 必须声明适用语言；
12. **Canonical IR First, Markdown as Projection**；
13. **Recipe, Not 1000 Site Scripts**；
14. **Persistent Frontier, Not In-Memory Traversal**；
15. **Idempotent + Recoverable**：幂等键、Lease、Fencing Token、Checkpoint、Inbox/Outbox；
16. **Fair by Default**：Incremental、Revalidation、Repair 必须预留容量；
17. **Bounded Concurrency Everywhere**：任务数、在途请求、结果集合、Browser 与进程生命周期都有硬边界；
18. **No Silent Degradation**：过滤、截断、预算耗尽、partial result、cache fallback、降级必须有 typed reason；
19. **Correlate by Identity, Never by Position**；
20. **Config Is Capability**：高能力配置经过 Capability Firewall；
21. **Runtime Is Execution Plane**：第三方 Runtime 不拥有 Coverage、Identity、Document、Version 或 Markdown 真相；
22. **Behavior Beats Naming**：生产语义以 pinned release + Contract Test 为准；
23. **Runtime Cache Is Disposable**：本地 cache 可丢弃，不得推进业务版本真相；
24. **Derived Artifact Never Overwrites Evidence**：Cleaned HTML、Candidate、IR、Markdown 均是可重放派生物；
25. **Weak Freshness Signal Cannot Close Truth**：head fingerprint、长度相近等弱信号不能单独证明正文未变化。

- **httpx/aiohttp**：CMS API、robots、Sitemap、Feed、Conditional GET、普通网页；
- **RFC 9309 Robots Engine**；
- **平台原生 SitemapProvider**：显式 Sitemap、robots Sitemap、Sitemap Index durable shard；
- **平台原生 CommonCrawlIndexProvider**：固定 index release、流式查询、Evidence、Checkpoint；
- **Crawl4AI AsyncUrlSeeder pinned release**：Sitemap/CC URL 发现加速器；
- **Crawl4AI pinned package/image**：复杂页面、JS Render、Deep/Adaptive gap discovery、Browser Runtime、Markdown Candidate；

- **Wayback Adapter**：历史缺口证据；

### 4.3 Extraction / Search

- **Trafilatura**：Generic Candidate；
- **lxml/BeautifulSoup**：DOM/XPath、Metadata、Repair、Protected Structure Fingerprint；
- **JSON-LD/OpenGraph/Microdata**；
- **CSS/XPath/Regex Recipe**；
- **Crawl4AI DefaultMarkdownGenerator / ContentFilter**：Markdown Candidate，不直接作为 canonical；
- **SimHash/MinHash**：近重复；
- **OpenSearch BM25 + pgvector + RRF**；
- embedding、reranker、LLM 只做增强。

## 6. 全历史 URL 发现与 Coverage

### 6.1 Provider 优先级

每个 Source 的历史发现按以下优先级执行：

1. 官方 CMS/API；
2. Sitemap / Sitemap Index；
3. RSS / Atom；
4. Archive / Pagination / Tag / Category；
5. 静态链接图；
6. Common Crawl Index；
7. Wayback；
8. Crawl4AI URL Seeder、Domain Mapping、Deep/Adaptive Crawl 作为补洞与加速。

任何单一 Provider 都不能自动证明“全历史完整”。

### 6.2 Observation 模型

Provider 返回的每一条 URL 先写 `url_observation`：

```text
observation_id
source_id
provider_id
provider_run_id
observed_url
observed_at
provider_timestamp
provider_metadata
provider_evidence_uri
```

随后统一执行：

```text
Normalize -> Scope Check -> MIME Hint -> URL Identity -> Dedup -> Frontier Upsert
```

不允许 Provider 内部去重结果直接成为平台最终 Inventory。

### 6.3 Provider Completion Attestation

每次 Provider Run 保存：

```text
started_at / finished_at
checkpoint / cursor / shard
items_seen / unique_urls
status
completion_type
stop_reason
truncated
budget_exhausted
known_gap
provider_release
```

只有满足 Adapter 的明确完成条件时，`completion_type=ATTESTED_COMPLETE`。

以下情况一律不能标完整：

- 返回非空列表；
- HTTP 200；
- `success=true`；
- 达到 limit；
- cache hit；
- 搜索结果不再增加但没有协议级结束条件；
- Deep Crawl 达到配置深度/页面预算。

### 6.4 Crawl4AI URL Seeder 的定位

AsyncUrlSeeder 可批量从 Sitemap/CC 等发现 URL，但平台必须：

- pin release；
- 限定 modes/domain；
- 将返回值转成 Observation；
- 保存 provider evidence 与 cutoff；
- 不把 Seeder 内部 cache/seen/queue 当成 durable checkpoint；
- 不用 Seeder 返回条数证明 Coverage。

### 6.5 Coverage 计算

每个 Source 维护：

```text
provider_inventory
provider_attestation
historical_time_range
observed_url_count
fetchable_url_count
article_count
known_gap_count
unresolved_gap_count
backfill_stop_reason
```

Web 后台必须能回答：“为什么系统认为这个站回填完成/未完成？”

### 7.2 公平调度


- source concurrency semaphore；
- domain concurrency semaphore；
- browser slot semaphore；
- provider-specific quota。

robots、站点政策和明确 Rate Limit 优先级高于吞吐量目标。

## 8. Revalidation Engine 与增量同步

这是增量同步的核心，不直接依赖 Crawl4AI Runtime Cache。

### 8.1 增量入口

增量触发来源：

- CMS API 新 revision；
- Sitemap `lastmod`；
- RSS/Atom `updated`；
- Webhook；
- Archive 新链接；
- 定时 Revalidation；
- 强制完整刷新；
- 用户手工重抓；
- Provider Reconcile。

### 8.2 Revalidation Ledger

PostgreSQL 保存：

```text
url_id
last_fetch_at
last_verified_at
last_changed_at
etag
last_modified
raw_body_hash
semantic_body_hash
head_fingerprint
validator_strength
validation_method
validation_result
cache_served
runtime_cache_status
consecutive_304
forced_refresh_due_at
validation_error_count
source_validator_trust_score
```

### 8.3 证据强度

**STRONG**：

- CMS/API revision/version id；
- 标准 Conditional GET 304，且该 Source 的 validator 经过验证；
- 完整 GET 后 body hash 与历史一致。

**MEDIUM**：

- ETag/Last-Modified 发生变化；
- Sitemap/RSS 更新时间发生变化。

**WEAK**：

- `<head>` fingerprint 相同；
- 页面长度相近；
- link graph 相似。

只有符合 Source Policy 的强证据才允许推进 `last_verified_at`。

### 8.4 状态机

```text
DUE_FOR_REVALIDATION
      |
      +-- Provider 明确 changed ------> FETCH_REQUIRED
      |
      +-- Conditional GET 304 --------> VERIFIED_UNCHANGED
      |
      +-- validator changed ----------> FETCH_REQUIRED
      |
      +-- weak unchanged -------------> WEAK_UNCHANGED
      |                                  |
      |                                  +-- sample due -> FETCH_REQUIRED
      |
      +-- validation error -----------> VALIDATION_DEGRADED
                                         |
                                         +-- 可服务旧版本
                                         +-- 不推进 last_verified_at
                                         +-- 安排重试

FETCH_REQUIRED
      |
      v
RAW_ARTIFACT
      |
      +-- body hash unchanged --------> VERIFIED_UNCHANGED
      |
      +-- body hash changed ----------> NEW_DOCUMENT_VERSION
```

### 8.5 强制定期完整抽样

任何 weak/validator 路径都必须配置：

```text
forced_full_refresh_interval
forced_sample_rate
```

抽样完整抓取发现“validator 未报变化但 body hash 已变”时：

1. 记录漏检；
2. 降低 `source_validator_trust_score`；
3. 缩短强制刷新周期；
4. 必要时禁用该 Source 的弱验证跳过策略。

## 9. HTTP Fast Lane、Browser Slow Lane 与 Cache Policy

### 9.1 HTTP First

普通文章优先 `httpx/aiohttp`：

- GET/Conditional GET；
- Redirect chain；
- ETag/Last-Modified；
- Content-Type/MIME；
- Content-Length 上限；
- robots；
- Response headers；
- 原始字节与编码检测。

满足正文质量条件则不启 Browser。

### 9.2 Browser Escalation

仅以下情况进入 Browser Slow Lane：

- HTTP 页面正文为空/占位；
- JS 客户端渲染；
- 需要有限滚动/点击才能出现文章正文；
- Shadow DOM/iframe 且 Source Policy 允许；
- HTTP Candidate 明显低质量；
- Source Recipe 指定。

Browser 通过长期 Runtime Pool 复用，不为每 URL 启动新进程。

### 9.3 平台 Cache Policy Compiler

业务层不直接暴露 Crawl4AI `CacheMode`，只暴露：

```text
AUTHORITATIVE_FETCH
VALIDATE_THEN_FETCH
REPLAY_FROM_ARTIFACT
RUNTIME_CACHE_WARMUP
DIAGNOSTIC_CACHE_READ
```

Compiler 根据 pinned runtime release 生成实际配置。

推荐：

- **AUTHORITATIVE_FETCH**：Runtime cache 禁用，确保得到当前网络响应；
- **VALIDATE_THEN_FETCH**：平台 Revalidation Engine 先判断，确认需要抓取后使用 fresh fetch；
- **REPLAY_FROM_ARTIFACT**：直接处理 S3 Raw Artifact，不访问网络；
- **RUNTIME_CACHE_WARMUP / DIAGNOSTIC**：允许 Runtime cache，但不推进业务版本。

### 9.4 Smart Cache 的使用边界

Crawl4AI Smart Cache 可用 ETag、Last-Modified 和 `<head>` fingerprint 降低完整 Browser 成本，但必须遵守：

1. `<head>` fingerprint 是弱证据，正文可在 head 不变时变化；
2. Runtime validation error 可能返回旧 cache (`hit_fallback`)；
3. `hit_fallback` 只能作为 serving fallback，不得更新 `last_verified_at`；
4. Runtime cache 不进入 Coverage/Version 真相；
5. `BYPASS/ENABLED/...` 的实际语义以 pinned release 的 Contract Test 为准，不以名称猜测。

### 9.5 Runtime Cache 状态归一化

平台统一记录：

```text
MISS
HIT_UNVERIFIED
HIT_VALIDATED
HIT_FALLBACK
DISABLED
BYPASSED
UNKNOWN
```

`HIT_FALLBACK` 必须在 Web 与告警中显式展示。

## 10. Raw Artifact 与内容处理流水线

### 10.1 不可变 Raw Artifact

每次真实网络抓取生成：

```text
artifact_id
url_id
attempt_id
retrieved_at
status_code
redirect_chain
response_headers
mime
encoding
body_sha256
object_uri
fetch_release
browser_release
provenance
```

对象存储采用 content-addressed 或 append-only 方式，绝不覆盖历史。

### 10.2 Cleaner

Cleaner 只生成派生的 `cleaned_html`，不能覆盖 raw。

清洗前先建立 Protected Structure Manifest：

- `<pre>/<code>`；
- `<table>`；
- `<blockquote>`；
- `<figure>/<figcaption>`；
- Mermaid；
- MathJax/KaTeX；
- 脚注；
- 高亮代码容器；
- 图片与 alt/caption。

清洗后计算结构召回，低于阈值进入 REPAIR/REVIEW。

### 10.3 Extraction Portfolio

同一 Raw Artifact 可产生多个 Candidate：

1. Source Recipe；
2. Trafilatura；
3. Crawl4AI raw markdown；
4. Crawl4AI fit markdown；
5. JSON-LD/Article DOM；
6. 受控规则修复 Candidate。

所有 Candidate 记录：

```text
candidate_id
artifact_id
extractor_release
content_hash
structure_manifest
language_profile
quality_score
failure_reason
```

### 10.4 Candidate Quality Gate

评分维度：

- 标题/正文存在；
- 正文密度；
- 导航/广告噪声；
- 代码、表格、列表、公式结构召回；
- 链接/图片说明；
- 标题层级；
- CJK/混合语言保留；
- 与 Raw DOM 的文本覆盖率；
- Candidate 间一致性。

禁止使用单一英文 `split()` word count 作为 CJK 正文质量门槛。

### 10.5 Canonical IR

最终不直接“选一个 Markdown 字符串”，而是建立结构化 IR：

```text
Document
  metadata
  sections[]
    heading
    paragraphs[]
    code_blocks[]
    tables[]
    lists[]
    quotes[]
    equations[]
    figures[]
    links[]
    footnotes[]
```

IR 带 source span/provenance，随后由 Deterministic Renderer 输出 Markdown。

### 10.6 Markdown 规范

统一 Front Matter：

```yaml
---
document_id: ...
source_id: ...
source_url: ...
canonical_url: ...
title: ...
author: ...
published_at: ...
updated_at: ...
retrieved_at: ...
language: ...
version: ...
raw_body_hash: ...
semantic_body_hash: ...
renderer_release: ...
---
```

文件路径建议：

```text
knowledge/<source_key>/<year>/<document_id>-<slug>.md
```

`document_id` 保证稳定，slug 只用于可读性。

## 11. Document Identity、版本与去重

### 11.1 URL Identity

保存：

```text
observed_url
normalized_url
canonical_url
redirect_target
canonical_tag_target
source_scope
```

不要仅以 canonical tag 无条件合并，需要 Source Policy 与跨域白名单。

### 11.2 Document Identity

优先级：

1. CMS/API stable id；
2. canonical URL + Source；
3. stable permalink；
4. content signature + metadata 辅助合并。

### 11.3 新版本判定

同时计算：

- `raw_body_hash`：网络响应字节/规范化原始正文 hash；
- `semantic_body_hash`：去除允许变化的模板噪声后 hash；
- Candidate/IR hash。

规则：

- 原始 hash 不变：不新建 Document Version；
- 原始变、语义不变：记录 fetch revision，可按策略不产生知识版本；
- 语义 hash 改变：生成新 Document Version；
- Renderer 升级：生成新 Projection Release，不伪造内容更新时间。

### 11.4 删除与 Tombstone

连续出现 404/410 或 Provider 明确删除时：

- 不删除历史 Artifact；
- Document 标记 tombstone；
- 保存 first_missing_at / confirmed_deleted_at / evidence；
- 搜索层按产品策略隐藏或降权。

### 12.1 Task 模型


### 12.2 Transactional Outbox

业务状态更新与后续事件在同一 PostgreSQL transaction 中写 Outbox，独立 Relay 发布到 Redis Streams。

避免：

```text
DB 已提交但消息没发
消息已发但 DB 没提交
```

### 12.3 Lease + Fencing

Worker 领取 Task 时递增 fencing token；所有写入必须带 token 条件，过期 Worker 即使恢复也不能覆盖新 Worker 结果。

### 12.4 Retry 与 DLQ

错误分类：

```text
TRANSIENT_NETWORK

ROBOTS_BLOCKED
ACCESS_DENIED
PARSER_ERROR
BROWSER_CRASH
VALIDATION_ERROR
QUALITY_REPAIRABLE
PERMANENT_NOT_FOUND
CONFIG_ERROR
```

不同错误独立退避；永久错误不无限重试。

## 13. Crawl4AI Runtime Service Plane

将 Crawl4AI 作为受控执行服务，而不是业务数据库。

组件：

```text
Runtime Registry
Runtime Gateway
Config Compiler
Browser Pool
Local Dispatcher
Result Materializer
Artifact Promotion Gate
Runtime Contract Test
```

要求：

- pinned package/version/image digest；
- 每次调用带 `runtime_release`；
- bounded micro-batch；
- `arun_many(stream=true)` 或等价流式处理，避免巨型结果常驻内存；
- Runtime 健康异常时 drain/replace，不在活跃任务中强杀共享 Browser；
- browser/context/session 有 TTL 与最大任务数；
- Runtime 本地 SQLite/cache 清理不影响业务恢复；
- 任何需要持久化的 HTML、Screenshot、PDF、diagnostic 必须晋升 S3。

## 16. 安全、合规与能力边界

1. 默认遵守 robots 与站点公开访问政策；
2. 不默认绕过登录墙、付费墙、CAPTCHA、WAF；
3. Web/API 普通用户不能提交任意 JS/Python；
4. Proxy、CDP、Browser Profile、文件路径、Webhook、secret 都走 capability allowlist；
5. URL 必须通过 SSRF 防护：scheme、host、DNS/IP 重解析、私网/metadata 地址封禁；
6. 对下载文件做 MIME、大小、扩展名、压缩炸弹检测；
7. Webhook 出站限定允许域；
8. Secret 只以引用进入 Worker；
9. Runtime 与控制面网络隔离；
10. Source Profile 修改必须记录操作者、release、diff。

## 19. 部署与扩展

### 19.1 初始生产拓扑

```text
2x API/Web
2x Scheduler/Outbox Relay
N x Discovery Worker
N x HTTP Fetch Worker
N x Browser Runtime Worker
N x Extract/Render Worker
PostgreSQL HA
Redis HA
S3/MinIO
OpenSearch
pgvector
Prometheus/Grafana
```

### 19.2 扩容维度

- Discovery Worker 按 Provider backlog；
- HTTP Worker 按 network throughput；
- Browser Worker 按内存/CPU 与 host policy；
- Extract Worker 按 Artifact backlog；
- Search independently scale。

不要把 1000 个站映射成 1000 个常驻 Worker；Worker 是共享执行池，Source 是数据/策略实体。

### 19.3 PostgreSQL 规模策略

- URL/Observation/Task 表提前做索引与分区；
- 高频 Task 状态变更与不可变 Artifact metadata 分开；
- 尽量批量 upsert；
- Coverage 汇总用异步 materialized snapshot；
- OpenSearch/pgvector 不参与事务真相。

## 20. 新站接入流程

```text
1. 创建 Source Draft
2. DNS/robots/sitemap/feed/CMS 自动探测
3. 生成 Provider Candidate
4. 小样本抓取 20~100 URL
5. 评估 HTTP/Browser 比例、正文质量、结构保真、语言
6. 自动生成/人工确认 Extraction Recipe
7. 配置 Revalidation Policy
8. 灰度 Backfill
9. 验证 Coverage/Quality/Cost
10. 批准 Production Backfill
11. 自动切入 Incremental
```

低成本扩站的关键是把站点差异沉淀为：

```text
Source Profile + Provider Adapter + Recipe + Revalidation Policy
```

而不是新建爬虫项目。

## 23. 验收标准

系统达到生产可用至少满足：

1. 1000 个 Source 可通过配置接入，不需要 1000 个代码仓库；
2. 任一 Source 能展示历史 Provider、Coverage 与 Known Gap；
3. 大型 Backfill 不阻塞 Incremental；
4. 任一 Markdown 可反查 Raw Artifact、URL、Attempt、Release；
5. Worker/Browser Runtime 重启不丢业务 Task；
6. Runtime cache 全清后平台仍可恢复；
7. `hit_fallback` 不会被记为已验证新鲜；
8. 定期 full refresh 能测量 validator 漏检率；
9. 代码、表格、公式、CJK 样本达到设定结构/文本召回阈值；
10. 新增普通技术博客能在 Profile + Recipe 范式内完成接入；
11. 所有高能力配置经过 Capability Firewall；
12. Search/RAG 结果能回溯具体 Document Version 与原始证据。

## 24. 最终推荐架构

最终采用：

> **PostgreSQL Truth Store + S3/MinIO Immutable Artifact + Redis Streams Durable Transport + Declarative Source/Profile + Multi-Provider Discovery + Persistent Frontier + Revalidation Engine + HTTP First / Browser Slow Lane + Crawl4AI Runtime Service Plane + Extraction Portfolio + Canonical IR + Deterministic Markdown + OpenSearch/pgvector + Web Admin。**

其中最关键的边界是：

- **Provider 返回不是 Coverage 真相；**
- **Runtime cache 不是 Freshness 真相；**
- **Markdown Candidate 不是 Canonical 真相；**
- **搜索索引不是 Document 真相。**

Coverage、Freshness、Artifact、Document Version 与 Release 全部由平台自己的持久模型管理。这样既能完成 1000 个技术博客的全历史回填，又能以可解释、可扩展、低浏览器成本的方式长期做增量同步和 Web 运营。
