# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个长期运行、可横向扩展、可审计、可重放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章并稳定清洗为 Markdown；后续持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计和离线重处理。

设计按以下量级考虑：

- 1000+ Source，后续扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 千万级 Chunk / Embedding 长期增长；
- 中英日韩等多语言技术内容；
- HTTP 为主，Browser 为受控 fallback；
- 历史发现支持 CMS API、Sitemap、Feed、Archive、Common Crawl URL Index 等多来源；
- PostgreSQL + Object Storage 保存事实；Markdown、Filtered Markdown、Chunk、Embedding、全文/向量索引均为可重建 Projection。

平台必须能回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已基本覆盖；
2. 一个 URL 从哪里发现、如何规范化、经过哪些跳转后被抓取；
3. 一个动态页面执行了哪些点击/滚动/等待，使用哪一版 Recipe；
4. 一个 Markdown 来自哪个 Snapshot、Extractor、Filter、Schema 和 Document Version；
5. 源站变化后哪些内容真的变化，哪些派生物需要重建；
6. Chunk、Embedding、Analyzer、Browser Runtime、内容过滤器和索引策略升级后能否不重新访问源站完成重放；
7. 抓取失败、结构漂移、Browser 成本、内容过滤误删、反爬、索引或检索回归时能否在 Web 中定位和运营；
8. 一个批量抓取任务发生取消、限流、Worker 崩溃或流式消费中断后，哪些 URL 已可靠提交、哪些仍应重试。

## 2. 核心设计原则

1. **Config First**：普通站点主要通过 Source / Site Profile / Release 配置接入，不修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence 与 exhaustion reason 证明，不能用“队列为空”或达到 `max_pages` 冒充完整。
3. **Discovery Before Fetch**：先低成本发现、分类、去重 URL，再决定是否真实抓取正文。
4. **Authoritative First**：CMS/API/Sitemap/Feed 优先，Archive/Common Crawl 用于补洞和外部证据。
5. **HTTP First, Browser Last**：Browser 只处理动态发现面、动态渲染、结构探索或低质量 fallback。
6. **Recipe, Not Site-Specific Code**：动态交互和结构化抽取必须声明式、版本化，禁止长期堆积 `if site == ...` 分支。
7. **Bounded Interaction**：点击、滚动、等待、session 复用都必须有预算和明确停止条件。
8. **Snapshot First**：先保存不可变网络事实，再做抽取、清洗、建版。
9. **IR First, Markdown as Projection**：Canonical IR / Document Version 是内容事实层，Markdown 是可重建输出。
10. **Filtered Content Is Projection**：Pruning、BM25、LLM Filter 都是有损派生，不得覆盖 Canonical IR 或 canonical Markdown。
11. **Stable Identity**：Document、Version、Chunk、Embedding、Index 身份必须稳定且 release-aware。
12. **Release Everything**：影响结果的策略、Browser Recipe、Schema、Content Filter、模型、索引和 Runtime 均版本化。
13. **Idempotent + Recoverable**：任务具备幂等键、lease、fencing、checkpoint、retry、partial success。
14. **Stream and Commit Per URL**：多 URL 批任务按单 URL 流式持久化、提交与 ack，一个失败项不能回滚成功项。
15. **Local Dispatcher Is Not Global Scheduler**：Crawl4AI Dispatcher/RateLimiter 只保护单 Worker，平台 Scheduler 才是 durable 调度与限流真相。
16. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary、Search Index 故障不能阻塞抓取事实同步。
17. **Evidence Everywhere**：发现、分类、跳转、交互、抓取、抽取、过滤、身份、版本和检索均保存证据。
18. **Language-aware Retrieval**：分词、stemming、stopwords、技术 token 处理由 Analyzer Release 管理。
19. **Hybrid Retrieval by Default**：技术语料默认 BM25 + Vector + RRF，Reranker 是可降级增强层。
20. **Benchmark Before Switch**：Analyzer、Content Filter、Embedding、Vector Index、RRF、Reranker 升级经固定评测后切生产。
21. **Generation Instead of Destructive Rebuild**：索引升级后台构建新 Generation、验证、原子切换，禁止生产 drop-and-recreate。
22. **Web 管理是平台能力**：Coverage、失败、版本、成本、Recipe、Schema、Filter、Generation、实验和 Release 都必须可运营。
23. **安全边界每跳执行**：Redirect 和 Browser navigation 每跳重新执行 SSRF/Egress/Scope 校验。
24. **Ephemeral State Is Not Truth**：Crawl4AI cache、Browser session、Worker 内 dispatcher state 不承载决定性业务状态。


## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST / Command API、Schema 校验、内部服务接口；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、URL Observation、Resolution、Fetch、Interaction、Document、Version、Projection、Release、Audit、Outbox；
- **Transactional Outbox**：数据库状态变更与消息发布事务一致；
- **Redis Streams**：consumer group、retry、backpressure，只做任务运输；
- **React/Vue + TypeScript**：Web 管理台。

### 4.2 抓取与抽取

- **HTTPX / aiohttp**：HTML、Feed、Sitemap、API、Conditional GET、低成本跳转解析；
- **BeautifulSoup / lxml / CSS / XPath / Regex**：wrapper、meta refresh、selector、结构化抽取；
- **Trafilatura / Readability**：确定性正文候选；
- **Crawl4AI / Playwright**：URL Seeding、Prefetch、动态页面、Browser Interaction、结构化抽取、Markdown Candidate、Browser fallback 与 Worker 内批量调度；
- **S3 / MinIO**：raw response、HTML、Rendered DOM、Feed payload、PDF、WARC、Canonical IR、Markdown、Asset、debug artifact、fixture。

Crawl4AI 生成的 `raw_markdown`、`fit_markdown` 都只能作为 Extraction Candidate / Projection，不能替代 Snapshot 与 Canonical IR。

### 4.3 历史发现

- CMS API / Sitemap / RSS / Atom / JSON Feed；
- Archive / Category / Tag / Author / Docs TOC；
- Common Crawl URL Index；
- DuckDB / Athena / Spark / Polars 用于批量历史索引扫描。

### 4.4 检索

- **OpenSearch**：生产 BM25、过滤、聚合、Alias/Generation、Hybrid Search；
- **pgvector / OpenSearch kNN**：首期向量实现；
- **Qdrant / Milvus**：向量规模或独立扩缩容需求提高后可替换；
- **RRF**：默认融合；
- **Cross Encoder Reranker**：可选精排服务。

### 4.5 可观测与部署

- Prometheus + Grafana + OpenTelemetry；
- Docker / Kubernetes；
- Artifact Registry 保存应用镜像、浏览器内核、Embedding/Reranker 模型和运行时依赖。

## 9. 新站接入 PROBE

新增站点先 PROBE，不直接深爬：

1. 规范化 entry URL，确定 domain、allowed origins、scope；
2. 获取 robots 和 Sitemap 声明；
3. 探测 Sitemap Index / Sitemap；
4. 探测 RSS / Atom / JSON Feed；
5. 探测 WordPress REST、Ghost、Substack 等平台能力；
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination；
7. 低成本查询 Common Crawl；
8. 对 URL path 做模板聚类；
9. 对未知 hub 做轻量 HTML + links Prefetch；
10. 小预算 BFS / BestFirst 探索未知结构；
11. 抽样比较 HTTP 与 Browser 的正文质量与成本；
12. 检测 wrapper、short-link、meta refresh、JS redirect；
13. 如果只有动态页面才能发现历史 URL，生成候选 Interaction Recipe；
14. 对重复 DOM 生成候选 Structured Schema，并用 fixture 校验；
15. 推断语言、Analyzer、Content Filter 和 article template；
16. 对已知 URL 类型生成 Route Match fixture；
17. 自动生成首版 Profile，在 Web 审核后启用。

Prefetch 只用于轻量发现、分类和路由决策，不是正文 Snapshot，也不能替代 Fetch Attempt。

## 11. Common Crawl 的边界

Common Crawl 只能证明某 URL 在某次 crawl 中被观察或抓取，不能证明站点历史完整。

```text
common_crawl_observation
  source_id
  crawl_id
  url_id
  capture_time
  status
  mime
  warc_filename
  warc_offset
  warc_length
  content_digest
```

1000 站点级历史枚举优先批量扫描 URL Index，并缓存 `(registered_domain, crawl_id)`；CDX 只做低频补充。

恢复已下线文章时标记 archive origin 和 capture time，不能伪装为当前 live fetch。

## 12. URL Normalization、Classification 与 Resolution

### 12.1 Normalization

典型规则：lowercase host、default port removal、fragment removal、path slash normalization、安全 percent-encoding、query key ordering、tracking param removal、站点级 semantic param allowlist。

禁止全局删除所有 query，因为 `?id=123`、`?p=456`、`?page=7` 可能具备正文或分页语义。

### 12.2 Classification

```text
ARTICLE_CANDIDATE
DISCOVERY_SURFACE
ASSET
NAVIGATION
EXTERNAL_REFERENCE
IGNORE_BY_POLICY
UNKNOWN
```

过滤只影响后续调度，原始 Observation 与 Evidence 永久保留。

### 12.3 Resolution Plane

```text
Observed URL
 -> Normalized Candidate
 -> HTTP Redirect
 -> Wrapper Param / HTML Target
 -> Meta Refresh
 -> Browser Navigation Fallback
 -> Resolved Fetch Target
```

`rel=canonical`、`og:url` 属于 Identity Evidence，不等同于 Redirect。

## 13. Fetch Route Policy

默认：

```text
HTTP_STATIC
 -> HTTP_ALT_HEADERS
 -> HTTP_PLATFORM_API
 -> BROWSER_CRAWL4AI_RECIPE
 -> BROWSER_PLAYWRIGHT_CUSTOM
 -> SITE_CUSTOM_EXTRACTOR
```

Browser Worker 与 HTTP Worker 独立部署。Browser 不与 API 服务共享 Playwright event loop。

## 14. 调度、`arun_many()` 与 Worker 并发模型

Crawl4AI 的 `arun_many()` / Dispatcher 只负责单 Worker 内多 URL 并发、内存保护和本地速率控制，不能替代平台 durable scheduler。

### 14.1 两层调度

```text
平台 Scheduler
  global token bucket
  + registrable-domain token bucket
  + source token bucket
  + route/provider budget
  + priority
  + durable Task / lease / retry / next_run_at
        ↓
Browser/Crawl4AI Worker
  MemoryAdaptiveDispatcher / SemaphoreDispatcher
  + RateLimiter
        ↓
AsyncWebCrawler.arun_many(stream=True)
```

平台限流是跨节点持久事实；Worker-local RateLimiter 只是第二道安全阀。429/503、`Retry-After` 等信号需要写回 Task 的 `next_run_at`，不能只在某个 Worker 内 sleep 后丢失。

### 14.2 小批 lease + 单 URL 流式提交

```text
lease N tasks
 -> build per-URL CrawlerRunConfig
 -> arun_many(stream=True)
 -> result arrives
 -> validate lease/fencing token
 -> persist FetchAttempt / Snapshot per URL
 -> commit per URL
 -> ack per URL
```

一个失败 URL、超时 URL 或取消 URL 不能回滚整个 batch。严禁用一个长事务包住整个 `arun_many()`。

### 14.3 自适应批大小

批次大小根据：

- Worker 可用内存；
- 页面 DOM/HTML 大小；
- Browser context/page 数；
- 响应时延；
- 单域名并发限制；
- 对象存储吞吐；
- Extraction backlog；
- CPU；
- 流式结果消费速度。

动态调整，不固定 `batch_size=1000`。

### 14.4 per-URL CrawlerRunConfig

```text
PDF URL        -> PDF extraction config
Article URL    -> article config
Dynamic Hub    -> interaction config
JSON/API       -> structured config
Fallback       -> default config
```

所有 matcher 的顺序、优先级和 config 引用保存到 Route Match Release，发布前通过 fixture，防止同一 URL 因规则顺序变化静默改路由。

## 16. Content Filter 策略与质量门禁

### 16.1 PruningContentFilter

Pruning 是 query-independent 的启发式 DOM 裁剪。当前 Crawl4AI 实现包含以下主要信号：

```text
text_density     weight 0.4
link_density     weight 0.2
tag_weight       weight 0.2
class_id_weight  weight 0.1
text_length      weight 0.1
```

并结合 `min_word_threshold`、fixed/dynamic threshold、tag importance 等进行筛选。

技术博客的风险包括：短代码、参数定义、表格、链接密集参考资料、简短 changelog 被误删。因此启用：

```text
preserve_tags
preserve_classes
```

用于保护语义结构。例如全局可谨慎保护 `pre/code/table/th/time`，站点级再对白名单 class 做精确保护。禁止宽泛保护 `div/span`。

### 16.2 BM25ContentFilter

Crawl4AI 的 BM25 Filter 是页面块级词法相关性过滤，不是向量检索。当前实现使用 `rank_bm25.BM25Okapi`，大致流程：

```text
HTML
 -> body text chunks
 -> query
 -> lower/split tokenization
 -> optional Snowball stemming
 -> clean_tokens
 -> BM25 score
 -> tag priority weight
 -> threshold filter
```

部分结构标签会对 BM25 分数叠加权重，最终类似：

```text
adjusted_score = bm25_score * tag_weight
```

它适用于：

- 针对某主题生成临时精简视图；
- 给 LLM 减少 token；
- RAG query 阶段的局部候选过滤。

禁止用于：

- canonical Markdown；
- Document identity；
- Document Version hash；
- 判断源站正文是否变化。

当前 Crawl4AI BM25 Filter 默认英文语言/词干语义并采用空白型 tokenization 假设，中文/CJK 不能直接沿用。Filter Release 必须记录 `use_stemming`、`stemmer_language`、`tokenization_mode`、`language_scope`。

生产全文 BM25 必须由独立 Analyzer Release 和 OpenSearch 等检索引擎负责，不能把 Crawl4AI 页面过滤器当全库检索器。

### 16.3 LLM Filter

LLM Filter 只用于低频、高价值、可接受成本的派生视图或离线分析。必须记录模型 Release、prompt/schema、token/cost、输入 hash，不能进入 canonical 内容链路。

### 16.4 Filter Quality Features

```text
content_retention_ratio
heading_retention_ratio
code_block_retention_ratio
table_retention_ratio
list_retention_ratio
link_retention_ratio
reference_section_retained
preserved_node_count
preserve_rule_hit_count
language_consistency
truncation_signal
```

对每个 Source/Template 维护历史基线。Filter Release 导致 retention 或 code/table preservation 突降时进入 quarantine，不自动切生产。

Query-dependent Projection 的幂等键必须包含 `runtime_query_hash`，并配置 TTL/缓存策略，防止无限膨胀。

## 18. 增量同步与 Reconcile

信号优先级：

```text
Feed/API cursor
 -> Sitemap lastmod
 -> High-yield Surface
 -> Conditional GET
 -> Metadata Probe
 -> Full HTTP
 -> Browser fallback
```

保存 ETag、Last-Modified、previous_body_hash。

304 时：

- 不创建 body Snapshot 副本；
- 不抽取；
- 不建新 Version；
- 不重复 Markdown/Filter/Chunk/Embedding Projection；
- 只记录 Observation 与 Fetch Attempt。

调度分层：

```text
Tier 0 Feed/API            分钟级
Tier 1 Sitemap/Blog Index  10~60 分钟
Tier 2 Category/Archive    1~6 小时
Tier 3 Deep Reconcile      每周/每月
Tier 4 Common Crawl        新 collection 或按月
```

根据新 URL 率、失败率、重复率、Browser 比例和成本动态调频。

即使有 Feed，也周期 Reconcile Sitemap、Archive、Surface、Common Crawl，用于发现 Feed 窗口外遗漏、URL 迁移、删除、结构漂移和新历史候选。

`CacheMode.DISABLED/BYPASS` 只适合特定抓取策略或调试，不能替代 ETag/Last-Modified、provider cursor 和 Reconcile 驱动的生产增量同步。Crawl4AI cache 命中与否不能决定 Document Version。

## 21. Chunk 设计与稳定身份

### 21.1 主策略：Structure-aware

默认：

1. Heading / Section 是第一层语义边界；
2. 段落、列表、引用尽量完整；
3. fenced code 默认不拆；
4. 表格默认不拆；
5. 保存 heading path 与 block range；
6. 超长代码/表格走专门策略；
7. 超长普通 section 再进入 recursive fallback。

### 21.2 Recursive fallback

优先段落、换行、语言标点，再退化到空格/字符；长度优先使用目标 Embedding tokenizer 的 token 计数。

`chunk_size` 与 `overlap` 属于 Chunk Release，并通过检索评测选择。

### 21.3 稳定 Chunk ID

禁止：

```text
hash(file_path + chunk_index)
hash(source + chunk_index)
```

推荐：

```text
chunk_id = hash(
  document_version_id
  + chunk_release_id
  + logical_block_range
  + normalized_text_hash
)
```

文档头部新增内容不能导致所有后续未变化 Chunk 被误判为新 Chunk。

## 22. Embedding 与流式批处理

### 22.1 Embedding Release

```text

```

Embedding ID：

```text

```

### 22.2 流式 Worker

禁止一次性把全库 Chunk 加载到内存并一次 encode：

```text
query pending chunks
 -> lease batch
 -> tokenize/embed
 -> validate
 -> persist embedding
 -> idempotent upsert target generation
 -> commit per-item result
 -> checkpoint
 -> next batch
```

支持动态 batch、最大 batch token、OOM 自动缩 batch、retry、partial success 和 backpressure。Embedding backlog 不阻塞 Source Sync。

### 22.3 Vector Payload Contract

写入向量引擎前统一校验：

```text
embedding_release_id == target_generation.embedding_release_id
dimension == embedding_release.dimension
values are numeric
no NaN / Inf
canonical dtype / serialization matches adapter
normalization invariant matches release when required
chunk_id and embedding_id are present
payload schema version matches vector_index_release
```

单条坏向量进入 quarantine / retry，不拖垮整个 batch。

## 25. Reranker、Context Assembly 与索引 Generation

Reranker 不扫描全库：

```text
大规模粗召回
 -> Top-N 融合候选
 -> Cross Encoder Reranker
 -> Top-K
 -> Context Assembly
```

独立 `rerank-service`：模型常驻优先、dynamic batch、最大 batch token、GPU 并发限制、OOM 自动降 batch、超时降级到 RRF，不进入 Source Sync 关键路径。

Context Assembly 根据 document diversity、heading path、chunk adjacency、same-document overlap、token budget、source trust、duplicate suppression 组装。

Index Generation 生命周期：

```text
BUILDING
 -> VALIDATING
 -> READY
 -> ACTIVE
 -> RETIRED
```

触发新 Generation：Chunk Release、Analyzer Release、Embedding 模型/维度/metric、Vector Index Release、OpenSearch schema 或检索数据模型变化。

新 Generation 后台构建、离线回归、READY 后 Alias/逻辑指针原子切换；禁止生产索引 drop-and-recreate。

## 33. 验收标准

### 33.1 Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有 exhaustion evidence；
- known gap 可枚举、可重跑；
- 达到预算不会错误标 COMPLETE；
- Common Crawl 不作为完整性证明。

### 33.2 增量

- Feed/API/Sitemap 新文章在目标 SLA 内进入系统；
- 304 不重复抽取、建版、投影；
- 未变化 Projection 不重复计算；
- Reconcile 能发现 Feed 窗口外遗漏和结构漂移；
- 不依赖持续 `CacheMode.DISABLED` 做全量重抓；
- Crawl4AI cache 状态不影响文档事实版本。

### 33.3 Browser / Recipe / Batch

- Browser 不是默认抓取路线；
- 动态 Discovery Surface 可独立使用 Browser，文章正文仍优先 HTTP；
- 每个 Interaction Recipe 可版本化、可 diff、可回滚；
- click/scroll/wait 有明确预算和停止条件；
- `arun_many(stream=True)` 结果按 URL 独立提交；
- 100 URL 中 90 成功时 90 个成功事实不会被 10 个失败项回滚；
- stream 提前关闭、timeout、cancel 后 Browser page/context 与 Dispatcher permit 可回收；
- Worker Dispatcher/RateLimiter 不替代 durable scheduler；
- 429/503/Retry-After 能写回 durable next_run_at；
- Runtime Artifact 能复现 Browser + Crawl4AI 运行环境。

### 33.4 Route Match

- Article/PDF/API/Dynamic Hub 各有 URL fixture；
- 重叠 matcher 有显式优先级；
- expected rule 与 actual rule 可回归；
- 未命中时进入明确 fallback；
- Route Match Release 改动可 diff、可灰度、可回滚。

### 33.5 Schema / Markdown / Filter

- Structured Schema 有 fixture、必填字段和 zero-match 告警；
- 抽样验证 title/author/time、正文完整、导航噪声低、heading 正确、code/list/table/image/link 保留；
- Markdown 可从 IR 确定性重建；
- Crawl4AI Raw Markdown 只是候选/对照；
- Pruning/BM25/LLM Filter 不覆盖 canonical Markdown；
- query-dependent `fit_markdown` 不参与文档身份和版本判断；
- Pruning Release 可记录 `preserve_tags/classes`，技术代码、表格、参数结构有保护测试；
- BM25 Filter 明确为词法过滤，不与向量检索混淆；
- CJK Filter 不依赖默认英文 stemming/whitespace tokenization；
- Filter Release 有 retention/code/table/heading 门禁；
- REFILTER 不重新访问源站。

### 33.6 Chunk / Embedding

- Chunk 保留 heading path 与 block range；
- fenced code 与表格默认不破坏；
- Chunk ID 不依赖 chunk_index；
- RECHUNK 不创建新 Document Version；
- REEMBED 不重新抓源站；
- Embedding backlog 不影响 Source Sync；
- 向量维度、NaN/Inf、归一化、Release/Generation 不一致在入库前拦截；
- 单条无效向量不会导致整批回滚。

### 33.7 检索

- 中文/英文/技术 token 有固定回归集；
- CJK 不依赖 whitespace tokenizer；
- BM25 + Vector + RRF 可解释；
- Vector Index 参数有 benchmark；
- Reranker 故障可降级；
- Retrieval Trace 能区分不同 score type；
- 新 Generation 验证通过后才能 ACTIVE；
- 生产升级无 drop-and-recreate。

### 33.8 可靠性

- Worker 崩溃后 lease 可恢复；
- stale worker 的旧 fencing token 不能覆盖新结果；
- fan-out 保留 partial success；
- Browser session 丢失不丢 durable checkpoint；
- stream cancellation 不造成长期 page/task/permit 泄漏；
- Embedding/Index/Reranker/Filter 故障不阻塞 Source Sync；
- Runtime/Model Artifact 可复现、可回滚；
- 所有高风险管理操作可审计。

## 34. 最终架构原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：发现、分类、去重后再抓正文。
3. Authoritative First：权威来源优先，Archive/Common Crawl 只补洞。
4. HTTP First, Browser Last：Browser 是昂贵兼容层，不是默认抓取器。
5. Browser Discovery Is Separate：动态发现面可用 Browser，但不要因此把全部文章正文 Browser 化。
6. Recipe, Not Site-Specific Code：动态交互用版本化 Recipe，不在业务代码堆站点分支。
7. Deterministic Schema First：规则化结构优先 CSS/XPath/Regex，LLM 只做辅助和 fallback。
8. Bounded Interaction：点击、滚动、等待、session 均有明确预算和停止条件。
9. Worker Dispatcher Is Local：Crawl4AI `arun_many()`/Dispatcher/RateLimiter 负责 Worker 内资源保护，平台 durable scheduler 负责全局任务事实。
10. Stream and Commit Per URL：批量抓取结果流式持久化，失败项独立重试，不整批长事务。
11. Fence Stale Workers：lease/fencing token 防止超时 Worker 写入陈旧结果。
12. Route Match Is Released：per-URL `CrawlerRunConfig` matcher 有顺序、fixture、Release 和回滚。
13. Runtime Cancellation Is Tested：流式提前关闭、timeout、SIGTERM 必须验证 page/context/permit 清理。
14. Snapshot First, Replay Later：原始网络事实不可变，规则升级优先离线重放。
15. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
16. Filtered Content Is Derived：Pruning/BM25/LLM 都是有损派生，不覆盖 canonical 内容。
17. Preserve Technical Structure Explicitly：Pruning 用受控 `preserve_tags/classes` 保护代码、表格和参数结构。
18. BM25 Filter Is Lexical：Crawl4AI 页面 BM25 是 BM25Okapi 词法过滤，不是向量检索。
19. Language Policy Is Explicit：Filter 与生产检索分别管理 stemming、tokenization、Analyzer 和语言范围。
20. Query-dependent Views Are Not Versions：BM25/LLM query view 不创建正文版本。
21. Stable Chunk Identity：Chunk 身份不能依赖 file path + chunk_index。
22. Structure-aware First：技术文档优先按标题、块、代码、表格切分。
23. Streaming Embedding：批次、lease、checkpoint、幂等，禁止全库一次性加载。
24. Validate Before Vector Write：向量维度、有限数值、归一化、序列化和 Release 一致性写前校验。
25. Language-aware BM25：生产全文检索有可版本化 Analyzer。
26. Benchmark Vector Index：IVF/HNSW/FLAT 等通过 recall/latency 基准选择。
27. Hybrid Retrieval by Default：BM25 与 Vector 互补，RRF 为稳定融合基线。
28. Typed Retrieval Scores：不同阶段 raw score 带 score type，不做跨阶段数值比较。
29. Reranker as Optional Service：精排可降级，不进入事实同步关键路径。
30. Generation Instead of Destructive Rebuild：后台构建、验证、原子切换。
31. Release Everything：策略、Recipe、Schema、Route、Filter、模型、索引、浏览器、运行时均可追踪和回滚。
32. Ephemeral State Is Not Truth：Crawl4AI cache、proxy runtime、browser session、dispatcher state 不能成为业务真相。
33. Model Artifact Is Immutable：模型在构建阶段固定 revision 与 digest，生产不临时下载。
34. Benchmark Before Switch：任何 Content Filter、Analyzer、Runtime 或检索升级经过固定评测。
35. Idempotent + Recoverable：任务可重复、可恢复、可观察，partial success 不丢失。
36. Source Sync 与 AI 解耦：抓取事实不依赖 Embedding、Reranker、LLM 或 Search 服务。
37. Evidence Everywhere：所有重要判断均保存可解释证据。
38. Web 管理是平台能力：Coverage、质量、Recipe、Route、Filter、版本、成本、Batch、Generation、实验和 Release 都必须可运营。
