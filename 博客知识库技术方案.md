# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站、公开 Newsletter** 的长期知识库采集平台，并能平滑扩展到数千站点、百万级文章。

系统必须同时满足：

1. **全历史回填**：尽可能发现并抓取每个已批准 Source 的全部历史文章；
2. **持续增量同步**：发现新文章、正文更新、URL 迁移、删除和重发布；
3. **稳定输出 Markdown**：由不可变网页事实经过抽取、质量校验和 Canonical IR 后生成可重建 Markdown；
4. **低成本扩站**：新增网站优先通过 Provider、Source Profile、Recipe 配置完成，而不是复制一份新爬虫；
5. **Web 可运营**：支持 Source 接入、Backfill、Incremental、Coverage、失败诊断、版本回放、质量、成本、检索和审计；
6. **可搜索与 RAG**：支持关键词、向量、混合检索、同主题聚合和可追溯引用；
7. **可选内容编排**：可以基于已经通过质量闸门的知识库生成 Digest、专题、Newsletter，但生成结果不得污染采集事实层；
8. **可观测、可恢复、可重放**：任意文档、任务、生成稿和发布结果都能解释其来源、版本和执行路径；
9. **部署可渐进扩展**：开发期可单机 Docker Compose，生产期按队列拆分并水平扩容，业务语义不重写；
10. **模型可替换**：云模型、本地 LocalAI/Ollama/vLLM/OpenAI-compatible endpoint 都通过统一 Provider 抽象接入，采集主链不依赖 LLM。

### 1.1 核心 SLO

- **Coverage**：每个 Source 能解释发现 Provider、时间分区、分页/游标、停止条件和 Known Gap；
- **Freshness**：新文章从发布/发现到 PASS Markdown 的延迟可监控；
- **TTFM**：Time To First Markdown，从 URL 首次发现到首个可用 Markdown；
- **TTFR**：Time To Fully Ready，从发现到 Summary/Embedding/Entity 等增强完成；
- **Extraction Quality**：标题、正文完整率、噪声率、代码块/表格/列表保留率、截断率；
- **Reliability**：任务成功率、Retry、DLQ、Queue Age、Checkpoint Resume 成功率；
- **Browser Efficiency**：HTTP 命中率、Browser avoided、Browser recovery、Browser 单文档成本；
- **Identity Quality**：Document Identity 误合并/漏合并率；
- **Traceability**：任意 Markdown 可回溯 Source、URL、Artifact、Extractor、Quality、Renderer Release；
- **Retrieval Quality**：Recall@K、MRR、nDCG、stale-version rate、duplicate-result rate；
- **Editorial Quality**：citation reject rate、human edit ratio、agent disagreement、publish rollback/失败率；
- **Cost**：按 Source、Run、Queue Class、每 1000 篇 PASS 文档统计抓取、Browser、存储、Search、LLM、Embedding 成本。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不把 HTTP 200、DOM 很长或 Crawler success 直接视为正文正确；
- 不把搜索引擎结果数当历史完整性证明；
- 不把 Crawl4AI 原始 Markdown、LLM 摘要或改写直接作为 Canonical Markdown；
- 不允许 LLM 生成或覆盖 canonical/source citation URL；
- 不因 URL 曾抓过就永久停止复检；
- 不把 Redis、Browser Session、Crawler Cache、Search Index、Agent Memory 当业务真相；
- 不让慢路径失败、预算耗尽或降级结果静默进入 PASS；
- 不把语义相似直接等价为同一 Document Identity；
- 不让用户偏好、Newsletter 选题或 AI Editor 决定某个已批准 Source 的文章是否进入 Collection Truth；
- 不允许 Editorial Agent 默认自行扩大来源集合或绕开采集主链重新抓网页；
- 不默认使用 Browser 自动操作第三方 Newsletter 后台；
- 不默认对所有文档构建 GraphRAG。

## 2. 核心设计原则

1. **Coverage First**：先建立 URL Inventory，再批量抓正文；
2. **Authoritative First**：CMS/API、Sitemap、RSS/Atom、Archive 优先；
3. **Search Is Gap Only**：外部搜索只做补洞和新来源发现，不是 Coverage Truth；
4. **Discovery / Fetch / Extract / Quality 分离**；
5. **HTTP First, Browser Last**：Browser 是受治理慢路径；
6. **按交互复杂度路由**：静态、渲染、简单交互、复杂有状态交互分别处理；
7. **Crawl4AI 做内容型 Browser 抽象，Playwright 做状态型交互**；
8. **Snapshot First**：先保存不可变 Artifact，再抽取和清洗；
9. **Extractor Is Candidate Generator**：任何抽取器只生成候选；
10. **Critique Before Publish**：Candidate 必须经过独立 Quality Gate；
11. **Repair Is Bounded**：修复是有限状态机，禁止无限递归重试；
12. **Canonical IR First, Markdown as Projection**；
13. **Recipe, Not 1000 Site Scripts**：站点差异优先由 Profile/Policy/Recipe 表达；
14. **Source Adapter, Not Provider Special Cases**：RSS/API/Sitemap/Newsletter 等统一为 Observation；
15. **Stable Identity**：Source、URL、Artifact、Document、Version 使用稳定 ID；
16. **Idempotent + Recoverable**：任务有幂等键、lease、fencing token、checkpoint；
17. **Fair by Default**：大站 Backfill 不得饿死 Incremental 和小站；
18. **Bounded Concurrency Everywhere**：禁止无界 asyncio gather、Browser Context、LLM fan-out；
19. **No Silent Degradation**：截断、预算耗尽、降级必须显式；
20. **Release Everything That Changes Results**：Profile、Route、Recipe、Runtime、Extractor、Quality、Renderer、Prompt、Model、Embedding、Rank、Publication Adapter 全部版本化；
21. **LLM 低频、旁路、可替换**：采集主链默认确定性；
22. **Collection Truth 与 Discovery/Serving/Curation 分离**；
23. **Document Identity 与 Story Cluster 分离**；
24. **Progressive Enrichment**：Quality PASS 后先发布 Markdown，慢增强异步补齐；
25. **Priority Means When, Not Whether**：优先级决定何时处理，不决定是否永久保存；
26. **Feedback Is Evidence, Not Policy**；
27. **Provenance Before Generation**：引用必须来自真实网络观察；
28. **Evidence Before Persona**：AI Writer 的人格只改变表达，不改变事实权限；
29. **Draft First Publication**：外部内容发布默认先创建 Draft，再人工确认；
30. **Same Semantics, Different Topology**：单机 Pilot 与生产集群共享同一数据模型、状态机和任务协议。

### 3.1 真相边界

**PostgreSQL + Object Storage 是业务真相。**

- PostgreSQL：Source、Provider、URL Identity、任务状态、游标、Release、Coverage、Quality、Document、Version、Identity、关系、Editorial 状态、发布状态、审计；
- S3/MinIO：Raw HTML、MHTML、截图、Trace、Candidate、IR、Markdown、Enrichment、Evidence Package、Generation Output、Publication Snapshot；
- Redis Streams：任务运输、背压、consumer group，不保存不可替代业务状态；
- OpenSearch / pgvector / Story Cluster / Rank Projection：均可重建；
- Browser Session、Crawler Cache、Worker 内存、Agent Memory：易失执行状态；
- 外部 Newsletter 平台上的 Draft/Post：是发布 Projection，不是知识库真相。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST API、Command、Schema 校验；
- **PostgreSQL**：Truth Store、任务状态、Coverage、版本、审计；
- **Redis Streams**：任务队列、consumer group、backpressure；
- **Redis Lua Token Bucket / Semaphore**：跨 Worker 域名限流与资源令牌；
- **React / Next.js + TypeScript**：Web 管理后台；
- **OpenTelemetry + Prometheus + Grafana + Structured Logging**：Trace/Metric/Log；
- **S3/MinIO**：不可变对象存储；
- **Vault/KMS/Secret Manager**：凭据引用。

### 4.2 Discovery / Fetch

- **httpx/aiohttp**：robots、Sitemap、Feed、CMS API、Conditional GET、普通网页；
- **Crawl4AI**：Browser Render、动态链接发现、简单交互、诊断 Candidate；
- **Playwright Python**：复杂多步、有状态、需要 Step 级恢复的交互；
- **SearXNG / 合规 Search API Adapter**：External Search Gap、新 Source Candidate；
- **PyMuPDF/pdftotext**：PDF；扫描件再进入 OCR；
- **Python email/MIME parser**：Newsletter Inbox Provider。

### 4.3 Extraction / Search

- **Trafilatura**：Generic Main Content Candidate；
- **lxml/BeautifulSoup**：DOM/XPath、Metadata、DOM Repair；
- **JSON-LD/OpenGraph/Microdata**：结构化元数据；
- **CSS/XPath/Regex Recipe**：确定性正文/字段抽取；
- **SimHash/MinHash**：近重复候选；
- **OpenSearch BM25 + pgvector + RRF/weighted fusion**：混合检索；
- **可选 reranker / LLM**：只在 Canonical 与 Query Service 之后工作。

### 4.4 LLM Provider Gateway

统一支持：

- 云端模型 Provider；
- OpenAI-compatible API；
- LocalAI；
- Ollama/vLLM 等本地或私有部署 Adapter；
- 未来其它模型网关。

业务代码不直接依赖具体厂商 SDK，而是调用：

```text
GenerationJob
 -> LLM Policy
 -> Provider Resolver
 -> Provider Adapter
 -> Structured Output Validator
```

采集、抽取和 Markdown 发布不依赖该网关可用性。

生产环境至少记录：

## 6. Source、Provider 与配置模型

### 6.1 Source Input

支持：

- Domain；
- RSS / Atom；
- Sitemap / Sitemap Index；
- WordPress REST API；
- Ghost / Content API；
- Hugo/Jekyll/静态 Archive；
- 自定义 JSON API；
- 手工 URL；
- Newsletter Inbox；
- GitHub Release / Docs 等特殊 Provider。

### 6.2 Provider 输出统一 Observation

无论输入来自哪里，都转换为：

```text
URLObservation
- source_id
- provider_binding_id
- observed_url
- canonical_hint
- title_hint
- published_at_hint
- updated_at_hint
- discovered_at
- provider_cursor
- provenance_ref
```

正文链路不关心 URL 来自 Sitemap、RSS、API、Archive 还是 Newsletter。

### 6.3 Source Profile

```yaml
source_id: example
allowed_hosts:
  - blog.example.com
article_patterns:
  include:
    - /blog/**
  exclude:
    - /tag/**
    - /author/**
providers:
  - type: sitemap
    url: https://blog.example.com/sitemap.xml
  - type: rss
    url: https://blog.example.com/feed.xml
fetch_policy:
  http_first: true
  browser_fallback: true
rate_limit:
  requests_per_second: 1
  max_concurrency: 2
quality_profile: generic_article_v3
```

Source Profile 任何变更都产生新的 `source_release`，不能原地静默修改生产规则。

### 6.4 Site Family

对于 Medium、Substack、WordPress、Ghost、Hugo 等大量同构站点，支持 `site_family`：

```text
site_family
 -> default provider bindings
 -> default URL patterns
 -> default extractor recipes
 -> default quality profile
 -> per-source overrides
```

这样新增站点通常只需要域名和少量覆盖配置。

## 7. 全历史发现与 Coverage

### 7.1 Provider 优先级

```text
1. CMS / 官方内容 API
2. Sitemap Index / Sitemap
3. RSS / Atom 历史范围
4. Archive / 年月分页 / Category Listing
5. 站内文章链接图
6. External Search Gap
```

### 7.2 URL Inventory First

Backfill 不应该把“边逛边抓正文”作为唯一模式，而应先构建 URL Inventory：

```text
source
 -> provider partitions
 -> URL observations
 -> normalized url_id
 -> classification
 -> fetch admission
```

好处：

- 能统计发现数量；
- 能并行抓正文；
- 能独立复跑 Discovery；
- 能发现 Provider 之间差异；
- 能做时间分区回填；
- 能证明 Coverage，而不是只有“爬了很多页”。

### 7.3 Coverage Evidence

每次 Provider Run 记录：

```text
provider_run
- source_id
- provider_type
- started_at
- finished_at
- cursor_start
- cursor_end
- partition_key
- discovered_count
- new_url_count
- duplicate_count
- stop_reason
- known_gap
- evidence_artifact_id
```

`stop_reason` 必须是显式枚举：

```text
END_OF_PAGINATION
DATE_BOUND_REACHED
NO_NEW_URLS_AFTER_N_PAGES
API_CURSOR_EXHAUSTED
ROBOTS_BLOCKED
AUTH_REQUIRED
RATE_LIMIT_BUDGET_EXHAUSTED
MANUAL_STOP
```

### 7.4 Provider 交叉对账

对同一 Source 做：

```text
CMS set
Sitemap set
Archive set
RSS set
Search Gap set
   -> union/intersection/diff
```

重点显示：

- Sitemap 独有；
- Archive 独有；
- CMS 独有；
- 时间段断层；
- 年/月分区异常。

### 7.5 External Search 只能补洞

SearXNG 或外部 Search 可用于：

- `site:domain` + 时间分区补洞；
- 发现未暴露在 Archive/Sitemap 的孤儿页；
- 发现新 Source Candidate。

搜索结果必须进入 `search_evidence`，不能直接宣称历史完整。

## 8. 增量同步

### 8.1 Provider 级增量

优先顺序：

1. RSS/Atom 新 item；
2. Sitemap `lastmod`；
3. CMS/API cursor；
4. Archive 首页/前几页 diff；
5. 首页/分类页 lightweight probe；
6. 周期性 Verify。

### 8.2 Conditional GET

普通网页优先使用：

- `ETag` / `If-None-Match`；
- `Last-Modified` / `If-Modified-Since`；
- HEAD/轻量 GET；
- 内容指纹。

HTTP 304 记录 Observation/heartbeat，不进入 Browser。

### 8.3 更新检测

```text
new fetch artifact
 -> normalize meaningful content
 -> strong hash
 -> compare latest version
     |-- same    -> heartbeat only
     |-- changed -> create document_version
```

不能只比较原始 HTML，因为广告、推荐位、Cookie banner 和动态时间会制造无意义变化。

### 8.4 删除与迁移

周期 Verify 检查：

- 404/410；
- redirect chain；
- canonical 变化；
- 内容迁移；
- soft-404；
- syndication。

删除不物理删除历史版本，只更新当前可用状态和关系。

### 8.5 增量调度

按 Source 活跃度自适应：

```text
high-frequency source -> minutes/hours
normal blog           -> hours/day
rarely updated        -> days
```

但必须设置最小 Verify 周期，避免长时间不复检。

## 9. Fetch 路由与交互

### 9.1 路由级别

```text
L0 Metadata/API
L1 HTTP HTML
L2 Crawl4AI Browser Render / Simple Interaction
L3 Playwright Stateful Interaction
```

### 9.2 HTTP First

默认先用 httpx/aiohttp，因为：

- 成本低；
- 吞吐高；
- 易限速；
- 易缓存；
- 易复现；
- 支持 Conditional GET。

仅在以下条件升级 Browser：

- 正文依赖 JS 渲染；
- HTML 明显为空壳；
- 必须点击“加载更多”；
- 页面有动态展开；
- Browser 版本历史上已验证更可靠。

### 9.3 Crawl4AI 定位

Crawl4AI 负责：

- 动态页面渲染；
- 简单 JS 交互；
- 动态链接发现；
- 批量 Browser 抓取；
- 生成诊断 Markdown Candidate。

**Crawl4AI 输出不直接成为 Canonical Markdown。**

第三方 Crawler 的 `score`、priority、`max_pages`、batch 等语义必须在 pinned runtime 上做契约测试，不能根据字段名称推断。

### 9.4 Playwright 定位

复杂交互才进入 Playwright：

- 多步状态流程；
- 状态型分页；
- 复杂 modal/tab；
- 无限列表需要业务 key 定位；
- 需要 Step/Checkpoint/Resume；
- 合规允许的受控登录流程。

每个 Step 记录：

```text
interaction_step_run
- step_index
- action_type
- locator_strategy
- expected_state
- started_at
- finished_at
- retry_count
- screenshot_artifact
- trace_artifact
- result
```

优先 Semantic Wait，不允许大量固定 sleep。

### 9.5 Candidate 发现与请求预算分离

页面观察到的全部内部链接应先持久化为候选事实，再由预算决定抓哪些：

```text
Fetched Parent Artifact
 -> enumerate observable links
 -> normalize/dedupe
 -> persist candidate observations
 -> score/classify
 -> admission by budget
```

不能因为某个 crawler 的 `max_pages` 到达上限，就把尚未派发的已观察链接从事实层抹掉。

## 10. Artifact、正文抽取与质量

### 10.1 Immutable Artifact

每次抓取先保存 Artifact：

```text
artifact
- artifact_id
- url_id
- fetched_at
- status_code
- headers
- redirected_url
- mime_type
- raw_object_key
- screenshot_key
- trace_key
- runtime_release
- fetch_route
- content_length
- hash
```

原则：

- Artifact 永不原地覆盖；
- Extractor 升级只重跑 Artifact，不必重新访问网站；
- 质量争议可以回放；
- 合规删除通过 retention/tombstone 策略统一处理。

### 10.2 Extraction Portfolio

候选顺序建议：

1. JSON-LD / structured article body；
2. 站点 Deterministic CSS/XPath Recipe；
3. Trafilatura Precision/Balanced/Recall；
4. DOM Repair + Generic Extractor；
5. Crawl4AI Markdown 作为 Diagnostic Candidate。

任何 Extractor 都不能直接发布。

### 10.3 Candidate 记录

```text
extraction_attempt
- artifact_id
- extractor_release
- title
- authors
- published_at
- updated_at
- body
- links
- images
- code_blocks
- tables
- candidate_hash
- diagnostics
```

### 10.4 Quality Gate

至少检查：

- 标题存在；
- 正文字数/字符数范围；
- 主体文本密度；
- 导航/页脚噪声率；
- 重复段落比例；
- 代码块完整性；
- Markdown fence 是否闭合；
- 表格结构；
- 截断迹象；
- 登录/验证码/WAF 文案；
- soft-404；
- 标题与 URL/metadata 一致性；
- Candidate 间一致性；
- 页面声明的正文长度与抽取长度异常；
- 时间/作者字段置信度。

输出：

```text
PASS
WARN
REPAIR
REJECT
```

### 10.5 Bounded Repair

```text
Candidate
 -> Quality
 -> REPAIR
      |-- alternate extractor
      |-- alternate route HTTP -> Browser
      |-- deterministic DOM repair
      |-- re-fetch once
 -> Quality
 -> stop
```

修复次数必须有上限，失败进入 DLQ/人工诊断。

## 11. Canonical IR 与 Markdown

### 11.1 Canonical IR

建议定义结构化中间表示：

```json
{
  "document_id": "...",
  "version_id": "...",
  "title": "...",
  "authors": ["..."],
  "published_at": "...",
  "updated_at": "...",
  "canonical_url": "...",
  "source_id": "...",
  "blocks": [
    {"type": "heading", "level": 2, "text": "..."},
    {"type": "paragraph", "text": "..."},
    {"type": "code", "language": "python", "text": "..."},
    {"type": "table", "rows": []},
    {"type": "image", "src": "...", "alt": "..."}
  ],
  "provenance": []
}
```

Canonical IR 是正文结构真相，Markdown 是 Projection。

### 11.2 Markdown Renderer

```text
Canonical IR
 -> renderer_release
 -> markdown
```

Renderer 升级时可以离线重建全部 Markdown，不重新抓网页。

### 11.3 Markdown 文件建议

```text
knowledge/
  <source_id>/
    <yyyy>/
      <document_id>.md
```

Frontmatter：

```yaml
---
document_id: ...
version_id: ...
source_id: ...
url: ...
published_at: ...
updated_at: ...
fetched_at: ...
quality: PASS
renderer_release: ...
---
```

文件名不要只依赖标题，避免重名、标题变化和跨平台非法字符问题。

### 11.4 文件输出与对象存储

Markdown 可以：

- 保存在 S3/MinIO；
- 同步到 Git 仓库；
- 导出为目录；
- 由 API 按版本获取。

若使用 Git 镜像，Git 只是 Projection，不是任务/版本业务真相。

## 12. Document Identity、版本与去重

### 12.1 URL Identity

规范化处理：

- scheme/host 大小写；
- default port；
- tracking query；
- fragment；
- trailing slash；
- canonical；
- redirect chain。

但不要激进删除业务参数。

### 12.2 Document Identity

强证据优先：

- canonical URL；
- publisher stable ID；
- GUID；
- exact normalized content hash；
- verified redirect/migration。

Embedding/语义相似不能单独合并 Document。

### 12.3 Document Version

```text
document
  -> version v1
  -> version v2
  -> version v3
```

每个版本绑定具体 Artifact/Extraction/Quality/IR。

### 12.4 Story Cluster

语义相似、标题相似、共享实体、发布时间接近，可以形成 `story_cluster`，用于：

- 搜索折叠；
- Digest 去重；
- 多来源比较；
- RAG context diversity。

Cluster 是可重建 Projection，不影响 Document Identity。

## 13. 调度、队列与可靠性

### 13.1 Queue Class

```text
incremental_high
verify
backfill_small
backfill_large
browser
repair
extract
enrichment
curation
publication
```

### 13.2 Fair Scheduler

调度优先级建议综合：

```text
priority = freshness_weight
         + source_fairness
         + queue_age
         + retry_penalty
         + manual_priority
```

`manual_priority` 只影响何时执行，不决定文章是否永久保存。

实现上至少考虑：

- per-source concurrency；
- per-domain token bucket；
- queue class quota；
- global browser semaphore；
- aging 防饿死；
- Backfill 分片；
- Incremental 保留容量。

### 13.3 幂等键

示例：

```text
fetch:<url_id>:<expected_revision>
extract:<artifact_id>:<extractor_release>
render:<version_id>:<renderer_release>
enrich:<version_id>:<enrichment_release>
curate:<issue_id>:<agent_release>:<evidence_package_id>
publish:<issue_id>:<target_id>:<publication_release>
```

### 13.4 Lease + Fencing Token

Worker 领取任务时：

- DB 写 lease；
- 生成 fencing token；
- 超时可被其他 Worker 接管；
- 旧 Worker 回写时发现 token 过期则拒绝写入。

防止长任务重复执行产生乱序覆盖。

### 13.5 Transactional Outbox

DB 状态改变和队列消息通过 Outbox 保证一致性：

```text
DB transaction:
  update business state
  insert outbox event
commit

outbox relay -> Redis Streams
```

避免“DB 成功但消息没发”或“消息发了但 DB 没提交”。

### 13.6 Retry / DLQ

按错误类型配置：

- 网络瞬时错误：指数退避 + jitter；
- 429：尊重 Retry-After；
- 4xx 永久错误：通常不盲重试；
- Browser Crash：有限次数换 Worker；
- Quality REPAIR：进入 Repair FSM；
- Policy Block：不重试；
- 人工可从 Web 一键 replay。

## 16. 可选 Editorial / Digest / Newsletter Plane

该平面只消费已经 PASS/WARN 且满足使用策略的 Document Version，不能反向修改 Collection Truth。

### 16.1 目标

支持：

- 技术周报；
- 专题 Digest；
- Newsletter；
- 团队内部知识简报；
- 自动生成“本周新增”摘要；
- 多角色虚拟编辑部。

### 16.2 基础数据流

```text
PASS Document Versions
 -> Issue Snapshot
 -> Candidate Query
 -> Story Cluster 去重
 -> Source/Topic Diversity
 -> Manual PIN / EXCLUDE / PRIORITIZE
 -> Evidence Package
 -> Writer/Editorial Perspective Workers(optional)
 -> AI Editor / Deterministic Composer
 -> Citation Validator
 -> Editorial Quality Gate
 -> Human Review
 -> Publication Adapter
```

### 16.3 Evidence Package

每一期在生成前冻结输入：

```text
evidence_package
- evidence_package_id
- issue_id
- created_at
- selection_policy_release
- document_version_ids[]
- canonical_urls[]
- content_hashes[]
- object_refs[]
```

原则：

- Writer 默认只能消费 Evidence Package；
- 不允许 Writer 自己重新抓原网页或扩展来源集合；
- 所有角色基于同一事实快照；
- Prompt/Model 升级后可重放；
- Evidence Package 不因后续网页变化而改变。

### 16.4 Virtual Newsroom / Perspective Workers

可选并行角色：

```text
Evidence Package
   |------> security_writer ------|
   |------> infra_writer ---------|--> Editor
   |------> community_writer -----|
```

每个 Agent 使用结构化输入输出：

```json
{
  "agent_release": "security_writer_v3",
  "items": [
    {
      "document_version_id": "...",
      "section": "security",
      "headline": "...",
      "summary": "...",
      "why_it_matters": "...",
      "evidence_refs": ["..."],
      "confidence": 0.92
    }
  ]
}
```

规则：

- Persona 只能控制表达、角度和栏目风格；
- 不能修改 canonical URL、作者、发布时间、Artifact 或 Document Identity；
- Agent 不拥有 Collection 权限；
- fan-out 有并发、Token、成本、超时和最大角色数限制；
- 某个 Agent 失败可降级，不允许无限重试；
- 全部输入/输出和 Release 都保留用于回放。

### 16.5 Manual PIN

管理员可手工指定文章必须进入某一期：

```text
editorial_directive
- directive_id
- issue_id
- document_version_id
- action: PIN | EXCLUDE | PRIORITIZE
- reason
- created_by
- created_at
```

规则：

- 只影响指定 Issue；
- 不修改 Source Coverage；
- 不修改全局 Quality；
- 不修改 Document Identity；
- 可审计、可撤销。

这类人工 PIN 是“编辑精选”，不是抓取策略。

### 16.6 Writer / Editor 版本化

```text
editorial_agent_release
- role
- persona_version
- prompt_version
- output_schema
- llm_policy_release

writer_release
- persona_version
- prompt_version
- provider_release
- model
- generation_params
- output_schema

editor_release
- prompt_version
- provider_release
- model
- selection_policy
- style_policy
- citation_policy
```

### 16.7 Citation Gate

生成结果进入 Review 前必须检查：

- citation URL 来自 Evidence Package 中真实 Document/Artifact；
- 每个事实段有 Evidence；
- 无不存在的 URL；
- 无跨文章错误归因；
- 无 REJECT 文档参与生成；
- Manual PIN 内容没有被 Agent 静默丢失；
- 输出结构符合 schema；
- 总长度/栏目规则符合 Policy。

### 16.8 Human Review

默认流程：

```text
DRAFT
 -> AUTO_CHECKED
 -> REVIEW_REQUIRED
 -> APPROVED
 -> EXTERNAL_DRAFT
 -> PUBLISHED
```

Web UI 提供：

- 原文与生成稿并排；
- 引用跳转；
- 每个 Writer 候选对比；
- 逐段 diff；
- 局部重生成；
- Approve/Reject；
- PIN/EXCLUDE；
- 查看 Prompt/Model/Provider Release；
- 发布快照。

自动发布必须由单独 Policy 显式启用。

```text
- model_revision
- max_context
- structured_output_capability
- tool_capability
- privacy_class
```

### 17.2 路由策略

可以按以下维度选择 Provider：

- 数据隐私；
- 任务类型；
- 质量基线；
- 上下文长度；

例如：


- LLM 不可用不能阻塞 Markdown；

## 20. 安全、合规与访问策略

### 20.1 robots / Terms Policy

Source 建档时记录：

- robots 结果；
- Terms 备注；
- 是否公开访问；
- 是否允许 Browser；
- 是否允许存 Raw HTML；
- retention policy；
- 联系/下线策略。

### 20.2 Secret

数据库只保存 Secret Reference：

```text
secret_ref: vault://crawl/source-123/api-key
```

### 20.3 网络安全

Browser/HTTP Worker 防 SSRF：

- 禁止 localhost / metadata IP；
- 私网地址默认禁止；
- DNS rebinding 防护；
- redirect 每跳重新校验；
- 下载大小限制；
- MIME allowlist；
- zip bomb/大文件防护。

### 20.4 内容安全

抓取内容视为不可信输入：

- 禁止执行页面提供的任意下载代码；
- 文本中的 prompt injection 不影响系统工具权限；
- LLM 只能读取明确传入的 Evidence Package；
- Generation Plane 无权调用采集管理写 API；
- 外部链接不得自动升级为可信 Tool 指令。

### 20.5 权限分离

至少区分：

- Source Admin；
- Operator；
- Reviewer；
- Publisher；
- Read-only；
- Service Account。

自动发布权限不得默认授予 Writer/Editor Agent。

## 22. 部署拓扑

### 22.1 单机 / 开发 Pilot

用于开发和小规模验证，推荐 Docker Compose：

```text
api-scheduler-worker x1
browser-worker x1 optional
postgres
redis
minio
opensearch optional
prometheus/grafana optional
local-llm optional
```

可以把 API、Scheduler、Discovery、HTTP Fetch、Extract 合并在一个应用容器或同一镜像的不同进程中，但必须继续使用：

- 同一 PostgreSQL schema；
- 同一 Redis Streams contract；
- 同一 Outbox；
- 同一 Run/Task state machine；
- 同一 S3/MinIO object key；
- 同一 Source/Profile/Release；
- 同一 Artifact/Quality/Version 模型。

Pilot 适合开发、Golden Test、少量 Source 验证，不作为 1000 站长期生产容量假设。

### 22.2 初始 1000 站生产规模

建议起步：

```text
API x2
Scheduler x2
Discovery Worker x2-4
HTTP Worker x4-8
Browser Worker x2-4
Extract Worker x4
Enrichment Worker x2-4
Editorial Worker x1-2 optional
PostgreSQL HA
Redis
S3/MinIO
OpenSearch
Grafana/Prometheus
```

Browser Worker 独立部署，避免 Chromium 内存抖动拖垮 API/HTTP Worker。

### 22.3 容器化与编排

全部组件 Docker 化；生产可使用 Kubernetes 或等价编排。

Browser Worker 设置：

- memory limit；
- ephemeral storage limit；
- context 数量上限；
- worker recycle；
- node pool 隔离。

### 22.4 扩展方式

主要按队列水平扩展：

- Discovery backlog 高 -> 扩 Discovery Worker；
- HTTP queue 高 -> 扩 HTTP Worker；
- Browser queue 高 -> 扩 Browser Worker；
- Extract backlog 高 -> 扩 Extract Worker；
- Enrichment backlog 不影响 TTFM；
- Curation backlog 不影响 Collection Freshness。

从 Pilot 扩到生产原则上只改变部署角色数量和资源，不改变业务状态语义。

## 29. 验收标准

### 29.1 全历史

随机抽取至少 30 个 Source：

- 能解释 URL Inventory 来自哪些 Provider；
- 能显示分区、游标和停止条件；
- Known Gap 明确；
- Sitemap/CMS/Archive 交叉对账；
- 不以搜索结果数作为完整性结论；
- 能看到尚未抓正文但已发现的 URL。

### 29.2 增量

- RSS/API 来源新文章在目标 Freshness SLO 内进入 Markdown；
- 页面更新产生新 Version；
- 未变化页面不重复生成版本；
- 删除/迁移能被 Verify 发现；
- 304/无变化页面不进入 Browser 慢路径。

### 29.3 质量

Golden Dataset 上：

- 正文完整；
- 导航噪声低；
- 代码块、表格、列表可接受；
- WAF/登录页不进入 PASS；
- Renderer 可离线重建；
- Crawl4AI 原始 Markdown 不会绕过 Quality Gate。

### 29.4 可靠性

- Worker 崩溃后任务可恢复；
- 重复投递不生成重复 Version；
- Redis 清空不丢业务真相；
- Browser 崩溃不会拖垮 HTTP Worker；
- Backfill 不饿死 Incremental；
- 任务超时后旧 Worker 不能用过期 fencing token 覆盖新结果。

### 29.5 可追溯

任意 Markdown 能回答：

- 从哪个 Source 来；
- 原始 URL；
- 抓取时间；
- 哪个 Artifact；
- 哪个 Extractor/Quality/Renderer Release；
- 为什么是当前 Document Version。

### 29.6 Editorial / Newsletter

- 每个生成稿引用全部可回溯 Evidence Package -> Document Version；
- Writer 不默认自主访问外部网页；
- Manual PIN 不影响 Collection Coverage；
- 未批准 Draft 不发布；
- Writer/Editor Model/Provider/Prompt 可回放；
- Publication 失败不影响知识库文档状态；
- 外部平台不支持稳定写 API 时可以安全退化为 Markdown/HTML 导出；
- 自动发布必须有显式 Policy。

### 29.7 部署可扩展

- Pilot 与生产使用同一 schema/state machine/object contract；
- 从单机迁到多 Worker 不需要重写业务模型；
- Browser、Extract、Enrichment 可以独立扩容；
- 本地 LLM 与云 Provider 切换不影响 Collection Truth。

## 30. 最终推荐架构摘要

```text
HTTP          = 默认、高吞吐、低成本数据路径
Crawl4AI      = Browser Render + Simple Interaction + Dynamic Discovery + Diagnostic Candidate
Playwright    = Stateful Interaction Engine，负责复杂多步、Step/Checkpoint/Trace
Recipe DSL    = 将站点差异变成平台能力，而不是 1000 个脚本
Provider      = 将 RSS/Sitemap/API/Newsletter 等统一转成 URL Observation
Search Gap    = 补洞与新来源发现，不是 Coverage Truth
URL Inventory = 全历史 Coverage 的基础事实层
Artifact      = 不可变网页事实
Extractor     = Candidate Generator
Quality       = 独立发布闸门
Canonical IR = Markdown 与后续 Projection 的结构真相
Document ID   = 强身份事实，不由 Embedding 相似直接合并
Story Cluster = 同主题 Projection，用于检索折叠与多样性
Renderer      = Canonical IR -> Markdown
Provenance    = Citation URL 的事实证据
LLM Provider  = 云/本地模型统一可替换入口，不进入采集真相链
Evidence Pack = Editorial Plane 的固定事实快照
Virtual Newsroom = 受控的多角色生成层，Agent 不自主抓源站
Manual PIN    = 人工编辑指令，只作用于指定 Issue
Human Review  = 生成式发布默认最终闸门
Publication   = Draft First + Capability Negotiation
Docker Pilot  = 小规模部署形态，与生产共享同一业务语义
```

这套方案的关键不是选择某一个“万能爬虫”，而是把 **发现、Coverage、抓取、不可变事实、抽取、质量、身份、版本、Markdown、检索、生成式编排和外部发布** 拆成明确边界。

对于 1000 个技术博客，核心长期资产是 `URL Inventory + Artifact + Canonical IR + Document Version + Provenance`；Crawl4AI、Playwright、Extractor、LLM、本地模型、Newsletter 平台都只是可替换执行组件。这样新增网站、扩到数千站点、做长期增量同步、升级模型或增加 Web 运营功能时，都不会破坏业务真相，也不会因为某一个工具或平台变化而重写整个系统。
