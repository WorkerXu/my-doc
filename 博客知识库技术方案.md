# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站和公开 Newsletter** 的长期采集与知识库平台，并可平滑扩展到数千站点、百万到千万级文章。

平台必须同时满足：

1. **全历史回填**：尽可能完整发现每个已批准 Source 的历史文章，并能解释发现通道、覆盖率、缺口、截断与停止原因；
2. **持续增量同步**：发现新文章、正文修改、元数据变化、URL 迁移、重定向、删除与重发布；
3. **Markdown 稳定可重放**：保存不可变 Raw Artifact，经版本化 Cleaner、Extractor、Canonical IR 和 Renderer 生成最终 Markdown；
4. **技术内容保真**：代码块、表格、公式、Mermaid、列表、引用、脚注、图片说明不能被通用降噪算法静默删除；
5. **低成本扩站**：新增网站优先通过 Source Profile、Provider、Recipe 和 Traversal Policy 配置完成，不维护 1000 份独立爬虫脚本；
6. **Web 可运营**：支持站点接入、审批、Backfill、Incremental、Coverage、Frontier、质量、成本、诊断、暂停、恢复、重跑、灰度和审计；
7. **任务可恢复**：Provider Run、Task、Attempt、URL、Artifact、Candidate、Document、Version 全链路有持久状态，Worker/Runtime 崩溃可恢复；
8. **可搜索/RAG**：支持 BM25、向量与混合检索，并能回溯原文、版本、Source、抓取证据和处理 Release；
9. **主链不依赖 LLM**：LLM 只做可选 Repair/Enrichment，不参与历史完整性、URL 身份、正文存在性、版本真相和权限边界的最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 可查看 Provider Inventory、Completion Attestation、Known Gap、Backfill Stop Reason；
- **Freshness**：新文章/更新从发布或发现到 PASS Markdown 的 P50/P95/P99 延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文、代码、表格、列表、链接、图片说明、公式的召回率与噪声率；
- **Protected Structure Recall**：受保护技术节点在 Candidate/IR 中的保留率；
- **Multilingual Retention**：中文、日文及中英混排正文保留率；
- **Reliability**：Task 成功率、Retry、DLQ、Queue Age、Lease Recovery；
- **Replayability**：相同 Raw Artifact + 相同 Release 可得到相同派生结果；
- **Provider Integrity**：部分返回、缓存命中、预算耗尽不能被误报为“已完整枚举”；
- **Artifact Durability**：需要保留的 Runtime/Provider Artifact 必须晋升平台对象存储；
- **Browser Efficiency**：HTTP Fast Lane 命中率、Browser Avoided、Browser 单文档成本；
- **Revalidation Integrity**：强验证成功率、弱验证漏检率、`hit_fallback` 数量、强制刷新抽样命中变化率；
- **Fairness**：大型 Backfill 不得长期饿死 Incremental、小站、Repair 与 Reconcile。

## 2. 核心设计原则

1. **Coverage First**：先构建可解释 URL Inventory，再抓正文；
2. **Authoritative First**：官方 CMS/API、Sitemap、Feed、Archive 优先；
3. **Observation Before Selection**：先保存发现事实，再 Normalize、Scope、Classify、Dedup；
4. **Successful Return != Provider Complete**：正常返回、非空结果、cache hit 均不能自动代表 Provider 完成；
5. **Completion Must Be Attested**：只有具备可验证结束语义的 Provider Adapter 才能声明完成；
6. **Discovery / Revalidation / Fetch / Clean / Extract / Quality / Canonicalize / Projection 分离**；
7. **HTTP First, Browser Slow Lane**；
8. **Snapshot First**：先保存 Provider Evidence / Raw Artifact，再生成派生物；
9. **Candidate Portfolio, Not Single Extractor**：多个确定性候选互相校验；
10. **Protected Structures Are First-Class**：代码、表格、公式等先识别、再验证召回；
11. **Language Assumptions Must Be Explicit**：word/token threshold 必须声明适用语言；
12. **Canonical IR First, Markdown as Projection**；
13. **Recipe, Not 1000 Site Scripts**；
14. **Persistent Frontier, Not In-Memory Traversal**；
15. **Idempotent + Recoverable**：幂等键、Lease、Fencing Token、Checkpoint、Inbox/Outbox；
16. **Fair by Default**：Incremental、Revalidation、Repair 必须预留容量；
17. **Bounded Concurrency Everywhere**：任务数、在途请求、结果集合、Browser 与进程生命周期都有硬边界；
18. **No Silent Degradation**：过滤、截断、预算耗尽、partial result、cache fallback、降级必须有 typed reason；
19. **Correlate by Identity, Never by Position**；
20. **Config Is Capability**：高能力配置经过 Capability Firewall；
21. **Runtime Is Execution Plane**：第三方 Runtime 不拥有 Coverage、Identity、Document、Version 或 Markdown 真相；
22. **Behavior Beats Naming**：生产语义以 pinned release + Contract Test 为准；
23. **Runtime Cache Is Disposable**：本地 cache 可丢弃，不得推进业务版本真相；
24. **Derived Artifact Never Overwrites Evidence**：Cleaned HTML、Candidate、IR、Markdown 均是可重放派生物；
25. **Weak Freshness Signal Cannot Close Truth**：head fingerprint、长度相近等弱信号不能单独证明正文未变化；
26. **Offline Means No Network**：离线 Replay 必须由平台 Artifact + egress deny 保证，不能依赖 `READ_ONLY` 之类的 Runtime 名称。

- **Wayback Adapter**：历史缺口证据；

### 4.3 Extraction / Search

- **Trafilatura**：Generic Candidate；
- **lxml/BeautifulSoup**：DOM/XPath、Metadata、Repair、Protected Structure Fingerprint；
- **JSON-LD/OpenGraph/Microdata**；
- **CSS/XPath/Regex Recipe**；
- **Crawl4AI DefaultMarkdownGenerator / ContentFilter**：Markdown Candidate，不直接作为 canonical；
- **SimHash/MinHash**：近重复；
- **OpenSearch BM25 + pgvector + RRF**；
- embedding、reranker、LLM 只做增强。

## 6. 全历史 URL 发现与 Coverage

### 6.1 Provider 优先级

每个 Source 的历史发现按以下优先级执行：

1. 官方 CMS/API；
2. Sitemap / Sitemap Index；
3. RSS / Atom；
4. Archive / Pagination / Tag / Category；
5. 静态链接图；
6. Common Crawl Index；
7. Wayback；
8. Crawl4AI URL Seeder、Domain Mapping、Deep/Adaptive Crawl 作为补洞与加速。

任何单一 Provider 都不能自动证明“全历史完整”。

### 6.2 Observation 模型

Provider 返回的每一条 URL 先写 `url_observation`：

```text
observation_id
source_id
provider_id
provider_run_id
observed_url
observed_at
provider_timestamp
provider_metadata
provider_evidence_uri
```

随后统一执行：

```text
Normalize -> Scope Check -> MIME Hint -> URL Identity -> Dedup -> Frontier Upsert
```

不允许 Provider 内部去重结果直接成为平台最终 Inventory。

### 6.3 Provider Completion Attestation

每次 Provider Run 保存：

```text
started_at / finished_at
checkpoint / cursor / shard
items_seen / unique_urls
status
completion_type
stop_reason
truncated
budget_exhausted
known_gap
provider_release
```

只有满足 Adapter 的明确完成条件时，`completion_type=ATTESTED_COMPLETE`。

以下情况一律不能标完整：

- 返回非空列表；
- HTTP 200；
- `success=true`；
- 达到 limit；
- cache hit；
- 搜索结果不再增加但没有协议级结束条件；
- Deep Crawl 达到配置深度/页面预算。

### 6.4 SitemapProvider

Sitemap Index 必须拆成 durable shard：

```text
sitemap_index_run
  -> sitemap_shard_1
  -> sitemap_shard_2
  -> ...
```

每个 shard 单独保存：

- URL；
- ETag/Last-Modified；
- fetch time；
- parse result；
- child count；
- checkpoint；
- completion attestation。

增量阶段对 Sitemap 使用 Conditional GET；`lastmod` 只做变化线索，不直接代表正文已变化。

### 6.5 Common Crawl / Wayback

只作为历史缺口补洞：

- 固定 index/release；
- 保存查询条件与返回证据；
- 流式读取，避免一次性加载大结果；
- URL 仍进入 Observation/Scope/Identity；
- Archive 出现不等于当前 URL 仍有效；
- Archive 缺失也不能证明文章从未存在。

### 6.6 Crawl4AI URL Seeder 的定位

AsyncUrlSeeder 可批量从 Sitemap/CC 等发现 URL，但平台必须：

- pin release；
- 限定 modes/domain；
- 将返回值转成 Observation；
- 保存 provider evidence 与 cutoff；
- 不把 Seeder 内部 cache/seen/queue 当成 durable checkpoint；
- 不用 Seeder 返回条数证明 Coverage。

### 6.7 Coverage 计算

每个 Source 维护：

```text
provider_inventory
provider_attestation
historical_time_range
observed_url_count
fetchable_url_count
article_count
known_gap_count
unresolved_gap_count
backfill_stop_reason
```

Web 后台必须能回答：“为什么系统认为这个站回填完成/未完成？”

## 7. URL Identity、Canonical 与去重

### 7.1 三种 URL 必须分开

```text
observed_url      Provider 实际看到的 URL
normalized_url    平台规则归一化后的 URL
canonical_url     经证据判定的文章主 URL
```

不能直接把 `<link rel=canonical>` 当绝对真相，因为网站模板、镜像、错误配置可能把大量文章指向同一个 canonical。

### 7.2 Normalize

可安全做：

- host 小写；
- 默认端口移除；
- fragment 移除；
- 已知 tracking query 移除；
- Unicode/percent encoding 规范化；
- Source 级 trailing slash 规则。

不可全局盲做：

- query 参数排序/删除；
- path 大小写合并；
- 日期段重写；
- `www` 与 apex 合并；
- HTTP/HTTPS 强制合并。

这些都必须受 Source Policy 控制。

### 7.3 Dedup

分层去重：

```text
URL exact identity
        -> redirect/canonical alias
        -> raw body hash exact duplicate
        -> semantic body hash
        -> SimHash/MinHash near duplicate
```

近重复只用于候选关联，不能自动删除原始 Document Version。

## 8. Persistent Frontier 与公平调度

### 8.1 Frontier

核心字段：

```text

canonical_url
state
priority
next_action_at
last_discovered_at
last_fetch_at
last_verified_at
retry_count

lease_until

```

状态示例：

```text
DISCOVERED
DUE_FOR_REVALIDATION
FETCH_REQUIRED
FETCHING
FETCHED
EXTRACT_PENDING
PASS
REPAIR
REVIEW
DELETED
BLOCKED
DEAD
```

### 8.2 公平调度

全局 Scheduler 使用分层队列：

```text
P0 incremental-hot
P1 revalidation
P2 new-source-backfill
P3 historical-gap
P4 repair/replay
```

并按 `source_id / host / domain / workload_class` 做 Weighted Fair Queueing。

必须预留 Incremental/Revalidation 容量，避免单个大型站点 Backfill 占满 Browser、Redis 或 Worker。

### 8.3 全局限流

Redis Lua 维护：

- host Token Bucket；
- source concurrency semaphore；
- domain concurrency semaphore；
- browser slot semaphore；
- provider-specific quota。

robots、站点政策和明确 Rate Limit 优先级高于吞吐量目标。

### 8.4 Backpressure

触发条件：

- Redis Stream Pending/Queue Age 超阈值；
- PostgreSQL latency 上升；
- S3 上传积压；
- Browser pool 饱和；
- Worker memory/CPU 高水位；
- 单 host 429/503 增加。

策略：

```text
暂停低优先级 discovery
-> 降低 batch size
-> 减少 browser slots
-> 延迟 historical-gap
-> 保留 incremental/revalidation 预算
```

## 9. Revalidation Engine 与增量同步

这是增量同步的核心，不直接依赖 Crawl4AI Runtime Cache。

### 9.1 增量入口

增量触发来源：

- CMS API 新 revision；
- Sitemap `lastmod`；
- RSS/Atom `updated`；
- Webhook；
- Archive 新链接；
- 定时 Revalidation；
- 强制完整刷新；
- 用户手工重抓；
- Provider Reconcile。

### 9.2 Revalidation Ledger

PostgreSQL 保存：

```text
url_id
source_id
last_fetch_at
last_verified_at
last_changed_at
etag
last_modified
raw_body_hash
semantic_body_hash
head_fingerprint
validator_strength
validation_method
validation_result
validation_reason
validation_http_status
cache_served
runtime_cache_status
runtime_cache_mode_effective
runtime_check_cache_freshness_effective
runtime_release
runtime_cache_contract_release
consecutive_304
forced_refresh_due_at
validation_error_count
validator_false_negative_count
source_validator_trust_score
```

### 9.3 证据强度

**STRONG**：

- CMS/API revision/version id；
- 经该 Source 验证过的标准 Conditional GET 304；
- 完整 GET 后 body hash 与历史一致。

**MEDIUM**：

- ETag/Last-Modified 发生变化；
- Sitemap/RSS 更新时间发生变化；
- 已知可靠但非正文级的 Provider change signal。

**WEAK**：

- `<head>` fingerprint 相同；
- 页面长度相近；
- link graph 相似；
- 局部 metadata 未变化。

只有符合 Source Policy 的强证据才允许推进 `last_verified_at`。

### 9.4 状态机

```text
DUE_FOR_REVALIDATION
      |
      +-- Provider 明确 changed ------> FETCH_REQUIRED
      |
      +-- Conditional GET 304 --------> VERIFIED_UNCHANGED
      |
      +-- validator changed ----------> FETCH_REQUIRED
      |
      +-- weak unchanged -------------> WEAK_UNCHANGED
      |                                  |
      |                                  +-- sample due -> FETCH_REQUIRED
      |
      +-- validation error -----------> VALIDATION_DEGRADED
                                         |
                                         +-- 可服务旧版本
                                         +-- 不推进 last_verified_at
                                         +-- 安排重试

FETCH_REQUIRED
      |
      v
RAW_ARTIFACT
      |
      +-- body hash unchanged --------> VERIFIED_UNCHANGED
      |
      +-- body hash changed ----------> NEW_DOCUMENT_VERSION
```

### 9.5 强制定期完整抽样

任何 weak/validator 路径都必须配置：

```text
forced_full_refresh_interval
forced_sample_rate
min_validator_trust_score
```

抽样完整抓取发现“validator 未报变化但 body hash 已变”时：

1. 记录 false negative；
2. 降低 `source_validator_trust_score`；
3. 缩短强制刷新周期；
4. 提升该 Source 的 fresh-fetch 比例；
5. 必要时禁用该 Source 的弱验证跳过策略。

## 10. HTTP Fast Lane、Browser Slow Lane 与 Runtime Cache

### 10.1 HTTP First

普通文章优先 `httpx/aiohttp`：

- GET/Conditional GET；
- Redirect chain；
- ETag/Last-Modified；
- Content-Type/MIME；
- Content-Length 上限；
- robots；
- Response headers；
- 原始字节与编码检测。

满足正文质量条件则不启 Browser。

### 10.2 Browser Escalation

仅以下情况进入 Browser Slow Lane：

- HTTP 页面正文为空/占位；
- JS 客户端渲染；
- 需要有限滚动/点击才能出现文章正文；
- Shadow DOM/iframe 且 Source Policy 允许；
- HTTP Candidate 明显低质量；
- Source Recipe 指定。

Browser 通过长期 Runtime Pool 复用，不为每 URL 启动新进程。

### 10.3 平台 Cache Policy Compiler

业务层不直接暴露 Crawl4AI `CacheMode`，只暴露：

```text
AUTHORITATIVE_FETCH
VALIDATE_THEN_FETCH
REPLAY_FROM_ARTIFACT
RUNTIME_CACHE_WARMUP
DIAGNOSTIC_CACHE_READ
```

Compiler 根据 pinned runtime release 生成实际配置。

#### AUTHORITATIVE_FETCH

- 禁止从 Runtime cache 返回旧正文；
- 必须产生真实网络响应证据；
- 使用通过 Contract Test 的具体配置，不按 enum 名称猜测；
- 结果晋升为平台 Raw Artifact。

#### VALIDATE_THEN_FETCH

- 平台 Revalidation Engine 先判断；
- 确认需要抓取后使用 fresh fetch；
- Runtime Smart Cache 只做可选额外优化；
- Runtime 的 `hit_validated` 不能覆盖平台 Freshness 结论。

#### REPLAY_FROM_ARTIFACT

- 直接处理 S3/MinIO Raw Artifact；
- 不访问网络；
- 建议 Replay Worker 使用 egress deny；
- **不能映射成 Crawl4AI `READ_ONLY` 来保证离线**，因为 `READ_ONLY` 在 cache miss 时仍可能真实联网。

#### RUNTIME_CACHE_WARMUP / DIAGNOSTIC_CACHE_READ

允许 Runtime cache，但不推进业务版本、Freshness 或 Coverage。

### 10.4 Crawl4AI Smart Cache 的使用边界

当前已验证的 Runtime 行为中，Smart Cache 使用 ETag、Last-Modified 和 `<head>` fingerprint 降低完整 Browser 成本，但必须遵守：

1. `check_cache_freshness` 是显式开关，不能假定默认启用；
2. `<head>` fingerprint 是弱证据，正文可在 head 不变时变化；
3. Runtime validation error 可能返回旧 cache (`hit_fallback`)；
4. `hit_fallback` 只能作为 serving fallback，不得更新 `last_verified_at`；
5. Runtime cache 不进入 Coverage/Version 真相；
6. `READ_ONLY` 只代表不写 Runtime cache，不代表禁止联网；
7. `BYPASS/ENABLED/...` 的真实读写语义必须以 pinned release 的 Contract Test 为准。

### 10.5 Runtime Cache 状态归一化

平台统一记录：

```text
MISS
HIT_UNVERIFIED
HIT_VALIDATED
HIT_FALLBACK
DISABLED
BYPASSED
UNKNOWN
```

并附加：

```text
returned_artifact_origin = NETWORK | RUNTIME_CACHE | PLATFORM_ARTIFACT
freshness_evidence_strength = STRONG | MEDIUM | WEAK | NONE
business_verification_advanced = true | false
```

`HIT_FALLBACK` 必须在 Web 与告警中显式展示。

### 10.6 Runtime Cache Contract Test Matrix

每次 Runtime package/image 升级必须执行至少以下矩阵：

| 模式 | freshness | 初始缓存 | 服务端行为 | 必验结果 |
|---|---|---|---|---|
| DISABLED | 任意 | hit/miss | 200 | 不读、不写、真实抓取 |
| BYPASS | 任意 | hit | 200 | 实测读写行为，禁止按名字推断 |
| ENABLED | false | hit | 任意 | 可直接 hit，不发生 freshness 校验 |
| ENABLED | true | hit | 304 | `hit_validated`，记录验证证据 |
| ENABLED | true | hit | 200 + head 同 | Runtime 可判 fresh，但平台只认 WEAK |
| ENABLED | true | hit | head 变 | 重新抓取 |
| ENABLED | true | hit | timeout/error | `hit_fallback`，不推进业务验证时间 |
| READ_ONLY | 任意 | miss | 200 | 仍会真实联网，但不写 Runtime cache |
| WRITE_ONLY | 任意 | hit | 200 | 不读旧缓存，真实抓取并写 |

每个 case 记录：

```text
should_read
should_write
network_called
request_method
conditional_headers
cache_status
cache_written
returned_content_hash
returned_artifact_origin
validation_status
```

## 14. Document、Version 与变化判定

### 14.1 Document 与 Version 分离

```text
Document = 逻辑文章身份
DocumentVersion = 某次业务意义上的正文版本
RawArtifact = 某次真实抓取证据
```

一个 Document 可对应多个 URL Alias、Raw Artifact 和 Version。

### 14.2 版本生成

完整抓取后：

```text
raw body hash unchanged
    -> 不创建新 DocumentVersion

raw changed
    -> Cleaner/Extractor/IR
        -> semantic content hash unchanged
            -> 只更新 fetch evidence / metadata
        -> semantic content hash changed
            -> 创建新 DocumentVersion
```

这样可以避免广告、时间戳、推荐栏变化制造无意义版本。

### 14.3 元数据版本

标题、作者、发布时间、canonical 变化应单独记录 metadata diff；是否创建新 DocumentVersion 由 Version Policy 决定。

## 15. 重定向、删除、重发布与 URL 迁移

### 15.1 Redirect

保存完整 redirect chain：

```text
old_url -> 301 -> new_url
```

不立即删除旧 URL Identity，而是创建 alias/redirect relation。

跨 host 跳转必须重新经过 Approved Host/Scope Policy。

### 15.2 删除

单次 404/5xx 不能立即判删除。

建议：

```text
404/410
  -> TOMBSTONE_CANDIDATE
  -> 多次确认 / provider reconcile
  -> DELETED_CONFIRMED
```

410 权重高于 404，但仍保存历史版本。

### 15.3 重发布

相同正文出现在新 URL：

- 先保留独立 Observation；
- 通过 canonical/redirect/body hash/metadata 判断 relation；
- 不因 near-duplicate 自动合并；
- Web 后台可人工确认 Document merge/split。

## 18. Crawl4AI Runtime Service Plane

Crawl4AI 不直接嵌入业务 API 进程，作为独立 Runtime Service Plane。

### 18.1 Runtime Gateway

输入：

```text

url

runtime_release
browser_profile

```

输出：

```text
result_id

html/artifact reference
response headers

cache_status

```

平台必须按 `attempt_id/url identity` 关联结果，不能按返回数组位置关联。

### 18.2 Bounded Micro-Batch

批量抓取必须有硬边界：

```text
max_urls_per_batch
max_inflight_per_runtime
max_result_bytes
max_browser_pages
max_batch_wall_time
```

大 Backfill 使用小批流式处理，不一次提交数十万 URL。

### 18.3 Browser Pool

- 长期进程复用；
- context/page 有寿命上限；
- 内存高水位自动 recycle；
- 单 Source/host 并发受全局 admission 控制；
- 崩溃只影响 Attempt，不影响业务 Frontier。

### 18.4 Runtime 不拥有的状态

禁止依赖 Runtime 本地状态决定：

- URL 是否已完成；
- Backfill 是否完整；
- Document 当前版本；
- last_verified_at；
- Markdown canonical 输出；
- Source pause/resume 真相。

```text
-> S3 Artifacts
-> Rebuild Redis transport
-> Reconcile Frontier/Task
-> Rebuild Search Projection
```

不需要恢复 Crawl4AI 本地 cache 才能恢复业务。

### 26.3 Replay

任意历史 Raw Artifact 可用指定：

```text
cleaner_release
extractor_release
quality_policy_release
ir_schema_release
renderer_release
```

重新生成派生物，且不访问网络。

## 28. 最终推荐架构

最终采用：

> **PostgreSQL Truth Store + S3/MinIO Immutable Artifact + Redis Streams Durable Transport + Declarative Source/Profile + Multi-Provider Discovery + Persistent Frontier + Revalidation Engine + HTTP First / Browser Slow Lane + Crawl4AI Runtime Service Plane + Runtime Contract Release Gate + Extraction Portfolio + Canonical IR + Deterministic Markdown + OpenSearch/pgvector + Web Admin。**

最关键的边界是：

- **Provider 返回不是 Coverage 真相；**
- **Runtime cache 不是 Freshness 真相；**
- **Smart Cache 命中不是正文未变化的充分证据；**
- **`READ_ONLY` 不是离线安全边界；**
- **Runtime enum 名称不是生产契约，pinned release + Contract Test 才是；**
- **Raw Artifact 不可变，所有清洗/抽取/Markdown 都可重放；**
- **Browser 是昂贵慢路径，不是默认路径；**
- **Coverage、Version、Freshness、Markdown 的最终真相始终在平台层。**
