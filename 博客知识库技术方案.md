# 博客知识库技术方案

## 1. 建设目标与规模

建设一个长期运行、可横向扩展、可审计、可回放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客、技术文档站与公开 Newsletter，尽可能抓取完整历史文章并清洗为稳定 Markdown；后续持续增加网站，并以低成本完成增量同步、版本管理、搜索/RAG、Web 管理和离线重处理。

目标规模：

- 1000+ Source，架构可扩展到数千站点；
- 百万级 Document / Document Version；
- 数百万到千万级 URL Observation；
- 千万级 Chunk / Embedding；
- HTML、PDF、Markdown、TXT、JSON/API、RSS/Atom/JSON Feed；
- 中英日韩等多语言；
- HTTP 为默认抓取路线，Browser 为受控 fallback；
- CMS API、Sitemap、Feed、Archive、Category/Tag、Docs TOC、Common Crawl、受控 Deep Crawl 等多入口历史发现；
- PostgreSQL + Object Storage 保存事实；Markdown、全文索引、向量索引、Graph、AI Insight、Export、Dashboard Read Model 均作为可重建 Projection；
- Web UI、n8n、MCP、CI、Agent、外部系统只能通过受控 API / Event 边界驱动平台。

平台必须能回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已经基本覆盖；
2. 一个 URL 从哪里被发现、如何规范化、为何被过滤或放行、经过哪些跳转、最终抓到了什么；
3. 为什么某 URL 走 HTTP、平台 API、文件流、Crawl4AI Browser 或 Playwright；
4. 一个 Markdown 来自哪个 Snapshot、Extractor、Release 和 Document Version；
5. 源站变化后哪些内容真正变化，哪些派生物需要重建；
6. Worker 崩溃、批任务部分失败或外部自动化重启后如何恢复且不丢成功项；
7. 新增第 1001 个站点时，能否主要依靠配置、Probe 与审核接入，而不是增加站点专用代码；
8. 全量历史抓取是否有 durable checkpoint，能否从断点继续；
9. 百万 URL 批处理是否保持有界内存，并支持逐 URL 提交；
10. Browser 是否被复用且安全隔离，何时回收，是否因资源压力自动降并发；
11. 第三方 crawler API 升级后，是否只修改 Adapter 而不污染平台数据契约；
12. Markdown 导出到本地/S3/Git 后，是否仍能稳定映射回平台内部 Document Version。

## 2. 核心设计原则

1. **Config First**：普通站点靠 Source / Site Profile / Release 接入，不修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence、cursor、exhaustion reason 和 known gap 证明，队列为空不等于完整。
3. **Authoritative First**：CMS/API、Sitemap、Feed、Archive 优先，Common Crawl/Deep Crawl 用于补洞和交叉验证。
4. **Discovery Before Fetch**：先发现、Observation、规范化、过滤、分类、去重，再抓正文。
5. **Durable Streaming Frontier**：大站 URL 发现必须流式、小批持久化，禁止把全站 URL 一次性物化在内存。
6. **Filter With Evidence**：Filter 可 HARD/SOFT/DEPRIORITIZE，但任何决定都保存规则、原因和证据。
7. **URL Is Locator**：资源类型由响应 MIME、签名、跳转和站点规则判断，不能只看扩展名。
8. **HTTP First, Browser Last**：静态 HTML、Feed、API、Sitemap 优先 HTTP；Browser 只处理动态正文、交互和质量 fallback。
9. **Reuse Browser, Isolate Session**：复用 Browser/Crawler 进程降低成本，但 Cookie、LocalStorage、认证态和代理身份按 Source/Profile/安全域隔离。
10. **Adapter Is Boundary**：Crawl4AI/Playwright/HTTP 客户端只输出平台内部稳定契约，第三方 DTO、字段名和版本变化不得泄漏到事实层。
11. **Platform Permit Before Local Dispatcher**：平台全局/domain/source 配额是并发上限；Crawl4AI Dispatcher/Semaphore 只负责 Worker 内二级自适应控制。
12. **Bounded Window + Commit Per URL**：Worker 只 lease 有界窗口，流式返回结果；每个 URL 成功立即落库，不等待整批完成。
13. **Snapshot First**：先保存不可变网络事实，再做抽取、清洗、Markdown、Chunk、Graph、AI。
14. **IR First, Markdown as Projection**：Canonical IR / Document Version 是内容事实层，Markdown 可确定性重建。
15. **Full Canonical Before Fit Markdown**：Pruning/BM25/LLM 等有损过滤只能产生 FILTERED/ENHANCED Projection，绝不能覆盖 Canonical Markdown。
16. **Recipe, Not Site Code**：交互、路由、Filter、Schema、Selector、Extractor 均声明式、版本化、可回放。
17. **Stable Identity**：URL Alias、Document、Version、Chunk、Embedding、Graph、Analysis、Export 身份分离且稳定，禁止用简单 URL 字符串替换后的文件名作为内部主键。
18. **Release Everything**：影响结果的 Profile、Provider、Filter、Adapter、Recipe、Extractor、Markdown、Chunk、Embedding、Graph、Model、Prompt、Metric、Webhook、Export、Runtime 全部版本化。
19. **Idempotent + Recoverable**：任务有幂等键、lease、fencing token、checkpoint、retry、partial success。
20. **One Durable Task System**：PostgreSQL durable state + Transactional Outbox + Redis Streams 是唯一业务任务体系。
21. **External Automation Is Adapter, Not Truth**：n8n/MCP/CI/Agent 不能成为 Coverage、Task、Snapshot、Version 或 retry 状态真相。
22. **Projection Is Rebuildable**：全文、向量、Graph、AI、Export、Dashboard 都可从事实层离线重建。
23. **Generation Instead of Destructive Rebuild**：索引/图谱新版本后台构建、验证、原子切换。
24. **Security on Every Hop**：起始 URL、Redirect、Browser navigation、Webhook endpoint 每跳重新做 SSRF/Egress/Scope 校验。
25. **Source Friendly**：吞吐最大化不是唯一目标，robots、站点策略、分层限流和退避优先于速度。
26. **Benchmark Before Switch**：Adapter、Filter、Extractor、Markdown、Embedding、Graph、Retrieval、Metric 升级先固定回归，再激活。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST/Command API、Schema 校验、Webhook Receiver、内部服务接口；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、Observation、Snapshot metadata、Document、Version、Release、Audit、Outbox、Event、Webhook Delivery、Export metadata；
- **Transactional Outbox**：保证业务数据库事务与异步消息发布一致；
- **Redis Streams**：consumer group、retry transport、backpressure，只做任务运输；
- **React/Vue + TypeScript**：Web 管理台；
- **Docker/Kubernetes**：按 Discovery / HTTP Fetch / Browser / Extract / Projection Worker 类型独立扩缩容。

### 4.2 抓取与解析

- **HTTPX/aiohttp**：静态 HTML、Feed、Sitemap、API、Conditional GET、Range GET；
- **Crawl4AI**：URL Seeder、`arun_many()` 流式多 URL 抓取、Browser Interaction、Markdown/Structured Extraction Adapter、Worker 内 Dispatcher；
- **Playwright**：复杂 JS 与特殊交互 fallback；
- **lxml/BeautifulSoup/CSS/XPath/Regex**：确定性抽取；
- **Trafilatura/Readability**：通用正文候选；
- **PDF parser + OCR fallback**；
- **S3/MinIO**：raw response、HTML、Rendered DOM、PDF、WARC、Canonical IR、Markdown、Structured JSON、Graph/AI artifact、fixture。

### 4.3 检索与派生

- **OpenSearch**：BM25、过滤、聚合、Alias/Generation；
- **pgvector/OpenSearch kNN**：首期向量；规模增长后可切 Qdrant/Milvus；
- **RRF/Controlled Fusion**：BM25 + Vector 基线；
- **Graph**：首期 PostgreSQL 表验证价值，需要高阶图查询再增加 Neo4j/Memgraph Adapter；
- **Cross Encoder Reranker**：可选。

### 4.4 可观测与运营

- Prometheus + Grafana + OpenTelemetry；
- PostgreSQL incremental/materialized read model；
- 数据规模进一步增长后可增加 ClickHouse；
- SSE/WebSocket：Web UI 实时状态；
- Signed Webhook：外部系统事件交付。

```text
graph_ontology_release
graph_projection_release
retrieval_release
analysis_release
model_release
prompt_release
webhook_policy_release
export_sink_release
ops_metric_release
runtime_artifact_release
```

`runtime_artifact_release` 固定 Crawl4AI、Playwright、Browser Revision、Python、解析器、模型 digest、系统依赖和镜像 digest；`fetch_adapter_release` 固定第三方 DTO 到平台内部 `FetchAdapterResult` 的转换语义。

Crawl4AI 等第三方库升级必须执行：

```text
new runtime/adapter release
 -> fixture regression
 -> old/new result normalization diff
 -> raw/fit markdown hash diff
 -> canary
 -> activate
```

第三方字段从旧版 `result.markdown_v2.*` 迁移到新版 `result.markdown.*` 一类变化，只允许在 Adapter 内处理，禁止驱动 Snapshot、Document、Export 表结构跟着变化。

全文、向量、Graph 使用 Generation：

```text
BUILDING -> VALIDATING -> READY -> ACTIVE -> RETIRED
```

新 Generation 先离线构建、固定 judgment/fixture 验证、canary，再通过 Alias/逻辑指针原子切换。

## 7. 全量历史发现、Coverage 与 Durable Frontier

### 7.1 Provider Contract

```text
probe(source, profile) -> capability
discover(cursor, budget) -> candidates + evidence + next_cursor
checkpoint() -> durable_cursor
exhaustion() -> explicit_reason
```

Provider：

```text
CMS_API
SITEMAP
FEED
ARCHIVE
CATEGORY_TAG_AUTHOR
DOCS_TOC
DISCOVERY_SURFACE
BROWSER_DISCOVERY_SURFACE
COMMON_CRAWL_URL_INDEX
SITE_SEARCH
DEEP_CRAWL_BFS
DEEP_CRAWL_DFS
DEEP_CRAWL_BEST_FIRST
```

历史发现优先级：

```text
CMS/API
 -> Sitemap/Sitemap Index
 -> Historical Feed
 -> Archive year/month
 -> Category/Tag/Author
 -> Blog Index / Docs TOC
 -> Common Crawl
 -> HTTP/Browser Discovery Surface
 -> Best-First/BFS gap filling
 -> Site Search supplement
```

Deep Crawl 是 gap discovery，不是 Coverage 真相。

### 7.2 Coverage 事实

```text
coverage_provider_run
- run_id
- source_id
- provider_type
- provider_release_id
- cursor_before
- cursor_after
- status
- exhaustion_reason
- candidate_count
- committed_observation_count
- completed_count
- failed_count
- known_gap
- blocker
- evidence_ref
```

预算耗尽只能标记：

```text
known_gap = true
exhaustion_reason = BUDGET_EXCEEDED
```

只有主要权威 Provider exhausted，或剩余缺口均成为可解释、可枚举的 known gap，`FULL_BACKFILL` 才能结束。

### 7.3 Sitemap Index 分片与 checkpoint

大站 Sitemap Index 把每个 child sitemap 作为独立分片：

```text
sitemap_shard_state
- source_id
- sitemap_url
- parent_sitemap_url nullable
- etag
- last_modified
- content_hash
- parse_cursor
- observation_commit_cursor
- state
- last_success_at
- provider_release_id
```

处理流程：

```text
conditional fetch child sitemap
 -> stream parse URLs
 -> observation mini-batch commit
 -> outbox/task publish
 -> advance durable observation cursor
 -> finish shard
```

Provider checkpoint 只能在 Observation 已持久化后推进，避免“发现游标前进但 URL 未落库”。

### 7.4 Durable Streaming Frontier

禁止：

```text
all_urls = load_everything_from_sitemap()
await crawl(all_urls)
```

推荐：

```text
Provider page/shard
 -> 100~1000 URL mini-batch
 -> Observation commit
 -> Normalize/Filter/Classify
 -> Durable Task
 -> next Provider page/shard
```

Frontier 优先级：

```text
P0 new feed/API item
P1 manual/targeted fetch
P2 incremental high-yield URL
P3 historical authoritative provider
P4 historical gap/deep crawl
P5 reprocess/reindex/AI optional work
```

每 Source 和全局维护 `frontier_low_watermark`、`frontier_high_watermark`、`max_pending_per_source`、`max_pending_per_domain`、`max_observation_commit_lag`；下游积压超过高水位时暂停非紧急 Discovery，恢复到低水位再继续。

## 8. URL Observation、Normalization、Filter 与 Resolution

### 8.1 Observation First

```text
url_observation
- source_id
- observed_url
- provider_type
- provider_run_id
- parent_url nullable
- anchor_text nullable
- depth nullable
- observed_at
- evidence_ref
```

Filter 不能删除“曾经发现过这个 URL”的事实。

### 8.2 Normalization

全局安全规则：host lowercase、default port removal、fragment removal、path slash、安全 percent-encoding、query key ordering、tracking param removal。

站点规则：semantic query allowlist/denylist。禁止全局删除 query；`?id=123`、`?p=456`、`?page=7` 可能有业务语义。

### 8.3 URL Filter Chain

```text
HARD_REJECT
SOFT_REJECT
DEPRIORITIZE
ACCEPT
```

HARD 仅用于明确禁止域、robots/policy、后台/登录、静态资产等；路径猜测、相关性、category/tag 默认 SOFT/DEPRIORITIZE。

每次决策保存 `filter_release_id`、`rule_id`、`action`、`reason_code`、`score`、`evidence_ref`、`decided_at`。新 Filter Release 上线前对已知文章 URL fixture 做 recall 回归。

### 8.4 Classification / Resolution / Resource Probe

Candidate：

```text
ARTICLE_CANDIDATE
DISCOVERY_SURFACE
ASSET
NAVIGATION
EXTERNAL_REFERENCE
IGNORE_BY_POLICY
UNKNOWN
```

Resolution：

```text
Observed URL
 -> Normalized Candidate
 -> HTTP Redirect
 -> Wrapper Param / HTML Target
 -> Meta Refresh
 -> Browser Navigation Fallback
 -> Resolved Target
```

每一跳重新执行 DNS/IP/SSRF/origin scope 校验。`canonical`/`og:url` 是 Identity Evidence，不等同于 redirect。

Resource Probe 综合 Content-Type、Content-Disposition、magic bytes、Content-Length、HTML 壳、Range GET、redirect 和 Site Profile，产出 HTML/PDF/Markdown/Text/JSON/XML/Image/Archive/Unknown Binary 类型。

## 10. Fetch Plane：路由、稳定 Adapter、流式批处理与 Browser Pool

### 10.1 Fetch Route

```text
HTTP_STATIC
 -> HTTP_ALT_HEADERS
 -> HTTP_PLATFORM_API
 -> FILE_STREAM_FETCH
 -> BROWSER_CRAWL4AI_RECIPE
 -> BROWSER_PLAYWRIGHT_CUSTOM
 -> SITE_CUSTOM_EXTRACTOR
```

站点内部不同 URL 可按 matcher 使用不同 route/extractor：

```text
/blog/*      -> HTML article
/docs/*      -> docs profile
*.pdf        -> PDF parser
/api/*       -> JSON
/search/*    -> discovery only
/account/*   -> hard reject
```

### 10.2 Crawl4AI/Fetcher Stable Adapter Contract

Fetch Worker 不直接把第三方 `CrawlResult` 写入数据库。所有 HTTP/Crawl4AI/Playwright 结果先归一化：

```text
FetchAdapterResult
- requested_url
- final_url
- redirect_chain[]
- success
- status_code
- response_headers
- content_type
- body_ref/raw_html_ref nullable
- cleaned_html nullable
- raw_markdown nullable
- fit_markdown nullable
- markdown_with_citations nullable
- references_markdown nullable
- metadata nullable
- links[]
- media[]
- extracted_content nullable
- error_class nullable
- error_message nullable
- dispatch_metrics nullable
- runtime_release_id
- adapter_release_id
```

原则：

- 旧版 `markdown_v2`、新版 `markdown` 等字段差异由 Adapter 消化；
- `result.url` 视为执行结果中的 final URL 证据，仍与 requested URL、redirect chain 分开保存；
- title 不允许简单等于 Markdown 第一行，优先结构化 metadata/H1/JSON-LD/CMS 字段，并保存 confidence；
- 第三方 `fit_markdown` 只能作为候选派生数据，不直接成为 canonical 事实；
- `links` 必须回流 Observation，不由 Fetch Worker 无界递归；
- Adapter 对缺字段、未知字段、类型漂移产生显式 normalization error 指标，而不是静默丢弃。

### 10.3 Bounded Window Streaming

Worker 不接收“整个站点 URL 数组”，而是从 Durable Task Store lease 一个窗口：

```text
lease N tasks
 -> group by route/profile/domain
 -> acquire platform permits
 -> HTTP batch or Crawl4AI arun_many(stream=True)
 -> normalize each third-party result
 -> each result completes independently
 -> persist Snapshot/Attempt/links
 -> ACK current URL
 -> refill below low watermark
```

N 是几十/数百量级的执行窗口，不是全量历史 URL 数。

### 10.4 Browser Pool

Browser Worker 启动时建立长期存活池：

```text
Browser Worker
  └─ pool(runtime_release, profile/security_scope, proxy_scope)
       ├─ browser/crawler instance
       │    ├─ context/session
       │    └─ context/session
       └─ browser/crawler instance
```

Browser Process 可以复用；认证态不跨安全边界共享。

回收条件：`max_pages_per_browser`、`max_browser_age`、worker/browser RSS 超阈值、crash/page error 超阈值、Runtime Release 切换、drain/部署、context 泄漏或清理失败。

### 10.5 两层并发控制

第一层是平台 permit：

```text
Global -> route -> registrable-domain -> source -> host
```

第二层是 Worker 本地：

- Crawl4AI `MemoryAdaptiveDispatcher`；
- 或固定 Semaphore；
- `RateLimiter`；
- 本地 browser page/context ceiling。

本地 Dispatcher 可以因为内存/错误率而主动降低并发，但不能突破平台 permit 上限。

### 10.6 页面新链接不能直接递归抓

Fetch Result 的 links 必须回到：

```text
URL Observation
 -> Normalize
 -> Scope
 -> Filter
 -> Classify
 -> Dedupe
 -> Budget/Priority
 -> Durable Task
```

禁止 Fetch Worker 自己维护无限递归 frontier。

## 11. Rate Limit、Retry 与端到端 Backpressure

每个 Source/Profile 可配置 `max_rps`、`max_concurrency`、`burst`、`max_browser_seconds_per_hour`、`max_bytes_per_hour`、`max_pages_per_run`、`retry_budget`，同 registrable domain 的多个 Source 共享上层域配额。

Retry：

- 429/503：解析 `Retry-After`，退避并降低 host/domain concurrency；
- timeout/connection reset：exponential backoff + jitter；
- 401/403/404/410：按原因分类，不盲目重试；
- robots/policy：终止；
- Browser crash：换实例后有限重试；
- HTTP 正文质量不足：可触发 Browser fallback；
- Extractor 失败：优先从已保存 Snapshot 离线重试，不重新访问源站。

端到端背压信号：

```text
fetch_queue_lag
extract_queue_lag
snapshot_upload_lag
DB_commit_p95
object_store_p95
worker_RSS
browser_RSS
browser_page_count
429_503_rate
fetch_error_rate
```

控制逻辑：

```text
memory high OR downstream lag high
 -> shrink worker-local concurrency
429/503 high
 -> shrink host/domain permits + backoff
healthy AND queue lag high
 -> grow local concurrency, never above platform permits
```

### 12.2 Extraction Candidate

### 12.3 Canonical IR

```text
DocumentIR
  metadata:
    title/authors/published_at/updated_at/language/canonical_url/tags
    field_confidence/source_evidence
  blocks:
    heading/paragraph/list/quote/code/table/image/figure/formula
  assets[]
  outbound_links[]
  source_evidence[]
```

HTML/PDF/MD/TXT 最终统一进入 IR。

### 12.4 Quality

至少检查正文长度、标题一致性、link density、boilerplate、code/table 保留、language、published_at confidence、truncation、selector match、required field、DOM drift、HTTP 与 Browser 候选差异。低质量候选进入 quarantine，Web 可比较不同 Extractor。

### 12.5 Canonical Markdown

从 IR 确定性生成：去导航、广告、推荐、评论等 boilerplate；保留标题层级、代码、列表、引用、表格、图片 alt/caption、重要链接；解析相对链接；保留文章完整主体，不做 query-dependent 删减；Front Matter 记录 document/version/source/canonical URL/content hash/release。

### 12.6 Filtered / Fit Markdown 是有损 Projection

Crawl4AI `PruningContentFilter`、BM25 filter、LLM filter 等产出的 `fit_markdown` 只能存为：

```text
FILTERED_MARKDOWN
ENHANCED_MARKDOWN
```

它们适合检索/RAG，但不能覆盖 Snapshot、Canonical IR、Canonical Markdown。过滤阈值或模型升级后必须从事实层离线重建，而不是重新抓源站。

## 13. Document Identity、版本与增量同步

Identity 综合 platform stable ID、canonical/og:url、redirect evidence、Feed GUID、CMS/article ID、normalized URL、exact/near duplicate、title + published time。URL Alias、Document Identity、Document Version 分离。

Document Version 只在 Canonical IR 或关键元数据变化时创建。304、重复抓取、Markdown/Chunk/Embedding/Graph/AI/Export 策略升级不创建正文版本。

增量信号：

```text
Feed/API cursor
 -> Sitemap conditional fetch + lastmod
 -> High-yield Surface
 -> Conditional GET
 -> Metadata/Resource Probe
 -> Full HTTP
 -> Browser fallback
```

保存 ETag、Last-Modified、previous_body_hash、content_length、content_kind。304 不重复保存 body、不重新抽取、不新建 Version、不重做 Projection。

调度分层：

```text
Tier 0 Feed/API            分钟级
Tier 1 Sitemap/Blog Index  10~60 分钟
Tier 2 Category/Archive    1~6 小时
Tier 3 Deep Reconcile      每周/每月
Tier 4 Common Crawl        新 collection/按月
```

Feed/API 使用 overlap window；周期 Reconcile 发现迟到、Feed 窗口外遗漏、URL 迁移、删除和结构漂移。源站 404/410 不物理删除历史 Version，而创建 availability/tombstone 状态。

## 15. Structured Extraction、Chunk、Embedding、Search、Graph 与 AI

结构化抽取与 canonical 内容分离。优先级：

```text
platform API / JSON-LD / CSS / XPath / Regex
 -> deterministic extractors
 -> LLM only for complex/unstructured fields
```

LLM 使用 JSON Schema/Pydantic 约束，记录 token、latency、cost、validation error。

AI Analysis 与 Source Sync 解耦：SUMMARY、TOPIC、ENTITY、SENTIMENT、FAQ、ENHANCED_MARKDOWN 等均是可重放 Projection，失败不阻塞文档 READY。

Chunk 使用 Structure-aware 规则：Heading/Section 优先，段落、列表、引用尽量完整，code/table 默认不拆；`Chunk NEVER crosses Document Version boundary`，并保存 heading path/page/block range。

```text
chunk_id = hash(boundary_id + chunk_release_id + block_range + normalized_text_hash)
embedding_id = hash(chunk_id + embedding_release_id)
```

检索基线：

```text
BM25 + Vector
 -> hard SOURCE/DOCUMENT/VERSION/ACL scope
 -> RRF/controlled fusion
 -> optional reranker
 -> context assembly
```

Graph 是可选第三召回通道，不替代原文/BM25/Vector。只有固定 judgment set 证明增量收益后才默认开启。

## 20. 初始容量、部署与实施阶段

首期不要按“1000 站同时 Browser”设计，按站点分类：

```text
静态/Feed/API 站点         -> HTTP Worker 为主
轻度 JS                    -> HTTP + Browser fallback
重度 JS/交互               -> Browser Worker 专属队列
PDF/OCR                     -> 独立 CPU/OCR Worker
Embedding/Graph/AI          -> 独立低优先级 Projection Worker
```

起步默认模板，最终由压测调整：

- 每 domain 并发 1~4；
- 每 Source 并发 1~8；
- Browser Worker 每实例 context/page 上限小于 HTTP 并发一个数量级；
- Browser local adaptive ceiling 根据 RSS 自动收缩；
- Discovery mini-batch 100~1000 URL；
- Fetch lease window 20~200 URL，按 route 和内存调整；
- Redis Stream backlog 只做运输观测，真正任务状态以 PostgreSQL 为准。

### Phase 1：可用的全量历史库

Source/Profile、CMS/Sitemap/Feed/Archive Provider、URL Observation + Durable Frontier、HTTP Fetch、Snapshot、Extract + Canonical IR + Canonical Markdown、Document Identity/Version、Local/S3/Git Export、Web Source/Coverage/URL Trace、基础增量同步。

验收：选 30~50 个结构差异大的站点，证明可恢复全量、Coverage 可解释、Markdown 可重建。

### Phase 2：动态站与规模化执行

Crawl4AI Browser Adapter、稳定 `FetchAdapterResult`、`arun_many(stream=True)` bounded window、Browser Pool、MemoryAdaptiveDispatcher/Semaphore 二级并发、Domain/Source permit、Interaction Recipe、Adapter fixture/canary、Browser Pool/Streaming Web 视图、1000 Source 分层调度。

验收：长时间运行无明显内存爬升；worker 重启后 Task 可恢复；第三方 crawler 升级只改 Adapter；高峰 backlog 可通过背压稳定消化。

### Phase 3：质量与检索

Extractor fixture、Quality quarantine、Filtered/Fit Markdown Projection、Chunk/Embedding/OpenSearch、Hybrid Retrieval、Generation 切换。

验收：Canonical Markdown 完整性与检索 Projection 解耦；Filter/Embedding 升级不重新抓源站。

### Phase 4：高级能力

Graph、AI Analysis、n8n/MCP、Signed Webhook、高级运营分析/ClickHouse（确有需要再引入）。高级能力不得反向阻塞 Source Sync 主链路。

## 21. 最终推荐运行链路

### 全量历史

```text
Add Source
 -> PROBE
 -> Profile Review/Activate
 -> authoritative Providers
 -> stream URL Observations
 -> Durable Frontier
 -> bounded Fetch lease window
 -> platform permits
 -> HTTP or Browser Pool
 -> stable Fetch Adapter normalization
 -> per-URL Snapshot commit
 -> Extract / Quality / Canonical IR
 -> Identity / Document Version
 -> Canonical Markdown
 -> Export
 -> async Chunk/Index/Graph/AI
 -> Coverage reconcile
```

### 增量同步

```text
Feed/API cursor + overlap
 -> Sitemap Conditional GET
 -> high-yield surfaces
 -> Conditional GET / 304
 -> changed Snapshot only
 -> new Document Version only when canonical content changes
 -> rebuild affected Projections
 -> periodic Reconcile for late/missing/moved URLs
```

### 动态页面

```text
HTTP quality insufficient
 -> Browser route
 -> acquire domain/source permit
 -> lease/reuse Browser Pool instance
 -> worker-local adaptive dispatcher
 -> interaction recipe with hard budget
 -> normalize Crawl4AI/Playwright result through Adapter
 -> Snapshot
 -> release context/page
 -> recycle browser by policy
```

这套方案把 Crawl4AI 的 URL Seeder、流式多 URL 抓取、Dispatcher、Browser 复用和 Markdown 能力放在正确的执行层位置，同时用稳定 Adapter 隔离其版本与 DTO 演进，并把 Coverage、持久化 frontier、幂等、增量、版本、回放、质量和 Web 管理留在平台事实层。这样既适合首期 1000 个技术博客，也能在后续新增网站和升级抓取组件时保持可扩展、可恢复、可审计。
