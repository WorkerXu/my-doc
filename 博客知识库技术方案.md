# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站与公开 Newsletter** 的长期知识库采集平台，并可继续扩展到数千站点、百万至千万级文章。

系统需要同时满足：

1. **全历史回填**：尽可能完整发现每个已批准 Source 的历史文章，并能解释每个 Provider 的覆盖范围、已知缺口、截断原因与停止原因；
2. **持续增量同步**：稳定发现新文章、正文更新、URL 迁移、重定向、删除、重发布和元数据变化；
3. **稳定 Markdown**：保存不可变 Raw Artifact，经版本化抽取、质量门禁、Canonical IR 与 Renderer 生成可重放 Markdown；
4. **低成本扩站**：新增网站优先通过 Source Profile、Provider、Extraction Recipe、Traversal Policy 配置完成，不维护 1000 份站点脚本；
5. **Web 可运营**：支持站点接入、审批、Backfill、Incremental、Coverage、Frontier、质量、成本、诊断、暂停、恢复、重跑和审计；
6. **任务可恢复**：Provider Run、Task、Attempt、URL、Artifact、Document、Version 全链路可追踪，Worker/Runtime 崩溃后自动恢复；
7. **可搜索/RAG**：支持 BM25、向量与混合检索，并能回溯原文、版本、Source 与抓取证据；
8. **主链不依赖 LLM**：LLM 只做可选增强，不参与历史完整性、URL 身份、robots、正文存在性、版本真相等最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 均可查看 Provider Inventory、Completion Attestation、Known Gap、Backfill Stop Reason；
- **Freshness**：新文章从发布/发现到 PASS Markdown 的 P50/P95/P99 延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文、代码块、表格、列表保留率与噪声率；
- **Reliability**：Task 成功率、Retry、DLQ、Queue Age、Lease Recovery；
- **Replayability**：相同 Raw Artifact + 相同 Release 可重放 IR/Markdown；
- **Provider Integrity**：部分返回、缓存命中、预算耗尽不能被误报为“已完整枚举”；
- **Artifact Durability**：必须保留的 Runtime/Provider Artifact 在 TTL 到期前晋升平台对象存储；
- **Browser Efficiency**：HTTP 命中率、Browser Avoided、Pool Reuse、Browser 单文档成本；
- **Fairness**：大型 Backfill 不得长期饿死 Incremental、小站和 Repair。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不默认使用个人持久 Browser Profile 或模拟真人操作绕过访问限制；
- 不把 HTTP 200、Runtime `success=true`、DOM 很长直接视为有效文章；
- 不把 Common Crawl、Wayback、搜索结果、Deep Crawl、URL Seeder 返回条数单独视为历史完整性证明；
- 不把 Crawl4AI 即时 Markdown 或 LLM 摘要直接作为 Canonical Markdown；
- 不把 Redis、Runtime Queue、Seeder Queue/Cache、Browser Session、Visited Set、Search Index 当业务真相；
- 不允许普通 Web/API 用户透传任意 JS/Python、代理、CDP、服务器路径、任意 Seeder 原生配置、任意 secret 或 webhook URL。

## 2. 核心设计原则

1. **Coverage First**：先建立可解释 URL Inventory，再抓正文；
2. **Authoritative First**：官方 CMS/API、Sitemap、Feed、Archive 优先；
3. **Observation Before Selection**：发现事实先保存，再 Normalize/Scope/Classify/Dedup；
4. **Successful Return != Provider Complete**：函数正常返回、非空列表、cache hit、`status=valid` 都不能自动代表 Provider 完成；
5. **Completion Must Be Attested**：只有具备可验证结束语义的 Provider Adapter 才能声明完成；
6. **Discovery / Fetch / Extract / Quality / Projection 分离**；
7. **HTTP First, Browser Slow Lane**；
8. **Snapshot First**：先保存不可变 Provider Evidence / Raw Artifact；
9. **Canonical IR First, Markdown as Projection**；
10. **Recipe, Not 1000 Site Scripts**；
11. **Persistent Frontier, Not In-Memory Traversal**；
12. **Idempotent + Recoverable**：幂等键、Lease、Fencing Token、Checkpoint、Inbox/Outbox；
13. **Fair by Default**：Incremental、Provider Revalidate、Repair 必须预留容量；
14. **Bounded Concurrency Everywhere**：不仅结果队列有界，任务数、在途请求、结果集合与进程生命周期也必须有平台硬边界；
15. **No Silent Degradation**：过滤、截断、预算耗尽、partial result、cache fallback、降级必须有 typed reason；
16. **Correlate by Identity, Never by Position**；
17. **Config Is Capability**：高能力配置统一经过 Capability Firewall；
18. **Runtime Is Execution Plane**：第三方 Runtime 不拥有 Coverage、Identity、Document 或 Markdown 真相；
19. **Local Safety != Global Admission**：Runtime Dispatcher、RateLimiter、Seeder Semaphore 只负责实例内保护；
20. **Behavior Beats Naming**：生产语义以 pinned release + Contract Test 为准，不以参数名或文档宣传语推断；
21. **Runtime Artifact Is Ephemeral Until Promoted**；
22. **Result Transport Is Not State Store**；
23. **Drain/Replace Before In-Place Kill**；
24. **Zero Must Not Mean Unbounded by Accident**；
25. **External Historical Index Is Evidence**：Common Crawl、Wayback 可显著补洞，但单独不能证明全历史完整。

## 5. Source 接入与配置模型

### 5.1 Source Profile

新增站点使用声明式配置：

```yaml
source:
  name: example-tech-blog
  entry_url: https://example.com/blog/
  approved_hosts: [example.com]
  allowed_paths: [/blog/]
  denied_paths: [/login/, /account/]

providers:
  - type: sitemap
    url: https://example.com/sitemap.xml
    conditional_get: true
  - type: rss
    url: https://example.com/feed.xml
  - type: archive
    start_url: https://example.com/blog/archive/
  - type: common_crawl_index
    purpose: historical_gap
  - type: crawl4ai_url_seeder
    purpose: discovery_acceleration
    modes: [sitemap, cc]

fetch:
  mode: auto
  http_timeout_s: 20
  browser_profile_class: public-default
  browser_intent:
    render_js: true
    scroll: bounded
    wait_selector: article

extract:
  recipe: generic_article_v3
  content_selectors: ["article", ".post-content"]
  exclude_selectors: ["nav", "footer", ".related"]

incremental:
  feed_poll: 10m
  sitemap_poll: 1h
  archive_reconcile: 1d
  full_reconcile: 7d
```

### 5.2 Capability Firewall

Web/API 用户只提交 intent，禁止透传：

- 任意 `js_code` / Python；
- 任意 proxy / CDP / `user_data_dir`；
- 任意 cookies、secret、服务器 path；
- 任意 LLM base URL / webhook destination；
- 未审批的 Seeder/Common Crawl query；
- 无硬上限的 `concurrency` / queue / time / result budget；
- `0=unbounded` 的配置；
- 不受控 deep crawl strategy；
- 任意网络目标与本地文件协议。

Config Compiler 将已审批 Source Intent 编译成 Provider/Runtime Config，并记录最终能力、硬预算和拒绝原因。

Crawl4AI v0.9.2 自身已将 `SeedingConfig` 排除在 untrusted 网络请求可直接构造的类型之外；平台继续采用更严格的 intent -> compiler 边界，不把 Seeder 原生配置暴露给普通用户。

### 5.3 Browser Profile Class

平台只维护少量受审 Browser Profile：

```text
public-default
public-js-heavy
public-media-light
isolated-authenticated
```

站点 selector/wait/scroll 优先放低成本 CrawlerRunConfig/Recipe。只有改变浏览器进程能力、网络边界或 credential scope 才新建 Browser Profile Release。

## 6. Provider 分层、历史 URL 发现与 Coverage

### 6.1 Provider 分层

#### A. 可声明 Completion 的 Provider

优先使用平台原生、能给出 typed terminal outcome 的 Provider：

1. CMS/官方内容 API；
2. Native Sitemap / Sitemap Index；
3. RSS/Atom；
4. 官方 Archive / Category / Pagination；
5. Native CommonCrawlIndex；
6. Wayback Gap Provider。

Common Crawl/Wayback 仍属于历史证据，不单独证明 Source 的完整历史。

#### B. Discovery Accelerator

```text
Crawl4AI URL Seeder
Domain Mapping
Deep Crawling
Adaptive Crawling
Search Adapter
```

这些组件适合发现、补洞、排序与低成本 Probe，但默认 **不能声明 `completion_attested=true`**。

### 6.2 Observation First

所有发现先落：

```text
url_observation
- observation_id
- source_id
- provider_run_id
- provider_component
- provider_ref
- observed_url
- discovered_at
- published_at_hint
- updated_at_hint
- parent_url
- anchor_text
- depth
- raw_provider_status
- evidence_artifact_id
- provider_release_id
```

之后执行：

```text
normalize -> scope -> classify -> dedup -> frontier
```

不能先用不透明过滤永久丢 URL，再宣称 Coverage 完整。

### 6.3 Provider Run 与 Completion Attestation

```text
provider_run
- provider_run_id
- source_id
- provider_id
- provider_type
- provider_component
- provider_release_id
- runtime_release_id
- started_at
- terminal_at
- terminal_outcome
- completion_attested
- raw_observation_count
- selected_count
- filtered_count
- duplicate_count
- result_limit
- hard_request_budget
- hard_byte_budget
- hard_wall_clock_budget
- truncated
- error_class
- evidence_artifact_id
```

推荐 terminal outcome：

```text
EXHAUSTED
NOT_MODIFIED
RESULT_LIMIT_REACHED
REQUEST_BUDGET_REACHED
BYTE_BUDGET_REACHED
TIME_BUDGET_REACHED
DATE_BOUND_REACHED
ROBOTS_BLOCKED
ACCESS_DENIED
RATE_LIMITED
ERROR_PARTIAL
PROVIDER_ERROR
CANCELLED
```

规则：

- `EXHAUSTED` / `NOT_MODIFIED` 只有 Adapter 能证明本次约定范围完成时才可 `completion_attested=true`；
- `RESULT_LIMIT_REACHED`、预算耗尽、`ERROR_PARTIAL` 必须 `completion_attested=false`；
- 非空列表不能自动设置完成；
- 缓存命中不能自动设置完成；
- Discovery Accelerator 的普通返回默认不设置完成。

### 6.4 Provider Checkpoint

```text
provider_checkpoint
- provider_id
- request_url
- etag
- http_last_modified
- response_sha256
- observed_lastmod_hint
- cc_index_id
- page_cursor
- shard_cursor
- checkpoint_artifact_id
- checked_at
- provider_release_id
```

Provider Evidence 与 Checkpoint 必须支撑 retry/replay，而不是依赖 Pod 本地目录。

### 6.5 Sitemap / Feed 增量同步

优先使用：

```text
If-None-Match
If-Modified-Since
```

- 304：更新检查时间，复用上次 Provider Evidence；
- 200：保存新 Provider Artifact，计算 body hash，再与旧 Inventory diff；
- 不支持 validator：退化到 body hash + `<lastmod>` hint + 周期 full reconcile；
- `<lastmod>` 只作 hint，不直接作为内容版本真相；
- 不使用字符串 `<lastmod>` 排序替代规范化时间与内容 hash。

### 6.6 超大 Sitemap Index 持久分片

当 sub-sitemap 数或预计 URL 数超过阈值：

```text
Root Sitemap Index
 -> save Provider Artifact
 -> materialize sub-sitemap list
 -> create provider_shard
 -> durable Fair Scheduler
 -> Conditional GET per shard
 -> streaming XML parse
 -> batch upsert observations
 -> shard checkpoint
```

不让单进程同时持有全站 `seen/results/discovered_urls`，也不一次创建所有子 sitemap Task。

### 6.7 Native CommonCrawlIndex Provider

可重放历史回填必须显式固定：

```text
cc_index_id
url_pattern
query parameters
page/shard checkpoint
query evidence artifact
```

同一 Backfill Run 的 retry/replay 复用同一 `cc_index_id`。需要补最新 Common Crawl 时创建新 Provider Run。

## 7. Crawl4AI URL Seeder 的生产定位与实现边界

生产基线采用 **pinned Crawl4AI release/image digest**；当前已验证的重要参考行为来自 v0.9.2。任何升级都必须重新跑 Contract Test。

### 7.1 定位

```text
provider_type = CRAWL4AI_URL_SEEDER
role = DISCOVERY_ACCELERATOR
mode = SITEMAP | CC | SITEMAP_PLUS_CC
```

Seeder 可以产生 Observation 和 Probe Hint，不直接产生 Document、Coverage Complete 或 PASS Markdown。

### 7.2 Coverage 不把 `sitemap+cc` 当一个完整 Provider

Coverage 拆分为：

```text
Provider Run A = NATIVE_SITEMAP
Provider Run B = NATIVE_COMMON_CRAWL_INDEX
Seeder Run     = DISCOVERY_ACCELERATOR
```

三者结果在 Coverage Snapshot 汇总。

原因不仅是两个来源缺少独立 completion 语义，还包括当前实现的实际执行顺序固定为：

```text
sitemap -> cc
```

即使配置字符串写成 `cc+sitemap`，仍先运行 sitemap。若前一来源触发停止条件，后一来源可能尚未执行。

### 7.3 `max_urls` 是前置软停止，不是 Coverage 硬配额，也不是全局 Top-K

当前 worker 根据共享 `results` 长度触发停止，多个 worker 之间不是硬配额事务，内部请求/结果可能少量超出，最后再对返回 List 做切片。

更重要的是：BM25 在 discovery/validation 完成后才计算。因此：

```text
query + max_urls=10
```

语义接近：

```text
先获取约 10 个候选
 -> 停止更多发现
 -> 对这批候选评分
 -> 排序
```

而不是：

```text
全量发现
 -> 全量评分
 -> global top 10
```

在 `sitemap+cc` 下，如果 sitemap 已先达到 `max_urls`，CC 可能完全没有执行。

平台因此必须把限制阶段显式区分：

```text
DISCOVERY_CANDIDATE_LIMIT
POST_FILTER_LIMIT
POST_SCORE_TOPK
PLATFORM_OBSERVATION_BUDGET
REQUEST_BUDGET_REACHED
BYTE_BUDGET_REACHED
TIME_BUDGET_REACHED
```

平台硬预算由 Scheduler/Provider Adapter 负责，不能将 Seeder `max_urls` 达限解释成 Provider exhausted。

### 7.4 Bounded Queue 不等于端到端内存有界

Seeder 主流程的 `asyncio.Queue` 有上限，能给 producer/worker 提供局部 backpressure，但同一进程仍可能持有：

```text
seen set                O(N)
results list            O(N)
sitemap discovered_urls O(N)
sub-sitemap task set    O(number_of_sub_sitemaps)
```

因此超大站不能因“queue bounded”就推导出“百万 URL 全流程内存安全”。平台对大 Source 使用 durable shard/streaming observation，不让单个 Seeder Attempt 承担全站 O(N) 生命周期。

### 7.5 Sitemap Index fan-out 不由 `SeedingConfig.concurrency` 完整约束

当前 Sitemap Index 会先把所有 sub-sitemap 读入列表，再为每个 sub-sitemap 创建 asyncio task，结果通过有界 queue 回传。结果 queue 有界，但 task 数不是。

生产大 Sitemap Index 一律优先 Native SitemapProvider durable shard；Seeder 只用于中小站加速或受控 gap job。

### 7.6 `hits_per_sec` 不是严格 QPS

当前实现用：

```text
asyncio.Semaphore(hits_per_sec)
```

包围局部 `_validate()`，其本质是局部并发上限，而不是按秒补 token 的时间窗口限流；对 Sitemap/CC discovery 内部请求也不能替代平台统一 admission。

平台负责：

```text
per_host_qps
per_host_concurrency
per_registrable_domain_concurrency
per_source_concurrency
Retry-After
origin_backoff_until
```

Seeder local semaphore 只做第二道保护。

### 7.7 Smart Sitemap Cache 只作 Accelerator，不替代 Conditional GET

Seeder 的 sitemap cache 保存 TTL、`sitemap_lastmod`、URL 列表等信息，但当前路径为了校验 `<lastmod>`，可能在 cache 判断之前仍先探测并 GET sitemap 内容。

此外 `<lastmod>` 聚合/比较属于实现细节，不具备 HTTP validator 的严格语义。因此：

```text
Seeder cache hit           != Provider unchanged
Seeder cache exists        != Cache complete
sitemap_lastmod newer      != Document version truth
```

生产增量由 Native SitemapProvider 使用 ETag/Last-Modified/304/body hash；Seeder cache 仅作执行加速。

### 7.8 Attempt-Scoped Cache Isolation

每个 Seeder Attempt 使用独立目录：

```text
seeder-cache/<attempt_id>/...
```

- 失败 Attempt 的 cache 不复用；
- retry 使用新目录或显式强制重新获取；
- 成功 cache 可以作为可选 Accelerator Artifact 晋升，但不作为 Coverage Evidence；
- 不让 partial cache 污染后续重试。

尤其 Common Crawl 本地 JSONL cache 是边下载边写；如果流在中途失败，文件存在不等于完整。平台必须把“有文件”与“成功完成并原子晋升”分离。

### 7.9 Common Crawl 固定 Index 不依赖 Seeder `latest`

Seeder 可以自动获取 latest Common Crawl index 并本地缓存，这适合探索，不适合历史 replay。

生产可重放 CC 使用 Native CommonCrawlIndexProvider，显式固定 `cc_index_id`。如果短期复用 Seeder wrapper，也必须由平台注入固定版本行为并通过 Contract Test，不把内部字段暴露给普通用户。

### 7.10 Partial Error 不得被普通 List 返回掩盖

Seeder producer 与 sub-sitemap 子任务存在记录错误、继续处理已发现 URL 的 best-effort 路径，因此可能出现：

```text
已发现一部分 URL
某一来源/子 sitemap 后续失败
函数仍给出非空结果集合
```

所以：

```text
List returned       != Provider completed
Non-empty result    != Provider completed
```

Seeder Adapter 若不能可靠取得每个 source/shard 的 typed terminal state，就保持 `completion_attested=false`。

### 7.11 全历史模式关闭前置语义过滤

完整性优先时 Seeder 建议：

```text
pattern = *
filter_nonsense_urls = false
query = null
score_threshold = null
extract_head = false
live_check = false
```

先保存 Observation，再由版本化 Selection Policy 分类。

`filter_nonsense_urls` 是版本相关 heuristic；当前 release 过滤 utility、hidden、admin/login/search/print 等路径，但规则会随版本变化，不能作为永久 Inventory 删除标准。

### 7.12 Partial Head / Live Check 只作 Hint

`live_check=True` 使用 HEAD 探测；HEAD 405、网络波动、多级 redirect 等不代表文章不存在。

`extract_head=True` 实际是受限 partial GET：读取页面前部、跟随有限 redirect，并解析 title/meta/link/JSON-LD/lang。可以保存：

```text
url_probe_observation
- observed_url
- final_url
- probe_type
- status
- title_hint
- canonical_hint
- content_type_hint
- published_at_hint
- updated_at_hint
- language_hint
- probe_artifact_id
- runtime_release_id
```

最终仍需平台 Fetch + Scope + MIME + Raw Artifact + Soft-404 + Quality Gate。

Seeder `status=valid` 不能直接映射 `VALID_ARTICLE`。

### 7.13 BM25 只作优先级，而且分数依赖当前候选集合

当前 metadata BM25 基于候选集合计算，再做集合内归一化。候选集合变化时同一个 URL 的归一化分数可能变化；所有原始分数相同时还可能得到统一的中间分值。

仅用于：

- focused discovery；
- repair/gap priority；
- 主题子集；
- 管理端候选排序。

不得用于全历史 Inventory 的永久保留/删除判定。

### 7.14 文档描述不能代替当前 Release 行为

官方 URL Seeding 文档描述过 `extract_head=false + query` 的 URL-based scoring，但 v0.9.2 实际 `urls()` 路径会告警并不产生 `relevance_score`，官方对应测试也验证“无分数”。

因此每个生产 Release 都绑定：

```text
crawl4ai_version
commit_sha
image_digest
url_seeder_release_id
contract_test_suite_version
```

Web 管理端展示“实际能力矩阵”，而不是复制上游文档参数说明。

### 7.15 不用 `many_urls(1000 domains)` 代替平台调度

`many_urls()` 本质是对所有 domain 创建 `urls()` coroutine 并 `asyncio.gather()`，适合开发/小批探索，不提供 durable lease、跨 Source 公平性、Checkpoint 或全局 admission。

```text
 -> ack Task
```

不一次把 1000 Source 交给同一进程的 gather。

## 11. Fetch Plane

### 11.1 HTTP Fast Lane

优先使用 HTTP：

- robots；
- Sitemap/Feed/API；
- 普通文章；
- Conditional GET；
- GET + MIME sniffing；
- redirect chain；
- status/headers/TLS/网络错误分类。

HEAD 只作提示；304 只表示对应 representation 未变，不表示 Source Inventory 完整。

### 11.2 Browser Slow Lane

仅在以下条件升级 Browser：

- HTTP DOM 缺正文；
- 正文依赖 JS；
- 需要有限滚动/点击；
- Source Profile 明确声明；
- HTTP Candidate 质量失败且 Browser Repair 有价值。

Browser 请求必须经过 Global Admission，不允许 Discovery 直接向 Browser 灌入大批 URL。

## 12. Crawl4AI Runtime Service Plane

### 12.1 Runtime Registry

```text
runtime_instance
- runtime_instance_id
- runtime_release_id
- image_digest
- crawl4ai_version
- browser_version
- browser_profile_classes
- dispatcher_capabilities

- health
- drain_state
```

生产只允许 pinned release。升级前运行 Contract Test。

### 12.2 双层 Backpressure

```text
Persistent Frontier
 -> Platform Fair Scheduler
 -> Global Admission
 -> bounded micro-batch
 -> Runtime Dispatcher
 -> Browser pool / HTTP execution
 -> streaming materialization
```

平台负责 durable/global/fairness；Runtime 负责 ephemeral/local/resource safety。

### 12.3 Dispatcher Policy

MemoryAdaptive/Semaphore 均只作为单 Runtime 局部控制。

要求：

- micro-batch 有硬上限；
- 不允许 `0=unbounded`；
- Runtime local requeue 不消耗源站 retry budget；
- 高内存等待超时映射为 Runtime 资源错误；
- Semaphore 即使抓取并发有界，也不能接收 mega-batch；
- Capacity Planner 使用实测有效并发而非参数名推断。

### 12.4 Runtime Outcome 归一化

```text
FINAL_SUCCESS
FINAL_FAILURE
LOCAL_REQUEUED
NO_CONFIG_MATCH
CANCELLED_ON_STREAM_CLOSE
RUNTIME_MEMORY_PRESSURE_TIMEOUT
```

Runtime local requeue 不是平台 retry。

### 12.5 Result Identity

禁止：

```python
for input_url, result in zip(urls, results):
    persist(input_url, result)
```

必须按 correlation identity：

```text
runtime_task_item
- runtime_task_id
- attempt_id
- input_url_identity_id
- correlation_key
- normalized_outcome
- materialized_at
```

### 12.6 Streaming 与 Stream Close

Browser micro-batch 优先 streaming，完成一个物化一个。

stream 被取消时：

```text
RUNNING_STREAM
 -> RUNTIME_STREAM_ABORTED
 -> verify runtime cleanup
 -> keep already materialized terminal items
 -> reconcile unmaterialized items
 -> durable requeue with fencing
```

### 12.7 Micro-batch 计算

```text
batch_size = min(
  runtime_batch_max_urls,
  available_runtime_slots * batch_factor,
  per_domain_budget,
  lease_deadline_budget,
  expected_result_bytes_budget,
  memory_headroom_budget
)
```

Browser Repair 默认 1 URL/Job；Browser Backfill 采用小批量 streaming。

## 13. Result Materializer 与 Artifact Promotion

每收到 terminal result：

1. 校验 task/correlation identity；
2. 校验 schema；
3. 保存原始 response metadata；
4. 将 required artifact 从 Runtime 临时存储晋升 S3/MinIO；
5. 写 checksum/size/MIME；
6. 创建 Raw Artifact；
7. 事务更新 Attempt/Task；
8. Outbox 触发 Extraction。

“Runtime 成功”但 required artifact 未晋升时，不允许平台 Task 进入业务 `SUCCEEDED`。

Webhook 只作提示；Reconciler 最终根据 PostgreSQL + Object Storage 证据闭合。

## 20. 安全与合规

### 20.1 Robots / Scope

- 尊重 robots.txt 与 Source policy；
- 每次 redirect 后重新校验；

- link-local；
- RFC1918；
- metadata IP；

- DNS rebinding；
- Browser/Seeder Runtime egress policy。

### 20.3 Runtime Secure Profile

- container non-root；
- read-only filesystem；
- 临时目录配额；
- seccomp/AppArmor；
- CPU/memory/pids limit；
- secret 只用引用；

## 22. 取消、暂停、Drain 与恢复

### 22.1 Stop 语义

- **Pause Source**：停止发新 Task；
- **Pause Provider**：停止新 Provider Lease，保留已落 Observation/Checkpoint；
- **Cancel Run**：停止新 lease，关闭 Runtime stream，reconcile 未 terminal item；
- **Drain Runtime**：停止新 Admission，等待 active job 收敛；
- **Replace Runtime**：新实例通过 health/contract 后切流，再下线旧实例。

### 22.2 Crash Recovery

Worker/Runtime 崩溃：

1. lease 到期；
2. Reconciler 查看哪些 item/shard 已 terminal materialize；
3. 已持久化成功项不重抓；
4. 其余重新进入 PENDING；
5. fencing token 防止旧 Worker 回写；
6. Provider Checkpoint、Coverage、Frontier、origin backoff 不受 Runtime 重启影响；
7. 失败 Seeder Attempt 的 local cache 不作为重试真相；
8. CC/Sitemap partial cache 不存在“文件存在即成功”的恢复路径。

## 23. Search / RAG Projection

从 Canonical IR/Document Version 构建，可随时重建：

- OpenSearch BM25；
- pgvector embedding；
- RRF 混合；
- chunk 保留 `document_id/version_id/section_path/source/url`；
- 默认返回最新 ACTIVE Version，可查历史版本；
- embedding/reranker 模型版本化；
- 删除 Search Index 不影响 Raw/IR 真相。

Seeder BM25 与搜索 BM25 完全不同：前者只作发现优先级，后者基于 Canonical 内容构建 Serving Projection。

## 28. 验收标准

上线前至少满足：

1. 新站可配置接入，不复制站点爬虫代码；
2. 每个 Source 可展示 Provider Inventory、Completion Attestation、Coverage、Known Gap 和 Stop Reason；
3. `List returned`、非空结果、cache hit、`status=valid`、BM25 分数都不能自动代表 Provider/Article Truth；
4. `RESULT_LIMIT_REACHED`、预算耗尽、`ERROR_PARTIAL` 不得标记 Coverage 完成；
5. Coverage 模式的 Sitemap 与 Common Crawl 有独立 Provider Run、Evidence 与 terminal outcome；
6. Common Crawl 回填显式固定 `cc_index_id`，retry/replay 不静默漂移；
7. Seeder CC cache、Sitemap cache、HEAD cache 不作为 Provider Completion Evidence；
8. 失败 Seeder Attempt 的 partial cache 不复用为成功真相；
9. `sitemap+cc` 的固定执行顺序不能被误解为两个来源均完成；
10. `max_urls` 不能被当作平台硬预算或全量 BM25 Top-K；
11. `max_urls` 导致后一来源未执行时必须可见；
12. `hits_per_sec` 不能被当作严格 QPS；
13. bounded result queue 不能被当作端到端内存有界证明；
14. 超大 Sitemap Index 使用 durable shard，不一次创建无硬上限的 sub-sitemap task；
15. Seeder Smart TTL Cache 不替代 ETag/Last-Modified Conditional GET；
16. `<lastmod>` 只作 hint，不作为版本真相；
17. 文档与实际 release 行为冲突时以 pinned source + Contract Test 为准；
18. Incremental 不会被大型 Backfill 饿死；
19. Worker/Runtime 崩溃后 Task 自动恢复；
20. Raw Artifact 不可变，IR/Markdown 可重放；
21. HTTP 与 Browser 有明确升级条件；
22. Browser micro-batch 有硬上限；
23. Runtime Result 按 identity 关联，不按列表位置；
24. stream early close 后未 terminal item 可准确重调度；
25. 跨 Worker host/domain QPS/并发严格生效，Runtime/Seeder local limiter 只作第二道保护；
26. Source、Provider、Seeder、Runtime、Extractor、IR、Renderer 全部可版本追溯；
27. Web 管理端能区分 Provider Complete、Partial、Truncated、HTTP Cache、Seeder Cache、pre-score limit、post-score top-K、平台全局限流与本地并发；
28. 所有 Provider 预算耗尽、截断与部分错误都进入 Coverage；
29. Search Index 可从 Canonical 数据删除后重建；
30. 全链路有 correlation、审计、Contract Test 与 Chaos Recovery。

## 29. 最终架构结论

最终系统不是“让一个爬虫进程抓 1000 个博客”，而是把长期知识库拆成明确的事实边界：

```text
Source / Provider / Coverage / Frontier / Task Truth
    = PostgreSQL

Provider Evidence / Raw / IR / Markdown Truth
    = Object Storage + PostgreSQL Metadata

Cross-worker Scheduling / Politeness
    = Fair Scheduler + Redis Lua + Durable Backoff

Replayable URL Inventory
    = Native CMS/Sitemap/RSS/Archive/CommonCrawlIndex Providers

Discovery Acceleration
    = Crawl4AI URL Seeder + Domain Mapping + Deep/Adaptive Gap Jobs

Browser Execution
    = Pinned Crawl4AI Runtime + bounded dispatcher/browser pool
```

生产关键约束：

**Provider 先保存 Observation 再筛选；Provider Complete 必须有可验证 Attestation；Sitemap 增量使用标准 Conditional GET；Common Crawl 显式固定 index；超大 Sitemap 使用持久分片；URL Seeder 只作 Accelerator，且它的组合源顺序、`max_urls`、cache、`status=valid`、BM25、local semaphore、bounded queue 都不是业务真相；平台只给 Runtime/Seeder 有界工作单元；所有结果按 identity 关联；所有关键语义由 pinned release + Contract Test 验证。**

采用该架构后，可同时获得：

- 1000+ 技术博客的可解释历史覆盖；
- 低成本增量同步；
- 新站配置化扩展；
- 大站可分片、可恢复的 URL Inventory；
- 稳定可重放 Markdown；
- 完整 Web 运维与诊断；
- 可水平扩容的 HTTP/Browser/Provider 执行面；
- 不依赖任何单个 Runtime、Seeder cache、latest index 或进程内队列的长期可靠性。
