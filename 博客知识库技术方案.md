# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客/工程博客/技术文档站/公开 Newsletter** 的长期知识库采集平台，并可继续扩展到数千站点。平台的核心不是“能把网页抓下来”，而是持续回答四个问题：

1. **历史是否尽量抓全**：有哪些文章、发现来源是什么、为什么认为 Provider 已经穷尽、还有哪些 Known Gap；
2. **增量是否足够及时**：新文章、修改、URL 迁移、删除何时被发现；
3. **内容是否可用**：正文能稳定转换为结构化 Canonical IR 与 Markdown，而不是把 Cookie、导航、登录页当正文；
4. **结果是否可追溯**：任意 Markdown 都能追溯到 Source、URL、Snapshot/Render Artifact、Recipe、Runtime、Extractor、IR、Quality、Version 和 Release。

最终提供：

- 全历史文章 URL 发现与正文回填；
- 定时增量同步、已知 URL 复检和删除判定；
- HTML/动态页面/PDF 等内容获取；
- 正文清洗为 Markdown；
- 原始事实、Canonical IR、Markdown 和索引分层保存；
- Web 管理、Probe、配置、审核、调度、回放、失败处理；
- 全文搜索、RAG/向量检索与批量导出；
- 站点新增主要依赖配置化 Source Profile/Recipe，而不是新增专用爬虫代码。

### 1.1 核心 SLO

平台以业务可用性而不是 HTTP 200 比例作为 SLO：

- **Coverage**：历史 URL 覆盖率、Provider exhaustion evidence、Known Gap；
- **Freshness**：新文章发现延迟、已知文章复检延迟；
- **Quality**：正文完整率、噪声率、结构质量、Quarantine 比例；
- **Data Supply**：URL 从首次发现到 `Quality=PASS` 且 Markdown/索引可用的 `time_to_usable_data`；
- **Reliability**：任务成功率、Retry、DLQ、队列年龄、Worker 恢复时间；
- **Cost**：每 Source、每 1000 个有效文档、每个 accepted version 的网络/CPU/Browser/存储/LLM 成本；
- **Traceability**：任意输出都能定位到不可变事实和版本化执行环境。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不用 LLM 的主观判断代替 Coverage 证明；
- 不把 Redis、Browser session、Crawler cache/frontier 当业务真相；
- 不允许 Web/API 用户直接向 Browser 透传任意 JavaScript、Playwright evaluate、代理或系统参数；
- 不把 LLM 摘要、翻译、重写作为 Canonical Markdown；
- 不把标题、slug、图片 alt 或展示 URL 当跨阶段唯一主键；
- 不因为 URL 曾经抓过就永久停止检查；
- 不把 crawler `success=true` 或 HTTP 200 直接等价为正文成功。

## 2. 核心设计原则

1. **Coverage First**：先证明“文章有哪些”，再批量抓正文。
2. **Authoritative First**：CMS/API、Sitemap、Feed、Archive 优先，动态列表/Deep Crawl 只在需要时补洞。
3. **Discovery Before Fetch**：URL 发现、规范化、Scope、去重独立于正文抓取。
4. **Discover Cheap, Fetch Expensive**：低成本 Provider 先跑，Browser 后置。
5. **HTTP First, Browser Last**：正文静态 HTTP 优先；确定性 Browser fallback；Agent Browser 极少使用。
6. **Deterministic Before Agentic**：主链无 LLM 也能完成 Backfill 和 Incremental。
7. **Snapshot First**：先保存不可变抓取事实，再做 Extract/IR/Markdown。
8. **IR First, Markdown as Projection**：Canonical IR 是内容事实，Markdown 是可重建投影。
9. **Quality Is First-Class**：传输成功和内容合格是不同状态。
10. **Cost Is First-Class**：每次高成本 Browser/LLM 都必须可归因。
11. **Tool Contract, Not Framework Coupling**：Crawl4AI/Playwright/httpx 通过 Adapter 接入。
12. **Recipe, Not Site Code**：selector、pagination、scroll、click、virtual scroll、wait 等通过版本化 Recipe 表达。
13. **Semantic Recipe, Not Runtime Parameters**：业务 Recipe 表达“动作语义”，不直接等同于具体 crawler 参数。
14. **Stable Identity**：Source、URL、Snapshot、Document、Version 使用不可变 ID 关联。
15. **Idempotent + Recoverable**：Task 有幂等键、lease、fencing token、checkpoint、retry、DLQ。
16. **Fair by Default**：大站 Backfill 不得长期饿死小站和 Incremental。
17. **Detect Drift Online**：Golden Corpus 防平台升级回归，Drift Detector 防站点改版静默退化。
18. **Security on Every Hop**：start URL、redirect、href、iframe、Asset、Browser navigation 每跳重新校验。
19. **Release Everything That Changes Results**：Profile、Recipe、Recipe Compiler、Runtime、Extractor、Schema、Renderer 全版本化。
20. **Projection Is Rebuildable**：Markdown、全文索引、向量和派生结果可从事实层重建。
21. **Fail Closed on Semantic Incompatibility**：运行时升级若无法保持 Recipe 语义，阻止 Release，不能静默少抓。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST、内部 Command API、Schema 校验；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、Observation、Document、Version、Quality、Drift、Cost、Release、Audit、Outbox；
- **Redis Streams**：队列运输、consumer group、backpressure；
- **Redis Lua token bucket / semaphore**：跨 Worker Domain Admission 快速闸门；
- **React/Next.js + TypeScript**：Web 管理台；
- **Prometheus + Grafana + OpenTelemetry**：指标、日志、Trace；
- **S3/MinIO**：Raw HTML、DOM/MHTML、IR、附件、失败诊断和导出；
- **OpenSearch**：全文/BM25；
- **pgvector**：首期向量检索，通过 Adapter 可替换；
- **Docker Compose**：开发和小规模验证；
- **Kubernetes**：生产 Worker Pool 横向扩展和 HPA。

### 4.2 抓取与解析

- **httpx/aiohttp**：HTTP、Sitemap、Feed、CMS API、Conditional GET、附件；
- **Crawl4AI**：动态页面、受控 Browser、批量执行、URL mapping、Virtual Scroll 等能力，通过 Adapter 使用；
- **Playwright**：复杂但确定性的站点交互 Recipe；
- **lxml + trafilatura/readability 类算法**：默认正文抽取；
- **JSON-LD/OpenGraph/Microdata**：元数据优先；
- **PyMuPDF/pdftotext**：PDF；扫描件才进入 OCR。

### 4.3 Crawler 的定位

Crawl4AI/Playwright 是执行器，不是平台状态机：

```text
平台负责：
Task / Retry / DLQ / Coverage / Fairness / Global Rate Limit / Budget /
Checkpoint / Release / Quality / Audit

Crawler 负责：
单次导航 / 页面交互 / DOM / 链接 / 媒体 / 浏览器资源管理
```

生产锁定经过 Golden Corpus 验证的 Crawl4AI、Playwright、Chromium 和镜像版本。升级必须经过 Runtime Capability 检查、Benchmark、回归和 Canary。

## 6. 新站点接入：Probe -> Review -> Release

### 6.1 自动 Probe

新增 Source 后先进入 `PROBING`：

1. 读取 robots.txt；
2. 探测 `/sitemap.xml`、sitemap index、RSS/Atom；
3. 识别 WordPress/Ghost/Medium/Substack 等常见 CMS/API；
4. 发现 Archive、分页、year/month/category index；
5. 抽取 URL/path 样本，生成 include/exclude 候选；
6. 随机选 5~10 篇文章样本；
7. 比较 HTTP Extractor 与 Browser/Recipe 的正文质量；
8. 检测 JSON-LD、作者、发布时间、代码块、图片；
9. 估算历史 URL 数量和时间分布；
10. 权威发现不足时做受限 Prefetch Mapping；
11. 若列表依赖 JavaScript，识别 pagination/Load More/append scroll/virtual scroll，生成 Dynamic Listing Recipe 候选；
12. 估算 Browser 比例、历史回填成本和日常增量成本；
13. 生成 DRAFT Source Profile。

### 6.2 Web 审核

管理员查看：

- Discovery Provider 与优先级；
- URL 样本、include/exclude/path 分类；
- HTTP/Browser URL 产出与正文质量对比；
- Dynamic Listing 每轮 URL 增长、编译执行计划和收敛原因；
- Markdown 预览；
- Quality 分数；
- robots/Scope；
- 预计文章数、已发现数、Known Gap；
- 预计 Backfill 成本与 Browser 占比。

审核通过后发布 Source Profile/Recipe Release，再进入 Backfill。

## 7. 历史全量 URL 发现与 Coverage

### 7.1 Provider 优先级

推荐顺序：

```text
1. CMS / 官方 API
2. Sitemap / Sitemap Index
3. RSS / Atom
4. Archive / Pagination / Year-Month Index
5. Category/Tag Index（补充）
6. URL Seeder / 可选公开索引
7. Prefetch Mapping
8. Dynamic Listing Discovery
9. bounded Deep Crawl
10. 人工补充 / CSV 导入
```

顺序可按 Source 成本和可靠性调整，但 Browser Provider 默认不能压过可用权威数据源。

### 7.2 Coverage 不是“队列空了”

Backfill 完成需要可审计证据：

- CMS/Sitemap cursor 已穷尽或明确不可用；
- Archive 到达最老分页/年份边界；
- Provider 集合交叉后新增 URL 收敛；
- Dynamic Listing 达到可解释的 exhaustion boundary；
- Prefetch/Deep Crawl 达到 max_pages/max_depth/time budget 时形成 Known Gap，而不是假装“已抓全”；
- 预计总量存在时比较 expected_count；
- 历史时间分布异常空洞进入人工/自动补洞队列。

### 7.3 URL 规范化

统一执行：

- scheme/host 小写；
- 默认端口清理；
- fragment 移除；
- tracking 参数移除；
- query 仅保留 Source allowlist；
- trailing slash 由 Profile 决定；
- relative URL resolve；
- Canonical Link 只作为证据，不无条件信任；
- redirect 后 final URL 重新过 Scope/SSRF；
- 保留原始 observed URL 与 normalized URL。

### 7.4 Prefetch Mapping

```text
Phase A: Map
seed URLs
 -> cheap HTML + links
 -> normalize/scope/filter
 -> URL Observation + parent edge
 -> page/path classifier
 -> 估算站点空间

Phase B: Process
article candidates
 -> 正式 HTTP/Browser Fetch
 -> Snapshot/Render
 -> Extract/IR/Quality
```

Prefetch 必须设置 `max_depth / max_pages / time_budget`，并对日历、搜索、tag、query 无限空间设置 guard。

## 8. Dynamic Listing Discovery

JavaScript 栏目页、Infinite Scroll、Load More、虚拟列表作为独立 Discovery Provider，而不是正文 Browser 抓取里的临时脚本。

### 8.1 语义 Recipe IR

```yaml
name: dynamic_blog_list_v4
kind: dynamic_listing
start_urls:
  - https://example.com/blog

ready:
  type: CSS
  selector: ".information-flow-list"

harvest:
  item_selector: ".information-flow-list article"
  link_selector: "a[href]"
  extract:
    url: "a::attr(href)"
    title: "a::text"
    published_hint: "time::attr(datetime)"

interaction:
  mode: APPEND_SCROLL
  action: SCROLL_PAGE
  wait_after_action:
    type: ITEM_GROWTH
    selector: ".information-flow-list article"
    timeout_ms: 5000

convergence:
  no_growth_rounds: 3
  max_rounds: 40
  max_runtime_seconds: 120
  max_items: 5000
```

支持：

```text
STATIC
PAGINATION
CLICK_MORE
APPEND_SCROLL
VIRTUAL_SCROLL
```

Recipe 只描述业务语义，不直接出现 crawler 私有参数。

### 8.2 Runtime Capability Contract

每个 Runtime Release 保存机器可读能力契约：

```text
runtime_capability
- runtime_release_id
- crawler_name
- crawler_version
- playwright_version
- chromium_version
- capability_schema_version
- capabilities JSONB
- capabilities_hash
```

能力示例：

```json
{
  "supports_js_before_wait": true,
  "supports_js_only_session": true,
  "supports_scan_full_page": true,
  "supports_virtual_scroll": true,
  "js_execution_order": [
    "navigate",
    "js_before_wait",
    "wait_for",
    "delay",
    "js_after_wait",
    "capture"
  ]
}
```

### 8.3 Recipe Compiler

Recipe Compiler 将语义 IR 编译成具体 Runtime 的执行计划。当前 Crawl4AI 0.9.x Adapter 的典型映射：

```text
语义：TRIGGER -> WAIT -> HARVEST
 -> js_code_before_wait + wait_for + capture

CLICK_MORE 多轮交互
 -> session_id + js_only=True + 多次受控 action

APPEND_SCROLL
 -> scan_full_page 或逐轮 scroll + harvest

VIRTUAL_SCROLL
 -> VirtualScrollConfig 或逐轮 harvest + 业务侧 union

PAGINATION
 -> 提取 next href，作为新 URL 重新进入 discovery pipeline
```

**禁止把旧版本 `js_code/wait_for` 参数文本原样搬到新 Runtime。** 编译目标是保持语义，不是保持参数名。

### 8.4 运行时升级兼容门禁

Crawler/Playwright/Chromium/Recipe Compiler 升级：

```text
Build Runtime Capability
 -> compile ALL ACTIVE Recipes
 -> static compatibility check
 -> Golden Corpus replay
 -> compare Coverage / Quality / Cost
 -> Canary sources
 -> Approval
 -> Release
```

不兼容时阻止发布：

```text
RECIPE_RUNTIME_INCOMPATIBLE
UNSUPPORTED_INTERACTION_MODE
WAIT_SEMANTICS_CHANGED
VIRTUAL_SCROLL_CAPABILITY_MISSING
```

这样避免一次 crawler 行为变化导致数百个站点“任务成功但少抓”。

### 8.5 文章身份提取

Discovery 主身份必须来自真实链接：

```json
{
  "observed_url": "https://example.com/post/123",
  "title_hint": "文章标题",
  "published_hint": "2026-08-01T10:00:00Z",
  "parent_url": "https://example.com/blog",
  "round": 7,
  "provider": "DYNAMIC_LISTING"
}
```

禁止使用图片 alt、图片 URL 或展示标题作为唯一身份。

### 8.6 收敛算法

```python
seen = set()
no_growth = 0

for round_no in range(max_rounds):
    candidates = harvest_current_dom()
    urls = normalize_scope_filter_classify(candidates)
    new_urls = urls - seen
    seen |= new_urls
    persist_observations(new_urls, round_no)

    if incremental_overlap_reached(new_urls):
        stop("OVERLAP_BOUNDARY")
        break

    no_growth = no_growth + 1 if not new_urls else 0
    if no_growth >= no_growth_rounds:
        stop("NO_GROWTH")
        break

    perform_next_semantic_action()
    wait_for_item_growth_or_timeout()
else:
    stop("MAX_ROUNDS")
```

收敛核心是“规范化且通过 Scope/文章分类后的 URL 是否继续增长”，DOM 高度只作为辅助信号。

### 8.7 虚拟列表

虚拟列表会回收旧 DOM。必须：

- 使用 Runtime 的 virtual-scroll 合并能力；或
- 每轮滚动后立即 harvest + 写 URL Observation。

业务正确性不依赖最终 DOM 是否仍保留早期节点。

### 8.8 Dynamic Coverage Evidence

额外保存：

```text

recipe_compiler_version
runtime_release_id
runtime_capabilities_hash
compiled_plan_hash
interaction_mode
rounds
observed_items
unique_article_urls
new_urls_by_round[]
duplicate_ratio

last_published_hint
```

`NO_GROWTH/CURSOR_EXHAUSTED/OVERLAP_BOUNDARY` 可是正常结束；`MAX_ROUNDS/TIME_BUDGET/MAX_ITEMS` 必须形成 Known Gap。

### 8.9 安全动作白名单

## 9. 正文抓取与最小成本路由

### 9.1 Acquisition Planner

Planner 根据 Profile、历史成功率、Quality 和成本生成 FetchPlan：

```text
L0 CMS/API payload
L1 HTTP
L2 Crawl4AI deterministic Browser
L3 Playwright deterministic Recipe
L4 LLM-assisted extraction / Controlled Agent Browser
```

优化目标：

```text
minimize expected_cost / expected_accepted_document_version
subject to Quality SLO and Freshness SLO
```

任何自动策略建议与生产 Release 分离，策略变化必须可审核、可回滚。

### 9.2 HTTP Worker

默认支持：

- `If-None-Match`；
- `If-Modified-Since`；
- gzip/br；
- connect/read/write 分阶段 timeout；
- redirect 上限；
- per-domain connection pool；
- `Retry-After`；
- 429/503 指数退避 + jitter；
- body size 上限；
- MIME allowlist；
- 原始 header + body hash 保存。

### 9.3 Browser Worker

Browser 进程复用，Context 按安全域隔离，Page 按 Task 短生命周期：

- 默认拦截广告、追踪、字体、视频等非必要资源；
- 默认不截图、不生成 PDF；
- 仅诊断/Golden Corpus/审核时截图；
- 所有 wait/scroll/click 来自版本化 Recipe；
- 单 Worker 可用 crawler 内置 Dispatcher/RateLimiter，但全局公平和限流由平台控制。

拆分：

```text
Browser Discovery Worker
- 长页面、多轮交互、低并发、强预算

Browser Content Worker
- 单文章、短生命周期、正文完整度优先
```

### 9.4 Browser Fallback 条件

HTTP 成功但以下条件不满足时才升级 Browser：

- 正文长度过短；
- text density 低；
- JSON-LD/正文 DOM 明显缺失；
- 页面只含 hydration shell；
- Challenge/login/cookie 模板命中；
- Source Profile 明确要求 Browser。

Browser 仍失败则 Quarantine，不无限重试。

## 10. 正文抽取、Canonical IR 与 Markdown

### 10.1 Extractor Pipeline

```text
Snapshot / Render Artifact
 -> MIME / encoding normalize
 -> metadata extract
 -> DOM sanitize
 -> main-content candidate extraction
 -> boilerplate removal
 -> block reconstruction
 -> Canonical IR
 -> Quality Gate
 -> Document Version
 -> Markdown Renderer
```

### 10.2 Canonical IR

不要把 Markdown 当唯一事实。IR 示例：

```json
{
  "schema_version": 3,
  "title": "...",
  "canonical_url": "...",
  "author": ["..."],
  "published_at": "...",
  "updated_at": "...",
  "language": "zh-CN",
  "blocks": [
    {"type": "heading", "level": 2, "text": "..."},
    {"type": "paragraph", "text": "..."},
    {"type": "code", "language": "python", "text": "..."},
    {"type": "image", "src": "...", "alt": "..."},
    {"type": "table", "rows": []}
  ],
  "metadata": {}
}
```

IR 好处：

- Markdown Renderer 可升级后重建；
- 向量切块可按 block/heading 做结构切分；
- 代码块、表格、图片语义不丢；
- 内容版本 Hash 不受 Markdown 格式微调影响。

### 10.3 Markdown 输出

统一 Front Matter：

```yaml
---
document_id: ...
source_id: ...
url: ...
canonical_url: ...
title: ...
author: [...]
published_at: ...
updated_at: ...
retrieved_at: ...
version_id: ...
content_hash: ...
---
```

正文规范：

- 保留 heading 层级；
- fenced code block + language；
- 表格可还原则保留 Markdown，否则保留 HTML/IR 引用；
- 图片使用规范化 URL 或对象存储代理路径；
- 去除导航、相关推荐、Cookie、页脚、社交分享；
- 不把 AI 生成的摘要混入 canonical body。

### 10.4 Asset

图片/附件采用可配置策略：

```text
REFERENCE_ONLY
DOWNLOAD_REFERENCED
DOWNLOAD_ALL_CONTENT_ASSETS
```

下载资产需要 URL Scope/SSRF、MIME、size limit、hash 去重和对象存储生命周期策略。

## 11. Quality Gate、Golden Corpus 与 Drift

### 11.1 Quality Gate

至少检查：

- 标题存在；
- 正文长度；
- text density；
- boilerplate/link density；
- heading/code/table 结构；
- metadata confidence；
- 与历史版本的大幅缩水；
- 与其他页面的高度重复；
- Challenge/login/cookie/error-page 特征；
- Source 特定规则。

判定：

```text
PASS       -> 可成为 current version
QUARANTINE -> 保存但等待人工/备用 Extractor
FAIL       -> 不进入默认知识库
```

### 11.2 Golden Corpus

每个 Source 保存 3~10 个代表样本：

- 普通文章；
- 长文；
- 代码密集；
- 图片密集；
- 旧模板；
- 新模板；
- 关键动态列表页。

Runtime/Extractor/Recipe/Renderer 升级自动比较：

```text
URL yield
正文长度
结构 block 数
semantic hash diff
quality score
browser seconds
网络请求数
```

### 11.3 在线 Drift Detector

典型信号：

- selector hit rate 群体性下降；
- Dynamic Listing 每轮唯一 URL yield 骤降；
- HTTP Quality 下降同时 Browser fallback 暴涨；
- 大量页面变成相同 Cookie/Login/Challenge；
- Sitemap/Archive 路径模式突然变化；
- title/author/time 元数据缺失率骤升；
- Source 历史平均正文长度突然大幅缩水。

处置：

```text
Drift Alert
 -> Source DEGRADED / 保护性降速
 -> 保存失败样本
 -> Golden Corpus + 最近样本回放
 -> 生成 Profile/Recipe 候选
 -> Compare Coverage / Quality / Cost
 -> Approval
 -> New Release
```

若同一 Runtime Release 后大量不同 Source 同时退化，优先判定平台回归。

## 12. 增量同步与版本管理

### 12.1 增量发现

按 Source 能力组合：

```text
RSS/Atom
CMS cursor
Sitemap lastmod
Archive 最近分页
Dynamic Listing 顶部窗口
低频 Prefetch/Deep Crawl 补漏
```

使用 overlap window，例如从上次 watermark 往前回退 24 小时，通过 URL 去重吸收重复。

### 12.2 Dynamic Listing 增量

```text
打开列表顶部
 -> harvest
 -> normalize/dedupe
 -> 继续动作
 -> 遇到 overlap 时间边界
    或连续 K 个已知 URL + N 轮无 unseen URL
 -> 停止
```

Browser session 不作为 checkpoint。PostgreSQL 保存 watermark、最近 Observation、Provider cursor、Recipe Release、Runtime Release 和 Coverage Evidence。

### 12.3 已知 URL 复检

```text
Conditional GET
 -> 304: 更新时间戳，不创建 Version
 -> 200 + body hash 相同: 不 Extract
 -> body hash 变化: Extract -> IR
 -> semantic hash 相同: 不创建 Version
 -> semantic hash 变化: 新 Document Version -> Quality -> Projection rebuild
```

### 12.4 删除与 URL 迁移

不能把一次 404 当永久删除：

- 404/410 连续 N 次；
- 多个增量 run 不再观察到；
- Sitemap/CMS 明确消失；
- redirect 指向新 canonical；
- 经过 grace period 后再标记 DELETED/MOVED。

保留旧 Version 和历史 URL Identity，不物理删除知识库历史事实。

### 12.5 周期性深度校验

即使日常增量很轻，也定期做：

- 周/月级 Provider cross-check；
- 随机历史 URL Verify；
- Sitemap 全量 diff；
- 低频 Archive/Prefetch gap scan；
- Coverage 时间分布空洞检测。

用于发现 watermark 误差、排序变化、漏抓和删除。

## 13. 调度、可靠性与公平性

### 13.1 Transactional Outbox

业务状态更新与任务投递不做双写：

```text
DB transaction:
  update business state
  insert outbox event
commit

Outbox Relay -> Redis Streams
```

Worker 完成后也先写 PostgreSQL 再 ACK，保证 Redis 丢失可以从事实重建任务。

### 13.2 Lease + Fencing Token

Worker claim task：

```text
lease_owner
lease_until
fencing_token++
```

所有最终写操作检查 fencing token，旧 Worker 即使恢复也不能覆盖新 Worker 结果。

### 13.3 Retry 分类

```text
RETRYABLE:
timeout / connection reset / 429 / 503 / browser crash

RECIPE_OR_SOURCE:
selector timeout / template drift / no article links

PERMANENT:
out-of-scope / unsupported MIME / explicit denied
```

指数退避 + jitter；超过 max_attempts 进入 DLQ。

### 13.4 Weighted Fair Scheduler

队列不使用简单 FIFO。维度：

- Incremental > Verify > Backfill；
- Source 轮转；
- 大站分片；
- per-domain concurrency；
- Browser/HTTP 不同资源池；
- aging 防低优先级永久饥饿。

### 13.5 Global Domain Admission

```text
Redis token bucket  -> requests/sec
Redis semaphore     -> concurrent requests
DB policy           -> Source truth
```

遇到 429/503/Retry-After 自动降低速率，逐步恢复。Crawler 内部限速只作为第二层保护。

### 13.6 Backpressure

监控：

- stream lag；
- oldest task age；
- Browser pool saturation；
- object storage upload latency；
- Extract/index throughput。

压力高时优先保证 Incremental Freshness，暂停低优先级 Deep Crawl/Backfill。

## 19. 部署与扩展

### 19.1 Worker Pool

```text
Discovery Lightweight

Browser Content
Extract/Quality
```

- Source Profile/Recipe/Release；
- OpenSearch/pgvector 可从事实重建，因此不是唯一恢复点。

## 23. 最终验收标准

### 23.1 Coverage

随机抽取代表 Source，要求：

- Sitemap/CMS/Archive Provider 有 exhaustion evidence；
- 动态列表有 URL 增长曲线与 exhaustion reason；
- bounded Provider 达预算时明确 Known Gap；
- Provider 交叉后历史时间分布无无法解释的大空洞。

### 23.2 Freshness

- HOT Source 新文章在目标时间窗口进入 PASS Markdown；
- 大规模 Backfill 期间 Freshness SLO 不显著退化；
- 增量 watermark 丢失后能通过 overlap/URL Observation 恢复。

### 23.3 Quality

- Cookie/Login/Challenge 页面不进入 current version；
- 代码块/标题/发布时间等结构在 Golden Corpus 中稳定；
- Runtime/Extractor 升级无明显 Quality 回归。

### 23.4 Reliability

- Worker 强杀后 lease/fencing 自动恢复；
- Redis 清空后可从 PostgreSQL 重建任务；
- 重复投递不产生重复 Document Version；
- DLQ 可定位原因并重放。

### 23.5 Runtime Compatibility

- 所有 ACTIVE Recipe 都能针对目标 Runtime 编译；
- `trigger -> wait -> harvest` 等语义在版本升级后保持一致；
- 不支持能力时 Release 必须失败，而不是静默降级；
- 任意 Render Artifact 能定位 `recipe_release + compiler_version + runtime_release + capability_hash + compiled_plan_hash`。

### 23.6 Cost

- 每 Source 和每 accepted version 可归因；
- Browser 使用率和秒数可观察；
- 预算达到阈值时能降级非关键 Provider，不产生无界成本。

## 24. 最终方案结论

该平台以 **PostgreSQL + Object Storage 为事实层，Redis Streams 为运输层，配置化 Discovery/Extraction Recipe 为扩展面，HTTP-first/Browser-last 为成本策略，Canonical IR 为内容事实，Quality/Coverage/Release 为正确性护栏**。

对于 1000+ 站点，最关键的可扩展性来自两层解耦：

```text
站点差异
 -> Source Profile + Semantic Recipe

工具/版本差异
 -> Runtime Capability Contract + Recipe Compiler + Adapter
```

因此新增第 1001 个站点主要是 Probe、配置、Golden Corpus 和审核；升级 Crawl4AI/Playwright/Chromium 时也不需要把数百个站点 Recipe 按参数名人工重写。动态栏目、Infinite Scroll、Load More 和 Virtual Scroll 都通过统一的 `Dynamic Listing Provider -> URL Observation -> Coverage Evidence` 纳入历史全量与增量同步。

最终形成一条可恢复、可审计、可扩展的知识供应链：

```text
Discover
 -> Prove Coverage
 -> Fetch
 -> Preserve Fact
 -> Extract IR
 -> Quality Gate
 -> Version
 -> Render Markdown
 -> Index/RAG
 -> Incremental Verify
 -> Drift/Release Governance
```

这套边界保证知识库长期正确性不绑定某个 crawler 的临时行为，并能够在站点数量、页面模板和抓取运行时持续变化的情况下稳定演进。
