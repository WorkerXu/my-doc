# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个可长期运行、可横向扩展的技术博客知识库平台。首期约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章并清洗为稳定 Markdown；后续可持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计和离线重处理。

设计按以下量级考虑：

- 1000+ Source，后续可扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 多年运行、站点结构持续变化；
- 中英日韩等多语言技术内容；
- HTTP 为主、Browser 为受控 fallback；
- 历史 URL 发现允许接入 Sitemap、Feed、CMS API、Archive、Common Crawl 等多来源；
- 原始事实可长期保留，Markdown、全文索引、向量索引等派生结果可删除重建。

平台核心目标不是“能抓页面”，而是形成一套可证明历史 Coverage、可恢复任务、可回放处理、可追踪版本、可解释身份、可持续发现新文章、可增量重建投影、可替换底层抓取与检索组件的系统。

## 2. 核心设计原则

1. **Config First**：新增普通站点主要通过 Source / Site Profile 配置完成，不修改核心代码。
2. **Coverage First**：历史完整性必须由 Provider Evidence 和 exhaustion reason 证明，不能用“队列为空”“达到 max_pages”冒充完整。
3. **Discovery 与 Fetch 解耦**：先低成本发现候选 URL，再决定哪些 URL 需要真实抓取。
4. **Discovery Surface First-class**：Sitemap、Feed、Archive、Category、Tag、Blog Index、Docs TOC 等持续产出文章 URL 的页面必须作为长期资产维护。
5. **Authoritative First, Archive as Supplement**：CMS/API/Sitemap/Feed 优先；Common Crawl、Wayback 等第三方历史档案只作为补洞和证据，不能单独证明站点完整性。
6. **HTTP First, Browser Last**：Feed/API/Sitemap/HTTP 优先，Browser 只处理动态页面、结构探索或低质量 fallback。
7. **Resolution Is a First-class Plane**：Observed URL、Normalized Candidate、Resolved Target、Network Final URL、Canonical Identity 是不同事实。
8. **Snapshot First**：网络事实先保存不可变 Snapshot，再抽取、清洗、建版。
9. **IR First, Markdown as Projection**：Canonical IR / Document Version 是事实层；Markdown、Chunk、Embedding、全文索引均可重建。
10. **Canonical Content 与 Query View 分离**：BM25/LLM/Query-focused Fit Markdown 不能覆盖完整正文。
11. **Language-aware Retrieval**：分词、stemming、stopwords、BM25 threshold、tag weight 都必须按 Analyzer Release 版本化，不能假设所有博客都适合英文空格分词。
12. **Release Everything**：Profile、Discovery、Normalization、Classifier、Resolver、Fetch Route、Extractor、Quality、Markdown、Chunk、Analyzer、Embedding、Retrieval 均版本化。
13. **Idempotent + Recoverable**：所有任务有幂等键、lease、checkpoint、retry 和 partial success 语义。
14. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary 等失败不能阻塞源站事实同步；LLM 不能自动执行会导致 Coverage 丢失的永久过滤。
15. **Evidence Everywhere**：发现、分类、跳转、抓取、抽取、身份、版本、检索都可解释、可审计。
16. **Web 管理是平台能力**：异常、Coverage、Discovery Surface、跳转链、版本、成本、索引、策略 Release 都必须可运营。
17. **安全边界每跳执行**：重定向与 Browser 导航不能绕过 SSRF/Egress/访问策略。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST / Command API、Schema 校验。
- **PostgreSQL**：Source、Profile Release、Run、Task、Coverage、Discovery Surface、URL Observation、Redirect、Fetch、Document、Version、Projection State、Audit、Outbox。
- **Transactional Outbox**：数据库状态变更与消息发布保持事务一致。
- **Redis Streams**：任务运输、consumer group、retry、backpressure；不保存唯一业务事实。
- **React/Vue + TypeScript**：Web 管理。

### 4.2 数据面

- **HTTPX / aiohttp**：HTTP、Feed、Sitemap、API、条件请求和低成本跳转解析。
- **BeautifulSoup / lxml / CSS / XPath**：wrapper、meta refresh、selector、结构化 HTML 处理。
- **Trafilatura / Readability**：确定性正文候选。
- **Crawl4AI / Playwright**：动态页面、Browser fallback、URL Seeding、Deep Crawl、Domain Mapping、Markdown / 内容过滤 Adapter。
- **DuckDB / Athena / Spark**：Common Crawl Columnar/URL Index 的批量历史 URL 查询；1000 站点场景不依赖高并发 CDX API。
- **S3 / MinIO**：HTML、HTTP body、Rendered DOM、Feed payload、Common Crawl/WARC 恢复快照、PDF、Canonical IR、Markdown、Asset、调试产物。
- **OpenSearch**：全文检索、过滤、聚合、BM25。
- **pgvector / OpenSearch kNN** 起步；规模或独立扩展需求增加后可替换为 Qdrant / Milvus。
- **Prometheus + Grafana + OpenTelemetry**：指标、日志、Trace。

### 4.3 Crawl4AI 版本治理

Crawl4AI 不直接渗透业务模型，通过平台 Adapter 隔离：

```text
UrlSeederAdapter
DomainMapperAdapter
DeepCrawlAdapter
BrowserAdapter
MarkdownAdapter
ContentFilterAdapter
```

每次运行记录：

```text
adapter_release_id
crawl4ai_version
playwright_version
config_hash
runtime_image_digest
```

升级前用固定回归集比较：URL 发现量、重复率、正文长度、标题、代码块、表格、链接、图片、Browser 成功率和耗时，验证后再切换 Release。

## 7. 新站接入与 PROBE

新增站点先执行 `PROBE`，不直接深爬：

1. 规范化 entry URL，确定 registrable domain、allowed origins 和 scope。
2. 获取 robots 及 Sitemap 声明。
3. 探测 Sitemap Index / Sitemap。
4. 探测 RSS / Atom / JSON Feed。
5. 探测 WordPress REST、Ghost、Substack 等平台能力。
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination。
7. 低成本查询 Common Crawl 历史 URL；必要时使用 Domain Mapping 补充发现子域/历史路径，但发现结果必须再次经过 scope policy。
8. 对 URL 路径做模板聚类，推断 article pattern、archive pattern、分页规则。
9. 使用 BFS/BestFirst 小深度探索未知结构，寻找高产出的 Discovery Surface，而不是无边界全站抓取。
10. 抽样比较 HTTP 与 Browser 正文质量、JS 依赖和成本。
11. 检测 Feed/Search 链接是否存在 wrapper、短链、meta refresh、JS redirect。
12. 推断主要语言和 analyzer hint。
13. 对 Surface 灰区使用 LLM 辅助分类；只有人工接受后才进入生产 Profile。
14. 自动生成首版 Site Profile Release，在 Web 中人工审核/修正。

普通站点上线应主要完成“配置”，只有非常特殊站点才写 `SITE_CUSTOM_*` Adapter。

## 8. 全量历史发现与 Coverage

### 8.1 Provider Contract

所有发现 Provider 统一接口：

```text
probe(source, profile) -> capability
discover(cursor, budget) -> candidates + evidence + next_cursor
checkpoint() -> durable_cursor
exhaustion() -> explicit_reason
```

Provider 示例：

```text
CMS_API
SITEMAP
FEED
ARCHIVE
CATEGORY_TAG_AUTHOR
DOCS_TOC
DISCOVERY_SURFACE
DEEP_CRAWL
COMMON_CRAWL_CDX
COMMON_CRAWL_COLUMNAR
SITE_SEARCH
```

### 8.2 推荐发现顺序

```text
Authoritative CMS/API
 -> Sitemap Index / Sitemap
 -> Historical Feed
 -> Archive year/month
 -> Category/Tag/Author
 -> Blog Index / Docs Navigation / TOC
 -> Common Crawl historical candidates
 -> Discovery Surface traversal
 -> Deep Crawl gap filling
 -> Site Search as supplement
```

站内搜索、Common Crawl、Deep Crawl 都不能作为完整历史的唯一来源。

### 8.3 Common Crawl 的语义边界

Common Crawl 只证明：

```text
某个 URL 在某个 CC-MAIN collection 中曾被观察/抓取
```

不证明：

```text
某个域名的全部历史 URL 已被 Common Crawl 收录
```

因此 Common Crawl Provider 不允许单独生成 `COMPLETE`。

`common_crawl_observation` 可记录：

```text
source_id
crawl_id
url_id
capture_time
status
mime
warc_filename
warc_offset
warc_length
content_digest
observed_at
```

小规模交互查询可使用 CDX；1000 站点历史枚举应优先使用 Columnar/URL Index 批处理并缓存 `(registered_domain, crawl_id)` 结果。

### 8.4 Coverage 数据

`coverage_provider_run`：

```text
id
run_id
provider_type
provider_release_id
cursor_before
cursor_after
status
exhaustion_reason
candidate_count
completed_count
failed_count
known_gap
blocker
started_at
finished_at
```

`url_observation`：

```text
id
source_id
provider_run_id
observed_url_id
external_id
published_hint
updated_hint

observation_hash
observed_at
evidence_object_ref
```

达到预算只能：

```text

```

不能标记 COMPLETE。

### 8.5 Provider Overlap

系统应计算 Provider 交集和独有候选：

```text
Sitemap only
Feed only
Archive only
Common Crawl only
Deep Crawl only
Multi-provider observed
```

这可以发现 Sitemap 漏历史、Feed 窗口过短、Archive 不完整等问题。

### 8.6 FULL_BACKFILL 完成条件

一个 Source 的历史回填只有在主要权威 Provider 明确 exhausted，或者所有未覆盖区间都已记录为可解释 known gap 时才结束。

Web 必须能回答：

- 哪些 Provider 被使用；
- 每个 Provider 找到多少候选；
- Provider 之间的交集/独有 URL；
- 哪个时间区间/分页已穷尽；
- 哪些候选抓取失败；
- 哪些区间仍存在 gap；
- Common Crawl 是否只作为补充证据。

### 9.2 Surface 识别

先使用确定性结构特征：

- 同域链接数；
- 指向文章型 URL 模板的比例；
- 重复卡片 DOM 结构；
- 日期密度；
- pagination / next / older 信号；
- path template 一致性；
- 链接密度和正文长度；
- Schema.org ItemList / CollectionPage 等结构信号。

中间灰区才进入 LLM 辅助判断。

LLM 只输出结构化 Classification Evidence，例如：

```text
is_discovery_surface
surface_type
confidence
article_url_patterns
pagination_pattern
evidence
risks
```

LLM 输出不能直接改生产配置。管理员接受/拒绝后创建新的 Site Profile Release。

### 9.3 Surface 收益指标

每个 Surface 维护：

```text
new_urls_per_scan
changed_urls_per_scan
duplicate_ratio
failure_rate
bytes_per_new_url
latency
```

调度器根据收益自动升降频，高产 Surface 高频扫，长期无新增 Surface 降频，但周期性 Reconcile 不取消。

## 10. Candidate URL 规范化与分类

Discovery 与 Resolution 之间增加独立的 Candidate Normalization / Classification Plane。

### 10.1 URL Normalization Release

`url_normalization_release`：

```text
id
version
host_policy
path_policy
query_policy
tracking_param_rules
semantic_param_allowlist
fragment_policy
created_at
```

典型规则：

```text
lowercase host
punycode normalization
default port removal
fragment removal
path slash normalization
safe percent-encoding normalization
query key ordering
tracking param removal
site-specific semantic param preservation
```

可以删除 `utm_*`、`gclid`、`fbclid` 等已知跟踪参数，但不能全局删除所有 query 参数，因为 `?id=123`、`?p=456`、`?page=7` 可能具有正文或分页语义。

### 10.2 分类状态

候选 URL 分类：

```text
ARTICLE_CANDIDATE
DISCOVERY_SURFACE
ASSET
NAVIGATION
EXTERNAL_REFERENCE
IGNORE_BY_POLICY
UNKNOWN
```

所有过滤均保留原始 Observation 与 Classification Evidence，避免不可逆丢失。

### 10.3 URL Template

对 URL path 做模板聚类：

```text
/2026/08/my-post
/2026/08/another-post
 -> /{yyyy}/{mm}/{slug}
```

URL Template 可用于：

- article pattern 推断；
- listing/article 结构识别；
- Deep Crawl scorer；
- 新 URL 异常检测；
- Site Profile 自动建议。

## 11. Deep Crawl 的角色与策略

Deep Crawl 主要负责：

```text
未知站点结构探索
未知 Discovery Surface 发现
未知 URL Template 发现
Coverage gap 补充
```

不能用：

```text
max_depth reached
max_pages reached
queue empty
```

作为历史完整证明。

建议：

- PROBE：BFS 1~2 层，快速发现 hub/listing；
- 已知目标路径：BestFirst，根据 article template、anchor、结构特征优先；
- 特殊深层结构才使用 DFS；
- 强制 same-scope、query explosion、calendar trap、faceted navigation 限制；
- 使用 checkpoint/resume；
- Crawl4AI 内部恢复状态只是执行辅助，平台自己的 Task/Coverage 状态仍是事实源。

### 12.3 Resolution Cache

```text
(input_url_hash, resolver_release_id)
  -> resolved_url + evidence_ref + expires_at
```

规则：

- 301/308 可使用较长 TTL；
- 302/307、HTML wrapper 和 Browser navigation 较短；
- Resolver Release 变化自然失效；
- cache hit 仍引用历史 Evidence；
- 高风险跨域目标可以强制重新验证。

### 12.4 Redirect 与 Canonical 严格分离

```text
Network Final URL != Canonical Identity
```

`rel=canonical`、`og:url`、平台 ID 属于 Identity Evidence，不作为 redirect edge 直接跟随。

```text

```

- live fetch 明确失败/404/410；
- 已有 Common Crawl Observation；
- Source Policy 允许归档恢复；
- 权利、许可证和使用目的符合项目政策；

```text
snapshot_origin = COMMON_CRAWL_ARCHIVE
archive_capture_time
archive_crawl_id
```

不能伪装成当前源站抓取事实。

## 14. Snapshot、抽取、Canonical IR 与 Markdown

### 14.1 Snapshot First

每次实际网络或明确归档事实先落不可变 Snapshot：

```text
snapshot_id
fetch_attempt_id
snapshot_origin
content_type
body_hash
object_ref
headers_hash
rendered_dom_ref
captured_at
created_at
```

后续抽取规则升级时优先离线 replay，不重新打源站。

### 14.2 多候选抽取

同一 Snapshot 可以产生多个 `extraction_candidate`：

- CMS/API 正文；
- Site Selector；
- JSON-LD；
- Trafilatura；
- Readability；
- Crawl4AI cleaned HTML / Markdown Adapter；
- Rendered DOM 再抽取；
- Feed Content；
- PDF Text。

候选记录 extractor release 和 quality features。

### 14.3 Canonical IR

正文选择后生成结构化 IR：

```text
DocumentIR
  metadata
    title
    authors[]
    published_at
    updated_at
    language
    canonical_url
  blocks[]
    heading
    paragraph
    list
    quote
    code
    table
    image
    figure
  assets[]
  outbound_links[]
  source_evidence[]
```

### 14.4 Clean Markdown

Canonical Clean Markdown 必须确定性：

- 去除导航、广告、推荐、分享、评论等噪声；
- 保留标题层级；
- 保留代码 fenced block 与语言 hint；
- 保留列表、引用、表格；
- 保留必要图片和 alt；
- 正确解析相对链接；
- 尽量保留原文引用关系；
- 不做 query-dependent 删减。

### 14.5 链接引用投影

技术博客中的外链本身是重要知识线索。增加：

```text
link_reference
  document_version_id
  block_index
  original_href
  normalized_url
  base_url
  anchor_text
  relation
```

可生成：

```text
MARKDOWN_WITH_REFERENCES
OUTBOUND_LINK_MAP
```

它们是 Projection，不参与 Canonical Identity。

## 15. Quality、Document Identity、版本与去重

### 15.1 Quality

质量评分至少包含：

```text

content length
paragraph ratio
link density
boilerplate ratio
code preservation
table preservation
language consistency
published_at confidence
truncation signal
archive_origin_penalty_or_flag
```

低质量候选进入 quarantine，允许人工比较多 extractor 结果。

### 15.2 Identity Evidence

Document Identity 综合：

1. 平台稳定 ID；
2. rel=canonical / og:url；
3. Redirect Evidence；
4. normalized URL；
5. exact content hash；
6. near-duplicate signal；
7. title + published time 等弱特征。

不能只用 final URL。

`document_alias`：

```text

alias_type
confidence
evidence_ref
```

`alias_type` 可为：

```text
REDIRECT
CANONICAL
AMP
PRINT
MIGRATED
MIRROR
```

### 15.3 Document Version

`document_version`：

```text
id
document_id

canonical_ir_hash
metadata_hash
version_no
published_at
updated_at
accepted_at
version_reason

```

只有 Canonical IR 或需要追踪的关键元数据改变时创建新版本。

URL 参数变化、重复抓取、304、投影策略变化都不应创建正文版本。

## 16. 增量同步与 Reconcile

### 16.1 信号优先级

```text
Feed/API cursor
 -> Sitemap lastmod
 -> High-yield Discovery Surface
 -> Conditional GET
 -> Metadata Probe
 -> Full HTTP
 -> Browser
```

### 16.2 Feed/API

保存原始 Feed payload 和 Item Observation，比较：

```text
GUID / platform id
link
updated
published
content hash
```

新 link 先进入 Candidate Normalization，再进入 URL Resolution 和 Fetch。

### 16.3 Surface 增量调度

推荐初始调度层级：

```text
Tier 0: Feed / CMS API          分钟级或按需求
Tier 1: Sitemap / Blog Index    10~60 分钟
Tier 2: Category/Archive        1~6 小时
Tier 3: Deep Crawl Reconcile    每周/每月
Tier 4: Common Crawl Reconcile  新 CC-MAIN 发布后或按月
```

调度频率根据 `new_urls_per_scan`、失败率、重复率和抓取成本动态调整。

### 16.4 Conditional Fetch

保存：

```text
ETag
Last-Modified
previous body hash
```

304：

- 不创建 Snapshot body 副本；
- 不创建 Document Version；
- 不重复 Extraction；
- 不重复 Projection。

### 16.5 Reconcile

即使有 Feed，也周期执行 Sitemap / Archive / Surface / Common Crawl 差异核对，用于发现：

- Feed 窗口外遗漏；
- URL 迁移；
- Feed 未更新但正文发生变化；
- 删除/下线；
- 历史 Provider 新增可见页面；
- Common Crawl 新 collection 中出现的历史候选；
- 原有 Discovery Surface 失效或结构漂移。

单次 404 不立即删除知识库文档。多次观察或 authoritative API 明确下线后创建 Tombstone，历史版本保留。

## 18. Chunk、全文 Analyzer 与 BM25 Query View

### 18.1 Chunk

采用 heading-aware / structure-aware 切分：

- heading path 随 chunk 保存；
- 代码块尽量保持完整；
- 表格尽量不拆；
- 保留 block range；
- 超长代码/表格采用特殊 chunk policy；
- Chunk Release 变化允许离线 `RECHUNK`。

### 18.2 多语言 Analyzer

1000 个技术博客可能同时包含中文、日文、韩文、英文和混合代码文本，不能依赖英文 whitespace tokenizer。

定义 `analyzer_release`：

```text
id
version
language_policy
tokenizer
normalizer
stemmer
stopword_set
code_token_policy
symbol_policy
created_at
```

可选实现：

- 英文：standard tokenizer + language-matched stemming；
- 中文：ICU / Jieba 类 tokenizer；
- 日文/韩文：语言适配 analyzer；
- mixed code：保留 `foo_bar`、`ClassName`、`package.module`、版本号等技术 token。

Analyzer 是策略，不是真相层。

### 18.3 BM25 Query View

`query_view_release`：

```text
id
version
analyzer_release_id
query_extraction_policy
bm25_parameters
threshold
tag_weights
source_projection_type
created_at
```

`BM25_QUERY_VIEW` 正确链路：

```text
Canonical IR
 -> Clean Markdown / Blocks
 -> Analyzer
 -> BM25 score
 -> threshold gate
 -> restore original document order
 -> Query View
```

不是：

```text
HTML -> BM25 -> 唯一 Markdown
```

逐块保存解释证据：

```text
query_view_block_evidence
  projection_id
  original_index
  raw_score
  tag_weight
  adjusted_score
  threshold
  selected
  analyzer_release_id
```

Web 搜索调试台可以解释为什么某段进入 Query View。

## 19. Hybrid Search 与 Index Generation

默认检索：

```text
OpenSearch BM25
 + Vector Search
 -> score normalization / fusion
 -> metadata filter
 -> optional rerank
 -> Context Assembly
```

检索结果必须回溯到：

```text
Source
Document
Document Version
Canonical URL
Chunk Range
Analyzer Release
Embedding Release
Retrieval Release
Snapshot Origin
```

Embedding 模型、Analyzer 或 index schema 升级时创建新的 `index_generation`：

```text
BUILDING
 -> VALIDATING
 -> READY
 -> ACTIVE
 -> RETIRED
```

新 generation 后台构建并执行回归验证，成功后原子切换 alias；旧 generation 保留回滚窗口。

支持：

```text
RECHUNK
REEMBED
REINDEX
```

且这些任务不重新抓源站。

## 21. 限流、背压与成本治理

并发分层：

```text
global
 -> worker pool
 -> registrable domain
 -> source
 -> route type
 -> external provider
```

建议：

- HTTP 高并发；
- Browser 小并发独立扩容；
- Discovery Browser 与 Content Browser 分池；
- per-domain token bucket；
- 尊重 Retry-After；
- 高错误率 source 自动降速；
- Common Crawl CDX 使用独立低并发限流和强缓存；
- 批量历史发现优先 Columnar/URL Index，不通过多个 Worker 并发轰炸公共 CDX；
- backlog 高时优先 Source Sync，延后 Summary/Embedding 等非关键任务。

`budget_reservation`：

```text

resource_type
reserved_amount
consumed_amount

```

资源至少包括：

```text

browser_seconds
storage_bytes
common_crawl_query_bytes
embedding_tokens
llm_tokens
```

重点成本指标：

- `cost_per_accepted_document`
- `cost_per_changed_document`
- `browser_seconds_per_changed_document`
- `discovery_bytes_per_new_url`
- `surface_bytes_per_new_url`
- `resolution_cost_per_candidate`
- `projection_reuse_rate`
- `embedding_tokens_per_changed_document`

## 24. 安全与合规

- 遵守 robots 和站点访问策略。
- 不绕过登录、付费墙、验证码、WAF 或明确访问控制。
- scheme 只允许配置允许的协议，默认 http/https。
- 起始 URL 和**每次 redirect / Browser navigation** 都重新做 DNS/IP/Egress 校验。
- 阻止访问 private、loopback、link-local、metadata 等受限网络目标。
- 跨域跳转按 Source Policy 判断，而不是默认允许。
- Domain Mapping 新发现的 staging/admin/api/dashboard 等 host 不自动纳入抓取范围，必须经过 scope policy。
- Browser Worker 独立隔离网络、CPU、内存、wall-clock。
- API token、代理、对象存储密钥放 Secret Manager，不写 Profile 明文和普通日志。
- Common Crawl/其他 Archive 的历史内容恢复必须显式记录来源，并遵守项目的版权、许可证和使用策略。
- LLM 不能自动执行会永久忽略 URL、放宽抓取 scope 或绕过访问策略的操作。
- Web 高风险操作使用强类型 Command API、RBAC 和 Audit。

## 28. 验收标准

### Coverage

- 每个 Source 有可解释 Provider。
- FULL_BACKFILL 有明确 exhaustion evidence。
- known gap 可枚举、可重跑。
- 达到预算不会错误标记为完整。
- Common Crawl 不被当成完整性证明。
- Provider overlap/unique URL 可查询。

### Discovery Surface

- 关键 Blog Index / Archive / Category / Docs TOC 可被识别并长期监控。
- Surface 的来源、审核状态、规则 Release 可追踪。
- LLM 灰区判断不会自动覆盖人工确认和生产 Profile。
- Surface 失效或结构漂移可告警并重新审核。

### 增量

- Feed/API/Sitemap/高收益 Surface 新文章在目标 SLA 内进入系统。
- 304 不重复抽取、建版和投影。
- 未变化 Projection 不重复计算。
- Reconcile 能发现 Feed 窗口外遗漏和 Surface 漏洞。
- 新 Common Crawl collection 可触发低优先级历史补洞。

### Redirect / Identity

- wrapper/短链保留完整解析证据。
- 跳转循环可检测。
- 每跳执行 Egress 校验。
- final URL 与 canonical identity 分离。
- 同一文章多入口不会因包装 URL 大量产生重复 Document。

### Markdown

抽样验证：

- title / author / time；
- 正文完整性；
- 导航噪声；
- heading；
- code block；
- list；
- table；
- image；
- outbound link。

Markdown 必须可从 Canonical IR / accepted source 确定性重建。

### 多语言检索

- 中文/英文等代表性语料有独立 Analyzer Release。
- CJK 不依赖英文 whitespace tokenizer。
- BM25 Query View 可解释每块 score、threshold 和是否入选。
- Analyzer / Retrieval Release 升级有离线回归集。

### 可靠性

- Worker 崩溃后 lease 可恢复。
- Deep Crawl 可从 checkpoint 恢复，但平台不依赖框架内部状态作为唯一事实。
- fan-out 保留部分成功。
- Embedding/Index 故障不阻塞 Source Sync。
- Common Crawl CDX rate limit 不会阻塞主抓取链路。
- 所有高风险管理操作可审计。
- Crawl4AI/Playwright 升级可通过 Adapter Release 回滚。

## 29. 最终原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：低成本发现、分类、去重后再抓正文。
3. Discovery Surface First-class：把真正持续产生文章 URL 的入口当作长期运营资产。
4. Authoritative First, Archive as Supplement：CMS/API/Sitemap/Feed 是主要证据；Common Crawl 等只负责补洞和历史证据。
5. Common Crawl Is Evidence, Not Completeness：第三方 Web 采样不能替代站点完整性证明。
6. Evidence First：发现、分类、解析、抓取、身份和版本都保存证据。
7. HTTP First, Browser Last：Browser 是昂贵 fallback 和结构探索工具，不是默认抓取器。
8. Resolution Is Not Identity：跳转终点和 canonical 文档身份必须分离。
9. Snapshot First, Replay Later：原始事实不可变，规则升级优先离线回放。
10. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
11. Canonical Content 与 Query View 分离：BM25/LLM 过滤不能破坏完整正文。
12. Language-aware Analyzer：多语言分词、stemming、threshold、tag weight 必须 Release 化。
13. Release Everything：所有影响结果的策略与外部组件版本都可追踪、比较、回滚。
14. Idempotent + Recoverable：任务可重复、可恢复、可观察，partial success 不丢失。
15. Source Sync 与 AI 解耦：抓取事实不被 Embedding/LLM/Index 服务绑定，LLM 只做可审计的辅助判断。
16. Web 管理是平台能力：Coverage、Surface、异常、证据、版本、成本、检索解释都必须可运营。
