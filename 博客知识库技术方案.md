# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站、公开 Newsletter** 的长期知识库采集平台，可平滑扩展到数千站点、百万级到千万级文章。

系统需要满足：

1. **全历史回填**：尽可能完整发现并抓取每个已批准 Source 的全部历史文章；
2. **持续增量同步**：发现新文章、正文更新、URL 迁移、删除与重发布；
3. **稳定 Markdown**：Markdown 由可追溯 Raw Artifact 经过确定性抽取、质量门禁、Canonical IR 后生成；
4. **低成本扩站**：新增网站优先通过 Source Profile、Provider、Traversal Policy、Recipe 配置完成，而不是复制站点脚本；
5. **Web 可运营**：支持 Source 接入、Backfill、Incremental、Coverage、Frontier、失败诊断、暂停/取消/恢复、质量、版本、成本与审计；
6. **可搜索与 RAG**：支持关键词、向量、混合检索，并能回溯原文与版本；
7. **可观测、可恢复、可重放**：任意 URL、任务、Artifact、Markdown 均可解释来源、版本和执行路径；
8. **渐进扩展部署**：开发期 Docker Compose，生产期按队列和 Worker 类型水平扩容；
9. **采集主链不依赖 LLM**：LLM 仅用于可选增强，不参与 Coverage Truth、URL Identity、Canonical URL 的最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 能解释已发现 URL、Provider、Frontier、Known Gap 与停止原因；
- **Freshness**：新文章从发布/发现到 PASS Markdown 的延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文完整率、噪声率、代码块/表格/列表保留率、截断率；
- **Reliability**：任务成功率、Retry、DLQ、Queue Age、Checkpoint Resume 成功率；
- **Browser Efficiency**：HTTP 命中率、Browser avoided、Browser recovery、每文档 Browser 成本；
- **Identity Quality**：重复文章误合并/漏合并率；
- **Traceability**：任意 Markdown 可回溯 Source、URL、Artifact、Extractor、Quality、Renderer Release；
- **Cancellation**：停止请求到不再领取新任务的延迟、到 Run 完全 STOPPED 的延迟；
- **Cost**：按 Source、Run、Queue Class、每 1000 篇 PASS 文档统计抓取、Browser、存储、索引和模型成本。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不把 HTTP 200、DOM 很长或 crawler success 直接视为正文正确；
- 不把搜索引擎结果数、Deep Crawl 页数、`max_pages` 当历史完整性证明；
- 不把 Crawl4AI 即时 Markdown、LLM 摘要或改写直接作为 Canonical Markdown；
- 不因 URL 曾抓过就永久停止复检；
- 不把 Redis、Browser Session、Crawler Cache、Visited Set、Search Index 当业务真相；
- 不允许优先级、Scorer 或相关性阈值永久删除潜在历史文章；
- 不默认对所有文档构建 GraphRAG。

## 2. 核心设计原则

1. **Coverage First**：先建立 URL Inventory，再批量抓正文；
2. **Authoritative First**：CMS/API、Sitemap、RSS/Atom、Archive 优先；
3. **Deep Crawl Is Gap Provider**：站内深度抓取用于补洞，不作为 Coverage Truth；
4. **Search Is Gap Only**：外部搜索只用于补洞与发现新 Source；
5. **Discovery / Fetch / Extract / Quality / Projection 分离**；
6. **HTTP First, Browser Last**：Browser 是受治理慢路径；
7. **Snapshot First**：先保存不可变 Artifact，再抽取与清洗；
8. **Canonical IR First, Markdown as Projection**；
9. **Recipe, Not 1000 Site Scripts**；
10. **Stable Identity**：Source、URL、Artifact、Document、Version 使用稳定 ID；
11. **Idempotent + Recoverable**：任务使用幂等键、lease、fencing token、checkpoint；
12. **Fair by Default**：大站 Backfill 不能饿死 Incremental 和小站；
13. **Bounded Concurrency Everywhere**：禁止无界 asyncio gather、Browser Context、LLM fan-out；
14. **No Silent Degradation**：截断、预算耗尽、降级、过滤、跳过必须显式记录原因；
15. **Release Everything That Changes Results**：Profile、Traversal、Recipe、Runtime、Extractor、Quality、Renderer、Embedding、Rank 全部版本化；
16. **Priority Means When, Not Whether**：优先级决定何时处理，不决定是否永久保存；
17. **Observation Before Selection**：从页面观察到链接后先保存事实，再做 Filter/Score/Budget 选择；
18. **Persistent Frontier, Not In-Memory Traversal**：BFS/DFS/Best-First 的业务语义进入数据库；
19. **Runtime Checkpoint != Business Checkpoint**：第三方 crawler resume state 只是执行优化，PostgreSQL 才是恢复真相；
20. **Cooperative Cancellation**：停止是状态机，不把“点击停止”错误等同于“所有 in-flight 工作已经结束”；
21. **Same Semantics, Different Topology**：单机 Pilot 与生产集群共享状态机、模型和任务协议。

 Deep Crawl Prefetch                 Playwright                   pgvector

       |                              |                              |
       +------- Observation -> Persistent URL Inventory / Frontier -+
                                      |
                             Immutable Artifact
                                      |

                                      |

                              /              \
                           PASS              REPAIR
                              \              /

### 3.1 真相边界

**PostgreSQL + Object Storage 是业务真相。**

- PostgreSQL：Source、Provider、URL Identity、URL Observation、Crawl Frontier、Task、Cursor、Coverage、Quality、Document、Version、Release、Runtime Checkpoint Pointer、Audit；
- S3/MinIO：Raw HTML、MHTML、截图、Trace、Candidate、IR、Markdown、PDF、Runtime Checkpoint State、Enrichment；
- Redis Streams：任务运输、Consumer Group、Backpressure，不保存不可替代业务状态；
- OpenSearch / pgvector：可重建 Serving Projection；
- Crawl4AI state、Playwright Session、Worker 内存：易失执行状态。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST API、Command、Schema 校验；
- **PostgreSQL**：Truth Store、任务状态、Coverage、Frontier、版本、审计；
- **Redis Streams**：任务队列、Consumer Group、Backpressure；
- **Redis Lua Token Bucket / Semaphore**：跨 Worker 域名限流和资源令牌；
- **React / Next.js + TypeScript**：Web 管理后台；
- **OpenTelemetry + Prometheus + Grafana + Structured Logging**：Trace / Metric / Log；
- **S3/MinIO**：不可变对象存储；
- **Vault/KMS/Secret Manager**：凭据引用。

### 4.2 Discovery / Fetch

- **httpx/aiohttp**：robots、Sitemap、Feed、CMS API、Conditional GET、普通网页；
- **Crawl4AI**：Browser Render、Deep Crawl Prefetch、动态链接发现、简单交互、运行时 resume/cancel；
- **Playwright Python**：复杂多步、有状态、需要 Step 级恢复的交互；
- **SearXNG / 合规 Search API Adapter**：External Search Gap、新 Source Candidate；
- **PyMuPDF/pdftotext**：PDF；扫描件进入 OCR 慢路径；
- **Python email/MIME parser**：Newsletter Inbox Provider。

### 4.3 Extraction / Search

- **Trafilatura**：Generic Main Content Candidate；
- **lxml/BeautifulSoup**：DOM/XPath、Metadata、DOM Repair；
- **JSON-LD/OpenGraph/Microdata**：结构化元数据；
- **CSS/XPath/Regex Recipe**：确定性正文与字段抽取；
- **SimHash/MinHash**：近重复候选；
- **OpenSearch BM25 + pgvector + RRF**：混合检索；
- **可选 reranker / LLM**：只在 Canonical 数据之后运行。

### 4.4 Release 冻结

必须记录：

```text
runtime_release
source_profile_release
provider_adapter_release
traversal_policy_release
interaction_recipe_release
extractor_release
quality_release
identity_release
renderer_release
embedding_release
retrieval_release
```

任何改变结果的升级必须经过 Golden Replay / Offline Eval，必要时 Canary。

## 6. Source 接入流程

新增网站先自动探测，再人工确认。

### 6.1 自动探测

```text
1. robots.txt
2. sitemap index / sitemap.xml
3. RSS / Atom
4. CMS 特征：WordPress/Ghost/Medium/Substack/自建 API
5. 首页与归档页结构
6. URL pattern
7. 是否需要 JS Render
8. 是否存在分页、年份归档、标签、分类
9. Deep Crawl 浅层 Prefetch
10. Canonical / Redirect / Query 参数行为
```

### 6.2 Source Profile 草稿

```yaml
source:
  canonical_domain: example.com
  approved_domains:
    - example.com
  providers:
    - sitemap
    - rss
    - archive
    - deep_crawl
  fetch_route:
    default: http
    browser_patterns:
      - /interactive/*
  traversal:
    mode: bfs
    max_depth: 3
    max_pages_per_slice: 300
    include_external: false
    prefetch: true
    threshold_policy: priority_only
  extraction:
    generic: trafilatura
    article_selector: null
  incremental:
    rss_interval: 10m
    sitemap_interval: 6h
    home_probe_interval: 30m
```

人工在 Web Admin 审核后发布 immutable release。

### 6.3 Seed 安全校验

Deep Crawl 的起始 URL 不得仅依赖 crawler FilterChain 校验。控制面在创建 Run 前必须验证：

```text
seed 属于 approved_domains
scheme 为 http/https
Source enabled
robots/access policy 已计算
Traversal Policy 已发布
凭据/代理策略合法
```

## 7. Discovery 与 Coverage

### 7.1 Provider 优先级

```text
CMS/API
 -> Sitemap
 -> RSS/Atom
 -> Archive/Pagination
 -> HTML Listing
 -> Deep Crawl Prefetch
 -> External Search Gap
```

高优 Provider 的结果不能阻止其它 Provider 执行。最终 URL Inventory 是多个 Provider 的集合并集，并保留每条 Observation 的来源证据。

### 7.2 Backfill 流程

```text
Source Approved
 -> Probe Providers
 -> Run Authoritative Providers
 -> Normalize + URL Inventory
 -> Archive/Pagination Enumeration
 -> Deep Crawl Gap Scan
 -> Persistent Frontier
 -> Fetch
 -> Extract/Quality
 -> Coverage Reconcile
 -> Gap Review
 -> Backfill Complete
```

### 7.3 Coverage Ledger

```text
coverage_snapshot
- source_id
- provider_run_id
- provider_type
- discovered_count
- unique_url_count
- article_candidate_count
- fetched_count
- pass_count
- failed_count
- deferred_count
- known_gap_count
- stop_reason
- captured_at
```

### 7.4 “完成”不能只看数量

Backfill 完成至少满足：

- 权威 Provider 已完成或明确不可用；
- Persistent Frontier 无 READY/LEASED/RETRY；
- Deep Crawl / Archive 不再产生新增文章候选，或达到明确且可解释的收敛条件；
- 失败任务全部成功、DLQ 或人工接受；
- Known Gap 为空或被人工接受；
- 多 Provider URL 集合差异处于阈值内。

### 7.5 URL 规范化

建议顺序：

```text
resolve relative
 -> lower host
 -> remove default port
 -> strip fragment
 -> normalize path
 -> sort/clean query
 -> tracking parameter policy
 -> redirect identity
 -> rel=canonical evidence
```

不要过早删除 query 参数。每个 Source 先通过采样生成 Query Policy，再发布 release。

## 8. Deep Crawl 与 Traversal Policy

### 8.1 角色定位

Deep Crawl 只用于：

- 发现 Sitemap/RSS/API 漏掉的站内 URL；
- 发现归档、分页、标签、年份入口；
- 验证导航结构与 URL pattern；
- 处理 JS 动态链接；
- 定期执行 Coverage Gap 扫描。

不用于证明“历史已经完整”。

### 8.2 两阶段 Prefetch

```text
Phase A: Prefetch Discovery
- 获取 HTML / links / minimal metadata
- 记录 from_url -> to_url Observation
- 跳过 Markdown / LLM / 重型抽取
- 形成 Persistent Frontier

Phase B: Full Processing
- Fetch Raw Artifact
- Extraction / Quality / IR / Markdown
```

对 1000 站历史回填，这是默认模式。若 HTTP/Sitemap 已能完成发现，则优先不用 Browser Prefetch。

### 8.3 Observation Before Selection

执行顺序必须是：

```text
Page Result
 -> Extract Raw Links
 -> Persist Observation
 -> Normalize / Scope Check
 -> Filter Reason
 -> Score
 -> Budget / Admission
 -> Persistent Frontier
 -> Runtime Slice
```

禁止：

```text
crawler visited/threshold/max_pages
 -> 先裁剪
 -> 只保存被选中的 URL
```

原因是第三方 crawler 的 visited/seen、`score_threshold`、`max_pages` 都可能在一次运行内裁掉链接；如果 Observation 没有先落库，就无法区分“从未发现”和“发现但本轮未处理”。

### 8.4 BFS / DFS / Best-First

- **BFS**：Backfill 默认探测策略，优先覆盖浅层导航、分页与归档；
- **DFS**：只在路径深度结构明确的 Source Recipe 中启用；
- **Best-First**：固定预算下优先处理更像文章、归档、分页的 URL。

全历史模式统一解释为：

```text
score -> priority
```

除明确 deny rule 或 focused job 外，不因低分永久删除 URL。

### 8.5 Traversal Policy Release

```yaml
traversal:
  mode: bfs
  max_depth: 3
  max_pages_per_slice: 300
  include_external: false
  prefetch: true
  filter_chain:
    allow_domains:
      - example.com
    include_patterns:
      - /blog/*
      - /archive/*
    deny_patterns:
      - /login*
      - /search*
  scorer:
    article_path: 5
    archive_path: 4
    pagination: 3
    query_noise: -8
  threshold_policy: priority_only
```

每个 Observation 记录对应 `traversal_policy_release_id`。

### 8.6 `max_pages` 的业务解释

Crawler 的 `max_pages` 是执行保护，不是平台 URL 预算或 Coverage 证明。平台单独统计：

```text
observed_count
admitted_count
attempted_count
success_count
failed_count
deferred_budget_count
```

如果本轮容量不足，剩余候选进入 `DEFERRED_BUDGET`，而不是消失。

### 8.7 Bounded Slice

大型站点不能一次把整个 BFS level 或全部 PriorityQueue 交给一个 Worker 长时间占用。Scheduler 按 Source 做切片：

```text
incremental_high: 立即调度
source A backfill: 200~500 URL slice
source B backfill: 200~500 URL slice
source C browser: 独立慢队列
```

Slice 结束后未处理候选仍在 PostgreSQL Frontier。这样可获得公平性、低取消延迟、低内存压力和更可靠的 Worker 重启恢复。

### 8.8 Runtime Checkpoint 与 Business Checkpoint

Crawl4AI 的 `resume_state` / `on_state_change` 可用于恢复单次 traversal，但不与平台 Artifact、Observation、Task 状态形成同一事务。

因此：

```text
Crawl4AI resume_state = 执行优化
PostgreSQL crawl_frontier = 业务恢复真相
S3 Artifact = 抓取事实
Transactional Outbox = 状态与消息一致性
```

恢复时比较：

```text
checkpoint release
vs current runtime/traversal release
vs database frontier
vs artifact existence
```

以数据库为准。

大型 Run 不建议每个 URL 把完整 `visited/pending/depths` JSON 同步写主库；Runtime state 可周期性写 Redis/Object Storage，PostgreSQL 只保存 pointer、hash、release 和 captured_at。

### 8.9 协作式取消

第三方 crawler 的 `cancel()` / `should_cancel` 统一由 `DeepCrawlAdapter` 封装。平台状态：

```text
RUNNING
 -> STOP_REQUESTED
 -> DRAINING
 -> STOPPED
```

行为：

1. Web/API 写 `STOP_REQUESTED`；
2. Scheduler 停止发新 lease；
3. Worker 的 cancellation token 被 `should_cancel` 读取；
4. 同进程可额外调用 strategy.cancel()；
5. 当前 in-flight Fetch 允许完成或超时；
6. 最后 Artifact/Observation 提交完成后释放 lease；
7. Run 进入 `STOPPED`。

因为 BFS、DFS、Best-First 的取消检查粒度可能不同，Web Admin 必须把“停止请求中”和“已停止”分开显示。

### 8.10 Crawl4AI Adapter 与兼容性闸门

业务代码不得直接依赖 Crawl4AI 内部状态，统一经 `DeepCrawlAdapter`：

```text
validate_seed()
build_fresh_filter_chain()
build_scorer()
discover_slice()
normalize_result()
emit_observations()
capture_runtime_checkpoint()
map_cancellation()
translate_error()
```

Adapter 必须：

- 显式创建 FilterChain，不依赖可变默认实例；
- 不把 crawler pages_crawled 当 attempted count；
- 不依赖起始 URL 绕过 Filter 的行为；
- 屏蔽 hostname、filter、normalize 等第三方版本差异；
- callback 失败必须转换为平台 reason_code；
- 版本升级先执行 Golden Replay。

### 8.11 Crawl Graph Evidence

保存 `from_url -> to_url` 可用于：

- 解释 URL 来源；
- 识别分页链；
- 发现 orphan / weakly linked 内容；
- 比较 Sitemap 与站内导航差异；
- 计算 Coverage Gap；
- 构建轻量站点拓扑，不必默认构建 GraphRAG。

## 9. Fetch Plane

### 9.1 HTTP First

默认路由：

```text
HEAD/GET probe
 -> 普通 HTTP 成功且正文足够
    -> HTTP artifact
 -> JS shell / challenge / content incomplete
    -> Browser slow path
```

Browser 不是默认抓取器。

### 9.2 Conditional Fetch

增量复检使用：

```text
If-None-Match: ETag
If-Modified-Since: Last-Modified
```

`304` 不生成新正文版本，但更新 freshness observation。

### 9.3 Retry 分类

```text
DNS/TCP timeout      -> exponential retry
429                  -> Retry-After + domain throttle
5xx                  -> bounded retry
403/challenge        -> policy-based browser/proxy route
404/410              -> tombstone candidate, grace policy
parse/extract failure-> repair queue, 不等于 refetch 必须
```

### 9.4 Domain Rate Policy

每个域名维护：

```text
requests_per_second
burst
max_http_concurrency
max_browser_concurrency
retry_after_until
robots crawl-delay / local policy
```

Global Scheduler 先拿 domain token，再发任务。

### 9.5 Raw Artifact First

成功 Fetch 后先写不可变对象：

```text
raw/{source_id}/{yyyy}/{mm}/{artifact_id}.html.gz
```

附 metadata：

```text
requested_url
final_url
status_code
headers
fetch_started_at
fetch_finished_at
runtime_release
proxy/session route
payload_sha256
```

只有 Artifact durable 后，任务才能进入 EXTRACT。

## 10. 正文抽取、清洗与 Markdown

### 10.1 Extraction Portfolio

每个 Artifact 可产生多个 Candidate：

```text
recipe_css_xpath
structured_data
trafilatura
readability-like fallback
site-specific repair
browser rendered DOM fallback
```

不要直接选择“第一个有文字的结果”。

### 10.2 Candidate Quality Gate

核心指标：

```text
title_present
body_char_count
text_density
link_density
boilerplate_ratio
code_block_count
heading_count
table_count
image_count
published_time_confidence
truncation_signal
repeated_nav_signal
```

判定：

```text
PASS
REPAIR
REJECT_NOT_ARTICLE
REJECT_EMPTY
REJECT_BLOCKED
```

### 10.3 Canonical IR

Markdown 前先生成稳定中间表示：

```json
{
  "document_id": "...",
  "title": "...",
  "authors": ["..."],
  "published_at": "...",
  "updated_at": "...",
  "canonical_url": "...",
  "blocks": [
    {"type": "heading", "level": 2, "text": "..."},
    {"type": "paragraph", "text": "..."},
    {"type": "code", "language": "python", "text": "..."},
    {"type": "table", "rows": []}
  ]
}
```

这样可以：

- Renderer 升级时不用重抓；
- Markdown、HTML Preview、Chunk、Embedding 都从同一 IR 生成；
- 质量测试可以针对结构而非字符串。

### 10.4 清洗规则

确定性移除：

- 顶部导航、页脚、Cookie banner、分享按钮；
- 推荐阅读、热门文章、站点通用 CTA；
- 评论区默认不入主正文，可独立保留；
- 重复标题、重复作者卡片；
- 无意义 tracking 图片、1px beacon。

尽量保留：

- Heading 层级；
- Code Fence 与语言；
- 列表；
- 表格；
- Blockquote；
- 数学公式；
- 图片 alt / caption / 原始 URL；
- 内联链接。

### 10.5 Markdown Projection

建议 Front Matter：

```yaml
---
document_id: ...
source_id: ...
title: ...
canonical_url: ...
published_at: ...
updated_at: ...
fetched_at: ...
content_hash: ...
version_id: ...
---
```

正文从 Canonical IR 渲染。文件路径建议按稳定 ID，而不是完全依赖标题：

```text
md/{source_slug}/{yyyy}/{document_id}.md
```

标题仅作为可读 metadata，避免改标题导致文件身份漂移。

### 10.6 版本判断

生成标准化 `content_hash`：

```text
same content_hash -> 不生成新 Document Version
changed hash      -> 新 Version，旧版本保留
```

仅广告、时间戳、推荐卡片变化应尽量在 IR 清洗前被消除，减少无意义版本膨胀。

## 11. 增量同步

### 11.1 增量信号优先级

```text
RSS/Atom
 -> CMS API
 -> Sitemap lastmod
 -> Homepage / Archive probe
 -> Conditional recrawl
 -> Periodic Deep Crawl Gap Scan
```

### 11.2 每 Source 自适应频率

```text
高频站：RSS 5~10m，主页 15~30m
普通站：RSS 30m，Sitemap 6h
低频站：Sitemap/Archive 12~24h
```

根据历史更新速率动态调节，不对 1000 站统一固定高频。

### 11.3 Cursor 一致性

Provider 流程：

```text
读取 cursor
 -> 拉取一批
 -> 写 Observation/URL Inventory
 -> 创建 Fetch Task
 -> 同一 DB 事务推进 cursor + outbox
```

失败时 cursor 不推进。

### 11.4 更新与删除

- 正文 hash 变化 -> 新 Document Version；
- canonical 迁移 -> identity merge / redirect evidence；
- 404/410 首次出现 -> `MISSING_SUSPECTED`；
- 多次确认或权威 API 明确删除 -> `TOMBSTONED`；
- 历史 Markdown 不物理删除，Serving Index 可隐藏 current tombstone。

### 11.5 周期性 Full Gap Scan

增量 Provider 可能漏掉旧内容迁移或站点重构，所以每个 Source 定期执行低频 Coverage Gap Scan：

```text
Authoritative Provider Reconcile
+ shallow/deep prefetch
+ URL Inventory diff
```

## 12. Task、队列与可靠性

### 12.1 Task 类型

```text
DISCOVER_PROVIDER
DISCOVER_DEEP_SLICE
FETCH_HTTP
FETCH_BROWSER
EXTRACT
QUALITY
REPAIR
IDENTITY_RESOLVE
RENDER_MD
INDEX
ENRICH
RECONCILE_COVERAGE
```

### 12.2 幂等键

示例：

```text
DISCOVER: source_id + provider + run_id + cursor_window
FETCH:    url_id + fetch_policy_release + freshness_window
EXTRACT:  artifact_id + extractor_release
RENDER:   document_version_id + renderer_release
INDEX:    document_version_id + retrieval_release
```

### 12.3 Lease + Fencing Token

```text
READY
 -> LEASED(owner, lease_until, fencing_token)
 -> DONE
 -> RETRY
 -> DLQ
```

Worker 提交结果时必须带 fencing token，过期 Worker 的迟到提交不能覆盖新 lease 的结果。

### 12.4 Transactional Outbox

DB 状态与队列消息不要双写：

```text
BEGIN
  update task/frontier
  insert outbox_event
COMMIT

Outbox Relay -> Redis Streams
```

Consumer 再通过幂等键安全重放。

### 12.5 队列分级

```text
incremental_high
incremental_normal
backfill_normal
backfill_bulk
discovery_prefetch
browser_slow
repair
reindex
enrichment
```

Incremental 不应被大规模 Backfill 饿死。

### 12.6 Fair Scheduler

推荐两层公平：

```text
Queue Class 权重
 -> Source weighted round-robin / deficit round-robin
 -> Domain token bucket
 -> Worker capability admission
```

### 12.7 有界并发

每层都有限制：

```text
Global fetch slots
Per-domain HTTP slots
Per-domain Browser slots
Per-source active tasks
Per-worker memory budget
Browser contexts
Extraction CPU slots
LLM enrichment slots
```

禁止直接 `asyncio.gather(*millions_of_urls)`。

### 12.8 Retry / DLQ

Retry 必须保存：

```text
attempt_no
error_class
http_status
retry_after
next_retry_at
runtime_release
last_trace_id
```

超过阈值进入 DLQ，由 Web Admin 批量重放或接受 Known Gap。

### 12.9 Pause 与 Cancel 区分

```text
PAUSED: 不发新任务，保留 Run 可继续
STOP_REQUESTED: 用户要求本次 Run 终止
DRAINING: 等待 in-flight 收尾
STOPPED: 本次 Run 已终止
```

暂停后可继续同一 Run；停止后通常创建新 Run 继续，避免审计语义混乱。

## 22. 验收标准

平台达到可生产使用至少满足：

1. 新增一个标准博客主要通过 Web Source Profile 完成，不新增独立爬虫脚本；
2. 任意 Source 能执行全历史 Backfill，并解释 Coverage 与 Known Gap；
3. 任意发现 URL 都能解释来源、Filter、Score、Admission、Frontier 状态；
4. Worker 任意 kill 后不丢业务 Frontier，可通过 lease/checkpoint 恢复；
5. Crawl4AI runtime state 丢失时仍可从 PostgreSQL 重建；
6. `max_pages` 或低 score 不会让全历史候选静默消失；
7. 点击停止后立即停止发新 lease，并最终进入 STOPPED；
8. Raw Artifact 可重放生成新的 IR/Markdown，不必重新抓网页；
9. Incremental 能通过 RSS/Sitemap/Conditional GET 持续同步新内容与更新；
10. Markdown 保留标题、正文、代码、表格、列表等关键结构且通过质量门禁；
11. Search Index 全部可从 Canonical 数据重建；
12. 所有改变结果的组件都有 release，并通过 Golden Replay 后发布。

最终核心架构原则是：

> **权威 Provider 建 Inventory，Deep Crawl 补 Coverage Gap；Observation 先于选择，Persistent Frontier 保证不丢；Raw Artifact 保证可重放，Canonical IR 保证稳定 Markdown；Runtime Checkpoint 提升执行恢复效率，但业务真相始终在 PostgreSQL + Object Storage。**
