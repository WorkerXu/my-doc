# 博客知识库技术方案

## 1. 建设目标

建设一套面向 **1000+ 技术博客、工程博客、技术文档站和公开 Newsletter** 的长期知识库采集平台，并可平滑扩展到数千站点、百万至千万级文章。

系统必须同时满足：

1. **全历史回填**：尽可能完整发现每个已批准 Source 的历史文章，并能解释覆盖率、缺口与停止原因；
2. **持续增量同步**：稳定发现新文章、正文更新、URL 迁移、重定向、删除和重发布；
3. **稳定 Markdown**：从不可变 Raw Artifact 经确定性抽取、质量门禁、Canonical IR 生成可重放 Markdown；
4. **低成本扩站**：新增站点优先通过 Source Profile、Provider、Traversal Policy、Extraction Recipe 配置完成，不维护 1000 份站点脚本；
5. **Web 可运营**：支持站点接入、审批、Backfill、Incremental、Coverage、Frontier、质量、成本、暂停、恢复、诊断和审计；
6. **可恢复、可重放**：URL、Provider Run、Task、Attempt、Runtime Result、Artifact、Document、Version 全链路可追溯；
7. **可搜索/RAG**：支持 BM25、向量和混合检索，并能回到原文、版本、Source 与抓取证据；
8. **渐进扩展**：开发期 Docker Compose，生产期各执行面独立水平扩容；
9. **主链不依赖 LLM**：LLM 只做可选增强，不参与历史完整性、URL 身份、robots、正文存在性等最终判定。

### 1.1 核心 SLO

- **Coverage**：每个 Source 都有 Provider Inventory、Known Gap、Backfill Stop Reason；
- **Freshness**：新文章从发布/发现到 PASS Markdown 的延迟；
- **TTFM**：URL 首次发现到首个可用 Markdown 的时间；
- **Extraction Quality**：标题、正文、代码块、表格、列表保留率和噪声率；
- **Reliability**：Task 成功率、Retry、DLQ、Queue Age、Lease Recovery；
- **Provider Efficiency**：Conditional 304 命中率、Provider 重复枚举率、Sitemap Shard 吞吐、CC 查询成本；
- **Browser Efficiency**：HTTP 命中率、Browser Avoided、Pool Reuse、每文档 Browser 成本；
- **Runtime Stability**：queue saturation、真实内存压力、browser acquire latency、pool churn、drain latency；
- **Result Integrity**：批量/流式 Runtime Result 的物化完整率、cardinality mismatch、schema mismatch；
- **Replayability**：同 Raw Artifact + 同 Release 可复现 IR 和 Markdown；
- **Artifact Durability**：required runtime artifact 在 TTL 到期前晋升到平台对象存储的比例接近 100%。

### 1.2 非目标

- 不默认绕过登录墙、付费墙、CAPTCHA、WAF 或明确访问控制；
- 不默认使用个人持久 Browser Profile、模拟用户等反爬绕过手段；
- 不把 HTTP 200、Runtime `success=true`、DOM 很长直接视为文章正确；
- 不把搜索结果数、Common Crawl、Wayback、Deep Crawl 页数或 Seeder 返回条数当作历史完整性证明；
- 不把 Crawl4AI 即时 Markdown、LLM 摘要直接作为 Canonical Markdown；
- 不把 Redis、Runtime Cache、Seeder Cache、Browser Session、Visited Set、Runtime Queue、Search Index 当业务真相；
- 不允许外部用户提交任意 JS/Python、代理、CDP、服务器路径、任意 Seeder 原生配置或任意 webhook URL。

## 2. 核心设计原则

1. **Coverage First**：先建立 URL Inventory，再批量抓正文；
2. **Authoritative First**：CMS/API、Sitemap、RSS/Atom、官方 Archive 优先；
3. **Historical Gap Is Evidence, Not Truth**：Common Crawl、Wayback 只作为补洞证据；
4. **Discovery / Fetch / Extract / Quality / Projection 分离**；
5. **HTTP First, Browser Slow Lane**；
6. **Snapshot First**：先保存不可变 Raw Artifact；
7. **Canonical IR First, Markdown as Projection**；
8. **Recipe, Not 1000 Site Scripts**；
9. **Persistent Frontier, Not In-Memory Traversal**；
10. **Idempotent + Recoverable**：幂等键、Lease、Fencing Token、Checkpoint、Inbox/Outbox；
11. **Fair by Default**：大站 Backfill 不得饿死 Incremental、小站和 Repair；
12. **Bounded Concurrency Everywhere**；
13. **No Silent Degradation**：过滤、截断、预算耗尽、降级、结果缺失必须有原因；
14. **Observation Before Selection**：链接事实先保存，再 Filter/Score/Budget；
15. **Runtime Is Execution Plane**：第三方 Runtime 不拥有 Coverage、Identity、Document 或 Markdown 真相；
16. **Correlate by Identity, Never by Position**；
17. **Config Is Capability**：能改变代码、网络、浏览器、Seeder 行为或 secret 的字段必须经过 Capability Firewall；
18. **Untrusted by Default at Network Boundary**；
19. **Caller Never Owns Paths**；
20. **Webhook Is Hint, Reconciliation Is Truth**；
21. **Runtime Queue != Durable Queue**；
22. **Behavior Beats Naming**：pinned release + Contract Test 才是生产行为契约；
23. **Runtime Artifact Is Ephemeral Until Promoted**；
24. **Zero Must Not Mean Unbounded by Accident**；
25. **Runtime State Is Observation, Not Truth**；
26. **Control Browser Config Cardinality**：大量站点映射到少量 Browser Profile Class；
27. **Result Transport Is Not State Store**：Runtime Result 只做短期交接，结果立即逐条物化；
28. **Drain/Replace Before In-Place Kill**；
29. **Local Safety Is Not Global Admission**：Runtime Dispatcher、RateLimiter、Seeder Semaphore 只负责实例内保护，平台负责跨 Worker 的持久公平和礼貌性限流；
30. **Seeder Is Observation Plane**：Seeder Cache、`status=valid`、BM25 score、`max_urls`、latest CC index 都不是 Coverage/Article Truth。

## 5. Source 接入与配置模型

### 5.1 Source Profile

新增网站创建声明式 Source Profile：

```yaml
source:
  name: example-tech-blog
  entry_url: https://example.com/blog/
  approved_hosts: [example.com]
  allowed_paths: [/blog/]
  denied_paths: [/login/, /account/]

providers:
  - type: sitemap
    url: https://example.com/sitemap.xml
    conditional_get: true
  - type: rss
    url: https://example.com/feed.xml
  - type: archive
    start_url: https://example.com/blog/archive/
  - type: crawl4ai_url_seeder
    modes: [sitemap, common_crawl]
    purpose: gap_evidence

fetch:
  mode: auto
  http_timeout_s: 20
  browser_profile_class: public-default
  browser_intent:
    render_js: true
    scroll: bounded
    wait_selector: article

extract:
  recipe: generic_article_v3
  content_selectors: ["article", ".post-content"]
  exclude_selectors: ["nav", "footer", ".related"]

incremental:
  feed_poll: 10m
  sitemap_poll: 1h
  archive_reconcile: 1d
  full_reconcile: 7d
```

### 5.2 Capability Firewall

Web/API 用户只提交 intent，不允许直接透传 Runtime/Seeder 高能力字段。

普通配置禁止：

- 任意 `js_code` / Python code；
- 任意 `proxy` / `proxy_config`；
- `user_data_dir` / `cdp_url`；
- 任意 cookies/headers/secret；
- 任意服务器 path；
- 任意 LLM base URL；
- 任意 webhook destination；
- `0=unbounded` 的 queue/time/budget；
- 不受控 deep crawl strategy；
- 未审批的 `SeedingConfig`、Common Crawl query、超大 `concurrency`、`force`、前置过滤策略。

Config Compiler 根据已审批 Profile Release 生成 Runtime/Provider Config，并输出编译报告、最终能力集合、预算和拒绝原因。

Crawl4AI 网络边界本身也把高能力配置与 untrusted input 分离；平台仍必须保留自己的 Capability Firewall，不能依赖第三方默认值作为安全边界。

### 5.3 Browser Profile Class

平台只维护少量受审 Browser Profile，例如：

```text
public-default
public-js-heavy
public-media-light
isolated-authenticated
```

站点 selector、wait、scroll、正文规则优先放入低成本 CrawlerRunConfig/Extraction Recipe。只有真正改变浏览器进程能力、网络边界或 credential scope 的需求才生成新的 Browser Profile Release。

## 6. 历史 URL 发现、Provider 与 Coverage

### 6.1 Provider 优先级

推荐顺序：

1. CMS/官方内容 API；
2. Sitemap / Sitemap Index；
3. RSS/Atom；
4. 官方 Archive / Category / Pagination；
5. 站内静态链接图；
6. Crawl4AI URL Seeder / Domain Mapping / Deep Crawl 作为发现增强；
7. Common Crawl / Wayback；
8. 合规 Search Adapter 作为 Gap Evidence。

每个 Provider 只产生 Observation，不直接决定最终文章集合。

### 6.2 Observation First

```text
url_observation
- observation_id
- source_id
- provider_run_id
- provider_type
- provider_ref
- observed_url
- discovered_at
- published_at_hint
- updated_at_hint
- parent_url
- anchor_text
- depth
- raw_provider_status
- evidence_artifact_id
- provider_release_id
```

链接事实先落库，再做 scope/filter/dedup，避免过滤错误后无证据可查。

### 6.3 Provider Run 与 Checkpoint

```text
provider_run
- provider_run_id
- source_id
- provider_id
- provider_release_id
- runtime_release_id
- started_at
- finished_at
- termination_reason
- result_limit
- raw_observation_count
- selected_count
- filtered_count
- duplicate_count
- truncated

provider_checkpoint
- provider_id
- request_url
- etag
- http_last_modified
- response_sha256
- observed_lastmod_hint
- cc_index_id
- checkpoint_artifact_id
- checked_at
- provider_release_id
```

Provider 终止原因必须显式：

```text
AUTHORITATIVE_PROVIDER_EXHAUSTED
ARCHIVE_PAGINATION_EXHAUSTED
RESULT_LIMIT_REACHED
TIME_BUDGET_REACHED
DATE_BOUND_REACHED
ROBOTS_BLOCKED
ACCESS_DENIED
RATE_LIMITED
BUDGET_EXHAUSTED
PROVIDER_ERROR
CANCELLED
```

`RESULT_LIMIT_REACHED` / `BUDGET_EXHAUSTED` 绝不能被解释为“历史完整”。

### 6.4 Sitemap / Feed Incremental Revalidation

对 Sitemap、Feed、CMS API 优先使用：

```text
If-None-Match
If-Modified-Since
```

- 304：保留上次 Provider Evidence，不重新枚举正文 URL；
- 200：保存新 Provider Artifact，计算 body hash，解析并与旧 inventory diff；
- 不支持条件请求：退化到 response hash、站点 `<lastmod>` hint 和周期 full reconcile；
- `<lastmod>` 只是站点提示，不能替代内容 hash 或 HTTP validator；
- 不把 `<lastmod>` 字符串排序直接作为强一致版本判断。

### 6.5 Crawl4AI URL Seeder Provider Adapter

引入：

```text
provider_type = CRAWL4AI_URL_SEEDER
mode = SITEMAP | COMMON_CRAWL | SITEMAP_PLUS_CC
```

定位：**高性能 Discovery Adapter，不是控制面和业务真相。**

#### 6.5.1 全历史模式

完整性优先时：

```text
pattern = *
filter_nonsense_urls = false
```

先把原始 URL Observation 入库，再执行平台版本化的：

```text
normalize -> scope -> classify -> dedup -> frontier
```

不能在 Seeder 内先用“nonsense filter”、BM25、主题 pattern 永久丢掉 URL，否则 Coverage 无法解释漏项。

#### 6.5.2 `max_urls` 只表示预算

Seeder 达到 `max_urls` 会停止 producer/worker 并清理本地队列，因此平台映射为：

```text
termination_reason = RESULT_LIMIT_REACHED
truncated = true
```

不能映射为 Provider exhausted。

#### 6.5.3 Seeder Cache 只是 Accelerator

Seeder 本地 Sitemap/CC cache：

```text
cache hit != provider unchanged
cache miss != provider changed
cache file exists != provider complete
```

平台业务判断始终依赖 Provider Checkpoint + Provider Evidence。

当前 Sitemap smart cache 在验证 cache 前仍可能先 GET 根 sitemap 读取内容/`lastmod`；因此真正节省增量网络流量仍靠平台 Conditional GET，而不是把 local cache 当 HTTP revalidation。

#### 6.5.4 Common Crawl Index 必须固定

历史回填计划生成时解析并保存：

```text
cc_index_id
cc_query_pattern
cc_query_artifact
```

同一 Backfill Run 的 retry/replay 必须复用同一 `cc_index_id`，不能静默跟随“latest index”。需要补最新 CC 数据时创建新的 Provider Run。

Common Crawl/Wayback 继续只作为历史补洞证据，不单独证明 Coverage 完整。

#### 6.5.5 `hits_per_sec` 不是平台严格 QPS

当前 Seeder 将 `hits_per_sec` 映射为本进程 `asyncio.Semaphore`，实际更接近局部并发门，不是基于时间窗口的严格 token bucket。

因此：

- 跨 Pod/Worker per-host QPS 由 Redis Lua Token Bucket 控制；
- per-host / per-source concurrency 由平台共享 Semaphore 控制；
- Retry-After 和 429/503 backoff 存共享 `origin_backoff_state`；
- Seeder local semaphore 仅作第二道局部保护；
- Contract Test 每个 pinned release 验证真实请求速率语义。

#### 6.5.6 `status=valid` / Head Metadata 只是 Hint

Seeder 的 live check / partial-head probe 可用于：

- redirect hint；
- canonical hint；
- title/description；
- JSON-LD；
- language；
- published/updated hint；
- cheap relevance prioritization。

但不能直接产生：

```text
VALID_ARTICLE
Document
PASS Markdown
```

HEAD 可能 405、WAF 对 HEAD/GET 行为不同、redirect 可能多级、partial head 不是正文。最终仍需平台 Fetch + URL Validity + Raw Artifact + Quality Gate。

#### 6.5.7 BM25 只做优先级，不做完整性

Seeder BM25 依赖当前候选集合、metadata 完整度和简单 tokenization；分数会随候选集变化。

只允许用于：

- focused discovery；
- repair/gap priority；
- 主题子集；
- Web 管理端候选排序。

不得用于全历史 Inventory 的最终保留/删除判定。

#### 6.5.8 不用 `many_urls(1000 domains)` 代替平台调度

平台以 durable Provider Task 为单位执行：

```text
Fair Scheduler
 -> lease Provider Task / small domain batch
 -> invoke Seeder Adapter
 -> materialize Observations
 -> checkpoint
 -> ack Task
```

不一次把 1000 Source 交给进程内 `asyncio.gather()`，原因：

- 缺少 durable lease/retry；
- 缺少 Source fairness；
- Seeder 实例存在本地共享状态；
- 进程崩溃后无法从业务 checkpoint 恢复。

### 6.6 超大 Sitemap Index 分片

普通站点可直接使用 Seeder；当 sub-sitemap 数或预计 URL 数超过阈值时改为平台分片：

```text
Root Sitemap Index
 -> save Provider Artifact
 -> materialize sub-sitemap list
 -> create SITEMAP_SHARD task per sub-sitemap
 -> Fair Scheduler
 -> Conditional GET per shard
 -> streaming XML parse
 -> batch upsert URL Observations
 -> shard checkpoint
```

原因：即使结果 queue 有界，进程中仍可能存在：

```text
seen                    O(unique URLs)
results                 O(returned URLs)
discovered_urls         O(sitemap URLs)
regular_urls            O(one sitemap size)
sub-sitemap asyncio task O(number of sub-sitemaps)
BM25 corpus              O(scored URLs)
```

所以“bounded queue”不能被宣传为“整个 Provider Job 内存严格有界”。百万 URL Source 必须用分片 + 流式 Observation 物化。

### 6.7 Coverage Snapshot

```text
coverage_snapshot
- provider inventories
- accepted URL count
- fetched count
- PASS count
- known gaps
- excluded reasons
- provider termination reasons
- earliest known date
- latest known date
- provider disagreement
- truncated_provider_runs
- last_full_reconcile_at
```

Deep Crawl、Adaptive Crawling、URL Seeder、搜索结果、Common Crawl 或归档库只能补充证据，不能单独宣称“历史完整”。

### 6.8 Adaptive / Focused Discovery

Adaptive Crawling 只用于：

- 无权威列表时的 focused discovery；
- Provider disagreement 的定向补洞；
- 大型文档站只需特定主题时的预算优化。

它的停止条件必须记录 target、confidence、budget、termination reason，不替代 Coverage Inventory。

## 7. URL Identity、Scope 与 Persistent Frontier

### 7.1 Conservative Normalization

URL 身份分层：

```text
observed_url
normalized_url
redirect_target
canonical_url_hint
url_identity_id
```

默认只做保守规范化：scheme/host 小写、默认端口、fragment 删除、已知 tracking 参数剥离。路径大小写、尾斜杠、业务 query 不做激进合并。

`rel=canonical`、重定向、站点规则只是证据；真正 Document Identity 由平台版本化规则决定。

### 7.2 Scope Gate

每个发现 URL 必须经过：

```text
approved host
allowed/denied path
scheme
port policy
redirect re-check
robots eligibility
MIME expectations
```

Seeder 返回的 redirect target、canonical hint 不能绕过 Source Scope。

### 7.3 Persistent Frontier

```text
frontier_item
- source_id
- url_identity_id
- stage
- priority
- reason
- discovered_at
- next_attempt_at
- attempt_count
- lease_owner
- lease_until
- fencing_token
- last_error_class
- provider_evidence
```

Frontier 永久保存在 PostgreSQL。Runtime queue、Seeder queue、Crawl4AI PriorityQueue、asyncio Task 都不能替代它。

## 9. Fetch Plane

### 9.1 HTTP Fast Lane

优先使用 HTTP：

- robots.txt；
- Sitemap/Feed/API；
- 普通文章；
- Conditional GET：`If-None-Match` / `If-Modified-Since`；
- HEAD 仅作提示，最终以 GET + MIME sniffing 为准；
- 记录 redirect chain、status、headers、TLS/网络错误分类；
- 304 只表示 representation 未变，不表示 Source Inventory 完整。

### 9.2 Browser Slow Lane

仅在以下条件升级 Browser：

- HTTP DOM 缺正文；
- 页面正文依赖 JS；
- 需要有限滚动/点击才能加载正文；
- Source Profile 明确声明；
- HTTP Candidate 质量门禁失败且 Browser Repair 有价值。

Browser 请求必须经过 Global Admission 和 Runtime Admission，禁止直接从 Discovery 大批量灌入 Browser。

## 10. Crawl4AI Runtime Service Plane

### 10.1 Runtime Registry 与版本固定

每个实例注册：

```text
runtime_instance
- runtime_instance_id
- runtime_release_id
- image_digest
- crawl4ai_version
- browser_version
- browser_profile_classes
- dispatcher_capabilities
- max_input_body_bytes
- max_runtime_wall_clock
- max_artifact_bytes
- health
- drain_state
```

生产只允许 pinned release。升级前运行 Contract Probe，不根据文档字段名推断实际行为。

### 10.2 双层 Backpressure

```text
Persistent Frontier
  -> Platform Fair Scheduler
  -> Global Admission
  -> bounded micro-batch
  -> Runtime Dispatcher
  -> Browser pool / HTTP execution
  -> streaming materialization
```

平台队列负责 durable/global/business fairness；Runtime Dispatcher 负责 ephemeral/local/resource safety。

### 10.3 Dispatcher Policy

```text
runtime_dispatch_policy_release
- dispatcher_type: MEMORY_ADAPTIVE | SEMAPHORE
- max_session_permit
- semaphore_count
- memory_pressure_threshold_percent
- memory_critical_threshold_percent
- memory_recovery_threshold_percent
- memory_check_interval_s
- memory_wait_timeout_s
- fairness_timeout_s
- local_rate_limit_profile
- runtime_batch_max_urls
- stream_mode
- stream_close_policy
- result_contract_version
```

这些字段是期望配置，真正有效行为以 pinned Runtime Contract Test 为准。

### 10.4 MemoryAdaptiveDispatcher 执行契约

按“局部内存滞回 Admission”理解：

- 达到 pressure threshold：停止继续从本地队列填充新 active task；
- 达到 critical threshold：已经进入执行入口的 URL 可能被重新放回本地 PriorityQueue；
- 降到 recovery threshold：才恢复放任务，避免阈值附近抖动；
- 高内存持续超过 `memory_wait_timeout`：按 `RUNTIME_MEMORY_PRESSURE_TIMEOUT` 分类，不按文章失败分类；
- PriorityQueue 的 aging/fairness 只对当前 Runtime batch 生效，不是跨 Source 公平；
- 单任务 `memory_usage/peak_memory` 只做诊断，不能相加做容量账本。

本地 requeue 必须归一化为：

```text
LOCAL_REQUEUED
```

它不是平台 retry，不消耗 origin retry budget，也不能触发文章 DLQ。

### 10.5 SemaphoreDispatcher 的生产边界

固定 semaphore 模式适合资源成本稳定的小批量任务，但要固化两个行为：

1. 输入列表可能先为每个 URL 创建 asyncio Task，再由 `asyncio.Semaphore(semaphore_count)` 限制真正抓取；因此抓取并发有界不等于调度对象数量有界；
2. 当前 pinned release 下有效并发旋钮必须以 Contract Test 证明，不能仅凭参数名称推断 `max_session_permit` 与 `semaphore_count` 的实际语义。

平台要求：

- Semaphore 只接收 bounded micro-batch；
- `runtime_batch_max_urls` 是硬上限，不允许 `0` 表示无界；
- Capacity Planner 使用实测有效并发；
- 每次升级测试参数语义；
- Runtime 监控增加 `scheduled_async_tasks` 与 `semaphore_waiters`。

### 10.6 Runtime RateLimiter 不是全局礼貌性限流

进程内 RateLimiter 只能看作局部 pacing/backoff hint。

平台要求：

- 跨 Pod/Worker host/domain QPS、并发、Retry-After、backoff 由 Redis Lua + 共享 `origin_backoff_state` 控制；
- Runtime RateLimiter 只做第二道局部保护；
- Runtime 重启不能清除平台 backoff；
- 429/503 反馈写入 Observation，供所有 Worker 共享；
- Contract Test 验证延迟变化、真实请求次数和重发语义。

这与 Seeder `hits_per_sec` 的原则相同：**local limiter 不能替代 global admission。**

### 10.7 Config First-Match 契约

当一个 Job 携带多个 `CrawlerRunConfig` 时，按 pinned release 的实际 first-match 行为处理。

Config Compiler 必须：

- 做 matcher overlap/shadow 检测；
- 显式 rule order；
- 显式 default；
- 用代表性 URL fixture 做 match coverage test；
- 每个 Attempt 保存最终命中的 `crawler_run_config_release_id`、`matcher_rule_id`、matcher evidence。

`NO_CONFIG_MATCH` 是配置/路由问题，不消耗源站 retry budget。

### 10.8 Batch 与 Streaming 结果契约

Browser micro-batch 优先 Streaming：结果完成一个就立刻物化一个，降低大 `CrawlResult` 的驻留时间。

禁止：

```python
for input_url, result in zip(urls, results):
    persist(input_url, result)
```

必须按 identity 关联：

```text
runtime_task_item
- runtime_task_id
- attempt_id
- input_url_identity_id
- correlation_key
- normalized_outcome
- materialized_at
```

Adapter 输出统一 outcome：

```text
FINAL_SUCCESS
FINAL_FAILURE
LOCAL_REQUEUED
NO_CONFIG_MATCH
CANCELLED_ON_STREAM_CLOSE
RUNTIME_MEMORY_PRESSURE_TIMEOUT
```

结果条数和顺序都不能作为身份契约。

### 10.9 Stream Close 是取消协议

消费者取消、Worker shutdown 或 Materializer 失败都可能提前关闭 stream。

```text
RUNNING_STREAM
  -> RUNTIME_STREAM_ABORTED
  -> verify runtime cleanup
  -> inspect already materialized terminal items
  -> reconcile unmaterialized items
  -> durable requeue with fencing
```

已经 yield 且 Raw Artifact 已持久化的 item 保持 terminal；未 materialize 的 in-flight/queued item 才重新调度。

### 10.10 Micro-batch 计算

```text
batch_size = min(
  runtime_batch_max_urls,
  available_runtime_slots * batch_factor,
  per_domain_budget,
  lease_deadline_budget,
  expected_result_bytes_budget,
  memory_headroom_budget
)
```

高成本 Browser Repair 默认 `1 URL / Job`；普通 Browser Backfill 使用小批量。具体值由压测和 P95/P99 页面成本决定，不使用文档默认值直接上线。

### 11.1 Runtime Attempt


Runtime state 只作为 Observation；平台 Task 状态由物化证据和 Reconciler 推导。

### 11.2 Result Materializer

每收到一个 terminal result：

1. 校验 runtime task/correlation identity；
2. 校验 result schema；
3. 保存原始 response metadata；
4. 将 required artifact 从 Runtime 临时存储晋升到 S3/MinIO；
5. 写 artifact checksum/size/MIME；
6. 创建 Raw Artifact；
7. 用事务更新 Attempt/Task；
8. Outbox 触发 Extraction。

“Runtime 返回成功”但 required artifact 未晋升时，不允许 Task 进入业务 `SUCCEEDED`。

### 11.3 Webhook Inbox + Reconciler

Webhook 只做提示：先入 Inbox、验签/去重，再异步处理。Reconciler 周期检查：

- lease 超时；
- Runtime 消失；
- stream 中断；
- expected item 没 terminal materialization；
- artifact promotion 未完成；
- cardinality/schema mismatch；
- Provider Run 停在 RUNNING；
- Sitemap Shard checkpoint 不闭合。

最终以 PostgreSQL + Object Storage 的证据闭合状态。

## 21. 取消、暂停、Drain 与恢复

### 21.1 Stop 语义

- **Pause Source**：停止发新 Task，不杀已 materialize 成功项；
- **Pause Provider**：停止新的 Provider Lease，保存已落库 Observation 与 shard checkpoint；
- **Cancel Run**：停止新 lease，通知 Runtime stream close，并 reconcile 未 terminal item；
- **Drain Runtime**：停止新 Admission，等待 active job 收敛，超时后取消并 reconcile；
- **Replace Runtime**：新实例健康并通过 Contract Probe 后切流，再终止旧实例。

### 21.2 Crash Recovery

Worker/Runtime 崩溃：

1. lease 到期；
2. Reconciler 检查哪些 item / Provider Shard 已 terminal materialize；
3. 已持久化成功项不重抓；
4. 其余 item 重新进入 PENDING；
5. fencing token 防止旧 Worker 回写；
6. origin shared backoff、Coverage、Frontier、Provider Checkpoint 不受 Runtime 重启影响。

- pgvector embedding；
- RRF 混合；
- chunk 保留 `document_id/version_id/section_path/source/url`；
- 查询结果默认返回最新 ACTIVE Version，可选择历史版本；
- embedding/reranker 模型版本化；
- 删除/重做 Projection 不影响 Raw/IR 真相。

Seeder BM25 与这里的 Search BM25 是不同用途：前者只可作为发现阶段临时优先级，后者是对 Canonical 内容构建的可重建 Serving Projection。

## 23. 容量与扩展策略

### 23.1 初始部署

Docker Compose：

```text
api
scheduler
worker-provider
worker-http
worker-extract
runtime-crawl4ai
postgres
redis
minio
opensearch
prometheus/grafana
web-admin
```

先以 50-100 个站压测并形成每类站点成本画像，再扩大到 1000+。

### 23.2 生产拆分

独立伸缩：

```text
provider/discovery workers
sitemap shard workers
http fetch workers
browser runtime pools by profile class
artifact materializers
extraction workers
projection workers
scheduler/reconciler
```

Browser Runtime 按 P95/P99 页面内存、CPU、执行时长、slot utilization 扩容，而不是按 URL 数直接扩容。

### 23.3 Provider 分片原则

- 小站 Sitemap/Feed 可单 Provider Run；
- 大 Sitemap Index 先分解成 durable shard；
- shard 解析流式批量 upsert Observation；
- 不把全部 URL 放进一个 Python `seen/results` 生命周期；
- Provider task 有 `result_limit/time_budget` 时必须把 truncation 写 Coverage；
- Common Crawl 大查询按固定 index + pattern 分片，并保存 Evidence。

### 23.4 Runtime Micro-batch 原则

- HTTP 可大于 Browser，但仍必须 bounded；
- Browser Repair：1 URL/Job 优先；
- Browser Backfill：小批量 streaming；
- 同域 URL 不为了减少 Job 数而过度聚合；
- Batch 大小受 lease deadline 与 expected result bytes 约束；
- Semaphore 模式额外受 `scheduled_async_tasks` 上限约束。

### 24.2 Sitemap 增量同步

```text
Scheduler leases Provider Revalidate
 -> Conditional GET with ETag/Last-Modified
 -> 304: update checked_at only
 -> 200: save Provider Artifact + body hash
 -> parse / shard sitemap
 -> upsert new/updated Observations
 -> identity resolve
 -> enqueue changed/new URL

```

### 24.3 URL Seeder Gap Discovery

```text
Provider Task
 -> compile approved Seeder config
 -> global domain admission
 -> run Sitemap/CC discovery
 -> materialize every raw Observation
 -> store result_limit/cache/cc-index/termination metadata
 -> platform classify/filter/dedup
 -> compare authoritative Provider Inventory
 -> enqueue only proven gaps/candidates
```

### 24.4 Runtime Browser Job

```text
Platform Task Lease
 -> Global Domain/Browser Admission
 -> choose Runtime by profile/release/headroom
 -> build bounded micro-batch
 -> Runtime Dispatcher
 -> stream terminal result
 -> identity correlation
 -> promote artifact
 -> transactional materialization
 -> acknowledge platform Task
```

任何阶段崩溃都由 Lease + Reconciler + Idempotency + Provider Checkpoint 恢复，而不是依赖 Runtime/Seeder 内存队列。

## 27. 验收标准

上线前至少满足：

1. 新站可通过配置接入，不需要复制站点爬虫代码；
2. 每个 Source 可展示 Provider Inventory、Coverage 和 Stop Reason；
3. Incremental 不会被大型 Backfill 饿死；
4. Worker/Runtime 崩溃后 Task 可自动恢复；
5. Raw Artifact 不可变，IR/Markdown 可重放；
6. HTTP 与 Browser 有明确升级条件；
7. Runtime queue、Dispatcher、RateLimiter、Seeder cache/queue 不被当作平台 durable/global truth；
8. Browser micro-batch 有硬上限，Semaphore 不允许 mega-batch；
9. Runtime Result 通过 identity 关联，不通过列表位置；
10. Stream early close 后无残留 Browser task，并且未 terminal item 能被准确重调度；
11. 跨 Worker host/domain 限流严格生效，Runtime/Seeder 本地 limiter 不会成为唯一保护；
12. Source 配置、Provider、Seeder、Runtime、Extractor、IR、Renderer 全部可版本追溯；
13. Web 管理端能区分 Provider 截断、Seeder cache、本地并发、全局限流、配置错误、源站错误、Runtime 压力、物化失败和质量失败；
14. 搜索索引可删除后从 Canonical 数据重建；
15. 全链路有 correlation、指标、审计和 Chaos Recovery 验证；
16. Seeder `status=valid`、BM25、`max_urls`、cache hit 不会被当作 Coverage/Article Truth；
17. Sitemap/Feed 增量支持 Provider Checkpoint + Conditional GET；
18. Common Crawl 历史回填固定 `cc_index_id`，retry/replay 不静默漂移；
19. 超大 Sitemap Index 使用 durable shard，不依赖单进程 O(N) `seen/results`；
20. 所有 Provider 预算耗尽和截断都进入 Coverage，不能静默标记完成。

## 28. 最终架构结论

最终方案不是“让一个爬虫进程抓 1000 个博客”，而是把长期知识库拆成五类清晰事实：

```text
Provider / Coverage / Frontier / Task Truth
    = PostgreSQL

Provider Evidence / Raw / IR / Markdown Truth
    = Object Storage + PostgreSQL Metadata

Cross-worker Scheduling / Politeness
    = Platform Scheduler + Redis Lua + Durable Backoff

URL Discovery Acceleration
    = Native Providers + Crawl4AI URL Seeder + Gap Adapters

Browser Execution
    = Pinned Crawl4AI Runtime + Bounded Dispatcher + Browser Pool
```

Crawl4AI URL Seeding 非常适合作为 **高吞吐 URL Discovery Adapter**：Sitemap/Common Crawl 批量发现、Sitemap Index 并行、partial-head metadata probe、局部 backpressure 和缓存都能降低 1000+ 站点的发现成本。但它的本地 cache、`status=valid`、BM25、`max_urls`、`hits_per_sec`、latest CC index 和进程内 queue 都不能替代平台级 Provider Checkpoint、Coverage、Persistent Frontier、全局限流和 durable scheduling。

Crawl4AI Advanced Multi-URL Crawling 适合作为 **单 Runtime 的局部执行控制**：MemoryAdaptiveDispatcher 提供内存压力滞回和局部队列，SemaphoreDispatcher 提供简单固定并发，Streaming 支持边完成边物化。但这些能力同样不能替代平台级持久任务、公平调度、跨 Worker 限流、Coverage 和版本真相。

生产关键约束是：

**Provider 先保存 Observation 再筛选；Sitemap 增量用 Conditional GET；Common Crawl 固定 index；超大 Sitemap 持久分片；平台只给 Runtime 有界 micro-batch；所有结果按 identity 关联；Runtime local requeue 不等于平台 retry；stream close 必须 reconcile；Runtime/Seeder limiter 只是本地安全网；所有关键语义由 pinned release Contract Test 验证。**

以这组边界实现后，平台能够同时获得：

- 1000+ 技术博客的可解释历史覆盖；
- 低成本增量同步；
- 新站配置化扩展；
- 大站可分片、可恢复的 URL Inventory；
- 稳定、可重放的 Markdown；
- 可运营的 Web 管理；
- 可水平扩容的 HTTP/Browser 执行面；
- 不依赖某个 Runtime/Seeder 版本、某个本地 cache 或某个进程内队列的长期可靠性。
