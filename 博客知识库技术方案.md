# 博客知识库技术方案

## 1. 建设目标与规模边界

建设一个长期运行、可横向扩展、可审计、可重放的技术博客知识库平台。首期接入约 1000 个技术博客、工程博客和技术文档站，抓取尽可能完整的历史文章并稳定清洗为 Markdown；后续持续增加站点，并支持增量同步、版本追踪、全文/向量检索、Web 管理、质量审计、单 URL 手工摄取和离线重处理。

按以下量级设计：

- 1000+ Source，后续扩展到数千站点；
- 百万级 Document；
- 数百万到千万级 URL / Observation；
- 千万级 Chunk / Embedding 长期增长；
- 中英日韩等多语言技术内容；
- HTML、PDF、TXT、Markdown、JSON/API、RSS/Atom/JSON Feed 等多种资源类型；
- HTTP 为主，Browser 为受控 fallback；
- 历史发现支持 CMS API、Sitemap、Feed、Archive、Docs TOC、Common Crawl URL Index 等多来源；
- PostgreSQL + Object Storage 保存事实；Markdown、Filtered Markdown、Chunk、Embedding、全文/向量索引都是可重建 Projection。

平台必须能回答：

1. 一个站点理论上有哪些历史文章，为什么认为历史已基本覆盖；
2. 一个 URL 从哪里发现、如何规范化、经过哪些跳转后被抓取；
3. 一个 URL 最终返回 HTML、PDF、Markdown、JSON 还是其他资源，路由依据是什么；
4. 动态页面执行了哪些点击、滚动、等待，使用哪一版 Recipe；
5. 一个 Markdown 来自哪个 Snapshot、Extractor、Schema、Filter 和 Document Version；
6. 源站变化后哪些内容真的变化，哪些派生物需要重建；
7. Chunk、Embedding、Analyzer、Browser Runtime、过滤器和索引策略升级后能否不重新访问源站完成重放；
8. 批任务取消、限流、Worker 崩溃或流式消费中断后，哪些 URL 已可靠提交、哪些需要重试；
9. 用户手工提交一个 URL 后，当前处理到 Probe、Fetch、Extraction、Markdown、Embedding 还是 Index；
10. “对这一篇文章提问”“只搜索某个站点”“只查询某个版本”时，检索作用域是否被硬性约束；
11. HTML、PDF、Markdown 等不同输入类型是否进入同一逻辑知识库，而不是被输入形态割裂成不同语料孤岛；
12. Query 请求是否完全依赖已入库稳定身份，而不是再次访问远程 URL 判断资源类型。

## 2. 核心设计原则

1. **Config First**：普通站点通过 Source / Site Profile / Release 接入，避免修改核心代码。
2. **Coverage First**：历史完整性由 Provider Evidence 与 exhaustion reason 证明，不能用“队列为空”或达到 `max_pages` 冒充完整。
3. **Discovery Before Fetch**：先低成本发现、分类、去重 URL，再决定是否真实抓取正文。
4. **Authoritative First**：CMS/API/Sitemap/Feed 优先，Archive/Common Crawl 用于补洞和外部证据。
5. **URL Is Locator, Not Content Type**：URL 后缀只是弱证据，资源类型由最终响应、MIME、文件签名和站点规则综合判断。
6. **HTTP First, Browser Last**：Browser 只处理动态发现面、动态渲染、结构探索或低质量 fallback。
7. **Recipe, Not Site-Specific Code**：动态交互和结构化抽取声明式、版本化，禁止长期堆积 `if site == ...`。
8. **Bounded Interaction**：点击、滚动、等待、session 复用都有预算和明确停止条件。
9. **Snapshot First**：先保存不可变网络事实，再做抽取、清洗、建版。
10. **IR First, Markdown as Projection**：Canonical IR / Document Version 是内容事实层，Markdown 是可重建输出。
11. **Filtered Content Is Projection**：Pruning、BM25、LLM Filter 都是有损派生，不覆盖 canonical 内容。
12. **LLM Extraction Is Optional**：LLM 抽取、摘要、实体识别属于版本化 Projection/fallback，不作为 canonical 正文默认主路径。
13. **Stable Identity**：Document、Version、Chunk、Embedding、Index 身份稳定且 release-aware。
14. **Release Everything**：影响结果的策略、Recipe、Schema、Probe、Filter、模型、索引、Runtime 全部版本化。
15. **Idempotent + Recoverable**：任务具备幂等键、lease、fencing、checkpoint、retry、partial success。
16. **Stream and Commit Per URL**：多 URL 批任务按单 URL 流式持久化、提交与 ack，一个失败项不能回滚成功项。
17. **Local Dispatcher Is Not Global Scheduler**：Crawl4AI Dispatcher/RateLimiter 只保护单 Worker；平台 Scheduler 才是 durable 调度和全局限流真相。
18. **Async Command API**：抓取、PDF 解析、Embedding 等长任务由 API 接收命令并返回 durable ID，后台 Worker 执行。
19. **Source Sync 与 AI 解耦**：Embedding、Rerank、LLM、Summary、Search Index 故障不能阻塞抓取事实同步。
20. **Projection Readiness Is Explicit**：Canonical、Markdown、全文、Chunk、Embedding、Vector 等就绪状态独立表达，允许 `PARTIAL_READY`。
21. **Evidence Everywhere**：发现、分类、资源探测、跳转、交互、抓取、抽取、过滤、身份、版本和检索都保存证据。
22. **Language-aware Retrieval**：分词、stemming、stopwords、技术 token 处理由 Analyzer Release 管理。
23. **Hybrid Retrieval by Default**：技术语料默认 BM25 + Vector + RRF，Reranker 是可降级增强层。
24. **Retrieval Scope Is First-Class**：检索范围必须在召回层强约束，不用 Prompt 暗示替代数据库/索引过滤。
25. **Generation Instead of Destructive Rebuild**：索引升级后台构建新 Generation、验证、原子切换，禁止生产 drop-and-recreate。
26. **Web 管理是平台能力**：Coverage、失败、版本、成本、Recipe、Schema、Filter、Ingestion、Generation、实验和 Release 都可运营。
27. **Security on Every Hop**：起始 URL、Redirect、Browser navigation 每跳重新执行 SSRF/Egress/Scope 校验。
28. **Ephemeral State Is Not Truth**：Crawl4AI cache、Browser session、Worker 内 dispatcher state 不承载决定性业务状态。
29. **One Durable Task System**：PostgreSQL durable state + Transactional Outbox + Redis Streams 是统一业务任务体系，不并存互相竞争的第二套任务真相。
30. **Ingress-neutral Corpus**：`SOURCE_CRAWL`、`MANUAL_URL`、`FILE_UPLOAD` 以及 HTML/PDF/MD/TXT 只影响解析路由，不决定逻辑语料库或向量 Collection；进入 Canonical IR 后共享同一索引契约。
31. **Stable Query Target**：URL scope 必须先解析为内部 `document_id/document_version_id`；Query Plane 不重新 HEAD/GET 远程 URL，不根据“此刻的 MIME”选择索引。
32. **Compiled Query Runtime**：Haystack/LlamaIndex 等只作为 Query/RAG 编排 Adapter；Pipeline、模型客户端和 Store 客户端按 Retrieval Release 长生命周期复用，不在每个请求中重建。
33. **Benchmark Before Switch**：Analyzer、Chunk、Embedding、Vector Index、RRF、Reranker、Context Policy 升级均通过固定回归集后切生产。

### 3.1 真相边界

```text
PostgreSQL + Object Storage = Truth
Redis Streams              = Transport
OpenSearch / Vector Engine = Rebuildable Projection
Canonical Markdown         = Rebuildable Projection
Filtered/Fit Markdown      = Rebuildable Projection
Chroma                     = Optional Dev Projection Adapter
Haystack/LlamaIndex        = Query/Index Orchestration Adapter
Crawl4AI cache/session     = Ephemeral Execution State
Dispatcher/RateLimiter     = Worker-local Execution State
Common Crawl / Archive     = External Evidence / Optional Snapshot Origin
```

任何决定性业务状态不得只存在 Redis、搜索引擎、向量库、本地 cache、Browser session、Haystack Pipeline、Filtered Markdown 或 Worker 内存中。

## 4. 技术选型

### 4.1 控制面

- **FastAPI + Pydantic**：REST/Command API、Schema 校验、内部服务接口；
- **PostgreSQL**：Source、Profile、Run、Task、Coverage、URL Observation、Resolution、Probe、Fetch、Document、Version、Projection、Ingestion、Release、Audit、Outbox；
- **Transactional Outbox**：数据库状态变更与消息发布事务一致；
- **Redis Streams**：consumer group、retry、backpressure，只做任务运输；
- **React/Vue + TypeScript**：Web 管理台。

### 4.2 抓取与抽取

- **HTTPX / aiohttp**：HTML、Feed、Sitemap、API、Conditional GET、Range GET、跳转解析；
- **libmagic/python-magic 等价能力**：文件签名辅助 MIME 判定；
- **BeautifulSoup / lxml / CSS / XPath / Regex**：wrapper、meta refresh、selector、结构化抽取；
- **Trafilatura / Readability**：确定性正文候选；
- **PDF Parser + OCR fallback**：文本型 PDF 确定性解析，扫描型才 OCR；
- **Crawl4AI / Playwright**：动态页面、URL Seeding、Prefetch、Browser Interaction、Markdown Candidate、Browser fallback；
- **S3 / MinIO**：raw response、HTML、Rendered DOM、PDF、WARC、Canonical IR、Markdown、Asset、fixture、debug artifact。

Crawl4AI 的 `raw_markdown`、`fit_markdown` 只能作为 Extraction Candidate / Projection，不能替代 Snapshot 与 Canonical IR。

### 4.3 历史发现

- CMS API / Sitemap / RSS / Atom / JSON Feed；
- Archive / Category / Tag / Author / Docs TOC；
- Common Crawl URL Index；
- DuckDB / Athena / Spark / Polars 用于大批量历史索引扫描。

### 4.4 检索与 RAG

- **OpenSearch**：生产 BM25、过滤、聚合、Alias/Generation、Hybrid Search；
- **pgvector / OpenSearch kNN**：首期向量实现；
- **Qdrant / Milvus**：向量规模或独立扩缩容需求提高后替换；
- **Chroma**：开发、PoC、本地单机 Adapter，不作为生产事实存储；
- **RRF**：默认融合；
- **Cross Encoder Reranker**：可选精排服务；
- **Haystack/LlamaIndex**：Query/RAG 编排 Adapter，Pipeline 按 Retrieval Release 编译和缓存，不持有唯一业务状态。

### 4.5 可观测与部署

- Prometheus + Grafana + OpenTelemetry；
- Docker / Kubernetes；
- Artifact Registry 固定应用镜像、浏览器内核、Embedding/Reranker 模型和运行时依赖。

## 8. 统一 Document Ingress 与手工摄取

### 8.4 Ingress-neutral Corpus Contract

资源类型决定的是 parser/extractor，不是语料库身份：

```text
HTML_DOCUMENT     ┐
PDF_DOCUMENT      │
TEXT_DOCUMENT     ├─> Canonical IR -> Chunk Release -> Active Index Generation
MARKDOWN_DOCUMENT │
JSON_API          │
XML_FEED          ┘
```

禁止按输入形态长期维护：

```text
url-index
file-index
pdf-index
markdown-index
```

这些名称把“传输/解析类型”错误升级成“检索业务边界”，会造成跨资源搜索、版本升级和 Scope 管理复杂化。

物理拆分只允许由真正的兼容性/隔离需求决定，例如：

- Embedding dimension / model release 不兼容；
- tenant / authorization 安全边界；
- region / residency；
- 大规模容量分片；
- 独立生命周期或索引引擎约束。

`origin`、`content_kind`、`source_id`、`document_id` 均作为索引 payload metadata。

## 9. 新站接入 PROBE

新增站点先 PROBE，不直接深爬：

1. 规范化 entry URL，确定 domain、allowed origins、scope；
2. 获取 robots 和 Sitemap 声明；
3. 探测 Sitemap Index / Sitemap；
4. 探测 RSS / Atom / JSON Feed；
5. 探测 WordPress REST、Ghost、Substack 等平台能力；
6. 识别 Archive、Category/Tag/Author、Blog Index、Docs Navigation、pagination；
7. 低成本查询 Common Crawl；
8. 对 URL path 做模板聚类；
9. 对未知 hub 做轻量 HTML + links Prefetch；
10. 小预算 BFS / BestFirst 探索未知结构；
11. 抽样比较 HTTP 与 Browser 正文质量与成本；
12. 检测 wrapper、short-link、meta refresh、JS redirect；
13. 对 HTML/PDF/JSON/Feed 代表 URL 执行 Resource Probe；
14. 动态历史列表生成候选 Interaction Recipe；
15. 对重复 DOM 生成候选 Structured Schema，并用 fixture 校验；
16. 推断语言、Analyzer、Content Filter 和 article template；
17. 自动生成首版 Profile，在 Web 审核后启用。

Prefetch 只用于轻量发现、分类和路由决策，不是正文 Snapshot。

## 12. URL Normalization、Resolution 与 Stable Alias

### 12.1 Normalization

典型规则：lowercase host、default port removal、fragment removal、path slash normalization、安全 percent-encoding、query key ordering、tracking param removal、站点级 semantic param allowlist。

## 15. 调度、`arun_many()` 与 Worker 并发模型

Crawl4AI `arun_many()` / Dispatcher 只负责单 Worker 内并发、内存保护和本地速率控制，不能替代平台 durable scheduler。

### 15.1 两层调度

```text
平台 Scheduler
  global token bucket
  + registrable-domain token bucket
  + source token bucket
  + route/provider budget
  + priority
  + durable Task / lease / fencing / retry / next_run_at
        ↓
HTTP / Browser / Probe Worker
  MemoryAdaptiveDispatcher / SemaphoreDispatcher
  + RateLimiter
        ↓
AsyncWebCrawler.arun_many(stream=True) / HTTP batch
```

429/503、`Retry-After` 写回 Task 的 `next_run_at`，不能只在 Worker 内 sleep。

### 15.2 小批 lease + 单 URL 流式提交

```text
lease N tasks
 -> build per-URL config
 -> stream results
 -> persist per URL FetchAttempt/Snapshot/failure
 -> commit transaction
 -> ack per URL
```

一个 URL 失败、超时或取消不能回滚整个 batch。禁止一个长事务包住整个批次。

### 15.3 自适应批大小

根据 Worker 可用内存、DOM/PDF 大小、Browser context 数、CPU、流式消费速度、域名限流、大文件比例动态调整，不固定 `batch_size=1000`。

### 15.4 Lease 与 Fencing

```text
task_id
lease_owner
lease_until
fencing_token
attempt_no
next_run_at
```

过期 Worker 写结果时必须被 fencing token 阻止。

## 22. Chunk 设计与统一 Chunk Release

### 22.1 主策略：Structure-aware

默认：

1. Heading / Section 是第一层语义边界；
2. 段落、列表、引用尽量完整；
3. fenced code 默认不拆；
4. 表格默认不拆；
5. PDF 尽量按章节/页内块语义切分；
6. 保存 heading path、page range、block range；
7. 超长代码/表格走专门策略；
8. 超长普通 section 再进入 recursive fallback；
9. 长度以目标 Embedding tokenizer 的 token 计数为主。

HTML、PDF、Markdown、TXT 都在 Canonical IR 后进入同一 `chunk_release` 契约，禁止各 parser 自己形成不兼容的最终 Chunk 粒度。

固定 `split_by=word + 2000 words + 500 overlap` 只适合教程，不作为生产默认值；Chunk Size/Overlap 通过检索评测和成本评测决定。

### 22.2 稳定 Chunk ID

禁止：

```text
hash(file_path + chunk_index)
hash(source + chunk_index)
```

推荐：

```text
chunk_id = hash(
  document_version_id
  + chunk_release_id
  + logical_block_range
  + normalized_text_hash
)
```

文档头部新增内容不能导致全部后续未变化 Chunk 被误判为新 Chunk。

## 27. Query Runtime / Haystack 编排生命周期

Haystack、LlamaIndex 或自研 Pipeline 都只负责执行图，不成为唯一业务状态源。

### 27.1 启动/发布流程

```text
Query Service startup / Retrieval Release activation
 -> load active Query Runtime Release
 -> initialize long-lived BM25/Vector clients
 -> initialize query embedder / reranker / generator clients
 -> build pipeline graph
 -> warm-up fixtures
 -> mark runtime READY
 -> atomically switch active runtime pointer
```

### 27.2 请求流程

```text
request
 -> auth
 -> resolve stable scope
 -> select active retrieval/query runtime release
 -> inject query + filters + top_k + token budget
 -> execute cached pipeline
 -> persist retrieval trace
 -> return result
```

禁止每请求重新创建完整：

```text
Pipeline
DocumentStore client
Embedding model client
Retriever
PromptBuilder
Generator client
```

否则会造成连接抖动、对象初始化开销、版本漂移和额外延迟。

Pipeline cache key：

```text
retrieval_release_id + query_runtime_release_id + tenant/security boundary
```

Release 切换时新旧 runtime 并存一小段时间；新 runtime warm-up/验证通过后原子切换，旧 runtime 等 in-flight 请求结束后回收。

Query API **不得隐式同步抓取远程 URL**。RAG 生成模型只消费经过 scope 限制和版本明确的 Retrieval Context，不自行访问网络。

## 29. Reranker 与 Context Assembly

```text
大规模粗召回
 -> Top-N 融合候选
 -> Cross Encoder Reranker
 -> Top-K
 -> Context Assembly
```

Reranker 不扫描全库。独立 `rerank-service` 模型常驻、dynamic batch、最大 batch token、GPU 并发限制、OOM 自动降 batch；超时降级到 RRF，不进入 Source Sync 关键路径。

Context Assembly 根据 document diversity、heading path、chunk adjacency、same-document overlap、token budget、source trust、duplicate suppression、scope consistency 组装，避免 Top-K 全来自同一文章相邻 Chunk。

## 30. Index Generation 生命周期

禁止生产 Index `drop-and-recreate`。

```text
BUILDING
 -> VALIDATING
 -> READY
 -> ACTIVE
 -> RETIRED
```

触发新 Generation：

- Chunk Release 变化；
- Analyzer Release 变化；
- Embedding 模型/维度/metric 变化；
- Vector Index Release 变化；
- OpenSearch schema 变化；
- 检索数据模型变化。

流程：

```text
创建新 Generation
 -> 后台批量构建
 -> 离线回归验证
 -> READY
 -> Alias/逻辑指针原子切换
 -> 观察窗口
 -> 旧 Generation RETIRED
```

RECHUNK / REEMBED / REINDEX 优先使用已有 Snapshot / Canonical IR，不重新抓源站。旧 Document Version 向量不能在 Active 查询中误召回。

## 33. 安全与合规

- 遵守 robots 与站点访问策略；
- 不绕过登录、付费墙、验证码、WAF 或明确访问控制；
- 默认仅允许 http/https；
- 起始 URL、redirect、Browser navigation 每跳执行 DNS/IP/Egress 校验；
- 阻止 private、loopback、link-local、metadata 目标；
- 跨域跳转按 Source Policy 判断；
- DNS rebind 风险下连接前后都校验解析结果；
- Manual Ingestion 同样执行完整 SSRF 校验；
- 限制 redirect、响应大小、PDF/附件大小、解压比、Browser wall-clock、OCR 页数；
- 禁止 `file://`、`gopher://` 等非允许 scheme；
- Browser Worker 独立隔离网络、CPU、内存、wall-clock；
- Secret 进入 Secret Manager；
- Archive 恢复明确标记来源；
- 高风险 Web 操作用强类型 Command API、RBAC、Audit；
- 文件上传做 MIME/签名校验和恶意内容隔离，绝不执行附件代码。

### 33.1 Query Plane 最小权限

Query Service 原则上不需要访问公共互联网：

```text
allow: PostgreSQL / OpenSearch / Vector Engine / internal model services
block: arbitrary outbound HTTP to user-supplied URL
```

URL scope 只访问内部 alias table，从架构上消除“问答请求触发远程 URL 探测”的 SSRF 面。

## 38. 验收标准

### 38.1 Coverage

- 每个 Source 有可解释 Provider；
- FULL_BACKFILL 有 exhaustion evidence；
- known gap 可枚举、可重跑；
- 达到预算不会错误标 COMPLETE；
- Common Crawl 不作为完整性证明。

### 38.2 Resource Probe / 多类型资源

- 无扩展名 PDF 正确识别；
- `.pdf` URL 302 到 HTML 不进入 PDF parser；
- HEAD 不支持时受控 fallback；
- Content-Type 错误时结合文件签名纠正或进入冲突审核；
- HTML/PDF/TXT/MD/JSON/Feed 进入正确 extractor；
- 超大文件、压缩炸弹、异常 MIME 被预算/安全策略拦截；
- Route Hint 与 Probe 冲突可追踪。

### 38.3 增量

- Feed/API/Sitemap 新文章在目标 SLA 内进入系统；
- 304 不重复抽取、建版、投影；
- PDF/文件未变化不重复解析；
- 未变化 Projection 不重复计算；
- Reconcile 能发现 Feed 窗口外遗漏和结构漂移。

### 38.4 Browser / Batch

- Browser 不是默认抓取路线；
- 动态 Discovery Surface 可独立 Browser，正文仍优先 HTTP；
- Recipe 可版本化、diff、回滚；
- click/scroll/wait 有预算和停止条件；
- 批处理结果按 URL 独立提交；
- stream 提前关闭、Worker SIGTERM 后资源可靠释放；
- 未 ack task 可重放；
- Crawl4AI cache/session 不承载持久业务状态。

### 38.5 Schema / Markdown / Filter

- Schema 有 fixture、必填字段、zero-match 告警；
- title/author/time、正文、heading、code/list/table/image/link 有抽样质量验证；
- PDF/Markdown 原生结构尽量保留；
- Markdown 可从 IR 确定性重建；
- query-dependent `fit_markdown` 不作为 canonical；
- LLM Extraction 失败不影响 canonical。

### 38.6 Manual Ingestion

- `POST /ingestions` 返回 202 + durable ingestion ID；
- 相同 Idempotency-Key 不重复创建 Run；
- Web 展示单 URL 全链路阶段状态；
- Manual URL 同样执行 SSRF/Scope/robots/大小预算；
- canonical READY、Embedding 未完成时可 `PARTIAL_READY`；
- Query API 不隐式访问远程 URL。

### 38.7 Chunk / Embedding

- HTML/PDF/MD/TXT 使用统一 Chunk Release；
- Chunk 保留 heading path、page/block range；
- fenced code 与表格默认不破坏；
- Chunk ID 不依赖 chunk_index；
- RECHUNK 不创建新 Document Version；
- REEMBED 不重新抓源站；
- Embedding backlog 不影响 Source Sync；
- 向量维度、NaN/Inf、归一化、Release/Generation 不一致写前拦截；
- 单条坏向量不导致整批回滚；
- Vector Store deterministic ID 幂等 upsert。

### 38.8 检索、Scope 与统一 Corpus

- 中文/英文/技术 token 有固定回归集；
- CJK 不依赖 whitespace tokenizer；
- BM25 + Vector + RRF 可解释；
- DOCUMENT/SOURCE/VERSION Scope 不召回范围外 Chunk；
- URL scope 通过内部 alias 解析成 Document/Version，不访问远程 URL；
- 摄取 URL A、URL B 后对 A 提问不会召回 B；
- 摄取 PDF A、PDF B 后对 A 提问不会召回 B；
- ALL/SOURCE scope 能同时召回 HTML、PDF、Markdown，而不是被 `url-index/file-index` 割裂；
- 旧 Document Version 向量不会出现在 Active 查询；
- 新 Generation 验证通过后才能 ACTIVE；
- 生产升级无 drop-and-recreate。

### 38.9 Query Runtime

- Query Service 不为每个请求重建完整 Haystack/LlamaIndex Pipeline；
- DocumentStore/Vector/Embedding/Generator Client 可复用且有健康检查；
- Query Runtime 与 Retrieval Release 可追踪；
- 新 Runtime warm-up/验证后再切 active；
- Runtime 切换不破坏 in-flight 请求；
- Pipeline cache hit rate 可观测。

### 38.10 可靠性与安全

- Worker 崩溃后 lease 可恢复；
- fencing 阻止过期 Worker 覆盖结果；
- fan-out 保留 partial success；
- Browser session 丢失不丢 durable checkpoint；
- Embedding/Index/Reranker/LLM 故障不阻塞 Source Sync；
- Runtime/Model Artifact 可复现、可回滚；
- Query Plane 无任意公网 URL 访问权限；
- 所有高风险管理操作可审计。

## 39. 最终架构原则

1. Coverage First：先证明“应该有哪些 URL”，再看抓取成功率。
2. Discovery Before Fetch：发现、分类、去重后再抓正文。
3. Authoritative First：权威来源优先，Archive/Common Crawl 只补洞。
4. URL Is Locator：资源类型由实际响应证据决定，不由扩展名决定。
5. Route Hint + Probe Evidence：静态规则给 hint，运行时 MIME/签名决定最终路由。
6. HTTP First, Browser Last：Browser 是昂贵兼容层，不是默认抓取器。
7. Recipe, Not Site Code：动态交互版本化、可测试、可回滚。
8. Stream and Commit Per URL：批任务单 URL 持久化和 ack，partial success 不丢失。
9. Snapshot First, Replay Later：原始网络事实不可变，规则升级优先离线重放。
10. IR First, Markdown as Projection：Markdown 可重建，不是真相源。
11. LLM Is Projection, Not Truth：LLM 抽取/摘要可失败，不阻塞 canonical。
12. Unified Chunk Release：资源解析不同，但最终检索 Chunk 契约统一。
13. Stable Chunk Identity：Chunk 身份不依赖 file path + chunk_index。
14. Streaming Embedding：批次、lease、checkpoint、幂等，不全库一次性加载。
15. Validate Before Vector Write：向量维度、有限数值、归一化和 Release 写前校验。
16. Language-aware BM25：生产全文检索有版本化 Analyzer。
17. Hybrid Retrieval by Default：BM25 与 Vector 互补，RRF 为稳定融合基线。
18. Ingress-neutral Corpus：HTML/PDF/MD/TXT 不因输入形态分裂成长期独立 Collection。
19. Stable Query Target：URL scope 先映射内部 Document/Version，Query 不探测远程 URL。
20. Hard Scope Filter：Scope 在 BM25/Vector 召回层强制执行，选择 Collection 或 Prompt 都不能替代。
21. Typed Retrieval Scores：不同阶段 raw score 带 score type，不跨阶段硬比数值。
22. Compiled Query Runtime：编排图与客户端按 Release 长驻复用，不每请求重建。
23. Reranker as Optional Service：精排可降级，不进入事实同步关键路径。
24. Generation Instead of Destructive Rebuild：后台构建、验证、原子切换。
25. Async Command API：长任务 202 + durable ID，后台执行，前台查状态。
26. Projection Readiness Is Explicit：允许 canonical READY、Embedding PENDING。
27. One Durable Task System：PostgreSQL + Outbox + Redis Streams 维护统一业务任务真相。
28. Release Everything：策略、Probe、Recipe、Schema、Filter、模型、索引、Query Runtime、浏览器均可追踪和回滚。
29. Ephemeral State Is Not Truth：cache、browser session、dispatcher、orchestrator object 不是业务真相。
30. Benchmark Before Switch：任何检索升级经过固定 judgment set。
31. Source Sync 与 AI 解耦：抓取事实不依赖 Embedding、Reranker、LLM 或 Search 服务。
32. Evidence Everywhere：所有重要判断均保存可解释证据。
33. Security on Every Hop：Ingestion 每跳校验，Query Plane 不访问任意外部 URL。
34. Web 管理是平台能力：Coverage、质量、Probe、Recipe、版本、成本、Ingestion、Scope、Generation、Runtime 和 Release 都可运营。
