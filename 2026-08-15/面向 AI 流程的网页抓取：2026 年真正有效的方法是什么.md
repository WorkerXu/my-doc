# 面向 AI 流程的网页抓取：2026 年真正有效的方法是什么

## 1. 调研对象

- 编号：42
- 原文：Web Scraping for AI Pipelines: What Actually Works in 2026
- 作者：Pankaj Jaiswal / 47Billion
- 发布时间：2026-06-30
- 原文地址：https://medium.com/47billion/web-scraping-for-ai-pipelines-what-actually-works-in-2026-f468b1119abc
- 背景：47Billion 在 7Seers AI 教育/就业平台中建设实时 Web 内容管线的工程复盘

本文不是一个“万能爬虫”教程，而是一篇失败驱动的架构总结：单纯 HTTP 抓取会在客户端渲染页面上产生“200 成功但正文为空”的静默失败；全部切换浏览器又会带来显著资源成本、限流、访问挑战和维护成本；固定 CSS selector 会因页面模板变化产生更隐蔽的静默退化。最终合理方向是按证据分层路由、按质量逐级提取、把内容有效性独立验证，并对成本、漂移和访问限制建立长期治理机制。

对于“约 1000 个技术博客抓取全量历史文章并持续增量同步”的目标，本文最大的价值不是某个具体库，而是四个架构原则：

1. 获取成功与内容成功必须分离；
2. HTTP 与 Browser 必须按证据路由，而不是二选一；
3. 抽取器需要 fallback，同时还必须有漂移检测；
4. 最终知识内容必须可验证、可回放、可追溯，不能把某次 Markdown 输出当作唯一真相。

## 2. 原文的失败演进与核心架构

### 2.1 Attempt 1：HTTP + BeautifulSoup

原文最初使用普通 HTTP 请求加 HTML parser。静态页面可以正常工作，但现代 SPA/CSR 页面常只在初始 HTML 中返回壳结构，真正正文由 JavaScript 后续加载。

危险点不是请求失败，而是：

```text
HTTP 200
DOM 合法
parser 无异常
正文为空或极少
pipeline 仍继续
LLM 收到空/残缺内容
```

这类 silent failure 比显式异常更危险，因为它会被后续系统误认为可信内容，并最终污染 RAG、摘要、报告或知识库。

因此业务状态不能只有：

```text
FETCH_SUCCEEDED
```

而至少要拆成：

```text
TRANSPORT_SUCCEEDED
RENDER_SUCCEEDED
EXTRACTION_SUCCEEDED
CONTENT_FITNESS_PASSED
QUALITY_PASSED
PUBLISHED
```

前一状态成功不能推导后一状态成功。

### 2.2 Attempt 2：全部使用 Playwright

浏览器执行 JavaScript 后能解决很多动态页面，但它把问题从“拿不到正文”转化成“计算资源、页面就绪、限流、访问挑战和运维成本”。

原文给出的浏览器内存数字和代理成功率属于其环境观察，不能直接作为我们的容量参数；真正应进入方案的是“Browser 是昂贵资源，必须测量真实成本，并只在需要时升级”的原则。

对 1000 站系统，如果所有 URL 都直接进入 Browser，会出现：

- Browser pool 很快成为吞吐瓶颈；
- 单站慢页面拖长全局 queue lag；
- Chromium crash/timeout 形成大量重试风暴；
- 增量任务被历史回灌挤压；
- 资源扩容成本随 URL 数近似线性增长；
- Browser 本地并发控制无法解决跨 Worker、跨站点的公平性。

所以 Browser 不能是默认路径，而应是可解释的升级路径。

### 2.3 最终：Layered Architecture

原文最终采用概念上的分层：

```text
URL
 -> Decision Router
    -> Static HTML -> HTTP parser
    -> Dynamic/JS -> Browser renderer
 -> Extraction
    -> deterministic extraction
    -> Crawl4AI Markdown/JSON
    -> LLM extraction fallback
 -> clean structured content
 -> AI/RAG
```

对于知识库系统，需要继续向前和向后扩展：

```text
Discovery/Coverage
 -> Admission/Policy
 -> HTTP Probe
 -> Preflight Decision Router
 -> HTTP or Browser/PDF/API
 -> Immutable Snapshot
 -> Extraction Candidate Set
 -> Content Fitness Gate
 -> Extraction Drift Sentinel
 -> Canonical Document IR
 -> Deterministic Quality Validator
 -> Versioning/Index/Publish
```

这才是可以长期运行的生产形态。

## 3. HTTP-first Preflight Decision Router 的实现原理

### 3.1 为什么不能用域名白名单简单决定 Browser

同一个站点内部也可能同时存在：

- 服务端渲染博客文章；
- 客户端渲染搜索页；
- 静态 Markdown 文档页；
- JS 驱动的 Load More 列表；
- PDF/JSON/API 链接。

因此 `site.use_browser=true` 粒度过粗。正确做法是“站点 profile 提供先验，单 URL Probe 提供证据”。

### 3.2 HTTP Probe 最低采集指标

第一次请求应保存不可变 raw response，并计算：

```text
status
final_url
content_type
content_length
etag
last_modified
body_hash
html_chars
script_count
noscript_text_chars
main_candidate_text_chars
heading_count
paragraph_count
semantic_block_count
structured_data_presence
canonical
title
content_density
boilerplate_ratio
```

同时执行低成本 extraction probe：

```text
JSON-LD / OpenGraph / meta
selectolax / lxml DOM probe
Trafilatura / Readability candidate
Crawl4AI 非浏览器/LXML candidate（如适用）
```

### 3.3 Browser escalation 必须有原因码

建议标准原因：

```text
EMPTY_ARTICLE_BODY
SPA_SHELL
CLIENT_RENDER_MARKER
JS_PAGINATION
LOAD_MORE
INFINITE_SCROLL
SHADOW_DOM_REQUIRED
NAVIGATION_NOT_VISIBLE
HTTP_CONTENT_FITNESS_FAILED
```

每个抓取 attempt 记录：

```text
route_decision
route_reason[]
router_release_id
probe_metrics
estimated_cost_class
```

这样管理端可以真正回答：某站为什么用了 Browser、HTTP 能否替代、升级率是否异常、升级后内容增加了多少。

### 3.4 Router 不是一次性规则，而是可校准模型

对每站持续统计：

```text
http_success_rate
http_content_fitness_pass_rate
browser_escalation_rate
http_vs_rendered_content_delta
browser_timeout_rate
browser_cost_per_document
```

长期 HTTP 质量高的站应降低 Browser 预算；长期 HTTP 内容不足的特定 page type 可以直接绑定 Browser profile，但保留周期 Probe，防止网站改版后仍永久走昂贵路径。

## 4. Browser Readiness：加载完成不是“网络安静”

原文使用 Playwright 解决动态渲染，但生产系统需要比“启动浏览器并等待”更严格的 readiness contract。

Playwright 当前官方文档明确把 `networkidle` 标为 discouraged。原因在工程上很直观：埋点、WebSocket、广告、长轮询可能让网络长期不空闲；反过来，网络空闲也不代表目标正文已经完整。

建议版本化：

```text
browser_action_plan_release
  wait_until: domcontentloaded | load
  wait_for_css
  wait_for_js
  min_main_text_chars
  delay_before_snapshot
  scroll_plan
  max_scroll_rounds
  load_more_plan
  timeout
  session_policy
  resource_block_policy
```

优先级：

```text
HTTP 已完整
 -> domcontentloaded
 -> domcontentloaded + stable article selector
 -> explicit JS readiness condition
 -> bounded scroll/load-more action plan
 -> 特殊站点才考虑 networkidle
```

关键原则：Browser 本身返回 success 不等于页面 ready。必须把 readiness evidence 和渲染 DOM 一起保存。

## 5. Crawl4AI 在系统中的正确边界

原文把 Crawl4AI 作为面向 AI 的主要 extraction 工具，这个方向合理，但不能让框架承担整个业务系统的状态真相。

建议封装为 Adapter：

```text
Background Task
 -> Crawl4AI Adapter
 -> CrawlResult
 -> Immutable Artifact Commit
 -> Extraction Candidate Writer
 -> Fitness/Quality Validator
```

系统自身继续负责：

- durable frontier；
- run context；
- lease/heartbeat；
- domain quota；
- retries/dead-letter；
- completeness/coverage；
- document identity/version；
- publish state。

Crawl4AI 官方 `arun_many()` 支持 streaming，以及 MemoryAdaptiveDispatcher/SemaphoreDispatcher。正确使用方式是单 Worker 小批 claim 后流式消费，例如：

```text
DB claim 20~100 tasks
 -> group by domain/profile
 -> arun_many(stream=True)
 -> each result persisted immediately
 -> release/extend lease
 -> claim next batch
```

不要把百万 URL 一次性放进一个进程。MemoryAdaptiveDispatcher 解决的是 worker-local 资源自适应，不等于全局调度器。

## 6. Raw Markdown、Fit Markdown 与 Canonical Document IR

Crawl4AI 官方文档支持 `raw_markdown`，使用 Pruning/BM25 等过滤时还能得到 `fit_markdown/fit_html`。这非常有价值，但 fit 结果不能直接作为业务真相。

原因：内容过滤器的目标是降噪，不是证明语义完整。技术文章中的以下块容易被误伤：

- 短代码片段；
- CLI 参数；
- API 返回值说明；
- 表格；
- 脚注；
- 引用；
- 只有一两句的警告块。

建议每次抓取保存：

```text
RAW_HTTP or RENDERED_DOM
CLEANED_HTML
RAW_MARKDOWN
FIT_MARKDOWN
FIT_HTML
metadata
links/media
```

然后统一转成 Canonical Document IR：

```text
Document
  metadata
  blocks[]
    heading
    paragraph
    list
    quote
    code_block
    table
    image
    link
    embed_placeholder
```

最终 Markdown 由版本化 renderer 从 IR 生成。这样将来更换 Crawl4AI、Trafilatura、Readability、LLM 或 Markdown renderer 时，可以用已有 Snapshot 离线 replay，而不必重新访问源站。

## 7. Content Fitness Gate：解决最危险的 silent failure

Transport/Browser/Extractor 都成功后，必须经过独立 Content Fitness Gate。

建议最少计算：

```text
main_text_chars
semantic_block_count
heading_count
paragraph_count
code_block_count
table_count
link_density
boilerplate_ratio
content_density
title_body_similarity
raw_to_clean_ratio
raw_to_fit_ratio
rendered_vs_http_delta
```

不能只用固定字数阈值，因为：

- 一条 API method 文档可能 100 字就完整；
- 一篇长技术博客只有 100 字通常明显异常。

因此阈值必须按 `page_type + site_profile + history baseline` 组合计算。

一个简单可解释模型：

```text
fitness_score =
  w1 * text_completeness
+ w2 * structure_score
+ w3 * title_body_consistency
+ w4 * expected_block_score
- w5 * boilerplate_penalty
- w6 * abnormal_shrink_penalty
```

其中 `abnormal_shrink_penalty` 特别重要：如果同一文档前一个 accepted version 有 6000 字、20 个代码块，本次只剩 400 字、0 代码块，即使 400 字超过全局阈值，也应该进入疑似退化状态。

## 8. 本次新增重点：Extraction Drift Sentinel

这是根据原文“broken selector 比 bot detection 更危险”的观点，对现有总体方案最值得补强的部分。

已有 Content Fitness 可以发现明显空正文，但 selector/template drift 还可能产生“看起来不空、实际上抓错区域”的结果，例如：

```text
原来 selector 命中 article body
网站改版
selector 仍能命中某个 div
抽到推荐文章/评论区/摘要
文本长度看起来正常
基础 Fitness 仍可能通过
```

因此需要独立的 Extraction Drift Sentinel。

### 8.1 模板与候选基线

按 `site + page_type + extraction_pipeline_release` 保存滚动基线：

```text
dom_structure_fingerprint
main_selector_match_count
main_text_chars_p50/p10/p90
heading_count_distribution
code_block_count_distribution
table_count_distribution
link_density_distribution
metadata_presence_rate
raw_fit_ratio_distribution
candidate_similarity_baseline
```

`dom_structure_fingerprint` 不应直接 hash 全 DOM，否则广告/时间戳都会导致变化。应只对语义相关骨架做归一化，例如：

```text
article/main/section/heading 标签树
稳定 class token 白名单
JSON-LD @type
关键 aria/role
正文容器相对路径
```

### 8.2 Shadow Extraction

生产中不需要所有页面都双跑昂贵 extractor。可以对每站按 1%~5% 或固定每日样本做 shadow extraction：

```text
Primary: versioned site selector
Shadow: Trafilatura/Readability/Crawl4AI generic extraction
```

比较：

```text
text_length_ratio
heading_overlap
code_block_delta
table_delta
link_overlap
paragraph_minhash_similarity
metadata_agreement
```

如果 Primary 持续与 Shadow 分歧，或自身历史结构突然漂移，就触发 drift event。

### 8.3 Drift 状态机

建议：

```text
HEALTHY
 -> SUSPECTED
 -> CONFIRMED
 -> QUARANTINED
 -> RECOVERED
```

触发规则不能只看单页。例如：

```text
连续 N 个同 page_type 样本异常
或 15 分钟/1 小时窗口异常率 > threshold
或 accepted candidate 出现显著结构退化
```

进入 `QUARANTINED` 后：

1. 不允许有问题的 selector candidate 自动覆盖现有 accepted version；
2. 临时回退到最近健康的 generic extraction 或上一个 selector release；
3. 创建自动 REPROCESS canary；
4. Web 管理端展示差异样本；
5. 新 selector release 必须通过 Golden Sample/Canary 才重新发布。

这样把“网页改版”从静默数据污染变成可观察事件。

### 8.4 为什么 Drift Sentinel 与 Fitness Gate 都需要

两者职责不同：

```text
Fitness Gate：这个候选内容本身是否像一个有效文档？
Drift Sentinel：这个 extractor 相比历史/对照组是否发生系统性偏移？
```

单页质量与系统性漂移不能互相替代。

## 9. Extraction Fallback Contract

原文指出固定 selector 会频繁失效，而 LLM extraction 更有结构韧性，但成本更高。对 1000 站系统应明确版本化 fallback：

```text
Tier 1  JSON-LD / OpenGraph / meta / Feed/API metadata
Tier 2  Trafilatura / Readability / generic DOM extraction
Tier 3  Crawl4AI raw/fit candidate
Tier 4  versioned site CSS/XPath contract
Tier 5  LLM Structured Extraction + JSON Schema
Tier 6  Manual Review
```

实际顺序可按站点配置；例如高稳定站点可先走 selector，再 shadow generic extractor。关键是：Worker 不允许无限自由 fallback，所有路径必须属于 run context。

LLM extraction 原则：

- 只处理确定性方法质量不足的页面；
- 输入 cleaned HTML/fit HTML，而不是整页原始 HTML；
- 使用 JSON Schema；
- 输出仍要进 deterministic validator；
- 记录模型、prompt/schema release、token/cost；
- LLM 成功不能直接覆盖历史高质量版本。

## 10. 浏览器计算成本是调度约束

原文强调 Browser 内存开销，设计上应把它变成资源类，而不是普通 task。

建议运行时分类：

```text
ASYNC_NATIVE
BLOCKING_IO
CPU_BOUND
BROWSER
PDF
OCR
VALIDATOR
```

Browser Pool 独立设置：

```text
max_runtime_age
max_pages_per_runtime
rss_restart_threshold
per_domain_concurrency
browser_quota
queue_priority
```

并采集：

```text
browser_pages_per_runtime
browser_peak_memory
browser_crash_rate
browser_timeout_rate
browser_cost_per_document
browser_queue_lag
```

若 Browser backlog 过高，系统应优先保证 INCREMENTAL 和已抓 Snapshot 的 extraction/validation，不应继续无限扩大历史 Discovery。

## 11. 访问挑战与合规边界

原文讨论了代理、指纹和行为模拟等访问挑战经验，但总体方案不应把“规避检测”做成默认能力。

对于长期知识库，更可维护的状态模型是：

```text
ROBOTS_DENIED
AUTH_REQUIRED
PAYWALL
WAF_CHALLENGE
CAPTCHA_CHALLENGE
RATE_LIMITED
TERMS_REVIEW_REQUIRED
```

处理原则：

- robots/政策明确拒绝时停止；
- 优先官方 API、RSS/Feed、授权数据源、站点导出或合作数据；
- 429/503 尊重 Retry-After 并站点级退避；
- CAPTCHA/登录/付费墙不进入无限 Browser retry；
- Access Challenge 与普通 render failure 分开统计。

这样避免“抓不到 -> 加更多浏览器/重试 -> 更容易被限制”的正反馈故障。

## 12. 对 1000 个技术博客全量历史抓取的扩展

本文重点是单 URL 获取/抽取，但用户目标还要求“历史抓全”。因此必须在其分层架构前增加独立 Discovery/Coverage 层：

```text
Sitemap/Sitemap Index
Feed/RSS/Atom/JSON Feed
Platform API
Archive by year/month
Category/Tag/Author pagination
DOC_NAVIGATION
HTML recursive frontier
Browser dynamic listing
```

每个 URL 保存 discovery evidence。FULL_BACKFILL 不能以“队列空了”作为唯一完成条件，而应要求：

1. 主要 Provider 完成或明确记录 gap；
2. durable frontier 无可执行 URL；
3. retry/dead-letter 已处理；
4. Reconcile 不再产生显著新增；
5. Coverage Ledger 无未知断档；
6. Finalizer 对 discovered/admitted/fetched/accepted 做集合对账。

## 13. 增量同步的正确模型

技术博客的旧文章也会更新，所以“Markdown 文件已存在”不能作为跳过条件。

增量信号建议：

```text
Feed/API cursor
Sitemap lastmod
Navigation hash
ETag
Last-Modified
raw body hash
Document IR hash
overlap window
Periodic Reconcile
```

数据模型需要分离：

```text
URL observation
 -> document identity evidence
 -> logical document
 -> append-only document_version
```

只有 accepted Document IR 实质变化才生成新版本；纯抓取时间或无关响应头变化不应制造版本噪声。

## 14. Web 管理端需要新增的漂移治理能力

在已有站点、Run、URL、质量、成本管理之外，建议增加：

### Extraction Health

按站点/page type 展示：

```text
primary_extractor
selector_release
shadow_extractor
extraction_disagreement_rate
dom_fingerprint_change_rate
main_text_p50_delta
code/table loss rate
fitness_failure_rate
drift_state
last_good_release
```

### Drift Event 详情

展示：

- 首次异常时间；
- 受影响 page type；
- Primary vs Shadow Markdown diff；
- DOM skeleton diff；
- 最近 accepted version 对比；
- suspect URL 样本；
- 当前 quarantine/fallback 状态；
- 发布新 extractor release、回滚和 REPROCESS 操作。

这能显著降低 1000 个站点模板变化后的人工排障成本。

## 16. 对现有总体方案的最终优化结论

现有方案已经覆盖本文最重要的主线能力：HTTP-first、按证据 Browser escalation、版本化 Readiness、raw/fit Markdown、Canonical Document IR、Content Fitness、LLM fallback、Browser 成本、访问挑战状态、增量同步和 Coverage。

本次调研确认这些方向正确，同时补强一个以前只在实施阶段笼统出现、但没有工程闭环的能力：**Extraction Drift Sentinel**。

新增后形成：

```text
HTTP/Browser 决策防止不必要的昂贵抓取
Content Fitness 防止单页空/残缺/过度裁剪
Extraction Drift Sentinel 防止 selector/template 系统性静默漂移
Deterministic Quality Validator 防止低质量候选成为 accepted version
```

四层共同解决原文最核心的问题：生产系统最危险的不是显式失败，而是“技术链路看似成功、知识内容事实上已经错了”。
