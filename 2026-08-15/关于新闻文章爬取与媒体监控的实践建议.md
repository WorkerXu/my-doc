# 关于新闻文章爬取与媒体监控的实践建议：实现细节与技术原理分析

## 1. 调研对象

- 编号：10
- 名称：关于新闻文章爬取与媒体监控的实践建议
- 原始地址：https://www.reddit.com/r/webscraping/comments/1lb2nbu
- 来源类型：Reddit 实践讨论
- 核心做法：以 Crawl4AI 为主要抓取工具，Trafilatura 与 BeautifulSoup 作为正文抽取/解析补充。

该讨论本身很短，但它指出了一个对 1000+ 技术博客知识库非常关键的工程事实：**“获取页面”和“判断正文”不是同一件事，单一库不应该同时承担 URL 发现、网络访问、浏览器执行、正文抽取、Markdown 生成、质量判定与增量版本管理。**

因此，这篇调研的重点不是比较三个 Python 库的 API，而是把它们放入一条可扩展、可审计、可替换的生产数据链路中，明确每个组件应该负责什么、不应该负责什么，以及如何通过多候选抽取避免静默错误。

---

## 2. 三类工具的职责边界

### 2.1 Crawl4AI：抓取与浏览器运行时，不是业务真相

Crawl4AI 的强项是网页获取和浏览器执行。其 `BrowserConfig` 与 `CrawlerRunConfig` 将浏览器启动参数和单次抓取行为分离，支持动态页面等待、滚动、JavaScript、CSS/XPath 结构化抽取、Markdown 生成、截图、MHTML 等能力。

在平台里适合承担：

1. 动态页面渲染；
2. `Load more`、滚动、等待异步 DOM 等确定性交互；
3. 浏览器会话和浏览器资源池；
4. 抓取后的 DOM、链接、媒体等执行结果；
5. 作为某一种结构化抽取候选；
6. 生成诊断用 raw Markdown / fit Markdown。

不应该承担：

1. Source、Run、Task、Retry、DLQ 的最终状态机；
2. 历史 Coverage 是否完整的判断；
3. URL 的长期唯一身份；
4. Canonical Document Version；
5. 最终质量判定；
6. 增量同步的业务语义；
7. 唯一 Canonical Markdown 生成来源。

原因是 Crawl4AI 的抓取成功只说明一次运行成功，不代表历史 URL 已抓全，也不代表抽出的文本就是正确正文。尤其 `fit_markdown` 本质上经过内容过滤，适合 RAG 适配或快速阅读，不应被当作不可变知识库事实。

### 2.2 Trafilatura：通用正文候选抽取器

Trafilatura 的核心价值是基于文档结构、正文密度和多级回退算法提取主内容，并且可以输出 TXT、JSON、Markdown、XML 等格式。它支持：

- `favor_precision`：宁可少取，也优先减少噪声；
- `favor_recall`：宁可多取，也尽量避免正文缺失；
- `with_metadata`：输出标题、作者、日期等元数据；
- `include_tables`、`include_images`、`include_links`；
- `prune_xpath`：在抽取前做确定性 DOM 裁剪；
- `bare_extraction()`：返回 Python 结构，适合作为 Canonical IR 的输入，而不是直接把 Markdown 当最终结果。

Trafilatura 特别适合成为平台的 **Generic Extractor**，但它仍然只是候选产生器。启发式算法升级后，某些网站可能从“抽取正确”变为“包含推荐区”或者“漏掉代码块”，因此必须记录版本并支持 replay。

### 2.3 BeautifulSoup/lxml：DOM 操作和站点级修复工具

BeautifulSoup 的定位应非常克制：它擅长遍历、搜索、修改 DOM，也支持 CSS selector 和 `get_text()`，但它不是一个自动正文识别算法。

适合：

- 找 JSON-LD、OpenGraph、`article`、`main`、`time` 等结构化节点；
- 做少量站点级 DOM 清洗；
- 删除订阅框、推荐区、分享栏等已知噪声；
- 从复杂节点中补标题、作者、日期等字段；
- 对异常 HTML 做调试和快速规则验证。

不适合：

- 对所有网站直接 `get_text()` 后作为正文；
- 把每个网站都写成大量 BeautifulSoup 特判代码；
- 只靠 CSS selector 判断正文正确性。

BeautifulSoup 官方文档也明确指出，如果需求只是 CSS selector，直接使用 lxml 通常更快。因此生产方案应把 BeautifulSoup 看成“DOM 维修工具箱”，而不是整个抽取平台。

## 3. 正确的生产流水线

推荐主链：

```text
Discovery
 -> URL Identity
 -> Fetch Policy
 -> HTTP Snapshot
 -> Browser Fallback（必要时）
 -> Immutable Artifact
 -> Extraction Portfolio
 -> Candidate Scoring / Agreement
 -> Canonical IR
 -> Quality Gate
 -> Document Version
 -> Markdown Renderer
 -> Search / Vector / Export
```

最重要的原则是：**Snapshot First, Extraction Later**。

同一个 Artifact 应允许在不重新访问原站的前提下，用新的 Trafilatura 版本、新的 selector、新的 Markdown Renderer 重放。这样才能解决 1000 个网站长期运行时最昂贵的问题：抽取算法会升级、站点会改版，但不应每次都重新抓取历史网页。

---

## 4. Extraction Portfolio：从“双轨”升级为“多候选组合”

仅有“Generic + Deterministic”还不够细。建议在 Extract Worker 中实现 Extraction Portfolio。

### 4.1 候选层级

```text
Candidate A: Structured Data
  JSON-LD / OpenGraph / Microdata / embedded state

Candidate B: Trafilatura Precision
  favor_precision=true

Candidate C: Trafilatura Balanced
  默认模式

Candidate D: Trafilatura Recall
  favor_recall=true

Candidate E: Deterministic Recipe
  CSS/XPath/字段级规则

Candidate F: DOM Repair + Generic
  lxml/BeautifulSoup 先清理已知噪声，再进入通用抽取

Candidate G: Crawl4AI Raw Markdown / cleaned HTML
  只作为对照和诊断，不直接成为 Canonical
```

不是每页都要运行全部候选。平台根据 Source Profile、历史质量、页面类型和成本进行选择。

### 4.2 逐级回退

普通静态文章：

```text
HTTP HTML
 -> Structured Metadata
 -> Trafilatura Precision/Balanced
 -> Quality PASS ? accept candidate
 -> 否则 Deterministic Recipe
 -> 仍失败才 Browser
 -> Browser Artifact 再跑同一 Extraction Portfolio
```

动态页面：

```text
HTTP shell 判定
 -> Browser Render
 -> 保存 Render Artifact
 -> Structured Data
 -> Trafilatura / Recipe
 -> Agreement
```

这样 Browser 只解决“拿不到真实 DOM”的问题，而不是承担“什么是正文”的全部责任。

## 5. 抽取尝试必须成为一等数据

建议增加：

```text
extraction_attempt
- extraction_attempt_id
- artifact_id
- source_release_id
- extractor_kind
- extractor_release
- mode: PRECISION | BALANCED | RECALL | DETERMINISTIC | REPAIR
- input_kind: RAW_HTML | RENDERED_HTML | CLEANED_HTML
- started_at
- finished_at
- status
- output_object_key
- title
- text_length
- paragraph_count
- heading_count
- code_block_count
- table_count
- link_density
- boilerplate_score
- language
- semantic_hash
- quality_score
- failure_reason
```

这个表解决三个长期问题：

1. 能解释“为什么今天抽出来和一个月前不同”；
2. 能比较不同 extractor 的真实收益；
3. 能在升级 Trafilatura/Crawl4AI/规则后跑 Golden Corpus 回归。

最终 `document_version` 只引用被 Quality Gate 接受的 Canonical IR，而不是直接引用某个库返回的 Markdown 字符串。

## 6. Candidate Agreement 的实现

多抽取器真正有价值的地方不是“备用”，而是互相校验。

建议比较：

### 6.1 字段一致性

- title 是否一致或高度相似；
- author 是否冲突；
- published_at 是否相差异常；
- canonical URL 是否一致；
- language 是否一致。

### 6.2 正文一致性

- normalized text similarity；
- token/character overlap；
- 段落数量；
- heading 层级；
- code block / table 保留数量；
- 首尾段是否匹配；
- 链接密度和导航词比例。

### 6.3 典型判定

```text
Trafilatura Precision 与 Deterministic 高一致
 -> 高置信通过

Precision 明显短，Recall 与 Deterministic 高一致
 -> Recall 候选更可信

Deterministic selector 命中，但正文与 Generic 严重偏离
 -> selector drift，进入 QUARANTINE

所有候选都只有很短内容
 -> 可能是 JS shell / 登录墙 / 错误页，触发 Browser 或失败分类
```

这比“selector 命中了所以成功”可靠得多，因为站点改版后 selector 很可能仍能命中一个错误区域。

## 7. Precision / Recall 策略应由内容类型决定

Trafilatura 的 precision/recall 不是简单的性能开关，而是质量策略。

### 技术博客正文

默认 `BALANCED`，代码/表格密集站点在 Golden Corpus 中验证是否需要 `RECALL`。

### 新闻/媒体监控

通常优先 `PRECISION`，因为推荐阅读、相关新闻、热榜一旦混入正文，会导致：

- 关键词告警误报；
- embedding 被无关文本污染；
- 同一推荐文章在大量文档中形成重复片段；
- 版本 hash 因推荐区变化而频繁变化。

### 文档站

往往需要 `RECALL` 或结构化 selector，避免漏掉短段落、API 参数、代码说明。

因此 Source Profile 可以加入：

```yaml
extraction:
  portfolio:
    - structured
    - trafilatura
    - deterministic
  trafilatura:
    mode: balanced
    include_tables: true
    include_comments: false
  fallback:
    on_low_quality: deterministic
    on_shell: browser
```

## 8. Crawl4AI Markdown 为什么不能直接作为 Canonical

Crawl4AI 可以直接生成 Markdown，这是非常方便的能力，但平台应把它作为 Candidate/Projection，而不是事实层。

原因：

1. Markdown Generator 本身会升级；
2. `fit_markdown` 可能经过 Pruning/BM25/LLM 等过滤；
3. Markdown 是最终表现形式，无法完整表达所有抽取中间事实；
4. 不同来源的表格、图片、链接、代码结构需要统一策略；
5. 未来需要重渲染时，应从 Canonical IR 生成，而不是重新爬网页。

正确做法：

```text
Crawl4AI result.cleaned_html / raw HTML
 -> Extractor
 -> Canonical IR
 -> Platform Markdown Renderer
```

Crawl4AI 的 `raw_markdown` 可以用于 debug 和候选对比；`fit_markdown` 可以作为 RAG 派生层，但不能替换 Canonical IR。

## 9. 媒体监控场景对增量同步的启发

“媒体监控”比普通一次性爬虫更接近本项目长期增量同步的真实需求。

### 9.1 发现和正文抓取必须拆开

高频增量应该先跑低成本 Provider：

```text
RSS/API
 -> sitemap lastmod/diff
 -> archive/listing 首页
 -> bounded browser discovery
```

发现新 URL 后才进入正文 Fetch Queue。

### 9.2 新文章和文章修改是两种事件

至少区分：

```text
NEW_URL
KNOWN_URL_UPDATED_HINT
KNOWN_URL_RECHECK
CONTENT_VERSION_CHANGED
METADATA_CHANGED
REMOVED_OR_MOVED
```

RSS `updated`、Sitemap `lastmod` 只属于 hint，最终是否生成新 Document Version 仍由 Canonical semantic hash 决定。

### 9.3 推荐区变化不能制造正文版本

这正是使用正文抽取器而不是全 DOM hash 的原因。页面广告、推荐文章、阅读数、评论数频繁变化，如果直接 hash HTML，会产生大量假更新。

正确比较：

```text
Artifact Hash != Content Version Hash

artifact.sha256          -> 页面抓取事实
canonical semantic_hash  -> 正文语义版本
metadata_hash            -> 元数据版本
```

## 10. BeautifulSoup 的合理使用方式

建议只保留三类 BS/lxml 逻辑。

### 10.1 Structured Metadata Adapter

```text
JSON-LD
OpenGraph
canonical link
article:published_time
article:modified_time
time[datetime]
```

多个来源冲突时记录 Candidate，不静默覆盖。

### 10.2 DOM Repair Recipe

例如：

```yaml
repair:
  remove:
    - .newsletter-box
    - .related-posts
    - .share-tools
    - nav
    - footer
  unwrap:
    - .syntax-wrapper
```

Repair Recipe 必须版本化，不能散落在 Python `if domain == ...` 中。

### 10.3 Diagnostic Extractor

在 QUARANTINE 页面展示：

- Raw HTML；
- Rendered DOM；
- Trafilatura 候选；
- Deterministic 候选；
- DOM Repair 后候选；
- Canonical IR diff。

这样人工修复一次后可以生成可测试的 Recipe，而不是直接手工改数据库正文。

## 11. 成本与吞吐

对 1000 站点，浏览器是最贵资源，因此调度必须遵循：

```text
HTTP First
 -> Generic Extraction
 -> Quality Gate
 -> Browser only if necessary
```

Extraction Portfolio 本身也不能无脑全跑。建议按质量历史自适应：

```text
稳定站点：1 个主 extractor + 1% shadow candidate
新站点：2~4 个 candidate 全跑
发生 Drift：提高 shadow 比例
修复后：Canary 通过再降回正常比例
```

这样既能持续检测静默漂移，又不会把每篇文章的 CPU 成本扩大数倍。

## 12. Web 管理端应增加的能力

Source -> Extraction 页面建议展示：

1. 当前 Extraction Portfolio；
2. Trafilatura mode 与版本；
3. Deterministic Recipe 版本；
4. 最近 candidate agreement 分布；
5. HTTP -> Browser fallback 比例；
6. 每个 extractor 的 PASS/WARN/QUARANTINE 比例；
7. 不同 candidate 的正文 diff；
8. Golden Corpus replay 结果；
9. Shadow extraction 采样比例；
10. Drift 告警。

新增 Release 时，不能直接修改 ACTIVE 配置，应先：

```text
compile
 -> golden replay
 -> live sample
 -> candidate
 -> canary
 -> activate
```

## 13. 建议的错误分类

至少区分：

```text
FETCH_NETWORK_ERROR
FETCH_RATE_LIMITED
FETCH_ACCESS_DENIED
FETCH_BROWSER_CRASH
FETCH_EMPTY_SHELL
EXTRACT_NO_CONTENT
EXTRACT_TOO_SHORT
EXTRACT_TOO_NOISY
EXTRACT_METADATA_CONFLICT
EXTRACT_CANDIDATE_DIVERGED
EXTRACT_SELECTOR_DRIFT
QUALITY_STRUCTURE_LOSS
QUALITY_DUPLICATE_CONTENT
```

错误分类决定后续动作：重试、Browser fallback、换 extractor、QUARANTINE 或人工修复，不应全部归为 `crawl_failed`。

## 14. 对当前博客知识库方案的具体优化结论

本调研不需要推翻现有“HTTP First、Browser Last、Generic + Deterministic、Candidate Agreement、Canonical IR”路线，但需要进一步细化为可执行模型：

1. 将 Crawl4AI 明确降级为 Fetch/Browser Adapter 和候选产生器，禁止其运行结果直接成为业务真相；
2. 将 Trafilatura 提升为首选 Generic Extractor，并对 `precision/balanced/recall` 建模；
3. 将 BeautifulSoup/lxml 固定为 Metadata/DOM Repair/Diagnostic 层；
4. 增加 Extraction Portfolio 与逐级回退策略；
5. 增加 `extraction_attempt` 事实表，记录每个候选的版本、输入、质量与失败原因；
6. 把 Candidate Agreement 从“两个 extractor 对比”扩展为“多个候选评分与仲裁”；
7. 增加 shadow extraction，以低比例持续检测站点静默改版；
8. 明确 `raw_markdown`/`fit_markdown` 不能成为 Canonical Markdown；
9. 将媒体监控式增量同步表达为事件和 hint，最终版本变化仍由 Canonical semantic hash 决定；
10. Web 管理端增加 extractor 级质量、成本、回退和 diff 可视化。

这些调整能让系统在新增网站、站点改版、抽取库升级和长期增量运行时，避免陷入“每个站一套脚本”和“爬成功却正文错了”的维护困境。
