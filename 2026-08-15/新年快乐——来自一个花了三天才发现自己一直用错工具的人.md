# 新年快乐——来自一个花了三天才发现自己一直用错工具的人：实现细节与技术原理分析

## 1. 调研对象

- 原文：Happy New Year from a Guy Who Just Spent Three Days Learning He Was Using the Wrong Tool
- 作者：Mustapha Liaichi
- 地址：https://medium.com/@mustaphaliaichi/happy-new-year-from-a-guy-who-just-spent-three-days-learning-he-was-using-the-wrong-tool-20bf0450e58c
- 发布时间：2026-01-02
- 主题：Crawl4AI 与直接使用 Playwright 在复杂、有状态、长时间运行的网页交互任务中的边界

这篇文章最有价值的结论不是“Playwright 比 Crawl4AI 更好”，而是：**面向内容抓取的高层抽象与面向有状态浏览器交互的低层控制，应被视为两类不同执行模型，并在平台层进行显式路由。**

对 1000+ 技术博客知识库而言，这个结论直接影响动态归档、年份筛选、标签页、Load More、无限滚动、分页组件等站点的长期稳定性、可恢复性和维护成本。

---

## 2. 原文案例复盘

原文任务是从 IMDb 抓取约 30,000 部电影的国家维度评分分布。单个电影并不是“打开页面后抓最终 DOM”即可完成，而需要：

1. 打开评分页；
2. 枚举国家 Tab；
3. 点击某个国家；
4. 等待图表切换到该国家数据；
5. 抽取评分分布；
6. 切换下一个国家；
7. 重复直到所有国家完成；
8. 再进入下一部电影。

每部电影通常要进行 5～7 次交互，理论量级约 150,000～210,000 次点击。作者最终报告实际执行约 167,000 次国家 Tab 点击，任务持续运行约 5 天。

作者最初使用 Crawl4AI，通过 Python 中的 JavaScript 字符串完成循环、点击、等待和抽取。简单交互时这种方式很方便，但复杂流程出现了明显的工程问题：

- Python 控制流与浏览器 JavaScript 控制流被拆成两层；
- 错误发生在 JS blob 中，Python 侧较难定位到具体业务步骤；
- 数据需要浏览器侧序列化后再返回 Python；
- 重试通常只能围绕整个调用，而不是围绕“第几个 Tab 的哪一步”；
- 固定 `setTimeout` 把页面状态同步退化成时间猜测；
- 复杂循环难以可靠 checkpoint；
- 长时间运行时，很难回答“哪个逻辑 item 已经提交、哪个可以安全重做”。

作者改为直接使用 Playwright Python，把点击、等待、抽取、异常、重试、checkpoint 都放回显式 Python 控制流中，重写后完成了整个批量任务。

正确结论应表述为：

```text
内容是核心产物 -> 高层抓取抽象收益大
交互轨迹是核心产物 -> 直接浏览器自动化控制收益大
```

## 3. Crawl4AI 并非不能做多步交互，问题是抽象边界

当前 Crawl4AI 官方能力包含：

- `js_code`；
- `js_code_before_wait`；
- `wait_for`；
- `session_id`；
- `js_only`；
- `c4a_script`；
- 页面滚动、iframe、Shadow DOM、MHTML 等。

因此不能简单把文章理解成“Crawl4AI 只能抓静态页面”。它完全可以处理 Render、Load More、简单点击和同一 session 下的后续操作。

真正边界在于：**当业务需要把每个动作的前置条件、完成条件、局部输出、断言、错误类型、重试和 checkpoint 都独立治理时，继续把整个流程封装在 Crawl4AI 的脚本层会产生抽象泄漏。**

可以把两类任务表示为：

```text
内容抓取：
URL -> Fetch/Render -> Snapshot -> Extract -> Quality

有状态交互：
URL
 -> Action
 -> Observe
 -> Wait Semantic Condition
 -> Extract Partial Output
 -> Assert
 -> Commit
 -> Checkpoint
 -> Next Action/Branch/Loop
```

第二类任务的主要产物已经不只是最终 HTML，而是交互状态机和它产生的部分结果。

---

## 4. 技术原理：复杂交互本质上是有限状态机

普通博客正文抓取近似纯函数：

```text
fetch(url, config) -> artifact
extract(artifact, recipe) -> candidate
quality(candidate) -> canonical document
```

复杂交互则更像有限状态机：

```text
S0 NAVIGATE
 -> S1 WAIT_INDEX_READY
 -> S2 ENUMERATE_LOGICAL_ITEMS
 -> S3 SELECT_ITEM(key)
 -> S4 WAIT_ITEM_CHANGED
 -> S5 WAIT_ITEM_STABLE
 -> S6 EXTRACT_ITEM(key)
 -> S7 ASSERT_ITEM(key)
 -> S8 COMMIT_ITEM(key)
 -> next key
 -> DONE
```

状态至少包括：

- 当前逻辑 item key；
- 当前 page/cursor/tab/filter；
- 已提交 item 集合；
- 页面数据签名；
- 本步骤 attempt；
- partial output；
- 当前 Recipe Release；
- Browser/Context 状态；
- lease/fencing token。

因此复杂交互不能只记录“这个 URL 抓过没有”，而要记录“这个 URL 内的哪个逻辑步骤已经完成并提交”。

## 5. 对原文示例的两个生产级修正

原文核心观点成立，但其简化的 Playwright 示例仍有两处不应直接照搬到生产系统。

### 5.1 不应把 `networkidle` 当成统一完成条件

原文示例在点击国家 Tab 后使用 `wait_for_load_state("networkidle")`。Playwright 官方文档目前明确将 `networkidle` 标记为 discouraged，原因是网络安静并不等于业务数据完成：

- 页面可能有 WebSocket、长轮询、埋点等持续连接；
- 局部组件更新时不一定触发页面级 load state；
- 网络已经空闲，但 React/Vue 的下一轮渲染尚未稳定；
- 网络仍不空闲，但目标数据其实已经可安全抽取。

生产系统应该等待**业务语义条件**。

推荐优先级：

```text
业务数据签名变化
 -> 目标 Locator 达到期望状态
 -> 目标列表 count/text/href 集合稳定
 -> 指定 API response
 -> navigation/DOMContentLoaded
 -> 极小固定 delay 仅作最后安全边界
```

例如：

```text
before = fingerprint(current_rating_distribution)
click(country_tab)
wait until fingerprint(current_rating_distribution) != before
wait until fingerprint remains unchanged for quiet_window
extract
```

这比固定 `sleep` 或统一 `networkidle` 更符合实际状态机语义。

### 5.2 动态列表不能直接依赖 `locator.all()` 的瞬时结果

原文示例先执行 `locator(...).all()` 再循环。Playwright 官方文档明确说明：`locator.all()` 本身不会等待动态列表完成加载，如果列表仍在变化，会产生不可预测结果。

对于动态 Tab、年份列表、分页按钮，更稳妥的做法是：

1. 等待列表达到稳定条件；
2. 先提取稳定的逻辑 key，例如 `data-year`、文本、href、业务 id；
3. 循环时按 key 重新定位目标，而不是长期持有一次枚举出的 DOM/ElementHandle；
4. 每次动作之后重新验证当前 item 与输出的对应关系。

建议模式：

```text
wait list stable
keys = extract logical keys
for key in keys:
    locator = resolve locator by key
    action(locator)
    semantic wait
    extract
    assert output belongs to key
    commit key
```

这样可以显著降低 React/Vue 重渲染、虚拟列表、DOM 重建造成的漂移问题。

## 6. Playwright 的真正优势：步骤边界、自动等待和可诊断性

直接 Playwright 的价值不只是“全部写 Python”，更重要的是可以让动作成为结构化步骤。

建议每一步至少记录：

```text
interaction_step_run
- interaction_run_id
- step_id
- logical_item_key
- step_type
- locator_spec
- precondition
- completion_condition
- attempt
- before_signature
- after_signature
- output_ref
- started_at
- finished_at
- status
- error_type
- evidence_ref
```

Playwright Locator 自带 actionability checks。以 `locator.click()` 为例，会等待目标唯一、可见、稳定、可接收事件、启用等条件，超时会产生明确异常。对于复杂生产任务，这比在一段浏览器脚本里自行组织每个点击更容易建立统一错误模型。

应进一步利用 Playwright 的诊断能力：

- failure-only `trace.zip`；
- screenshot；
- DOM/MHTML snapshot；
- console message；
- `pageerror`；
- `requestfailed`；
- 必要时采样 HAR/关键 response 元数据。

成功路径不需要全量保存重型 Evidence，失败、首次运行、Canary、Drift 事件才提高采样级别。

## 7. Checkpoint 必须是逻辑状态，不是 DOM 状态

普通 URL Fetch 的幂等键可以是：

```text
FETCH:{url_id}:{fetch_policy}:{validator_state}
```

复杂交互应该额外有：

```text
INTERACT:{url_id}:{recipe_release}:{logical_run_key}
INTERACT_STEP:{interaction_run_id}:{step_id}:{logical_item_key}
```

Checkpoint 建议：

```text
interaction_checkpoint
- interaction_run_id
- recipe_release_id
- state_name
- loop_cursor
- logical_item_key
- committed_item_set_ref
- partial_output_ref
- page_signature
- committed_at
```

恢复流程：

```text
重新打开入口页
 -> 恢复基础页面状态
 -> 按逻辑 key 重放到最近 checkpoint
 -> 校验 page signature
 -> 跳过已原子提交的 item
 -> 从第一个未提交 item 继续
```

不要尝试把 DOM 节点、Locator、ElementHandle 直接持久化。可持久化的是 `year=2022,page=17,tab=DE` 这种业务逻辑状态。

## 8. 复杂度路由器是平台化的关键

不能形成“所有 JS 页面走 Crawl4AI”或者“所有动态页面走 Playwright”两个极端。建议统一 Interaction Complexity Router：

```text
L0 STATIC
- HTTP 即得到完整正文

L1 RENDER_ONLY
- 只需要 JavaScript 渲染
- Crawl4AI Browser Render

L2 SIMPLE_INTERACTION
- 少量 scroll / Load More / click
- 最终只需要一次完整 DOM
- Crawl4AI js_code/c4a_script + wait_for

L3 STATEFUL_INTERACTION
- 多步 click/wait/extract
- foreach tab/filter
- 分页后每步要提交结果
- 分支/循环/局部重试/checkpoint
- Direct Playwright Stateful Interaction Engine

L4 UNSUPPORTED_OR_BLOCKED
- 登录墙、CAPTCHA、明确访问控制等
- Known Gap / Manual Review
```

### 8.1 新增 L2 抽象泄漏保护

这是本文对现有方案最值得补充的工程机制。

系统不只要“推荐 L3”，还应在发布阶段阻止过度复杂的 L2 Recipe 上线。Static Validation 可以检查：

```text
L2_RECIPE_ALLOWED
- action_count <= max_simple_actions
- no foreach
- no branch
- no nested loop
- no extract-after-each-action
- no per-item checkpoint
- no arbitrary long JS orchestration blob
- only bounded simple interaction primitives
```

一旦出现下列信号，自动拒绝 L2 Candidate 或升级 L3：

```text
HAS_LOOP
HAS_BRANCH
EXTRACT_AFTER_EACH_ACTION
REQUIRES_PARTIAL_COMMIT
REQUIRES_STEP_RETRY
REQUIRES_CHECKPOINT
JS_ORCHESTRATION_TOO_COMPLEX
SIMPLE_INTERACTION_DRIFT_HIGH
```

这可以防止工程师因为“Crawl4AI 已经在项目里”就继续把复杂流程塞进 JS 字符串，避免文章中那类工具误用再次发生。

## 9. Recipe DSL 应把 Direct Playwright 平台化

直接 Playwright 不等于为 1000 个网站写 1000 个 Python 脚本。否则只是从一种不可维护方式换成另一种不可维护方式。

应提供版本化 typed Recipe DSL，例如：

```yaml
kind: browser_interaction
version: 8
entry:
  goto: "{{url}}"
  wait:
    locator: "main"

steps:
  - id: enumerate_years
    extract_keys:
      locator: "[data-year]"
      key: "attr:data-year"

  - id: crawl_years
    foreach_key: "{{steps.enumerate_years.keys}}"
    body:
      - click_by_key:
          locator: "[data-year='{{item}}']"
      - wait_signature_change:
          target: ".post-list a"
          fingerprint: href_set
      - wait_stable:
          target: ".post-list a"
          quiet_ms: 500
      - extract_links:
          locator: ".post-list a"
      - assert:
          min_items: 1
      - checkpoint:
          key: "{{item}}"

limits:
  max_actions: 200
  max_wall_time_s: 180
  max_retries_per_step: 2
```

Executor 才直接调用 Playwright；Source 配置只表达允许的动作和状态，不执行任意 Python/JavaScript。

只有 DSL 无法表达、站点价值足够高的场景才允许 `CUSTOM_PLAYWRIGHT_PLUGIN`，并要求代码审查、测试、版本化、Golden Replay、Canary 和受限权限。

## 10. 长时间运行任务的 Browser 生命周期

原文任务连续运行约 5 天，说明 Browser 不能按“单脚本”思路管理。

建议生命周期：

```text
Browser Worker Process
 -> long-lived Browser Process
 -> bounded BrowserContext Pool
 -> Page / Interaction Run
```

原则：

- Browser Process 长寿命，但按请求数、RSS、运行时长、崩溃率回收；
- Context 默认隔离，防止 cookie/localStorage 污染；
- Page 绑定一个短生命周期 task/run；
- Context Pool 有硬并发上限；
- L3 Playwright Pool 与 HTTP、Crawl4AI Pool 分离；
- 崩溃后只重建易失执行环境，业务状态从 PostgreSQL Checkpoint 恢复；
- 大站 Backfill 使用分片和公平调度，不能占满所有 Browser slot。

## 11. 对博客知识库技术方案的具体影响

现有方案已经正确包含以下方向：

- HTTP First, Browser Last；
- Crawl4AI 负责 Render/Simple Interaction；
- Direct Playwright 负责 Stateful Interaction；
- Step/Checkpoint；
- 语义等待；
- Locator Drift；
- Browser Context Pool；
- Interaction Recipe DSL；
- 失败 Evidence；
- 公平调度、预算和 Circuit Breaker。

本次调研进一步强化四个实现要求：

1. **增加 L2 Recipe Complexity Guard**：从治理层阻止把复杂状态机重新塞进 Crawl4AI JS；
2. **禁止把 `networkidle` 或固定时间作为统一完成条件**：完成条件必须与业务数据/Locator 状态绑定；
3. **动态列表使用稳定逻辑 key + 每轮重新定位**：不长期持有动态 DOM 的瞬时枚举结果；
4. **失败路径增加 Playwright Trace/Console/PageError/RequestFailed Evidence**：把“直接 Playwright 更容易调试”真正落实成平台能力，而不是依赖开发者本地调试。

---

## 12. 最终结论

这篇文章对博客知识库方案的核心启示可以归纳成一句话：

> 不要按“喜欢哪个爬虫框架”选择执行引擎，而要按页面的状态复杂度、恢复粒度和可观察性要求选择执行模型。

对 1000+ 技术博客平台，推荐保持三条主路径：

```text
HTTP
 -> 默认低成本正文抓取

Crawl4AI
 -> Browser Render + Simple Interaction + Dynamic Discovery

Direct Playwright
 -> Stateful Interaction + Step + Semantic Wait + Partial Commit + Checkpoint + Trace
```

绝大多数博客应停留在 HTTP/L1/L2 路径；只有真正具有循环、多步、每步抽取、局部提交和恢复需求的页面才升级 L3。平台同时用 Static Guard 阻止复杂逻辑被错误塞回 L2，用 Trace/Evidence 保证 L3 可诊断，用 Recipe DSL 保证扩展到更多站点时不会退化成大量一次性脚本。
