# 关于我的爬虫项目方案，希望获得帮助和反馈

## 1. 调研对象

- 编号：14
- 原始标题：Need help / feedback on my approach to my scraping project
- 来源：https://www.reddit.com/r/webscraping/comments/1nr1b6b/need_help_feedback_on_my_approach_to_my_scraping/
- 调研目标：评估“多来源 URL 发现 + listing page 识别 + Deep Crawl 补洞 + LLM/人工校验 + 分支剪枝”是否适合 1000+ 技术博客的全量历史采集、增量同步和 Web 管理，并分析如何融入现有博客知识库方案。

## 2. 原帖方案与真正有价值的思想

原帖提出的流程可抽象为：

1. 用 Sitemap 与 Common Crawl 生成 URL seed；
2. 去跟踪参数、去重，并结合 URL 正负关键词筛选候选 listing page；
3. Deep Crawl 站点，寻找第一阶段没有发现的 URL，再次识别 listing page；
4. 下载候选 listing page，让 LLM 判断是否确实是持续链接到目标内容的列表页；
5. 由用户人工确认，让后续识别越来越准确。

作者在后续回复中进一步说明，其目标不是抓完所有页面，而是找到“会通向多个叶子内容的分支”。如果某个路径下已经发现多个同模板叶子节点，就希望停止继续沿同一分支无差别探索，转向其他分支，从而减少计算和请求量。

这篇讨论最值得吸收的不是“用 LLM 判断网页”，而是三件事：

- **Discovery 与 Fetch 解耦**：先发现和理解 URL 图，再决定哪些 URL 值得抓正文；
- **listing page 是长期资产**：Archive、Category、Tag、Blog Index、Docs TOC、Pagination 等页面应作为持续发现新文章的入口；
- **探索预算应按分支收益分配**：不是所有路径都值得等价深爬，应优先探索高产出、高不确定性、尚未饱和的分支。

## 3. 与 1000 个技术博客需求的匹配度

### 3.1 高度匹配

1000+ 技术博客真正困难的是：

- 如何尽量证明历史文章没有漏；
- Sitemap 不完整、Feed 只保留最近若干篇时如何补洞；
- Archive/Category/Docs 导航隐藏深层文章时如何发现；
- 后续增量同步如何避免反复全站深爬；
- 站点结构变化后如何自动发现原有规则失效；
- 如何在成本可控的前提下扩展到更多站点。

原帖“多来源 URL 联合发现 + listing page 固化 + 深爬补洞 + 人工确认”与这些问题高度一致。

### 3.2 不能直接照搬

1. **Common Crawl 不是站点权威目录。** 它只能证明某个 URL 曾在某次 crawl 中被观察到，不能证明站点全部历史 URL 都已收录。
2. **仅靠 URL 正负关键词会误杀。** 技术博客常见无日期 slug、query permalink、Docs route、语言路径、历史迁移路径等，关键词只能作为特征而不能作为永久过滤依据。
3. **站点不是严格树。** Tag/Category 交叉、分页、循环导航、SPA、faceted navigation、日历陷阱会让“走到最深再回退”失去严格意义。
4. **“看到多个叶子节点就永久剪枝”风险很高。** 同一路径下可能同时存在历史分页、不同内容类型或后来新增的 URL 模板，过早剪枝会制造不可见 Coverage gap。
5. **LLM 不应进入正确性的关键路径。** LLM 可以辅助 Surface 分类和 Profile 建议，但不能自动决定“这个分支以后永久不抓”“这个 URL 永久忽略”。
6. **Common Crawl CDX API 不适合 1000 站点高并发批量历史扫描。** Common Crawl 官方明确说明 CDX 服务严格限流，较大规模过滤应使用其 URL Index（以前称 Columnar Index）等批量方式。

正确落地方式不是复制原方案，而是把它工程化为：**Provider Evidence + Discovery Surface + Discovery Graph + Branch Yield + Soft Pruning + Release + Reconcile**。

## 4. 技术原理一：Discovery Plane 与 Fetch Plane 分离

传统小爬虫常见流程：

```text
首页 -> 跟链接 -> 下载整页 -> 判断是不是文章 -> 保存
```

其问题是为了“发现 URL”先支付了完整抓取、渲染、Markdown 和抽取成本。

更适合本项目的流程：

```text
Discovery Plane
  CMS / Sitemap / Feed / Archive / Common Crawl / Surface / Deep Crawl
        -> URL Observation + Discovery Evidence

Normalization / Classification
        -> Article / Surface / Navigation / Asset / Unknown

Fetch Plane
        -> 只抓需要获取正文或验证结构的 URL
```

Crawl4AI 官方文档也明确区分 URL Seeding 与 Deep Crawling：URL Seeding 适合批量发现既有 URL 并在抓取前过滤，Deep Crawling 更适合实时发现和未知结构探索。生产系统应把二者作为互补 Provider，而不是二选一。

## 5. 技术原理二：增加 Prefetch Mapping，进一步压低发现成本

Crawl4AI 当前 Deep Crawling 支持 `prefetch=True`。Prefetch 模式只保留 HTML 与 links，不生成 Markdown、不执行正文抽取，适合“两阶段抓取”：先快速建立站点链接图，再只对命中的 Article/Surface 做后续处理。

因此建议把发现路由拆成：

```text
URL_SEED
  -> PREFETCH_MAP
  -> STRUCTURE_CLASSIFY
  -> SURFACE_VALIDATE
  -> CONTENT_FETCH
```

其中：

- `URL_SEED`：来自 Sitemap、Feed、CMS、Common Crawl 等；
- `PREFETCH_MAP`：轻量访问未知 hub/branch，只提取 links 与必要 head metadata；
- `STRUCTURE_CLASSIFY`：计算 URL template、link template、重复卡片、分页、叶子概率；
- `SURFACE_VALIDATE`：只对高价值/灰区 listing 页面做完整结构验证；
- `CONTENT_FETCH`：只对真正文章抓正文。

这样可以把“发现站点结构”和“生产 Markdown”完全分开，Browser/正文抽取资源不会被大量导航页消耗。

## 6. 技术原理三：Common Crawl 是历史候选补洞器

### 6.1 两种使用模式

#### CDX/API

适合：

- PROBE；
- 单站排障；
- Web 后台交互查询；
- 验证某个旧 URL 是否被观察过。

不适合：1000+ 域名跨多个 crawl collection 的高并发历史扫描。

#### URL Index（原 Columnar Index）

Common Crawl 已将 Columnar Index 更名为 URL Index。底层仍为 Apache Parquet，适合 Athena、Spark、DuckDB、Polars 等做分析和批量查询。

适合：

- 1000+ 域名批量历史 URL 枚举；
- 按 registered domain / crawl / status / MIME 过滤；
- 定期历史补洞；
- 计算多个 Provider 的 overlap。

建议实现独立 `COMMON_CRAWL_BULK` Provider：

```text
待扫描 domains
 -> 按 crawl_id 批量查询 URL Index
 -> domain 分桶
 -> 输出 URL Observation
 -> 进入统一 Normalization / Classification
```

幂等键：

```text
registered_domain + crawl_id + provider_release
```

### 6.2 Observation 语义

```text
common_crawl_observation
  source_id
  crawl_id
  url_id
  capture_time
  status
  mime
  warc_filename
  warc_offset
  warc_length
  content_digest
  observed_at
```

它证明：

```text
URL X 在 crawl Y 中被 Common Crawl 观察/抓取过
```

不证明：

```text
Source 的全部历史文章已被 Common Crawl 收录
```

因此 Common Crawl Provider 不能单独生成 FULL_BACKFILL COMPLETE。

### 6.3 历史已下线文章恢复

如果业务确实要求尽量恢复已经从源站删除的历史文章，可以配置：

```text
ARCHIVE_RECOVERY_COMMON_CRAWL
```

流程：

```text
live fetch -> 404/410/不可达
 -> 已有 CC Observation
 -> Policy 允许历史恢复
 -> Range 读取对应 WARC record
 -> Snapshot.origin = COMMON_CRAWL_ARCHIVE
 -> 使用统一 Extraction / Quality / Identity
```

必须把 archive capture 与 live fetch 严格区分，并满足版权、许可证、robots/访问策略和项目用途要求。

## 8. 技术原理五：建立 Discovery Graph，而不是假设站点是树

为了实现原帖“找通向多个叶子的分支”的思想，需要显式记录发现边：

```text
discovery_edge_observation
  source_id
  run_id
  parent_url_id
  child_url_id
  parent_template_id
  child_template_id
  anchor_text
  dom_path_signature
  link_region
  discovery_method
  observed_at
```

但不需要把整个互联网做永久图数据库。PostgreSQL 只保存当前 Source 的必要边、模板聚合结果和 provenance；高体量原始 links 可以按 Snapshot 存对象存储并设置生命周期。

真正用于调度的是“模板级图”：

```text
/blog/
  -> /blog/{slug}
  -> /blog/page/{n}
  -> /category/{slug}
```

以及每条模板边的统计：

```text
observed_links
unique_targets
article_probability
surface_probability
new_template_rate
new_article_rate
last_new_at
```

这样可以避免被单个 URL 图的规模拖垮，同时仍能做分支收益判断。

## 9. 原帖“叶子分支剪枝”的工程化改造：Soft Pruning

### 9.1 为什么只能软剪枝

例如观察到：

```text
/blog/a
/blog/b
/blog/c
```

不能因此永久认定 `/blog/*` 下只存在这一种文章模板，也不能永久停止扫描 `/blog/`。未来可能出现：

```text
/blog/series/x
/blog/2027/y
/blog/page/20
```

因此“剪枝”必须是可恢复、可解释、带 TTL 的调度降权，而不是删除。

### 9.2 Branch State

按模板维度建立：

```text
surface_branch_state
  id
  source_id
  parent_template_id
  child_template_id
  query_signature
  sample_count
  unique_leaf_count
  unique_child_template_count
  new_url_rate_ema
  new_template_rate_ema
  article_yield_ema
  duplicate_ratio_ema
  saturation_score
  exploration_priority
  suppression_until
  suppression_reason
  last_sampled_at
  last_new_url_at
  release_id
```

### 9.3 饱和判定

不是“看到两个叶子就停”，而是综合：

```text
saturation_score =
    w1 * leaf_template_stability
  + w2 * duplicate_ratio
  + w3 * consecutive_zero_new_pages
  + w4 * low_new_template_rate
  + w5 * low_new_article_rate
  - w6 * coverage_gap_signal
  - w7 * structure_change_signal
  - w8 * provider_disagreement_signal
```

建议只有满足最小样本数后才允许降权，例如：

```text
sample_count >= N
unique_leaf_count >= M
new_template_rate_ema < epsilon
new_article_rate_ema < epsilon
连续 K 个分页/分支没有发现新候选
```

阈值必须进入 `branch_policy_release`，可回滚。

### 9.4 软剪枝行为

当分支高饱和时：

- 不从数据库删除候选；
- 不把 URL 标记为永久 IGNORE；
- 降低 BestFirst priority；
- 设置 `suppression_until`；
- 在下次 Reconcile 或 TTL 到期后重新抽样；
- 始终保留少量 exploration budget，例如随机抽样 1%~5% 的被降权分支；
- Sitemap/Feed/CMS/API 等权威 Provider 新证据可以立即解除 suppression。

这样既继承了作者“避免重复走同类叶子”的成本优势，又不会让错误分类变成永久 Coverage 漏洞。

## 10. Best-First 分支优先级

Crawl4AI 的 BestFirst 策略支持 URL scorer，适合把平台的分支模型转成探索优先级。

建议调度分数：

```text
exploration_score =
    a * surface_probability
  + b * article_template_probability
  + c * coverage_gap_score
  + d * new_template_probability
  + e * historical_branch_yield
  + f * provider_disagreement
  - g * duplicate_probability
  - h * trap_probability
  - i * observed_cost
  - j * saturation_score
```

注意：框架 scorer 只是执行层排序，真正的 branch state、Evidence、Run 和 Coverage 仍由平台保存。

## 11. Discovery Surface 识别算法

建议三阶段。

### 11.1 确定性结构特征

- 同域 links 数；
- article template link ratio；
- 重复 card DOM；
- date density；
- pagination / next / older；
- Schema.org ItemList / CollectionPage；
- 主体 link density；
- URL template consistency；
- link region（main/sidebar/footer）；
- anchor 语义；
- 是否持续链接到多个叶子文章。

示例：

```text
surface_score =
    w1 * article_link_ratio
  + w2 * repeated_card_score
  + w3 * pagination_score
  + w4 * date_density
  + w5 * template_consistency
  + w6 * multi_leaf_branch_score
  - w7 * external_link_ratio
  - w8 * nav_noise_ratio
```

### 11.2 LLM 灰区判断

只给 LLM 精简输入：

- title；
- cleaned DOM/HTML 片段；
- 20~50 个代表 links；
- path/template 聚类；
- 结构特征；
- 可能的 pagination pattern。

结构化输出：

```json
{
  "is_discovery_surface": true,
  "surface_type": "PAGINATED_LISTING",
  "confidence": 0.91,
  "article_url_patterns": ["/blog/*"],
  "pagination_pattern": "/blog/page/{n}",
  "evidence": ["multiple repeated article cards"],
  "risks": ["tag links mixed with article links"]
}
```

LLM 结果只保存为 Classification Evidence。

### 11.3 人工确认

Web 展示候选 Surface、代表 links、规则分、LLM Evidence、预计新增文章数、分支模板和分页规则。

管理员接受/拒绝/编辑后创建新的 `Site Profile Release`，不覆盖旧策略。

所谓“LLM 学习”应落实为：

```text
人工标注集
 -> classifier/prompt 离线训练/优化
 -> regression set
 -> 新 classifier release
 -> 灰度验证
 -> 发布
```

而不是在线自动改生产规则。

## 12. Surface 健康度与结构漂移

原帖只讨论“找到 listing page”，但长期运行更重要的是发现它何时失效。

建议维护：

```text
surface_health_state
  ACTIVE
  DEGRADED
  SUSPECT
  REVIEW_REQUIRED
  RETIRED
```

健康信号：

```text
http_success_rate
article_link_ratio_delta
structure_fingerprint_delta
pagination_signal_delta
new_urls_per_scan
unexpected_external_ratio
empty_scan_streak
```

例如原来每次 `/blog/` 都能找到 20~30 个文章 link，突然连续三次变为 0，且 DOM fingerprint 大幅变化，应进入 `REVIEW_REQUIRED`，触发轻量 PROBE/Deep Crawl 重新寻找 Surface，而不是继续按旧 selector 空跑。

## 13. Pagination 的增量早停

历史回填需要遍历完整分页，但增量扫描不应每次从第 1 页扫到最老页。

每个 Surface 保存：

```text
pagination_cursor
head_fingerprint
last_seen_boundary_url
last_seen_boundary_published_at
consecutive_known_pages
```

增量流程：

```text
page 1
 -> 有新 URL：继续 page 2
 -> 连续 K 页全部为已知 URL 且结构未变化：早停
 -> 遇到 provider gap / structure drift：取消早停，升级 Reconcile
```

这会显著降低 Archive/Category 的长期扫描成本。

## 14. Deep Crawl 的正确角色

Deep Crawl 用于：

```text
未知结构探索
未知 Surface 发现
未知 URL Template 发现
Coverage gap filler
Surface 失效后的重新探索
```

不能用：

```text
max_depth reached
max_pages reached
queue empty
```

作为历史完整证明。

建议：

- PROBE：BFS 1~2 层找 hub；
- 未知结构：Prefetch + BFS；
- 已知高价值分支：BestFirst；
- 特殊深层路径：DFS；
- 全程 FilterChain + scope policy + query explosion/calendar/facet trap 防护；
- 用 `resume_state` / `on_state_change` 做执行层 crash recovery；
- 平台仍保存自己的 Task lease/checkpoint/Coverage，不能把业务事实只放在 Crawl4AI 内部 state。

## 15. Candidate URL 规范化与不可逆过滤边界

建议版本化 `url_normalization_release`：

```text
host normalization
punycode
default port removal
fragment removal
path slash policy
safe percent-encoding normalization
query sorting
tracking parameter removal
semantic parameter allowlist
```

常见 tracking 参数如 `utm_*`、`gclid`、`fbclid` 可以删除，但不能全局删除所有 query，因为 `?p=123`、`?id=456`、`?page=7` 可能具有正文或分页语义。

事实链保持：

```text
Observed URL
 -> Normalized Candidate
 -> Resolved Target
 -> Network Final URL
 -> Canonical Identity
```

任何被降权、忽略、合并的决定都保存原始 Observation 与 Evidence。

## 16. 基于 Surface + Branch Yield 的增量同步

建议初始层级：

```text
Tier 0: Feed / CMS API           分钟级或按需求
Tier 1: Sitemap / Blog Index     10~60 分钟
Tier 2: Category / Archive       1~6 小时
Tier 3: Deep Crawl Reconcile     每周/每月
Tier 4: Common Crawl Reconcile   新 crawl 发布后/按月
```

Surface 收益：

```text
new_urls_per_scan
changed_urls_per_scan
duplicate_ratio
bytes_per_new_url
requests_per_new_url
latency
failure_rate
```

Branch 收益：

```text
new_template_rate
new_article_rate
cost_per_new_template
cost_per_new_article
saturation_score
```

调度器按收益与不确定性动态分配预算。高产 Surface 高频扫；长期无新增但稳定的 Surface 降频；高饱和分支软剪枝；周期 Reconcile 和随机探索保证不会永久失明。

## 17. 1000 站点批量实现

建议独立 Worker：

```text
url-seed-worker
common-crawl-bulk-worker
prefetch-map-worker
surface-discovery-worker
discovery-browser-worker
normalization-classifier-worker
content-http-worker
content-browser-worker
```

Discovery Browser 与正文 Browser 分池，因为二者目标、超时、资源模型完全不同。

如果平均每站维护 5~20 个有效 Surface，1000 站大约是 5000~20000 个可调度发现入口；通过收益调度、条件请求和分页早停，其长期成本远低于周期性全站重爬。

## 18. Web 管理应增加的能力

### Source / Coverage

- Provider candidates、overlap、unique URL；
- 历史时间覆盖与 known gap；
- Common Crawl-only 历史候选；
- FULL_BACKFILL exhaustion reason。

### Discovery Surface

- Surface 类型、状态、结构 fingerprint；
- article link ratio；
- pagination；
- new URLs / scan；
- cost / new URL；
- health state；
- next revalidate time。

### Branch Explorer

这是本次调研建议新增的页面：

- parent/child URL template；
- 代表性 URL；
- leaf count；
- new template rate；
- article yield；
- saturation score；
- 当前 exploration priority；
- suppression reason / TTL；
- 最近随机复查结果；
- 手工“解除降权 / 强制重探”。

### Surface 审核

- 确定性分数；
- LLM Classification Evidence；
- 代表 links；
- 预计新增量；
- pagination pattern；
- 接受/拒绝/编辑后生成 Profile Release。

### URL Provenance

任意 URL 可查看：

```text
Sitemap observed
Feed observed
Common Crawl observed
Found from /blog/page/3
Found from category surface
Deep crawl parent

```

## 19. 对现有博客知识库方案的优化结论

现有方案总体方向正确，不需要推翻。本次调研建议在已有 Discovery Surface 设计上继续增强：

1. 增加 `PREFETCH_MAP` 两阶段发现路径，尽量避免为了发现 links 执行 Markdown/正文抽取；
2. 增加模板级 `Discovery Graph / discovery_edge_observation`，支撑分支 provenance 与收益分析；
3. 增加 `surface_branch_state` 与 `branch_policy_release`，把原帖“叶子分支剪枝”改造成可回滚 Soft Pruning；
4. 增加随机探索预算和 TTL，防止误判后永久漏掉新路径；
5. BestFirst scorer 中加入 Coverage gap、new template probability、historical yield 与 saturation penalty；
6. Surface 增加健康状态、structure fingerprint 和 revalidation；
7. Pagination 增加“连续 K 页无新 URL”增量早停，但 Coverage/Reconcile 可强制穿透；
8. Common Crawl 生产批量扫描统一使用 URL Index（原 Columnar Index）思路，CDX 仅做轻量/交互式能力；
9. Web 增加 Branch Explorer，明确展示为什么某条分支被降权以及何时恢复；
10. 所有降权、分类、剪枝和 LLM 判断都进入 Evidence + Release，不做不可逆在线自学习。

## 20. 不建议加入的设计

- 不让 LLM 自动永久忽略 URL/分支；
- 不把 Common Crawl 当成 Source 的完整目录；
- 不把 `max_pages`、`max_depth` 或 queue empty 当 Coverage COMPLETE；
- 不因观察到几个同模板叶子就永久停止整个路径；
- 不让 Crawl4AI 内部 state 成为平台唯一 checkpoint；
- 不让 Domain Mapping 自动把 staging/admin/api/dashboard 等子域加入抓取 scope；
- 不在 Discovery 阶段默认执行 Browser + Markdown 全处理。

## 21. 最终落地流程

```text
权威发现：CMS/API + Sitemap + Feed
        ↓
历史补洞：Archive + Common Crawl URL Index
        ↓
URL Normalization / Template Clustering
        ↓
Prefetch Mapping（只取 HTML + links）
        ↓
模板级 Discovery Graph
        ↓
Discovery Surface / Article / Navigation 分类
        ↓
Branch Yield + Saturation + Soft Pruning
        ↓
灰区：LLM Evidence -> 人工审核 -> Profile Release
        ↓
Article 才进入 HTTP/Browser 正文抓取
        ↓
高收益 Surface 长期增量同步
        ↓
分页早停 + 条件请求降低成本
        ↓
周期 Reconcile + 随机探索 + Surface Revalidate 防止永久漏抓
```

该模型保留了原帖“不要无差别抓所有页面，而要优先寻找通向多个目标叶子的高价值分支”的核心优势，同时把树假设、错误剪枝和 LLM 在线自学习的风险改造成可审计、可回滚、可恢复的工程机制，更适合 1000+ 技术博客的长期知识库。
