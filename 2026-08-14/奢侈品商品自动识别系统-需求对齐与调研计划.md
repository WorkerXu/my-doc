# 奢侈品商品自动识别系统：需求对齐与调研计划

## 一、已经对齐的业务目标

本项目解决的不是普通的“相似商品搜索”，而是：

> 从雷小安、奢当家、腕表之家、小迈步、爱回收等多个数据源的异构商品数据中，自动识别哪些记录实际上指向同一个**官方商品变体**，建立统一商品实体，并产生机器识别记录供后续审核。

### “相同商品”的粒度

只有以下关键官方属性一致，才允许认定为同一商品：

**腕表示例**

- 品牌
- 系列
- 子系列/款式
- Reference / 型号
- 表径
- 表壳材质
- 表盘颜色/盘面类型
- 表圈
- 表带/表链材质
- 机芯/功能等必要区分属性

**箱包示例**

- 品牌
- 系列/Model
- 款式
- 官方尺寸
- 材质
- 颜色
- 五金颜色/类型
- 图案/特殊版本
- 必要时的年代/季节/版本属性

最终哪些字段属于 **Hard Constraint（冲突即绝不能合并）**，哪些属于 **Soft Evidence（辅助判断）**，是本次调研需要输出的重要结果之一。

### 明确不属于“同一商品”的情况

例如：

- 同款不同尺寸
- 同款不同颜色
- 同款不同材质
- 同款不同盘面
- 同系列不同 Reference
- 箱包普通皮与鳄鱼皮版本
- 同款金色五金与银色五金
- 外观极像但官方 SKU / variant 不同

这些情况即使图片 Embedding 非常接近，也不能合并。

---

# 二、现状与关键约束

目前已确认：

- 数据规模：**100 万–1000 万条**
- 第一阶段品类：**腕表 + 箱包**
- 腕表：已有部分品牌 / 系列 / 型号标准库
- 箱包：标准主档预计不完整
- 标签数据：基本没有
- 冷启动必须主要依赖：
  - 规则
  - 已有商品知识
  - 预训练模型
  - 多模态模型
  - 自动生成的弱监督/伪标签
- 目标倾向：**Precision >> Recall**
- 原则：**宁可暂时识别不出来，也不能把两个不同官方变体错合并**
- 在线识别过程不能依赖人工判断
- 机器成功识别后：
  1. 标记原始记录已识别
  2. 建立识别关系
  3. 写入 Recognition Record
  4. 等待业务审核
- 审核不是模型在线判断链路的一部分，而是结果确认及后续模型学习的数据来源。

# 三、这次调研要回答的核心问题

最终调研不是简单比较“哪个模型准确率高”，而要回答下面 10 个问题。

## 1. Canonical Product 应该怎样建模

需要决定系统中的核心实体究竟是：

```text
Brand
  └── Product Family / Series
       └── Model
            └── Variant / SKU
```

还是腕表、箱包分别采用不同层级。

尤其要区分：

```text
Same Product
Variant Of
Same Series
Visually Similar
Unknown
```

不能把所有关系压缩成一个 similarity score。

Amazon VARM 的工作就是专门把 variant relationship 从普通 entity matching 中进一步拆分，并识别产生变体关系的具体属性，这与本项目“同款不同颜色/尺寸绝不能合并”的需求高度相关。

---

## 2. 如何解决平台字段名称和表达差异

重点研究：

```text
品牌标准化
系列标准化
型号标准化
颜色标准化
材质标准化
尺寸单位标准化
中英文/别名/俗称
全角半角
特殊符号
Reference 格式
平台自定义型号
品牌官方编号
```

例如：

```text
Rolex
劳力士
ROLEX
劳力士Rolex
```

最终统一为：

```text
brand_id = xxx
brand_name = Rolex
```

复杂问题则包括：

```text
Chanel CF
Chanel Classic Flap
香奈儿经典口盖包
经典款
11.12
A01112
```

系统要区分哪些是同义词，哪些实际上代表不同层级实体。

# 四、重点调研的已有工业案例

调研将按“生产系统价值”而不是论文新旧程度排序。

## A. 大规模商品 Catalog Matching

### Bing Shopping — Product Synthesis

这是非常接近本项目的一类经典工业场景。

Bing Shopping 的公开研究处理了不同 merchant 对同一商品使用不同描述和 schema 的问题，并包含：

- offer extraction
- schema reconciliation
- product identification
- attribute fusion
- 新商品生成

公开实验覆盖超过 80 万 offers、约 1000 个 merchants 和 400 个品类。

调研重点：

- Offer → Canonical Product 的建模方式
- 如何利用已有标准 Catalog
- 如何发现 Catalog 中尚不存在的新商品
- schema reconciliation 怎么做
- attribute fusion 怎么避免污染主档

---

## B. 超大规模两阶段商品去重

2025 年公开的一套电商商品去重系统面向超过 2 亿商品，核心采用：

```text
Text Embedding
       ↓
Vector Retrieval Top-N
       ↓
Candidate Pair
       ↓
Text + Image
Decider Model
       ↓
Duplicate Probability
```

而不是做全量 N² 两两匹配。

其公开方案还专门讨论了千万级向量索引的内存和成本问题。

本项目重点复盘：

- 为什么 Retrieval 和 Matching 必须拆开
- Top-K 如何选择
- ANN 如何建设
- 图片在哪一阶段使用最合理
- 千万商品规模下向量维度如何选择
- 候选召回率和计算成本如何平衡
- Decider Model 应输入什么特征

这将作为本项目规模架构的重要参考。

# 五、多模态商品识别专项调研

不能假设所有商品都有图片，也不能假设所有商品都有型号。

因此系统必须天然支持：

```text
文本齐全 + 图片齐全
文本齐全 + 无图片
文本弱 + 图片齐全
有型号
无型号
型号疑似错误
文字和图片冲突
```

2024 年工业级 Fashion Product Matching 研究显示，融合预训练文本和图像 encoder 后进行对比学习，在生产商品匹配任务上优于单模态方案；该工作同时讨论了生产环境下通过置信度和审核机制获得非常高 precision 的做法。

调研会重点比较：

### Text Encoder

例如：

- BGE
- E5
- multilingual embedding
- domain fine-tuned BERT
- 商品专用 encoder

### Image Encoder

例如：

- CLIP / SigLIP
- DINO 系
- MAE
- 商品领域模型

### Vision Language Model

研究其是否适合：

```text
图片 → 结构化属性
图片 → 商品描述
图片 → 型号候选
```

而不是简单用 VLM 直接输出：

```text
same / different
```

# 六、属性抽取与标准化专项调研

这是整个系统能否做到高 Precision 的核心。

Walmart 当前公开的 Catalog 管理方案明确把：

```text
Attribute Extraction
```

和：

```text
Quality Check
```

拆成两个模型/阶段，并同时利用商品文本与图片；对不同属性还设置不同可靠性要求。

本项目将借鉴这一思想，调研是否采用：

```text
Raw Product
     ↓
Attribute Extraction
     ↓
Attribute Normalization
     ↓
Attribute Validation
     ↓
Canonical Attribute
```

例如：

```text
"玫瑰金"
"Rose Gold"
"Everose"
"18K RG"
```

到底应该归一到：

```text
material = 18K Rose Gold
```

还是保留品牌专有语义：

```text
material = Rolex Everose Gold
```

会按照腕表和箱包分别研究。

# 七、候选召回 Blocking / Retrieval 专项

100 万–1000 万条数据不允许：

```text
N × N
```

比较。

因此将重点调研“多路召回”。

候选可能分别来自：

```text
型号召回
品牌 + 型号召回
品牌 + 系列召回
标准化标题召回
BM25
Embedding ANN
图片 ANN
属性组合召回
历史 Canonical Product
```

之后求并集：

```text
Candidate Set =
Model Candidates
∪ Text Candidates
∪ Image Candidates
∪ Attribute Candidates
```

Entity Matching 的经典生产 pipeline 同样通常把 Blocking 与 Matching 拆开；Ditto 的开源实现也是明确的 Blocking → Matching 两阶段结构。

调研要输出：

- 每种召回通道作用
- 每通道 Top-K
- Recall@K
- 计算成本
- 去重方式
- 品牌/类目分区策略

# 八、Pair Matching / Decider 研究

召回以后不直接合并。

需要建立：

```text
Product A
Product B
      ↓
Feature Comparison
      ↓
Pair Matcher
      ↓
match_probability
```

Pair Matcher 的候选技术包括：

### 规则

例如：

```text
ref_exact
brand_exact
size_exact
material_exact
color_exact
```

### 文本特征

```text
title_similarity
series_similarity
model_similarity
attribute_similarity
```

### 图片特征

```text
image_cosine_similarity
multi_image_max_similarity
visual_attribute_similarity
```

### 模型

调研：

- Gradient Boosting
- Cross Encoder
- Ditto
- Contrastive Encoder
- Multimodal Fusion
- Small LLM
- Large VLM / LLM

重点不是找单模型赢家，而是判断**哪个模型应该出现在哪一层**。

# 九、Hard Negative / Conflict Engine

这是本项目和普通商品推荐系统最大的不同。

最终很可能需要一个独立：

```text
Conflict Engine
```

例如：

```text
IF
brand_A != brand_B
THEN
NO_MATCH
```

```text
IF
case_size_A = 36mm
AND
case_size_B = 41mm
THEN
NO_MATCH
```

```text
IF
bag_size_A = Mini
AND
bag_size_B = Medium
THEN
NO_MATCH
```

即使：

```text
text_similarity = 0.97
image_similarity = 0.99
```

依旧：

```text
MATCH = false
```

调研最终需要形成：

### 腕表 Hard Conflict Matrix

以及：

### 箱包 Hard Conflict Matrix

这将成为系统保证 Precision 的第一道安全墙。

# 十、图关系与聚类策略

Pair Matching 只解决：

```text
A == B ?
```

但业务最终需要：

```text
A
B
C
D
```

归属于：

```text
Canonical Product P001
```

因此要进一步研究：

```text
Entity Resolution Graph
```

例如：

```text
A ──0.998── B
│
0.995
│
C
```

随后进行：

```text
Connected Components
Constrained Clustering
Correlation Clustering
Union-Find + Constraints
```

特别需要解决：

```text
A == B
B == C
但 A != C
```

这种 transitive conflict。

Precision 优先场景不能简单：

```text
connected component = 一个商品
```

这会是调研中的重点风险项。

# 十一、已有主档与新主档需要同时研究

因为目前腕表已有部分标准库，而箱包主档并不完整，所以系统需要同时支持两种模式。

## 模式 A：Entity Linking

```text
Source Product
       ↓
已有 Canonical Product
```

适合已有腕表 SKU。

## 模式 B：Entity Discovery

```text
Source Product A
Source Product B
Source Product C
       ↓
发现新的商品实体
       ↓
Proposed Canonical Product
```

适合：

- 新款腕表
- 标准库缺失型号
- 箱包
- 新出现的平台商品

Bing Shopping 的 Product Synthesis 正是值得重点参考的这种“已有 Catalog + 自动发现新商品”问题。

# 十二、冷启动 / 无标签方案专项调研

这是本项目最重要的研究主题之一。

目前没有足够训练集，所以不能一开始就假设：

```text
训练一个自己的分类模型
```

调研将比较四种冷启动方式。

## 方案 1：高置信规则产生正样本

例如：

```text
同品牌
+
完全一致 Reference
+
关键变体属性无冲突
```

作为高质量 Positive。

## 方案 2：Hard Negative 自动构造

例如：

```text
同系列
+
图片极像
+
表径不同
```

可以自动成为高价值 Negative。

这类数据往往比随机 Negative 更有训练价值。

## 方案 3：LLM Teacher 自动标注

研究：

```text
LLM Teacher
     ↓
自动生成匹配标签
     ↓
训练较小 Student Matcher
```

目标是降低为特定 Entity Matching 任务人工创建训练集的成本，并避免让大型模型承担全部在线 pair matching。

本项目会重点验证：

> LLM/VLM 最适合当“老师和困难样本裁判”，而不是承担千万级商品全部在线推理。

## 方案 4：审核结果持续学习

后续：

```text
机器识别
   ↓
业务审核
   ↓
Confirmed / Rejected
   ↓
Training Dataset
   ↓
Periodic Training
```

把现有“待审核”流程转化成数据飞轮。

# 十七、Precision-first 决策机制

最终方案不会设计单个：

```text
score > 0.8
```

就直接认为同商品。

重点调研三级或四级决策：

```text
CERTAIN_MATCH
LIKELY_MATCH
UNKNOWN
CERTAIN_NON_MATCH
```

在当前业务偏好下，默认建议的业务策略是：

```text
CERTAIN_MATCH
    → 创建识别记录
    → 标记机器已识别
    → Pending Review

LIKELY_MATCH
    → 暂不自动认定

UNKNOWN
    → 不处理

CERTAIN_NON_MATCH
    → 排除
```

即：

> “不确定”不是错误，而是一种合法输出。

这是整个系统实现“宁漏勿错”的关键设计原则。

# 十八、调研必须输出的评测方案

不能单纯使用：

```text
Accuracy
```

最终至少评估：

### Matching

```text
Precision
Recall
F1
PR Curve
```

但核心 KPI 为：

```text
Precision @ Auto-Match
```

建议重点观察：

```text
99%
99.5%
99.9%
```

不同 Precision 阈值对应可以自动识别多少商品。

最终更有意义的指标是：

```text
Coverage @ 99.9% Precision
```

即：

> 在错合并率足够低的情况下，系统到底能自动解决多少数据。

# 二十二、本次调研的核心判断标准

最终不是寻找：

> “理论上最先进的模型”。

而是寻找：

> **在 100 万–1000 万条奢侈品数据、字段缺失严重、图片不完整、无训练数据、官方变体必须严格区分的情况下，如何以最低可接受成本获得极高 Precision。**

因此所有技术都会围绕四个目标排序：

1. **不能错合并不同变体**
2. **能够处理缺字段和脏数据**
3. **能够处理未来没见过的新 SKU**
4. **能够扩展到千万级数据**

---

# 二十三、当前最值得验证的核心假设

调研将重点验证以下假设：

> **最优生产方案大概率不是单模型，而是“知识 + 规则 + 检索 + 多模态模型 + 冲突约束 + 图实体解析”的组合系统。**

其中：

```text
标准化/知识
负责理解商品是什么

Retrieval
负责从千万商品里找到几十个候选

ML/Multimodal
负责判断候选究竟有多像

Conflict Engine
负责阻止高相似但不同 Variant 的商品误合并

Graph Resolution
负责把 Pair Match 转成 Canonical Product

LLM/VLM
负责冷启动、属性理解和困难样本，而不是承担所有商品两两匹配

Review Feedback
负责逐渐形成自己的奢侈品训练数据资产
```

# 二十四、调研完成的验收标准

下一阶段深入调研完成后，应能直接回答以下问题，不再留下架构级决策：

- “同商品”在数据库里到底是什么实体？
- 腕表和箱包分别有哪些 Hard Constraint？
- 有型号和没型号分别怎么匹配？
- 有图和没图分别怎么匹配？
- 哪些字段应该用 LLM 抽取？
- 图片到底什么时候参与？
- 如何从 1000 万记录找到 20–100 个候选？
- Embedding 搜什么？
- BM25 搜什么？
- Pair Matcher 用什么模型？
- LLM 应该放在哪一层？
- 如何处理不同证据互相冲突？
- 怎么防止 A=B、B=C 导致错误地认为 A=C？
- 已有标准商品如何挂接？
- 不存在标准商品时如何创建候选主档？
- 没有人工标签如何冷启动？
- 审核结果如何形成训练数据？
- 如何实现增量识别？
- 需要哪些数据库表？
- 需要哪些索引？
- 千万数据量硬件成本是多少？
- MVP 应先做哪些能力？
- 到什么指标才能正式开启自动识别？

达到以上状态后，方案才算真正具备实施条件。

## 已对齐的项目约束摘要

- 商品归一粒度：**必须精确到官方变体级**，尺寸、材质、颜色、盘面等关键变体属性一致才可认定为同一商品。
- 数据规模：**100 万–1000 万条**。
- 风险偏好：**Precision 优先，宁可漏匹配，不能错合并**。
- 第一阶段品类：**腕表 + 箱包**。
- 现有主档：**腕表已有部分品牌/系列/型号标准库**。
- 标注数据：**基本没有，需要规则和预训练模型冷启动**。
