## 3.1 需求合同（RequirementSpec）

用户上传 APK，并输入“采集全量商品”。Task Planner 需要固定一个可复核的机器可读需求：

- 目标 APK 的哈希、版本、包名，分析授权范围及使用的合法账号权限。
- 商品覆盖范围：全部/选定分类、品牌、列表、详情和 SKU；包含字段（ID、名称、分类、品牌、型号、规格、价格、图片链接等）。
- 采集目标：首次全量基线，之后只采新增，不自动追踪已采商品的价格、属性和上下架变化。
- 时间安排、并发上限、目标域名、凭据引用、失败重试策略、成本预算和发布模式。
- “全量”证明标准：分类/品牌入口清单、分页结束证据、列表/详情覆盖、来源 `total`（若可信）及未知范围；无法证明时按未知覆盖处理。

`RequirementSpec` 经 Schema 校验后成为后续分析、生成和验收的唯一输入；会话中的自然语言修改生成新版本，不悄悄改变已发布版本。

## 3.2 APK 探索与接口证据

- 客户端 Pi Agent 使用锁定提交的 Seep、必要静态分析及用户授权的设备动态分析，发现分类、品牌、列表、详情、分页、认证和签名候选调用链。
- 候选接口必须经过允许范围内的请求验证，记录脱敏请求/响应样本、参数来源、应用代码证据、发现时间和置信标识。
- 发现列表成功不能等于全量成功：必须继续检查分页终止、分类入口、去重、详情可达性和疑似漏采。
- 探索信息生成 `DiscoveryEvidence`；没有证据的字段标注 `UNKNOWN`，不得由 Agent 补写猜测值来“通过验证”。
- 设备绑定、交互登录、无法合法在服务端持续执行的认证方式标记为 `BLOCKED`。不把客户端临时 Cookie、单次签名或私钥放入代码。
