## 1. 目标、范围与核心决策

创建私有仓库 `WorkerXu/product-data-hub`，交付两套客户端、服务端、部署配置、Connector SDK、接口及运行文档。

- **Tauri 客户端**：Tauri 2、Rust、React 19、TypeScript，支持 macOS、Windows。
- **Windows 客户端**：C#、WebView2，与 Tauri 版共用 React 工作台、业务逻辑和通信协议。
- **服务端**：目标 Ubuntu 22、8 核、12 GB 内存、200 GB 磁盘，公网 IP 提供 HTTPS 服务。
- **首批来源**：雷小安、腕表之家；分类范围由每次采集需求选择。
- **容量目标**：30 万来源商品、每日最多 1 万条新增、小时级采集。
- **客户端参考实现**：[Seep Desktop](https://github.com/angusdevgo/Seep-Reverse-Lab/tree/main/Tool/upstream/open-reverselab/desktop)，仅参考交互，真实采集业务独立实现。
- **用户主路径**：上传经授权可分析的 APK，输入“采集可访问范围内的全量商品及详情”，Agent 自动分析并生成 Connector；经过平台强制验证和预授权发布策略后，系统自动注册与调度执行。

### 1.1 核心架构决策

1. 每个来源的 Connector 由 **AI 按统一 SDK 生成三组件**：`SourceScheduler`（来源调度策略）、`SourceExecutor`（来源采集执行）、`SourceValidator`（来源语义验证），另附 Manifest、配置、依赖锁、测试样本和证据。
2. 平台**一次开发、长期复用**底层 `PlatformScheduler / Runner / PlatformValidator / AdmissionController / Registry`。Agent 不重新实现 Celery、Redis、数据库、时间触发器或生产发布系统。
3. **验证与生产使用完全相同的 Connector 包、SDK、Runner 和依赖镜像**；可以改变凭据、隔离数据空间和资源配额，但不得在验证之后偷偷重建包或改动脚本。
4. Agent 可以生成来源验证规则，但**不能修改平台强制验收项、伪造通过状态或自行激活生产版本**。测试与发布由独立平台执行。
5. 原方案“人工确认发布”调整为两种模式：`MANUAL_APPROVAL`（默认）与 `PREAUTHORIZED_AUTO`（管理员预授权自动发布）。自动模式必须先满足所有准入规则；权限不足、强依赖设备或覆盖证据不足时不得绕过阻塞。
6. 全量定义为“**指定账号权限和明确范围内可枚举、可访问的全部商品**”；未经证据证明不能声称达到 100% 覆盖。
7. 采集和同款识别解耦：Connector 保留原始来源商品、在售记录及 SKU 身份；跨来源同款归并仍走服务端清洗、规则审核和商品版本流水线。

### 1.2 成功交付的定义

对一个新的合法授权来源，平台能够在无需工程师手写来源采集代码的目标下，完成：生成三组件 → 构建不可变产物 → 执行真实试采、故障注入和独立运行测试 → 按准入策略自动发布 → 定时发现新商品、断点恢复和异常告警。无法生成可移植签名、无法维持认证或权限不满足时，需保留可审计的阻塞证据，不承诺必然自动成功。

## 2. 总体架构和职责边界

```text
用户上传 APK + 自然语言需求
          |
          v
Tauri / WebView2 React 工作台
          |
          v
客户端本地分析服务：Pi Agent + Seep + ADB（需要时）
          |  API 证据 / 采集覆盖分析 / Connector 候选代码
          v
FastAPI Connector Factory（持久化状态机）
          |
          +--> SourceScheduler   (AI 生成)
          +--> SourceExecutor    (AI 生成)
          +--> SourceValidator   (AI 生成)
          +--> Manifest / Lockfile / Fixtures / Evidence
          |
          v
Builder -> PlatformValidator -> 隔离 Runner 试采 -> AdmissionController
                ^                      |                 |
                +---- 失败证据 -> Agent 修复 <----+             |
                                                           PASS
                                                            |
                                                            v
                                                  不可变 Registry + Release
                                                            |
                                                            v
PlatformScheduler（时间、租约、DAG、并发） -> Celery / Redis
                                                            |
                                                            v
                                         生产 Runner（SourceExecutor + 双层 Validator）
                                                            |
                                                            v
                                      PostgreSQL 原始商品 / 断点 / 任务 / 审计
                                                            |
                                                            v
                                          本地清洗 -> 同款匹配 -> 审核 -> 最终数据池/API
```

### 2.1 模块职责：平台与 Agent 不得混淆

| 模块 | 实现主体 | 职责和禁止事项 |
|---|---|---|
| Task Planner / APK Analyzer | Pi Agent + Seep | 把提示词变为目标范围、验收要求；提取接口、分页、认证、数据模型和证据，不直接发布生产代码 |
| Connector Builder | 平台提供构建工具，Agent 提供代码/配置 | 校验目录与依赖、固定版本和哈希，生成不可变包；不执行未验证包的生产操作 |
| **SourceScheduler** | **Agent 生成** | 来源特有 DAG、分类/品牌展开、分页迭代、任务终止、任务优先级；不得直接启动进程或修改平台队列 |
| **SourceExecutor** | **Agent 生成** | 使用 SDK 的受限 HTTP / 授权凭据能力请求数据、解析记录、报告游标与执行证据；不得直接写正式数据库或调用宿主命令 |
| **SourceValidator** | **Agent 生成** | 检查来源返回结构、字段意义、身份键、详情关联、分页单调进度及可枚举覆盖证据；仅能输出 ValidationReport |
| PlatformScheduler | 平台固化 | 定时触发、租约互斥、调度状态、重试/取消、并发/限流、队列投递和 DAG 持久化 |
| Runner | 平台固化 | 沙箱加载、执行、资源计量、结果提交与可靠恢复；开发验证与生产共用 |
| PlatformValidator | 平台固化，不可由 Agent 修改 | Schema、签名/认证可移植性、异常注入、重试幂等、断点一致性、安全、测试真实性 |
| AdmissionController | 平台固化 | 根据验证报告、发布政策和预授权决定发布；拒绝缺失证据的版本 |
| Registry | 平台固化 | 保存不可变包、SDK/依赖哈希、测试报告、版本和回滚关系 |
| 商品后处理 | 服务端固定流水线 | 标准库清洗、候选召回、严格同款规则、审核和不可变版本发布 |

实施上第一版采用 **FastAPI 模块化单体 + Celery 独立队列/Worker + PostgreSQL + Redis + Docker Compose**，不为上述模块分别拆微服务，也不要求三个独立 AI Agent。
