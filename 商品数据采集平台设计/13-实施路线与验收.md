## 9. 实施顺序（按风险先后）

**阶段 A：先验证固定平台核心，不依赖 AI。** 建立私有仓库、Connector SDK v1、Manifest/Schema、不可变 Registry、最小 Runner、任务/断点/Outbox 和 PlatformValidator；用人工编写的假数据 Connector 验证三组件接口、幂等和原子提交。

**阶段 B：打通三组件完整工厂。** Factory 状态机、Builder、隔离测试环境、AdmissionController、预授权发布策略和自动激活；用模拟 HTTP 来源测试成功/失败两条闭环。

**阶段 C：接入 Pi + Seep。** 接入 APK 分析、证据索引、依据 SDK 的三组件代码生成、结构化失败反馈、Agent 修复、会话恢复及客户端工作台。

**阶段 D：真实来源验收。** 接入雷小安、腕表之家，验证分类/品牌/列表/详情、身份键、签名/认证、服务端独立执行、全量基线、后续只采新增和未知覆盖说明。真实来源测试不得以样例数据替代。

**阶段 E：商品匹配、部署和交付。** 完成标准库、匹配审核、不可变版本、对外 API、两套桌面客户端、指定 Ubuntu 服务器 Docker Compose 部署及运维文档。核对 SSH 主机指纹、现有服务及端口占用。IP HTTPS 采用原方案所列 Nginx＋Certbot 的 Let’s Encrypt 短期 IP 证书方案，实施前确认签发前提、公网 80/443、续期重载及到期告警；每日两次检查续期状态；提供数据库备份、恢复演练、Registry 版本回滚。

## 10. 关键验收标准

1. **生成闭环**：上传经授权的 APK + 商品采集需求后，Agent 能输出 Manifest、SourceScheduler、SourceExecutor、SourceValidator、fixtures、依赖锁和证据；所有产物通过 SDK Schema 校验。
2. **来源调度**：分类/品牌/商品详情动态 DAG 正确；不同页、重试、重复发现、取消恢复及多次周期触发不产生重复入库或遗漏后续任务。
3. **验证器有效性**：AI 来源 Validator 必须拒绝平台预置的字段缺失、重复游标、无效 ID 等故障注入；固定 PlatformValidator 不可被 Agent 修改。
4. **端到端独立运行**：在断开客户端和真机、无 APK 和本地分析目录的 Linux 隔离环境中，已发布 Connector 仍能完成获授权的试采和认证刷新。
5. **自动准入**：预授权模式下所有必测项目通过、构建哈希一致且符合发布政策时，Registry 自动激活、Scheduler 自动创建周期任务；任何强制项失败时不得自动发布。
6. **版本与恢复**：修改代码/配置/依赖后旧验证结果不能复用；正在运行的任务固定原哈希，新版本仅影响后续任务；支持安全回滚、服务重启恢复和断点幂等。
7. **全量证据**：报告所有已发现入口、分页终止、预期/唯一列表商品数、详情成功与失败、未知范围；详情失败仍可恢复补采；无可靠来源总数不得声称 100% 覆盖。
8. **只采新增**：首次全量建立基线，后续在无可靠增量接口时可遍历列表去重；旧商品不会自动追踪改价、属性变动、上下架。
9. **匹配正确性**：标准化、别名、尺寸单位和缺失值符合规则；冲突进入审核；在人工标注正负样本上自动关联准确率目标至少 99%，同时报告召回率和审核比例。
10. **目标容量**：在 8 核、12 GB 的目标服务器回放每日 1 万新增量及小时触发高峰，验证无 OOM、可消化积压并记录 API 延迟；本地模型推理遵循 4 核/4 GB 与单并发预算。
11. **客户端与运维**：Tauri macOS/Windows 与 C# WebView2 Windows 均验证真实 Pi 会话、取消/续跑、文件选择、设备提示；日志脱敏、凭据隔离、备份恢复、证书续期和回滚可演练。
